# Enforcement provider lifecycle

The `internal/enforcementprovider` package coordinates policy enforcement while a workload remains held. Orka does not select the provider implementation; operators pin its identity and trust material.

Operator configuration supplies a `TrustProfile` that pins provider ID, endpoint identity, Ed25519 key ID/key, minimum epoch, and algorithm. Orka verifies the descriptor signature and freshness against that profile before consuming the descriptor's proof key. A self-signed substitute, wrong endpoint, stale or revoked descriptor, unsupported protocol, or unsupported required capability fails closed.

Authorization treats provider policy bytes as opaque and binds their exact digest, generic capability list, request, attempt, workload, provider, audience, challenge, and idempotency key into the signed proof transcript. The provider performs prepare, activate, independent readback, and proof operations. The workload stays held after activation. First proof consumption rechecks freshness, every immutable authorization binding, the proof digest, and the signature in the same compare-and-swap that creates an immutable release obligation. Cleanup uses a durable idempotency identity and retains a `Cleaned` tombstone so provider resources can disappear without erasing replay protection. `FileStore` deep-copies mutable state, strictly validates its versioned JSON, binds each state file to its canonical absolute path, rejects hard-link aliases, holds parent-directory, path, and inode locks for its lifetime, and requires `Close` before another controller can own the same path.

`NewUnixProvider` uses a bounded versioned JSON protocol over a Unix socket and authenticates the server UID with Linux peer credentials. Other platforms compile but fail closed at peer authentication; UID authentication identifies an OS principal, not a cryptographically unique process. The synthetic provider remains available for isolated tests. The external conformance test drives a configured server by supplying socket and trust-file environment variables.

> **Protocol revision:** this implementation negotiates `orka.enforcement-provider/v2` and Unix frame version `2`. Revision 2 intentionally replaces the draft v1 number/RFC3339 timestamp mix, proof transcript, authorization digest, and cleanup request contract. A v1-only descriptor or frame is rejected; it is never decoded under v2 semantics.

Persisted proof-bearing attempts are treated as untrusted during recovery. Before any provider status, release, or cleanup side effect, Orka reauthenticates the pinned descriptor and authorization, reverifies the proof signature and every binding, recomputes the proof digest, and recomputes any release and cleanup obligation IDs. A mismatch fails closed with zero provider calls. Provider response envelopes and every nested operation result use the same bounded, depth-limited decoder and reject duplicate keys, unknown fields, and trailing JSON.

`FileStore` requires its canonical parent directory to be private (`0700`) and owned by the current effective user. It holds the validated private parent directory lock for its lifetime. Its sidecar lock is opened without following symlinks, must be an owner-matching regular single-link file with private permissions, and is checked against the pathname inode after locking and again before operations. Lock replacement makes the live store fail closed.
