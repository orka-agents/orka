# 66. Decisions recovered from code comments: the ACP runtime and agent hosts

Date: 2026-11-22

## Status

Accepted. This record is a catalog produced by the comment ban in
[ADR 0062](0062-code-carries-no-comments.md). Each entry was a code comment that recorded a
non-obvious decision in `internal/acp`, `internal/harness`, `internal/ahphost`, `internal/agenthost`, and `workers/acp`. The comment was deleted, and the decision now lives here.

## Context

Round 2 of the comment cleanup classified every comment left after
[ADR 0063](0063-code-comment-decisions-round-1.md). In `internal/acp`, `internal/harness`, `internal/ahphost`, `internal/agenthost`, and `workers/acp` it found 949 distinct decisions
that a reader of the code alone could get wrong. Comments that stated the same rule in several
places are merged into one entry. Where an earlier ADR already records a decision, the entry
links it.

## Decision

Each entry names the symbols it governs, so `rg '<symbol>'` finds the code. Entries are
grouped by package and ordered by source position as of round 2.

### `internal/acp`

- **Built-in adapter digests have one source** (`acp.BuiltInRuntimeAdapterDigests`): acp.BuiltInRuntimeAdapterDigests is the only source of reviewed adapter artifact digests for the built-in codex, claude, copilot, and opencode runtimes, shared by controller runtime planning and the runtime supervisor so both sides advertise and expect identical digests. It returns nil for unknown providers and a fresh map per call so callers cannot mutate shared state.
- **Adapter-initiated requests are bounded per connection** (`acp.DefaultMaxConcurrentRequests`, `acp.ClientOptions.MaxConcurrentRequests`): acp.DefaultMaxConcurrentRequests (32) and ClientOptions.MaxConcurrentRequests bound concurrently handled adapter-initiated requests per ACP connection. Handlers can block on permission resolution, so an untrusted child flooding requests would otherwise pin one goroutine per message and exhaust supervisor memory; legitimate adapters issue only a handful at once. acp.ClientOptions.MaxConcurrentRequests bounds concurrently handled adapter-initiated requests and defaults to acp.DefaultMaxConcurrentRequests, because blocked permission handlers would otherwise let an untrusted child pin unbounded goroutines.
- **Prompt event buffer overflow is a supervisor-side failure** (`acp.ErrPromptEventBufferOverflow`): acp.ErrPromptEventBufferOverflow fails a prompt whose buffered events exceeded the advertised per-prompt limit before the controller-facing stream drained them. It signals a slow consumer in the supervisor, not an agent or provider error, so callers must classify it distinctly.
- **Request-written callback is the ambiguity boundary** (`acp.Client.CallWithWritten`): acp.Client.CallWithWritten invokes a non-blocking callback once the full JSON-RPC request is written to the adapter transport. After it fires, losing the response must not be treated as proof the adapter never accepted the operation; callers record this as their durable ambiguity boundary.
- **ACP request writes honor cancellation** (`acp.Client.call`): acp.Client.call writes the request in a goroutine and abandons it on context expiry, because the write blocks forever when the adapter stops reading stdin. If an abandoned write completes later, a courtesy $/cancel_request follows on the same ordered pipe so the adapter does not keep executing a request whose caller gave up.
- **Courtesy cancel is asynchronous** (`acp.Client.call`, `acp.RuntimeSession.Delete`): acp.Client.call sends the courtesy cancel notification from a separate goroutine so the caller, whose deadline has already passed, never blocks on an adapter that stopped reading stdin; adapter exit unblocks the pending write. acp.RuntimeSession.Delete sends its courtesy cancel from a detached goroutine because the notification is a blocking pipe write and a wedged adapter that stopped reading stdin would otherwise block Delete before the bounded process stop; adapter exit unblocks it.
- **ACP notification writes honor cancellation** (`acp.Client.Notify`): acp.Client.Notify runs the transport write in a goroutine and abandons it when the context expires, because the write blocks forever when the adapter stops reading stdin. The abandoned write holds writeMu until adapter exit closes the pipe.
- **Session resume and close require capability checks by callers** (`acp.Client.ResumeSession`, `acp.Client.CloseSession`): acp.Client.ResumeSession does not check the agent's advertised resume capability; callers must check it before calling. acp.Client.CloseSession does not check capabilities; callers must first check AgentCapabilities.SessionCapability(SessionCapabilityClose).
- **Excess adapter requests are rejected then dropped** (`acp.Client.dispatchRequest`): acp.Client.dispatchRequest admits adapter-initiated requests through a bounded gate; excess requests get a JSON-RPC error via a second bounded rejection lane rather than new blocked goroutines, and when that lane is also full the request is dropped because a peer flooding both lanes is not reading responses.
- **Pending durable workspaces are wiped, not reused** (`acp.PrepareDurableSessionWorkspace`): acp.PrepareDurableSessionWorkspace wipes a durable session tree that still carries a resume-pending marker without a later commit, because a resume that died mid-creation may have left modified state; only a recommitted tree is reused. When a resume marked its tree pending and never recommitted, a later creation stage failed after the provider may have modified the repository, so acp.PrepareDurableSessionWorkspace wipes the tree.
- **Publication transitions wipe the durable tree** (`acp.WipeDurableSessionWorkspace`): acp.WipeDurableSessionWorkspace clears the durable tree and its markers after a verified publication transition so the continuation re-materializes from the newly declared baseline instead of the previous checkpoint.
- **Wipe keeps the resume-pending marker until the tree is gone** (`acp.WipeDurableSessionWorkspace`): When a failed same-repository resume leaves a pending binding without a transition record, acp.WipeDurableSessionWorkspace retains that binding through the first durability barrier, so a crash before tree removal cannot leave markerless history that blocks the supervisor's next cold boot. acp.WipeDurableSessionWorkspace moves a committed binding to the pending path, or keeps an existing pending binding, until tree removal is durable, so a crash always leaves a recognizable cleanup record beside any surviving workspace history.
- **Committed marker outranks a stale pending marker** (`acp.PrepareDurableSessionWorkspace`): A crash between the commit rename and pending-marker retirement leaves both markers on disk; acp.PrepareDurableSessionWorkspace treats the committed marker as proof the commit completed, retires the stale pending marker, and resumes the tree instead of wiping it. Commit renames the committed marker into place before removing the pending marker, and resume moves rather than copies the committed marker aside, so when acp.PrepareDurableSessionWorkspace finds both markers it knows a commit completed and only pending retirement was interrupted; it retires the stale pending marker instead of wiping the tree.
- **Repository-identity transitions are staged before wiping** (`acp.DurableWorkspaceTransition`, `acp.MarkDurableWorkspaceTransitionAuthorized`): A durable workspace repository-identity transition writes its authorization durably before the old checkpoint is wiped, survives a mid-transition crash so the retry can read it, and is retired only by the next successful commit. acp.MarkDurableWorkspaceTransitionAuthorized durably records the controller-authorized repository-identity transition before the old checkpoint is wiped. A creation retry that finds no committed marker but a matching transition record may materialize fresh instead of failing closed, so a transient failure after the wipe cannot strand the lineage; the next commit retires the record.
- **Instruction projections are supervisor-authored** (`acp.InstructionProjection`): acp.InstructionProjection content is always supervisor-authored, never repository content, and its RelativePath lies beneath the private session home outside the task workspace so repository files cannot inject or overwrite agent instructions.
- **Instructions are projected between ownership finalization and spawn** (`acp.ProjectInstructions`): acp.ProjectInstructions must run after child ownership finalization and before the adapter is spawned, so the protected ownership it sets is not undone and the child never runs without its instructions.
- **Instruction restore verifies and requires a frozen child** (`acp.RestoreInstructions`): acp.RestoreInstructions reestablishes protected ownership after whole-tree validation while the caller keeps the child frozen, and verifies the existing bytes instead of rewriting a damaged or missing projection, so tampering is detected rather than silently repaired.
- **Supervisor reclaims instruction files with CHOWN** (`acp.RestoreInstructions`): The supervisor deliberately lacks CAP_DAC_OVERRIDE and CAP_DAC_READ_SEARCH, so acp.RestoreInstructions reclaims the child-owned 0440 instruction file with CHOWN before opening it, which is safe only because the child is frozen.
- **Copilot instructions reject @ imports** (`acp.ValidateCopilotInstructions`): acp.ValidateCopilotInstructions conservatively rejects any '@' in Copilot agent instructions because Copilot treats @ references as native file-import markers that could pull in files outside the projected instructions.
- **Operator tag groups identify operator processes** (`acp.OperatorTagFirstGID`): Each operator operation runs with exactly one supplementary group from acp.OperatorTagFirstGID..OperatorTagLastGID, unique among live processes, and no runtime file is owned by or grants access to those groups, so the tag identifies the process tree without granting privileges.
- **Operator commands run with the adapter's identity** (`acp.OperatorCommandConfig`): acp.OperatorCommandConfig commands run through the same exec helper, UID/GID, empty supplementary groups, resource limits, and parent-death fence as the RuntimeSession's ACP adapter, so an operator never gains the supervisor's root identity or capabilities.
- **Operator leaders are withheld from the session reaper** (`acp.operatorLeaders`, `acp.releaseOperatorLeader`): acp.operatorLeaders records started operator command leaders until their owner reaps them. A leader runs under the RuntimeSession UID as a direct supervisor child, so the session-wide cleanup reaper would otherwise reap it, losing the owner's exit status and freeing a PID that is also the process group the owner still signals. Each entry holds its own registration so releasing an earlier command whose PID was reused cannot withdraw the later command's entry. Stopping the adapter, which a prompt cancellation does while operator commands are admitted, reaps every exited process of the session UID; acp.operatorLeaders keeps operator leaders out of that sweep so their owners keep the exit status and process group.
- **Operator leader release follows owner reap** (`acp.StartOperatorCommand`): acp.StartOperatorCommand withholds the leader from the session reaper until release is called; the owner must reap the leader first and only then release, so the PID stays allocated and names only this command. An unreaped zombie leader still counts against the session's cleanup proof.
- **Operator leader registration is atomic with start** (`acp.StartOperatorCommand`): acp.StartOperatorCommand holds operatorLeaders.mu across cmd.Start so the session reaper can never observe the leader before it is registered.
- **Operator signals are not containment** (`acp.SignalOperatorCommand`): acp.SignalOperatorCommand only signals the command's process group and never kills the whole operation; containment must use KillOperatorTag, which finds every process carrying the operation's tag group.
- **Terminal operator commands lead their own session** (`acp.NewOperatorCommand`): On Linux, acp.NewOperatorCommand makes a terminal command a session leader with Setsid, which also satisfies the exec helper's process-group fence; non-terminal commands use Setpgid to lead their own group. Both set Pdeathsig SIGKILL.
- **Released operator leaders return to normal reaping** (`acp.releaseOperatorLeader`): After the owner reaps and releases an operator leader, acp.releaseOperatorLeader must remove its entry, because a stale entry would hide whichever later process receives that PID from the reaper and the session's cleanup could never be proven.
- **Zombies do not count as live processes** (`acp.procCredentials`): acp.procCredentials marks a thread group whose every thread exited as a zombie; it can never run again, so process-tree containment checks do not count it as live.
- **Partial /proc records prove nothing** (`acp.procCredentials`): acp.procCredentials.complete is true only when State, Uid, and Groups were all present and parsed; a partial or malformed /proc status record proves nothing about the process, so containment checks fail closed on it.
- **Only a vanished /proc entry means the process exited** (`acp.procEntryGone`): acp.procEntryGone treats a /proc read failure as proof of exit only for ENOENT or ESRCH; permission errors, I/O errors, a hidepid mount, or a malformed tree leave the process state unknown, so containment scans fail closed.
- **A zombie leader can have live threads** (`acp.threadGroupLive`): acp.threadGroupLive inspects every thread of a zombie leader because a leader that called pthread_exit shows as a zombie while its worker threads still run; an unreadable thread list or thread state reports ok=false instead of presuming the group dead.
- **Foreign-UID tagged processes block containment** (`acp.operatorTagScan.foreign`): acp.operatorTagScan.foreign counts live tag-carrying processes of another UID. The supervisor never kills them, but while any exists operator containment is unproven.
- **Operator tag scans relist until settled** (`acp.scanOperatorTag`): acp.scanOperatorTag re-lists the process table and examines new PIDs until a listing adds none, because processes forked during a scan are absent from the earlier listing. A scan that cannot settle within the relist limit, or any process that cannot be read completely for a reason other than having exited, reports ok=false; an unreadable process is never presumed gone.
- **Negative UID scans every UID** (`acp.taggedProcesses`): acp.taggedProcesses and acp.scanOperatorTag treat a negative uid as every UID, which acp.OperatorTagInUse relies on to check tag reuse across all users.
- **Unreadable process table keeps a tag in use** (`acp.OperatorTagInUse`): acp.OperatorTagInUse reports a tag as in use when the process table is unreadable or unsettled, so a tag group is never reassigned while an unseen process might still carry it.
- **Operation zombies are reaped after containment** (`acp.ReapOperatorTag`): The supervisor is a child subreaper, so an operator operation's orphaned descendants reparent to it, and the session-wide reaper runs only on freeze and stop; until then each zombie holds a PID against the session process limit. acp.ReapOperatorTag reaps only exited processes of the session UID carrying the operation tag, never the agent or held operator leaders, and must be called only after containment is proven and before the tag is released.
- **Tag reaping holds the leader registry lock** (`acp.reapOperatorTag`, `acp.reapExitedProcessesForUID`): acp.reapOperatorTag holds operatorLeaders.mu for the whole pass, like the session-wide reaper, so an operator leader cannot start and register behind the scan and be reaped out from under its owner. The session-wide UID reaper skips operator leaders, which only their owners reap, and holds operatorLeaders.mu for the whole pass so a command cannot start, exit, and be reaped before it is registered.
- **Zombie PIDs are stable until reaped** (`acp.reapOperatorTag`): acp.reapOperatorTag may wait on a scanned zombie by bare PID because an unreaped zombie's PID cannot be reused and no other owner waits for a reparented descendant, so the PID still names that process.
- **Operator containment needs two settled empty scans** (`acp.KillOperatorTag`): acp.KillOperatorTag kills every process of the session UID carrying the operation's inherited, undroppable tag group, which reaches descendants that changed process group, session, or parent. Like the RuntimeSession UID cleanup proof, termination is proven only by two consecutive settled empty scans separated by an observation interval; an unsettled or unreadable scan, or a tagged process of another UID, resets the proof.
- **Operator kills pin the process with a pidfd** (`acp.killOperatorTagProcess`): acp.killOperatorTagProcess pins a scanned PID with pidfd_open before re-reading its UID and tag, then signals through pidfd_send_signal, because the PID may have been reused by an unrelated process of another UID before the root supervisor signals it; if the pinned process exits, the signal fails with ESRCH instead of reaching a successor. Without pidfd support it never signals by bare PID, leaving the process alive so containment stays unproven.
- **Operator tags are never free outside Linux** (`acp.OperatorTagInUse`): On non-Linux builds acp.OperatorTagInUse always returns true because no tag can be proven free without /proc, and KillOperatorTag always reports containment unproven.
- **ACP artifact pins differ from wire version** (`acp.ACPSchemaArtifactVersion`): acp.ACPSchemaArtifactVersion, ACPSchemaSourceCommit, and ACPSchemaSHA256 pin the reviewed ACP schema artifact for supply-chain verification; bumping them does not change ACP wire compatibility, which stays protocolVersion=1 during initialize.
- **Production adapters are signaled by UID scope** (`acp.Process.signal`): Production supervisors run as root and give each RuntimeSession a non-reused UID, so acp.Process signals every process of that UID rather than the adapter's process group; UID scope cannot hit a recycled process-group ID and reaches descendants that left the adapter's group.
- **Operator tag groups are unforgeable and inherited** (`acp.operatorExecHelperProtocolVersion`): The orka-acp-operator-exec-v1 exec helper protocol launches each operator command with one supplementary tag group. Dropping or changing supplementary groups needs CAP_SETGID, which the child lacks, and every descendant inherits the group, so the supervisor can find and kill the whole operation after processes leave the process group, session, or tree.
- **Exec helper applies limits before exec** (`acp.RunExecHelper`): acp.RunExecHelper validates the trusted launch envelope and applies hard resource limits to its own process before replacing itself with the adapter, so the adapter never runs unconstrained; it is exported only for cmd/orka-acp-exec-helper.
- **Provider session metadata cannot shadow Orka fences** (`acp.MergeNewSessionMeta`): acp.MergeNewSessionMeta merges provider-specific session/new metadata with Orka-owned runtime identity metadata and rejects any provider key that would replace or shadow a protected Orka key, including case variants, so a provider profile cannot forge the session fence.
- **Session capabilities accept object or true** (`acp.AgentCapabilities.SessionCapability`): acp.AgentCapabilities.SessionCapability treats a session capability as advertised when the agent sends either the ACP capability object or a boolean true, because adapters in the field use both encodings.
- **Prompt usage is telemetry and never fails a prompt** (`acp.PromptResponse.Usage`, `acp.ParsePromptUsage`): acp.PromptResponse.Usage stays json.RawMessage and acp.ParsePromptUsage returns no count rather than an error for absent, malformed, negative, or implausible values, because token usage is telemetry only and a bad report must never fail the prompt response. acp.ParsePromptUsage is telemetry-only: absent, malformed, negative, or implausible usage values yield no count rather than an error.
- **Prompt usage counts are bounded** (`acp.maxPromptUsageTokens`): acp.maxPromptUsageTokens (2^40) bounds reported token counts to a plausible range that float64 telemetry sinks represent exactly; larger values are treated as unreported.
- **Null usage counts stay unreported** (`acp.ParsePromptUsage`): acp.ParsePromptUsage decodes each count through a pointer so a JSON null stays unreported instead of becoming an explicit zero.
- **Only provider-native denies narrow native policy** (`acp.BuiltInRuntimeNativePolicyUnrestricted`): acp.BuiltInRuntimeNativePolicyUnrestricted compares only provider-native grants: a full native grant stays unrestricted when brokered tools are added, an explicit empty allowlist stays deny-all, and denying a provider-native tool, whole or path-scoped such as Read(/workspace/private/**), narrows it. Denying any other tool does not, because the MCP policy enforces that deny and the provider's own tools are untouched.
- **Explicit tool allowlists stay authoritative** (`acp.NormalizeBuiltInRuntimeToolPolicy`): acp.NormalizeBuiltInRuntimeToolPolicy expands an implicit provider-native tool surface only when deny-only metadata or the Bash gate narrows it; explicit allowlists, including an explicit empty deny-all list, are never expanded.
- **Nil allowlist means unrestricted** (`acp.BuiltInRuntimeEffectiveAllowedTools`): acp.BuiltInRuntimeEffectiveAllowedTools returns nil for a nil allowlist so callers keep the unrestricted sentinel distinct from an empty deny-all list.
- **Read-intent OpenCode sessions disable Grep** (`acp.NormalizeOpenCodeToolPolicy`): acp.NormalizeOpenCodeToolPolicy blocks OpenCode's grep tool, along with mutation and Bash tools, in read-intent sessions because OpenCode's Grep permission cannot carry the path-specific secret-file exclusions applied to Read.
- **OpenCode grants are canonicalized for authorization** (`acp.NormalizeOpenCodeAuthorizationTools`): acp.NormalizeOpenCodeAuthorizationTools canonicalizes user-facing OpenCode tool grants so token and transaction allowlists compare against runtime policy names without exposing internal alias details to issuers.
- **OpenCode mutation aliases are one capability** (`acp.normalizeOpenCodeToolNames`): acp.normalizeOpenCodeToolNames treats apply_patch, edit, and write as one governed mutation capability because OpenCode selects apply_patch for GPT-family models and edit/write for others; brokered and custom tool identifiers are preserved unchanged.
- **Runtime credential IDs exclude the no-change sentinel** (`acp.maxRuntimeCredentialID`): acp.maxRuntimeCredentialID is 2^32-2 because Linux credentials are uint32 and all-bits-one is the no-change sentinel for ownership syscalls such as chown.
- **Workspace identity is recorded before the child starts** (`acp.SessionPaths.WorkspaceInode`, `acp.RecordWorkspaceIdentity`): acp.SessionPaths.WorkspaceDevice and WorkspaceInode are recorded by RecordWorkspaceIdentity before the session child starts; because the child may own the session root and rename entries, any later reopen of Workspace by path must verify this identity. acp.RecordWorkspaceIdentity must be called only while the supervisor exclusively controls the session tree, before the child starts, and released with ReleaseWorkspaceIdentity when the session ends. Platforms without Unix inode identity return an error that callers must treat as a refusal.
- **Workspace identity is pinned by an open descriptor** (`acp.SessionPaths.workspacePin`): acp.SessionPaths.workspacePin holds the recorded workspace directory open because a device/inode pair names a directory only while the inode stays allocated; if the child deleted its workspace, a new directory could reuse the inode number. Copies of SessionPaths share the pin.
- **Workspace identity comes from the held descriptor** (`acp.RecordWorkspaceIdentity`): acp.RecordWorkspaceIdentity stats the held directory descriptor rather than looking the path up again, so a rename between open and stat cannot substitute another directory.
- **Unpinned workspace identity is refused** (`acp.SessionPaths.PinnedWorkspaceIdentity`): acp.SessionPaths.PinnedWorkspaceIdentity errors when the workspace was never pinned or the pin was released, because recorded device/inode numbers prove nothing without a live pin; callers must treat the error as a refusal.
- **Workspace pin is released after the child stops** (`acp.SessionPaths.ReleaseWorkspaceIdentity`): acp.SessionPaths.ReleaseWorkspaceIdentity must be called only once the session child is proven stopped; afterwards every copy of the paths refuses PinnedWorkspaceIdentity.
- **Session base directory is traverse-only for children** (`acp.ensureRealDirectory`): acp.ensureRealDirectory chmods the session base directory through its verified handle after MkdirAll because MkdirAll applies the supervisor's private umask and identity-state setup may have created it already; child UIDs need traversal to their own private trees without being able to list or write the parent.
- **UID and GID allocation share one offset** (`acp.UIDAllocator.AllocateAboveReserve`): acp.UIDAllocator.AllocateAboveReserve returns the next never-reused UID/GID pair only when at least reserve pairs remain, checking and allocating from a single shared offset in one critical section so concurrent session creation can never reuse an identity or pair a UID and primary GID from different sessions.
- **Allocator counts are persisted before identities are used** (`acp.UIDAllocator.ConfigurePersistence`): acp.UIDAllocator.ConfigurePersistence restores the committed allocation count and installs a fail-closed callback that must durably commit each new count before an identity is returned to a session, so a restart can never hand out a UID/GID already used.
- **Durable high-water is bound to the allocator range** (`acp.UIDAllocator.Range`): acp.UIDAllocator.Range exposes the immutable paired UID/GID range so durable high-water state can be bound to one exact identity configuration and rejected if the range changes.
- **Durable workspace binding pins the repository** (`acp.DurableWorkspaceBinding`): acp.DurableWorkspaceBinding records the repository binding of a durable workspace's first materialization so a later cold resume can never silently continue against different source content; it never carries credentials or provider-native identifiers.
- **Durable checkpoints carry an identity high-water floor** (`acp.DurableWorkspaceBinding.SessionIdentityHighWater`): acp.DurableWorkspaceBinding.SessionIdentityHighWater records the allocator count durable before the checkpoint's child identity was admitted; a cold boot rejects allocator state below this floor so a partial restore cannot reuse a UID/GID already represented in surviving workspace data.
- **Durable checkpoints carry a generation floor** (`acp.DurableWorkspaceBinding.SessionGeneration`): acp.DurableWorkspaceBinding.SessionGeneration records the monotonic RuntimeSession generation that committed the checkpoint. A provider restoring an older snapshot of the same repository presents a valid identity with an earlier generation, and the resume assertion compares it against the controller's persisted floor so stale restores fail closed instead of silently dropping checkpoint-only edits from the next publication.
- **Durable continuity is judged on stable repository identity** (`acp.StableDurableWorkspaceIdentity`): acp.StableDurableWorkspaceIdentity reduces every no-repository baseline, which carries a Task-scoped protocol identity by design, to the bare no-workspace revision, and identifies repository workspaces by repository identity alone because the controller already verifies revision continuity before requesting the session.
- **Durable workspace identity comparison is case-insensitive for GitHub** (`acp.SameDurableWorkspaceIdentity`): acp.SameDurableWorkspaceIdentity mirrors the controller's repository-identity equivalence: GitHub identities are case-insensitive, so a continuation that changes only capitalization resumes the preserved tree instead of wiping it.
- **Fresh durable trees are covered by a pending marker first** (`acp.PrepareDurableSessionWorkspace`, `acp.stageDurableWorkspaceFreshPending`): acp.PrepareDurableSessionWorkspace reports resume only for committed content (marker plus workspace directory). Fresh content is covered by a pending marker carrying the allocator high-water before its tree is created, so a restart can verify the non-reuse fence and the next preparation can wipe a partial materialization. acp.stageDurableWorkspaceFreshPending publishes the cleanup record before a fresh tree exists, so a crash leaves either no tree or a tree whose identity floor is recoverable and never creates markerless durable history.
- **Stale transition records are retired before a new child** (`acp.PrepareDurableSessionWorkspace`): acp.PrepareDurableSessionWorkspace removes a transition record that survived an interrupted post-commit cleanup before starting a new child; failure is safely retryable because the committed checkpoint is intact and no session was initialized.
- **Durable workspace commit is atomic** (`acp.CommitDurableSessionWorkspace`): acp.CommitDurableSessionWorkspace writes the committed marker atomically; content covered only by the pending marker is treated as uncommitted and wiped by the next preparation.
- **Durable commit completes at the marker sync** (`acp.commitDurableSessionWorkspace`): acp.commitDurableSessionWorkspace makes the committed marker durable before retiring pending records; once that sync succeeds the commit is complete, and later cleanup failures are not returned because that would tear down an initialized child while its tree stays durably resumable. Prepare and the next commit retry stale-record retirement.
- **Failed commit sync rolls back to pending-only** (`acp.commitDurableSessionWorkspace`): If the durability barrier after the commit rename fails, acp.commitDurableSessionWorkspace removes the visible committed marker and restores pending-only state, so a retry wipes the initialized child's possibly modified tree instead of mistaking both markers for interrupted post-commit cleanup.
- **Resume invalidates the committed marker first** (`acp.MarkDurableSessionWorkspaceResumePending`): acp.MarkDurableSessionWorkspaceResumePending atomically moves a resumed tree's committed marker to the pending path before session initialization, so a creation that fails after the provider may have modified the repository leaves a pending record and the next preparation wipes the tree; a successful creation recommits the marker.
- **Wipe prefers the newest binding as cleanup record** (`acp.wipeDurableSessionWorkspace`): acp.wipeDurableSessionWorkspace uses the newest committed binding as the cleanup record; removing an older pending record first is safe because the committed marker still covers the tree until the atomic rename succeeds.
- **Marker retirement is durable before data deletion** (`acp.wipeDurableSessionWorkspace`): acp.wipeDurableSessionWorkspace syncs the committed-marker retirement before deleting workspace data, because the pending binding or an authorized transition record covers a crash after the barrier while a resurrected committed marker beside a deleted tree would not.
- **Supervisor reclaims child-owned trees before removal** (`acp.reclaimDurableWorkspaceTree`): The durable tree may still carry the previous child's ownership and 0700 modes, and the supervisor holds CAP_CHOWN but not CAP_DAC_OVERRIDE, so acp.wipeDurableSessionWorkspace reclaims the tree with reclaimDurableWorkspaceTree before traversing and removing it.
- **Session ownership is finalized before the provider starts** (`acp.FinalizeSessionOwnership`): acp.FinalizeSessionOwnership assigns the prepared session tree to the child identity without following symlinks, and must run after the trusted workspace artifact is materialized and before the provider process starts.
- **Read-intent workspaces are reclaimed from the child** (`acp.ProtectReadOnlySessionWorkspace`): acp.ProtectReadOnlySessionWorkspace runs after FinalizeSessionOwnership and gives the read-intent workspace tree, and the session root when it contains the workspace, back to the supervisor so the child can neither modify nor rename it; the child's unique group keeps read and search access. For a non-root supervisor whose child shares its identity (development and tests) it is a no-op because no filesystem isolation is possible there, and read-intent delta validation remains the enforcement; managed runtime Pods always run the supervisor as root. acp.ProtectReadOnlySessionWorkspace keeps the session root owned by the supervisor with mode 0710 because a child owning the workspace's parent could rename the workspace aside.
- **Ownership walks reclaim parents first** (`acp.ProtectReadOnlySessionWorkspace`, `acp.ReclaimSessionOwnership`): acp.ProtectReadOnlySessionWorkspace and acp.ReclaimSessionOwnership change each directory before filepath.WalkDir descends into it, because the supervisor lacks CAP_DAC_OVERRIDE and cannot traverse a child-owned 0700 directory it has not reclaimed. acp.ReclaimSessionOwnership returns a frozen session tree to the supervisor so it can validate workspace state without CAP_DAC_OVERRIDE, reclaiming parent directories before WalkDir descends into them.
- **Read-only workspace modes are fixed before the baseline** (`acp.ProtectReadOnlySessionWorkspace`, `acp.PrepareReadOnlyWorkspaceModes`): Applying read-only file modes in acp.ProtectReadOnlySessionWorkspace is normally a no-op after PrepareReadOnlyWorkspaceModes; any file it still changes differs from the captured baseline and fails workspace validation. acp.PrepareReadOnlyWorkspaceModes applies read-only file modes to the supervisor-owned workspace before its baseline is captured, because workspace validation compares exact modes for protected paths and ownership reclaim does not restore file modes, so the baseline must already hold the modes ProtectReadOnlySessionWorkspace leaves.
- **Permission waits are bounded** (`acp.MaxPermissionTimeout`): acp.MinPermissionTimeout (1m) and acp.MaxPermissionTimeout (1h) bound how long a runtime waits for a permission answer; a person may answer, so the window is configurable, but it can never be unbounded.
- **Prompt admission errors define retry semantics** (`acp.ErrPromptCancellationPending`, `acp.ErrPromptCancellationTimedOut`, `acp.ErrPromptLeaseExpired`, `acp.ErrPromptActivationExpired`): acp.ErrPromptCancellationPending rejects prompt admission until an earlier session-scoped cancellation write finishes; the prompt was not accepted and may be retried. acp.ErrPromptCancellationTimedOut closes admission permanently after an unresponsive cancellation transport forces retirement, because its queued write cannot be reused.
- **Required session mode is enforced** (`acp.RuntimeSessionConfig.RequiredModeID`): When acp.RuntimeSessionConfig.RequiredModeID is set, the adapter must report it as current in session/new and session/resume responses; an adapter that fell back to another mode fails creation or the in-place resume.
- **Native resume never falls back to a new session** (`acp.RuntimeSessionConfig.ResumeSessionID`): When acp.RuntimeSessionConfig.ResumeSessionID requests an installed native provider session, failure to advertise or complete session/resume fails creation without calling session/new.
- **Adapter relaunch revalidates the workspace** (`acp.RuntimeSessionConfig.ValidateAdapterRelaunch`): acp.RuntimeSessionConfig.ValidateAdapterRelaunch runs after an idle adapter's exit is proven and before a replacement launches, because the agent may have changed the workspace since creation checked it; an error retires the session as lost instead of starting a replacement.
- **Buffered prompt events are bounded by bytes** (`acp.RuntimeSessionConfig.MaxBufferedEventBytes`): acp.RuntimeSessionConfig.MaxBufferedEventBytes bounds the aggregate raw payload size of buffered unconsumed prompt events so a burst of large valid events cannot exhaust runtime memory before the event-count limit fires; consumers release bytes through PromptRun.Release.
- **Idle adapter exit is resumed in place or lost** (`acp.RuntimeSession.process`, `acp.AdapterLostError`, `acp.RuntimeSession.Process`): acp.RuntimeSession.process is replaced in place when an idle adapter exits and the agent supports session/resume, so holders must not cache the process pointer across idle periods. acp.AdapterLostError reports that the adapter exited while the session was idle and could not be resumed in place, because the agent does not advertise session/resume or the resume failed. The provider session is gone for this generation; the caller must retire the RuntimeSession so the controller continues from Orka's canonical transcript.
- **Session counts as frozen from any freeze attempt** (`acp.RuntimeSession.frozen`, `acp.RuntimeSession.Freeze`): acp.RuntimeSession.frozen is set as soon as a workspace freeze is attempted, even if the attempt fails, and cleared only after a proven thaw, so the session never assumes the child is running unfrozen when its state is uncertain. acp.RuntimeSession.Freeze sets frozen before attempting the freeze because a failed freeze may still have stopped part of the tree, and only a successful Thaw proves it runs again.
- **Graceful session close is capped** (`acp.closeSessionGraceCap`): acp.closeSessionGraceCap (5s) caps the graceful session/close wait during deletion so a wedged adapter cannot delay the proven process stop.
- **Adapter restart reserves the prompt identity** (`acp.runtimeSessionRestart`): acp.runtimeSessionRestart reserves the prompt identity and request digest before adapter recovery releases s.mu, and records cancellation even if its caller stops waiting, so no other prompt can claim the session mid-restart and a cancelled prompt is never submitted afterwards.
- **Failed initialization keeps its stop proof** (`acp.InitializationError`): acp.InitializationError retains the failed session's process stop proof; the session is sealed against prompts but remains available for a later cleanup attempt.
- **Prompt events keep their receive time** (`acp.PromptEvent.ReceivedAt`): acp.PromptEvent.ReceivedAt is stamped when the session receives the child's notification, before any pre-acceptance buffering, so it preserves the phase in which the child emitted the event even when the event is enqueued later; Timestamp marks enqueue time.
- **Prompt consumers release buffered bytes promptly** (`acp.PromptRun.Release`): Consumers of acp.PromptRun must call Release as soon as each event is received from Events, because unreleased bytes count against MaxBufferedEventBytes and eventually fail the prompt with ErrPromptEventBufferOverflow.
- **Creation failures carry cleanup evidence** (`acp.NewRuntimeSession`): Once the adapter child starts, every session creation failure goes through Delete via initializationFailed so the caller receives proven or unproven process cleanup evidence.
- **No session/close for an empty session** (`acp.NewRuntimeSession`): Session capabilities are recorded only once a provider session exists, so a failed creation never sends session/close for an empty session ID.
- **Creation and resume share one adapter handshake** (`acp.RuntimeSession.launchAdapter`): acp.RuntimeSession.launchAdapter starts the adapter and completes initialize, the HTTP MCP capability check, and optional authentication; creation and in-place resume both use it so they negotiate identically. On handshake failure it returns the started process and the caller owns cleanup: creation proves it through Delete, while resume stops it without proof.
- **Adapters are asked for session notices** (`acp.RuntimeSession.launchAdapter`): acp.RuntimeSession.launchAdapter advertises the ACP session notices client capability so adapters that support it (the pinned codex-acp and claude-agent-acp) send advisories such as Codex's missing model metadata warning as notice updates instead of prefixing them to the agent's reply.
- **Adapter recovery drops the session lock** (`acp.RuntimeSession.recoverExitedAdapterLocked`): acp.RuntimeSession.recoverExitedAdapterLocked is called with s.mu held, no active prompt, and no deletion; it releases the lock while restarting and resuming the adapter and re-acquires it before returning, so callers must re-validate deletion afterwards. A nil return means a live adapter is bound; *AdapterLostError means the provider session is unrecoverable for this generation.
- **Cancelled restart stops the replacement** (`acp.RuntimeSession.recoverExitedAdapterLocked`): If cancellation acquires s.mu after resume already answered, acp.RuntimeSession.recoverExitedAdapterLocked still stops the replacement before releasing the reservation, because the cancelled prompt must never be submitted or replayed.
- **Interrupted adapter restarts are lost** (`acp.RuntimeSession.recoverExitedAdapterLocked`): Even an interrupted adapter restart (caller gone, lease over) returns AdapterLostError, because a failed StartPrompt leaves the supervisor's prompt gates cancelling and the generation cannot take another prompt; retiring it hands recovery to the controller's transcript recreation.
- **Unbound replacement adapters are stopped** (`acp.RuntimeSession.recoverExitedAdapterLocked`): Although Delete cancels before joining a restart, acp.RuntimeSession.recoverExitedAdapterLocked also checks deletion after the restart and stops any replacement it cannot bind, so no adapter outlives its session.
- **Resumed adapters keep the provider session ID** (`acp.RuntimeSession.resumeAdapter`): acp.RuntimeSession.resumeAdapter proves the exited adapter tree is gone, launches a replacement through the creation handshake, and reconnects with session/resume; an agent that answers with a different provider session ID is rejected and the replacement stopped, because Orka's transcript continuity is bound to the original provider session.
- **Exited adapter tree is proven gone before relaunch** (`acp.RuntimeSession.resumeAdapter`): The replacement adapter reuses the session's UID/GID, so under the production fence (root supervisor, distinct child UID) acp.RuntimeSession.resumeAdapter proves the exited tree gone before another child exists under that identity, or a straggler could later be mistaken for the new adapter. Without a distinct identity the observed leader exit is the only evidence, as for deletion.
- **Old adapter output is drained before resume** (`acp.RuntimeSession.resumeAdapter`): acp.RuntimeSession.resumeAdapter waits for the exited client's read loop to finish, so any notification still buffered on the old stdout is delivered while no prompt is active and can never reach the prompt the replacement admits.
- **Provider sessions get a bounded graceful close** (`acp.RuntimeSession.closeProviderSession`): acp.RuntimeSession.closeProviderSession sends a bounded session/close before the process stop so agents that persist state on close (thread rollouts, session files) can do so; the request runs detached because the write can block on a wedged adapter, and adapter exit ends it.
- **Adapter error text is never logged** (`acp.RuntimeSession.closeProviderSession`): acp.RuntimeSession.closeProviderSession logs only the JSON-RPC error code of a failed session/close because the error message is adapter-controlled.
- **Adapter recovery happens before prompt access** (`acp.RuntimeSession.RecoverExitedAdapter`, `acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation`): acp.RuntimeSession.RecoverExitedAdapter restarts and resumes an adapter that exited while idle so the caller finishes that handshake before granting the prompt any provider or MCP access, and an agent that calls the model during session/resume is refused instead of spending the prompt's turns. It is the only path that restarts an adapter; StartPromptWithLeaseDeadline treats an exited adapter as lost. Only RecoverExitedAdapter restarts an adapter, before the caller grants the prompt any access; acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation treats an adapter that exited afterwards as lost rather than resuming it with the prompt's gates already open.
- **Late restarts are retired before any prompt write** (`acp.RuntimeSession.RecoverExitedAdapter`): A restart can finish its RPC on time but wait for s.mu past the lease; acp.RuntimeSession.RecoverExitedAdapter then retires the replacement before any ACP prompt write so the caller gets a typed AdapterLostError instead of a generic lease failure.
- **Prompt leases are absolute deadlines** (`acp.RuntimeSession.StartPromptWithLeaseDeadline`): acp.RuntimeSession.StartPromptWithLeaseDeadline takes the controller's absolute lease deadline rather than a duration so the bound holds across capability activation and admission delays.
- **Prompt admission precedes capability activation** (`acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation`): acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation checks admission before activating prompt capabilities so a pending cancellation cannot create remote authority. activate runs under the session lock and must not do transport I/O or call other RuntimeSession methods; its error leaves the prompt unaccepted. Expiry before activation returns ErrPromptLeaseExpired without calling activate; expiry after returns ErrPromptActivationExpired and the caller must retire or roll back the capabilities. Local capability locks can consume the remaining lease, so acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation never dispatches a prompt whose lease is already due and returns ErrPromptActivationExpired when activation succeeded, so the caller cannot reopen admission without retiring its capabilities.
- **Pending cancellation blocks prompt admission** (`acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation`): ACP session/cancel identifies only the provider session, not a prompt, so acp.RuntimeSession.StartPromptWithLeaseDeadlineAndActivation rejects admission with ErrPromptCancellationPending while any cancel write is still pending; settlement alone cannot admit a new prompt that an old cancel might still hit.
- **Prompt lease timers are fenced by absolute deadlines** (`acp.RuntimeSession.RenewPromptLeaseUntil`, `acp.RuntimeSession.expirePrompt`): A relative lease timer may already have fired after a backward wall-clock step, so only the absolute deadline or a locked cancellation decision ends renewal authority; acp.RuntimeSession.RenewPromptLeaseUntil resets the timer with a new version that fences any queued callback. acp.RuntimeSession.expirePrompt re-checks the absolute lease deadline because timers wait a relative duration while controller deadlines are absolute and a backward wall-clock step can fire the timer while authority is still live; it re-arms for the remaining time until the absolute deadline instead of expiring early.
- **Cancellation reserves the admission fence under lock** (`acp.RuntimeSession.startPromptCancellationLocked`): acp.RuntimeSession.startPromptCancellationLocked commits cancellation and reserves the admission fence (pendingCancelWrites) before unlocking, so the fence holds even if prompt settlement beats the courtesy cancel goroutine. The cancel admission fence outlives any committed stop; acp.RuntimeSession.startPromptCancellationLocked never holds s.mu across transport I/O and never releases a timed-out session for reuse.
- **Courtesy cancel writes have their own bound** (`acp.RuntimeSession.startPromptCancellationLocked`): Settlement can stop every prompt watchdog while the courtesy cancel write is still queued, so acp.RuntimeSession.startPromptCancellationLocked bounds that write with its own timeout of twice CancelGrace, independent of caller contexts.
- **Timed-out cancel writes retire the session** (`acp.RuntimeSession.startPromptCancellationLocked`): When the courtesy cancel times out with its write still queued, acp.RuntimeSession.startPromptCancellationLocked permanently closes admission (cancelWriteTimedOut) before stopping the transport, so a late old cancellation can never reach a replacement prompt even if cleanup is unproven.
- **Cancel escalation does not wait for the courtesy write** (`acp.RuntimeSession.cancelPrompt`): acp.RuntimeSession.cancelPrompt joins the exact prompt whose cancellation began under s.mu, and its grace-then-stop escalation must not wait for a blocked courtesy cancel write.
- **Waiting for settlement proves nothing remote** (`acp.RuntimeSession.WaitPromptSettlement`): acp.RuntimeSession.WaitPromptSettlement joins the exact local prompt without requesting another cancellation; proxies use it after revoking authority so the resulting request error is not delivered before the adapter consumes its courtesy cancel. The wait is bounded, and neither it nor its timeout supplies remote settlement or cleanup proof.
- **Delete cancels in-flight restarts first** (`acp.RuntimeSession.Delete`): acp.RuntimeSession.Delete closes admission and cancels any in-flight adapter restart before joining it, so the restart stops its unbound replacement without submitting the reserved prompt even if the deletion caller stops waiting.
- **Failed deletion observations are not cleanup proof** (`acp.RuntimeSession.Delete`): In acp.RuntimeSession.Delete a failed stop observation is not cleanup proof: a later caller may observe the same stopped process again, while callers already joined to an attempt keep that attempt's result even if another retry starts first.
- **No session/close to a frozen adapter** (`acp.RuntimeSession.Delete`): acp.RuntimeSession.Delete skips session/close when the adapter is frozen because it cannot read the request and sending it would only stall deletion for the close grace.
- **Parked pre-acceptance events are counted once** (`acp.RuntimeSession.runPrompt`): acp.RuntimeSession.runPrompt subtracts the bytes of events parked before prompt acceptance, which were already counted, subtracted from bufferedBytes before emitLocked counts the enqueue; otherwise the buffered-bytes budget would double count them.
- **JSON-RPC errors settle prompts conclusively** (`acp.classifyPromptErrorOutcome`): acp.classifyPromptErrorOutcome treats a structured JSON-RPC error as proof the adapter received and conclusively rejected or failed the prompt, mapping it to PromptOutcomeFailed; only loss of the response after the request write leaves the outcome unknown.
- **Lease expiry is judged by settlement receipt time** (`acp.RuntimeSession.finishPrompt`): Provider gates revoke at the exact lease deadline and their RPC error can beat the lease timer's courtesy cancel, so acp.RuntimeSession.finishPrompt decides expiry by comparing the original settlement receipt time with the lease deadline, not by timer scheduling or lock acquisition time, and never turns lost transport or settlement evidence into cancellation proof.
- **Event overflow cancels the prompt** (`acp.RuntimeSession.markOverflowedLocked`): acp.RuntimeSession.markOverflowedLocked records event loss and schedules the bounded prompt cancellation exactly once, and pre-acceptance overflow escalates the same way as post-acceptance overflow, because a prompt that permanently lost events must not hold a global prompt slot until settlement or lease expiry.
- **Lease expiry is committed under the renewal lock** (`acp.RuntimeSession.expirePrompt`): acp.RuntimeSession.expirePrompt commits expiry and fence replacement under the same lock as renewal and still stops an unresponsive prompt even if an earlier cancellation caller exited before grace escalation; the courtesy write stays idempotent through startPromptCancellationLocked.
- **Idle adapter restart honors the cancellation fence** (`acp.RuntimeSession.RecoverExitedAdapter`): acp.RuntimeSession.RecoverExitedAdapter must not restart an idle adapter while a pending or timed-out session/cancel write still fences the provider session, because that old queued cancel could otherwise hit the resumed session's next prompt.
- **Workspace pins use O_PATH without following links** (`acp.openWorkspaceDirectory`): On Linux acp.openWorkspaceDirectory opens the workspace with O_PATH|O_DIRECTORY|O_NOFOLLOW, which never follows a symlink and needs only search permission on the parents, so the supervisor can pin a child-owned workspace it cannot read.
- **Missing workspace identity support is a refusal** (`acp.errWorkspaceIdentityUnsupported`): acp.errWorkspaceIdentityUnsupported is returned on platforms without Unix device and inode numbers, and callers must treat it as a refusal, never as meaning no identity is required.
- **Workspace rejection messages are fixed strings** (`acp.WorkspaceValidationFailedMessage`): acp.WorkspaceValidationFailedMessage and the related rejection constants are the exact public messages the supervisor returns when a built-in runtime refuses a workspace; the controller surfaces them verbatim in Task status, so they must stay fixed and never include workspace contents.

### `internal/acp/skill`

- **Skill directory handles are duplicated close-on-exec** (`skill.dupCloseOnExec`): skill.dupCloseOnExec uses F_DUPFD_CLOEXEC rather than unix.Dup, which clears close-on-exec, so an adapter another session starts concurrently cannot inherit a handle into a private skill folder.
- **Projected skills use fixed modes** (`skill.Tree.WriteTo`): skill.Tree.WriteTo creates a destination that must not already exist and writes the skill with fixed modes (folders 0755, files 0644, image-executable files 0755) regardless of image modes; ownership is left to the caller, which assigns the whole session tree to the session identity.
- **Skills from images are untrusted** (`skill`): Package skill treats Agent Skills delivered from images as untrusted: nothing inside is executed or followed, folders are walked relative to file descriptors with O_NOFOLLOW, only real folders and regular files are accepted, every limit is enforced while reading, and SKILL.md is checked as untrusted prompt input before the skill is copied into a session.
- **Skill failure reasons are stable** (`skill.ReasonMissingMount`): The skill.Reason* constants appear verbatim in Task and RuntimePool status through the same FAIL line the toolbox checks use, so they must stay stable.
- **Skill check timeout extends the startup probe** (`skill.StartupCheckTimeout`): skill.StartupCheckTimeout bounds the supervisor's skill check, which runs before the supervisor serves with either mount method; the runtime startup probe is extended by the same amount so a slow check reports its FAIL line before kubelet restarts the container.
- **Skill directories are ordered parents first** (`skill.Tree.Dirs`): skill.Tree.Dirs lists slash-separated folders relative to the skill root with parents before children, which WriteTo relies on to create each folder under an already-created parent.
- **Skill diagnostics withhold secret-shaped messages** (`skill.failf`): skill.failf messages reach stderr, the termination log, and Task and RuntimePool status, and can quote image-controlled file names, frontmatter keys, and YAML errors, so a message that looks like it carries a credential is replaced with withheldDiagnostic while the stable reason is kept.
- **Skill frontmatter cannot widen tool policy** (`skill.allowedFrontmatterKeys`): skill.allowedFrontmatterKeys admits only descriptive Agent Skills fields (compatibility, description, license, metadata, name); keys that change runtime behavior such as allowed-tools, hooks, model, context, or agent are rejected so a skill can never widen the session's frozen tool policy.
- **Runtime-interpreted skill files are reserved** (`skill.reservedFiles`): skill.reservedFiles rejects agents/openai.yaml and agents/openai.yml in a skill because Codex reads them for tool dependencies, which it may install, and invocation policy, so they would act beyond the skill's instructions.
- **Only the root SKILL.md is allowed** (`skill.validateTree`): skill.validateTree rejects any nested SKILL.md because Codex and OpenCode scan skill folders recursively, so a nested file would become an extra skill that was never validated.
- **Skill markdown cannot contain shell preprocessing** (`skill.ValidateMarkdown`): skill.ValidateMarkdown rejects every !` and ```! marker because Claude Code runs such commands through the shell when a skill loads, before any tool policy applies; it rejects all markers rather than trying to tell code examples from commands.
- **Test tokens are split literals** (`skill.TestFailuresWithholdCredentialShapedDiagnostics`): Tests that need a credential-shaped token, such as skill.TestFailuresWithholdCredentialShapedDiagnostics and toolbox.TestRunWithholdsSecretShapedCopyDiagnostics, build it by concatenating split literals so the source file itself never contains a credential-shaped string that secret scanners would flag.

### `internal/acp/toolbox`

- **Toolbox subcommands run before supervisor setup** (`toolbox.IsSubcommand`): toolbox.IsSubcommand identifies the handoff, copy, and check subcommands that the supervisor binary dispatches before it hardens its process or reads its configuration, because they run in init containers and startup checks without supervisor configuration.
- **Toolbox failures print one stable FAIL line** (`toolbox.Run`, `toolbox.TerminationLogPath`): toolbox.Run returns the process exit code and on failure prints exactly one stable FAIL line to stderr, also writing it to the container termination log when possible, because Task and RuntimePool status parse that line. toolbox.TerminationLogPath receives the stable FAIL line so the controller can classify the failure from container status.
- **Toolbox copy is idempotent across retries** (`toolbox.Copy`): toolbox.Copy sanitizes the toolbox image source into Destination/root idempotently across init-container retries: a finished copy, proven by its completion marker, is skipped, and partial staging or an unmarked root is discarded and redone.
- **Toolbox copy resets the umask** (`toolbox.Copy`): toolbox.Copy sets umask 0022 before copying because its sanitized modes are exact and an inherited umask must not narrow them below what the agent identities need.
- **Toolbox completion marker follows publish** (`toolbox.publishCopy`): toolbox.publishCopy renames the staging tree to root before writing the completion marker, so a crash between the two leaves an unmarked root that the next run discards and redoes.
- **Toolbox source path is opened without following links** (`toolbox.openSourceDirectory`): toolbox.openSourceDirectory opens every component of the absolute source path with O_NOFOLLOW so a symlink anywhere in the chain fails the copy instead of being followed.
- **Untrusted directories are read in bounded batches** (`toolbox.directoryBatch`, `toolbox.checkArchInTree`): toolbox.directoryBatch (1024) bounds how many untrusted directory entries the copier holds at once, and limits are enforced while streaming, so a folder with millions of entries fails with TOOLBOX_TOO_MANY_ENTRIES instead of exhausting memory. Image-volume toolboxes have no copier in front of them, so toolbox.checkArchInTree reads each PATH folder in bounded batches capped by checkArchEntryLimit; a folder with millions of entries fails instead of exhausting supervisor memory.
- **Symlink text counts toward the copy size** (`toolbox.copyState.copyTree`): toolbox.copyState.copyTree counts symlink target text against MaxTotalBytes because link text occupies output space and the destination volume is sized for the copier's limit.
- **File size is enforced while copying** (`toolbox.copyState.copyRegular`): The toolbox copier reads one byte past MaxFileBytes so a file that grew after stat still fails the limit rather than being silently truncated.
- **Arch check resolves links only inside the toolbox** (`toolbox.checkArchInTree`): toolbox.checkArchInTree verifies every executable ELF directly inside each PATH entry folder matches the architecture, resolving symlinks only while they stay inside the toolbox tree; targets that leave the root fail closed because an external alias may re-enter the mount, and the kernel never follows a link during the walk.
- **Toolbox links resolve in component order** (`toolbox.resolveInsideTree`, `toolbox.absoluteLinkInsideTree`): toolbox.resolveInsideTree resolves directory and file links without letting the kernel follow either and keeps relative target components in order, because cleaning away .. before resolving an earlier directory link would check a different file. Only dangling paths, loops, and non-files are skipped; paths leaving the root, inspection failures, and chains beyond maxLinkHops fail closed. On each link hop toolbox.resolveInsideTree restarts from the pinned root with the real parent components, then the raw target components, then the unconsumed suffix, in that order.
- **Terminal directories in PATH links are skipped** (`toolbox.resolveInsideTree`): toolbox.resolveInsideTree treats a link that ends at a directory, even with trailing slashes or dots, as not a tool and does not demand read access to it; any child or .. component after it still requires real traversal.
- **Toolbox directory opens are verified against lstat** (`toolbox.openVerifiedToolboxDirectory`): toolbox.openVerifiedToolboxDirectory binds a no-follow directory open to the metadata observed before opening, so a swap between lstat and open is detected; the caller owns the returned descriptor.
- **Non-executable PATH files are not read** (`toolbox.elfArchAt`): The toolbox arch check decides from no-follow metadata before opening: non-executable PATH data needs no content check and may be unreadable to the verifier, so it is skipped without O_RDONLY.
- **Toolbox executables must be world readable and executable** (`toolbox.elfArchAt`, `toolbox.worldAccessBits`): Toolbox ELF tools and scripts must have o+rx because agent processes run as arbitrary identities independent of the verifier's UID or the image's ownership; otherwise the check fails with TOOLBOX_PERMISSION_DENIED. toolbox.worldAccessBits (o+rx) are the only permission bits that matter for session identities, because agent processes run as arbitrary UIDs that own nothing in a toolbox and belong to none of its groups.
- **Mounted toolbox check runs unprivileged** (`toolbox.CheckMounted`): toolbox.CheckMounted verifies an already mounted toolbox as an unprivileged user, opening the mount path component by component with O_NOFOLLOW and never following a symlink out of the toolbox tree.
- **Unknown ELF machines are rejected** (`toolbox.elfArch`): toolbox.elfArch returns isELF true with an empty arch for unsupported ELF machines so the caller rejects them instead of treating them as non-ELF data.
- **Toolbox handoff publishes atomically** (`toolbox.Handoff`): toolbox.Handoff copies the running binary into the handoff volume as HandoffBinaryName with mode 0555 by writing a temporary name and renaming, so the toolbox-copy container never sees a partial file; it needs no supervisor configuration and runs unprivileged.
- **Root toolbox verification is metadata-only** (`toolbox.VerifyMounted`): toolbox.VerifyMounted checks with lstat only that each mount path and PATH entry folder is a real, world-traversable folder; it never opens, reads, or follows anything inside a toolbox, which is what makes it safe for the root supervisor to call. toolbox.VerifyMounted checks ancestors in order so Lstat never follows a symlink in an earlier component.
- **Toolbox images are untrusted** (`toolbox`): Package toolbox never executes, follows, or trusts a file from a toolbox image: directories are opened relative to descriptors with O_NOFOLLOW, regular files are copied byte for byte with sanitized modes, symlink text is copied without being followed, and every other file type fails the copy.
- **Runtime mounts only the completed toolbox root** (`toolbox.OutputRootName`): The runtime container mounts toolbox.OutputRootName with subPath so the copier's staging tree and completion marker are never visible to agents.
- **Toolbox check timeout extends the startup probe** (`toolbox.ImageVolumeCheckTimeout`): toolbox.ImageVolumeCheckTimeout bounds the supervisor's unprivileged image-volume check, which runs before the supervisor serves; the runtime startup probe is extended by the same amount so a slow check reports its FAIL line before kubelet restarts the container.
- **Toolbox failure reasons are stable** (`toolbox.ReasonSourceOpen`): The toolbox.Reason* constants appear verbatim in Task and RuntimePool status, so they must stay stable.
- **Toolbox diagnostics withhold secret-shaped messages** (`toolbox.FormatFailureLine`): toolbox.FormatFailureLine renders the single failure line that reaches stderr, the termination log, and Task and RuntimePool status; because its message can quote image-controlled file names, a message that looks like a credential is replaced with WithheldDiagnostic while the reason is kept.
- **Last FAIL line wins** (`toolbox.ParseFailureLine`): toolbox.ParseFailureLine returns the last FAIL line when a termination message or log tail contains several, so the final failure is what the controller reports.
- **Empty toolbox arch means the node's** (`toolbox.Options.Arch`): An empty toolbox.Options.Arch means the copier's own architecture, which equals the node architecture because the copier runs on the node.

### `internal/ahphost`

- **Session backends authorize each call as the principal** (`ahphost.SessionBackend`): ahphost.SessionBackend splits responsibility: the host owns the AHP protocol, journal and fan-out, and a backend owns what a session does. Every backend call carries the Principal so the backend authorizes the Orka operation it causes with that principal's own constraints; being connected authorizes nothing else. See [ADR 0034](0034-agent-host-protocol-api.md).
- **Client actions are authorized after host validation** (`ahphost.SessionBackend.AuthorizeClientAction`): SessionBackend.AuthorizeClientAction runs only on a client action the host has already validated, and authorizes it as the Orka operation it causes. Only a *Rejection reaches the client as a rejection reason; backends must return one to reject visibly. See [ADR 0034](0034-agent-host-protocol-api.md).
- **Client action side effects run after journaling** (`ahphost.SessionBackend.HandleClientAction`): SessionBackend.HandleClientAction runs a client action's side effects only after the host has applied and journaled the action, and it runs off the connection's read loop so a slow side effect never stalls reading from the client.
- **Connections pick up prior-process turns on every initialize and reconnect** (`ahphost.ConnectionPreparer`): The host calls ConnectionPreparer.PrepareConnection whenever a connection initializes or reconnects, regardless of which channels the client then subscribes to, because a client that never subscribes to the root channel must still find its sessions' turns and held approvals live after a restart. It runs outside the user's lock, so it must return quickly and be idempotent.
- **Extension handler errors are masked as internal errors** (`ahphost.ExtensionHandler`): An ahphost.ExtensionHandler error other than ErrUnknownExtension (method-not-found) or *Rejection reaches the client only as an internal error, so backend error details never leak to AHP clients.
- **Held resources are released when an authorized action is not applied** (`ahphost.ActionReleaser`): A backend may reserve something, such as queue room, while authorizing a client action. When the host cannot apply an authorized action, HandleClientAction never runs, so the host calls ActionReleaser.ReleaseClientAction instead to let the backend free the reservation.
- **Root-channel resource reads carry no session** (`ahphost.ResourceReader`): ahphost.ResourceReader returns ErrResourceNotFound for anything it does not serve, so the host can try the next backend. A resourceRead on the root channel arrives with an empty session, and the backend must resolve which of the user's own sessions, if any, owns the resource.
- **Reconnect results are encoded with their type discriminator** (`ahphost.reconnectReplay`): ahphost.reconnectReplay and reconnectSnapshot exist because the generated AHP reconnect result variants omit the `type` discriminator that clients need to tell a replay from snapshots; replacing them with the generated types breaks reconnect.
- **One read loop and one writer per connection** (`ahphost.conn`): An ahphost.conn runs commands on its read loop in arrival order, and every write goes through a bounded queue drained by exactly one writer goroutine, so frames are never written concurrently and a slow client is bounded rather than stalling the host.
- **Client action side effects run in order off the read loop** (`ahphost.conn.handled`): conn.handled runs backends' side effects of client actions one at a time, in the order the client sent them, on a worker separate from the read loop, so a slow side effect never blocks reading and side effects never reorder.
- **Connections are pinged to survive proxies and detect dead clients** (`ahphost.conn.pingLoop`): conn.pingLoop pings idle connections so proxies that close quiet connections keep them open, and closes a connection whose client stopped answering pings.
- **Tokens are rechecked after a connection registers** (`ahphost.conn.run`): conn.run rechecks the connection token after the connection is registered, because a revocation that lands between the door's check and registration finds no connection to close; the recheck makes such a revocation take effect.
- **The read is not cancelled on close** (`ahphost.conn.run`): When a connection closes, conn.run stops commands, writes and pings at once but does not cancel the read: cancelling it would drop the connection before the close frame explaining why is written. The read ends with the close handshake.
- **Admitted client actions' side effects outlive the connection** (`ahphost.conn.handleLoop`): conn.handleLoop runs admitted client actions' side effects in order, including those still queued when the connection closes, because the action was already applied and journaled. The read loop is the only producer of conn.handled and closes it when it stops, which lets the worker drain the queue.
- **Action delivery never blocks** (`ahphost.conn.deliverAction`): conn.deliverAction is called while the user's hub lock is held, so it must never block; it sends only to connections subscribed to the channel that know the action's type at their negotiated version.
- **Token revocation is rechecked on every command** (`ahphost.conn`): Each AHP command rechecks the connection token before it runs, so revocation takes effect on the next command rather than only at the next sweep (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **authenticate params are never logged** (`ahphost.conn.handle`): No agent advertises a protected resource, so the AHP authenticate command is refused; its params are never logged because they carry the client's credential (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **completions answers an empty list** (`ahphost.conn.handle`): No agent offers completions, so the completions command answers an empty item list instead of an error, which keeps clients' input boxes working (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **resourceRead reaches no server path** (`ahphost.conn.resourceRead`): conn.resourceRead serves only content a channel advertises, such as a changeset's before and after files, through backends; the host itself reads no path on the server (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **Root-channel resource reads stay within the user's state** (`ahphost.conn.resourceRead`): The protocol scopes resourceRead to the root channel, so conn.resourceRead lets backends find the owning session, searching only the connected user's own state.
- **Initial subscriptions are deduplicated and capped** (`ahphost.distinctSubscriptions`): distinctSubscriptions removes repeated channels and refuses more than maxInitialSubscriptions distinct channels in one initialize or reconnect, because each channel is snapshotted under the user's hub lock and one frame must not make the host snapshot over and over.
- **Activation happens under the hub lock** (`ahphost.conn.activate`): conn.activate is called with the user's hub lock held, so live delivery starts exactly after the snapshot or replay baseline the client was sent, with no gap or duplicate.
- **Unknown clients must initialize again** (`ahphost.conn.reconnect`): conn.reconnect restores a client's negotiated state and replays what it missed, or sends fresh snapshots when the journal no longer covers the gap. A client the server does not know, or one bound to another user, is rejected and must initialize again; it never receives an empty replay (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **Missed root notifications force snapshots** (`ahphost.conn.reconnectResult`): Root notifications such as a session being added are not journaled, so a replay cannot carry one the client may have missed; when one was sent after the client's last seen sequence, conn.reconnectResult answers with snapshots so the client lists its sessions again.
- **Session list cursors name a session, not an offset** (`ahphost.sessionCursor`): listSessions orders sessions most recently modified first, then by URI, and a cursor names the last session a page held rather than its position, so sessions created, disposed or modified between pages never cause the next page to repeat or skip one.
- **Failed session creation is rolled back** (`ahphost.conn.createSession`): Until a new session is ready, any failure in conn.createSession takes back the catalog record, the stored channels and the backend's session, so the same URI can be created again.
- **Creators subscribe before session channels exist** (`ahphost.conn.createSession`): conn.createSession subscribes the connection to the new session before its channels exist, so no action applied to them is missed by the creating client.
- **Orphaned channels of a failed creation are cleared on reuse** (`ahphost.conn.freeSessionURI`): A session is cataloged before it is ready and loses its catalog record last, so channels left without a catalog record are leftovers of a failed creation. conn.freeSessionURI clears them for a new session with that URI, while a cataloged session or another kind of channel on the URI refuses the creation.
- **Rollback leftovers are found again** (`ahphost.conn.takeBackSession`): conn.takeBackSession removes what a failed createSession made. If the store fails during rollback, channels with a catalog record keep the session listed so it can be disposed of, and channels without one are cleared by the next creation of the URI.
- **Disposal reads session state before deleting anything** (`ahphost.conn.disposeSession`): conn.disposeSession reads the session's state to find its chats and changesets before disposing of anything, so a failed read leaves the whole session to be disposed of again instead of leaving its channels behind.
- **Session count failures do not fail session changes** (`ahphost.Host.updateActiveSessions`): Host.updateActiveSessions runs after a session is created or disposed of, so a failure to journal the count is logged rather than reported as a failed create or dispose; the next creation or disposal recounts.
- **Oversized request ids are refused** (`ahphost.maxRequestIDBytes`): A JSON-RPC request id is echoed in its response, so the host refuses a request whose id exceeds maxRequestIDBytes instead of queuing a large echo back to a client that may not be reading.
- **Actions emitted to a channel under creation are held** (`ahphost.channelCreation`): A terminal's backend can emit to its channel before the host has stored it, for example when the shell exits at once. ahphost.channelCreation holds such actions and Host.finishCreation applies them in order once the channel is stored, instead of failing them as actions on an unknown channel.
- **Channel URIs are claimed for one creation at a time** (`ahphost.Host.claimChannelURI`): Host.claimChannelURI reserves a channel URI per user so two connections of the same user cannot both create it as a session or a terminal; a second creation is refused while the first runs.
- **Root notification sequence starts at load** (`ahphost.userHub.rootNotified`): userHub.rootNotified is the sequence of the user's latest root notification or, until one is sent in this process, the sequence the hub first loaded at. Because root notifications are not journaled, a reconnecting client whose last seen sequence is not later than it may have missed one and receives snapshots.
- **Stored channel state records its kind** (`ahphost.storedChannelJSON`): ahphost.storedChannelJSON stores the kind of a channel's state, because decoding a snapshot state by shape alone cannot tell a terminal from a session: both have a lifecycle.
- **Token revocation must be wired to Host.CloseToken** (`ahphost.New`): Whoever builds an ahphost.Host must wire its TokenService's OnRevoke to Host.CloseToken; otherwise revoking an AHP token does not close the connections using it (ADR 0034 requires revocation to stop delivery). See [ADR 0034](0034-agent-host-protocol-api.md).
- **Snapshots, subscriptions and actions share the hub lock** (`ahphost.Host.locked`): Host.locked runs a function under the user's hub lock, the same lock under which actions are applied and delivered, so a snapshot taken, a subscription installed and a response queued inside it are never overtaken by a concurrent action and never miss one.
- **Summary sync failures do not fail committed actions** (`ahphost.Host.apply`): Once Host.apply has committed and delivered actions, a failure to bring the session's catalog summary in step is logged, not returned: the actions' side effects must still run, and the next action on the session syncs the summary again.
- **Terminal input is not kept in the journal** (`ahphost.journalEnvelope`): Terminal input is what a person typed, including passwords at prompts that do not echo, and it changes no state. ahphost.journalEnvelope keeps only that input arrived, without its data; only live subscribers ever see the data.
- **Session deletion removes channels before the catalog record** (`ahphost.Host.forgetSession`): Host.forgetSession deletes a session's channels before its catalog record, so while any channel is left the record keeps the session findable and disposing of it again finishes. Both deletions run under the hub lock actions apply under, so an in-flight action finishes first and a later one finds the session gone; neither writes it back.
- **The AHP door authenticates before the upgrade** (`ahphost.Host.ServeHTTP`): Host.ServeHTTP authenticates the connection token before the WebSocket upgrade, so a client without a valid token is refused with 401 and never reaches the protocol. The request URL can carry the token in ?tkn= and is never logged (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **The door does not use the request context** (`ahphost.Host.ServeHTTP`): Behind the Fiber adaptor, an http.Request's context is the fasthttp request, which is not safe to share with other goroutines, so Host.ServeHTTP verifies tokens and serves the connection under contexts derived from context.Background rather than r.Context().
- **websocket.Accept skips its origin check** (`ahphost.Host.ServeHTTP`): Host.ServeHTTP passes InsecureSkipVerify to websocket.Accept because originAllowed has already refused browser origins; the library's same-host check would also refuse native clients that send a non-web Origin.
- **Browser origins are refused on /ahp** (`ahphost.originAllowed`): originAllowed refuses browser origins so a web page cannot ride a token it was handed; native clients send no Origin, "null", or a non-web scheme and are allowed (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **Resource listing hides what the principal may not see** (`ahphost.ResourceLister.ListResource`): ResourceLister.ListResource returns ErrResourceNotFound for anything the principal may not see, so a client cannot tell a forbidden path from a missing one.
- **Resource watch contract** (`ahphost.ResourceWatcher.WatchResources`): ResourceWatcher.WatchResources reports changes under the URI until its context ends. It calls changed once with no changes when it starts watching, returns ErrResourceNotFound for anything the principal may not see, and reports again any changes that changed could not record.
- **A resource watch is live before its channel is stored** (`ahphost.conn.createResourceWatch`): conn.createResourceWatch registers the watch as live before storing its channel, so a sweep never mistakes a stored channel in use for one an earlier process left behind.
- **Released watch channels are left for the next sweep** (`ahphost.conn.releaseWatch`): A resource watch's channel outlives the watch. conn.releaseWatch marks the user for a new sweep so their next initialize or reconnect drops it, as it does a channel an earlier process left, rather than finding it and assuming a watch still runs.
- **Leftover channels are swept once per user per process** (`ahphost.Host.sweepOnce`): Host.sweepOnce drops, once per user in each process, the channels an earlier process left behind: resource watches, which never outlive their connection, and terminals whose shells are gone. A connection arriving while the sweep runs waits for it so it never reads a channel about to go, and a failed sweep is retried on the user's next initialize or reconnect.
- **A sweep overlapped by a release runs again** (`ahphost.Host.sweepOnce`): If a channel was left behind while a user's sweep ran, the sweep may have listed it as live, so Host.sweepOnce does not mark the user swept and the next initialize or reconnect sweeps again.
- **Stored channels are listed before live ones** (`ahphost.Host.sweep`): Host.sweep lists stored channels before live watches and terminals, because a watch is live and a terminal's shell starts before its channel is stored; this order guarantees a channel in use is never swept, including when a retried sweep runs after this process created some.
- **Leftover terminal shells are stopped before their channels go** (`ahphost.Host.sweep`): A terminal an earlier process left can still run its shell in the user's workspace, which outlives the process. Host.sweep asks the TerminalReaper to stop those shells first and keeps their channels, the last trace of them, until the shells are known stopped; a failed reap fails the sweep so it runs again.
- **Orphaned terminal channels are dropped before creating another** (`ahphost.Host.dropOrphanedTerminals`): Host.dropOrphanedTerminals runs before a terminal is created and removes stored terminal channels that no shell runs and no connection follows, so clients that never dispose of ended terminals cannot grow stored state without bound. Stored channels are listed before running ones, each dropped URI is claimed so it cannot be recreated meanwhile, leftover shells are stopped first, and the final check and delete run under the user's hub lock so a channel a connection starts following is kept.
- **Live terminals are listed again after claiming** (`ahphost.Host.dropOrphanedTerminals`): A terminal disposed of and created again under the same URI between dropOrphanedTerminals' first look and its claim would be running; once the claims hold, the function lists live terminals again so it never drops one in use.
- **Stored terminal output is bounded** (`ahphost.maxStoredTerminalContent`): maxStoredTerminalContent bounds how much output a terminal channel's stored state keeps for snapshots; trimTerminalContent keeps the end. Live delivery to subscribers is not trimmed.
- **Terminals are root-level resources owned by a backend** (`ahphost.TerminalProvider`): A terminal run by ahphost.TerminalProvider is a root-level resource of one user that belongs to the backend that created it, not to any session; its stored channel names that backend so actions reach it.
- **Failing to drop ended terminals does not block a new terminal** (`ahphost.conn.createTerminal`): conn.createTerminal drops ended, unfollowed terminals first so stored state stays bounded; if that fails it logs and continues, and the drop is tried again with the next terminal.
- **A terminal whose early output cannot be stored is taken back** (`ahphost.conn.createTerminal`): The shell may exit or write output before its channel is stored. If conn.createTerminal cannot store what the shell reported, it disposes of the terminal rather than leave a channel showing a shell that no longer runs.
- **Terminal list failures do not fail terminal changes** (`ahphost.Host.refreshTerminals`): Host.refreshTerminals runs after a terminal was created or disposed of; that change is done, so a failure to update the terminal list is logged rather than reported, which would leave the client unable to retry. The list is rebuilt whole on its next change.
- **AHP tokens carry a scannable prefix** (`ahphost.TokenPrefix`): AHP connection tokens start with ahphost.TokenPrefix (orka_ahp_) so secret scanners can recognize leaked tokens; changing the prefix breaks that detection.
- **Token owners are re-admitted on every check** (`ahphost.TokenService.Admit`): TokenService.Admit, when set, decides whether a token's owner may still connect, for example whether the OIDC subject allowlist still admits them; a refused owner's tokens are invalid at the door and on every recheck, because a token outlives the sign-in that minted it (ADR 0034). See [ADR 0034](0034-agent-host-protocol-api.md).
- **Malformed protocol versions compare as newest** (`ahphost.compareVersions`): compareVersions treats a malformed MAJOR.MINOR.PATCH version as newer than anything, so an action or notification with an unknown introduction version is never sent to a client as if it knew it.

### `internal/harness/v2`

- **Status capabilities use a distinct audience** (`harnessv2.StatusCapabilityAudience`): Status-read capabilities and mutation operation capabilities are signed with the same per-runtime secret, so StatusCapabilityAudience gives status tokens their own audience. A status token must never verify as a mutation capability or the reverse.
- **Status capabilities bind profile and instance but no fence** (`harnessv2.StatusCapabilityBinding`): Status reads disclose Task, prompt, permission, and fence identifiers, so the controller bearer alone must not authorize them; a status capability signed with the per-pool, per-epoch operation secret is required. The claims carry no fence, because status is how the controller first learns the supervisor-generated boot and instance IDs. StatusCapabilityBinding always binds the profile digest and binds the runtime instance ID whenever the caller knows its exact target, leaving it empty only for the initial pool discovery probe, so a captured token cannot be replayed against another replica sharing the secret.
- **Callers of VerifyStatusCapability must enforce nonce single use** (`harnessv2.VerifyStatusCapability`): VerifyStatusCapability checks the token signature and its profile and instance binding but does not remember nonces. It returns the single-use nonce, and the caller is responsible for rejecting any nonce it has already seen, which is what prevents replay of a captured status token.
- **ClassifyOperation never authorizes replay** (`harnessv2.ClassifyOperation`): ClassifyOperation applies the v2 replay matrix to the current expected fence and, when present, the durable or tombstoned record for the exact operation identity. A Fresh result only means no matching side-effect record was supplied; it is not permission to replay, which remains the controller's durable state machine's decision.
- **RuntimeSession tombstones outlive session deletion** (`harnessv2.RuntimeSessionTombstone`): RuntimeSessionTombstone keeps exact-generation replay classification available after a RuntimeSession is deleted. It must stay live until the controller has durably retired that RuntimeSession generation, otherwise a late replay could be misclassified as fresh.
- **Harness v2 client never retries mutations itself** (`harnessv2.Client`): The controller-side harness v2 Client never follows redirects, never logs credentials, and never retries mutating requests. Only the caller may resend the same operation identity, and only after inspecting RequestWriteEvidence and durable attempt state.
- **Pre-mutation revalidation reserves half the window for the mutation** (`harnessv2.WithBeforeMutation`): WithBeforeMutation runs a fail-closed check immediately before every mutating request is encoded, capability-signed, and sent, so callers can revalidate external authority between otherwise independent mutations. The check's context gets at most half of the effective remaining window, bounded by both request metadata expiry and the caller deadline, so the mutation itself always keeps time to complete.
- **Harness v2 client returns redirects instead of following them** (`harnessv2.WithHTTPClient`): The harness v2 HTTP client sets CheckRedirect to return the redirect response, because following a redirect would either leak the operation capability to another host or silently route a fenced operation to a different instance.
- **Supervisor control traffic bypasses environment proxies** (`harnessv2.NewProxylessTransport`): NewProxylessTransport clones http.DefaultTransport with proxy resolution disabled. Supervisor control traffic targets exact in-cluster Pod endpoints, and routing it through an inherited HTTP(S)_PROXY would either expose authenticated control headers to an intermediary or leave pools unreachable when the proxy cannot reach Pod IPs.
- **Only the native restore bundle gets the larger body allowance** (`harnessv2.Client.mutateJSON`): When creating a session with a native restore bundle, the request is checked twice: every field except the bundle must fit within the negotiated ordinary request limit, and only the bundle itself may use the larger allowance. This stops other fields from riding on the bundle's bigger budget.
- **Transport errors are reduced to stable sentinels** (`harnessv2.Client`): The harness v2 client does not keep arbitrary RoundTripper errors, because they may include request headers such as capabilities. Only context cancellation sentinels are preserved; every other transport failure is unwrapped to ErrClientTransport.
- **Harness v2 requests disable net/http automatic replay** (`harnessv2.newTrackedRequest`): Harness v2 requests set GetBody to nil so net/http cannot automatically replay an idempotent PUT or DELETE after a connection failure. Replay classification belongs to the controller's durable state machine, never the transport.
- **Harness v2 requests propagate trace context only** (`harnessv2.newTrackedRequest`): Harness v2 requests inject only W3C trace context headers, never baggage, and trace context is transport metadata that never enters canonical JSON or capability claims.
- **Only exact pass-through wrappers may delegate httptrace** (`harnessv2.HTTPTraceDelegatingTransport`): A RoundTripper may implement HTTPTraceDelegatingTransport only if it passes every request context unchanged to a transport whose httptrace evidence is exact, such as a wrapper that only adds a routing header. Request write evidence depends on httptrace observing the real connection, so a wrapper that buffers, retries, or rewrites requests must not claim delegation.
- **Request write evidence is conservative** (`harnessv2.RequestWriteEvidence`): RequestWriteEvidence records only what net/http and httptrace expose. ZeroBytes is reported only for the standard net/http transport when no headers were reported written, no body bytes were consumed, and the full request was not reported written; every other incomplete write, and any unknown or custom RoundTripper, is ambiguous and never treated as proof the request was not accepted.
- **Zero-byte evidence only permits resending the same identity** (`harnessv2.RequestWriteEvidence.SafeToResendSameIdentity`): SafeToResendSameIdentity is true only when the transport proved no request bytes were written, and it permits resending the same operation identity only. It never authorizes allocating a new prompt identity, which could duplicate a side effect.
- **Harness v2 client errors never carry authentication values** (`harnessv2.ClientError`): ClientError keeps the validated v2 error code and replay classification for HTTP protocol errors, but Message and Error() must never include authentication values such as bearer tokens or capabilities.
- **Transient pre-mutation failures retry the same sealed identity** (`harnessv2.MarkPreMutationRetryable`): MarkPreMutationRetryable marks a before-mutation validation failure as transient. The client still rejects the mutation locally and reports that no request bytes were written, so callers may retry the same sealed operation identity while its deadline remains valid, never a new one.
- **Prompt streams are non-reconnectable and must be read to EOF** (`harnessv2.PromptStream`): A PromptStream is one non-reconnectable prompt response. Callers must call Decode until io.EOF so the client can prove the stream held an accepted event and exactly one terminal event with no trailing frames, and a transport disconnect is never turned into a reconnect or replay; StartPrompt therefore has no reconnect parameter and no automatic retry.
- **Tests wait for the client's WroteRequest hook** (`harnessv2.clientTestAfterRequestWritten`): net/http can return a response before its deferred WroteRequest trace hook runs, which leaves write evidence ambiguous. The clientTestAfterRequestWritten test helper holds the handler until a WroteRequest hook it adds to the context fires; httptrace calls the client's hook before that one, so releasing on it guarantees the client already recorded the write.
- **Credential bootstrap seeds credential-free provider-hosted supervisors** (`harnessv2.SignCredentialBootstrap`): Provider-hosted supervisors boot credential-free because execution-workspace providers build workloads from provider-visible templates and may snapshot a booted instance, so no credential may exist in the process or template until the controller seeds it. A public per-instance nonce binds the target workload, and an Ed25519 signature from a key derived from a controller-only bootstrap seed authenticates the exact payload against a non-secret public key embedded in the template; that signing seed is distinct from every credential in the request body.
- **Provider token placeholder is replaced by the egress gateway** (`harnessv2.ProviderTokenEgressInjectionPlaceholder`): When the backend egress gateway injects the provider-proxy bearer, Core seeds ProviderTokenEgressInjectionPlaceholder as the runtime's provider token. The supervisor sends it as the Authorization bearer, the gateway replaces the whole header value before the request reaches the provider proxy, and the provider proxy must never accept the placeholder itself. See [ADR 0045](0045-substrate-egress-credential-injection.md).
- **Credential bootstrap is first-write-wins** (`harnessv2.CredentialBootstrapRequest`): Credential bootstrap seeding is idempotent and first-write-wins: an identical repeat of the seeded CredentialBootstrapRequest is acknowledged, and any different payload is rejected as a conflict, so a later request cannot replace seeded credentials.
- **Harness v2 canonical JSON form** (`harnessv2.CanonicalJSON`): CanonicalJSON rejects duplicate keys and emits the stable v2 canonical form used for digests: object keys sorted by UTF-8 byte order, insignificant whitespace removed, strings escaped as encoding/json does, and numerically equivalent finite numbers written with the same non-exponent decimal spelling. Changing any of these rules changes every digest and breaks controller-supervisor compatibility.
- **CanonicalValueWithLimits is byte-identical to CanonicalValue** (`harnessv2.CanonicalValueWithLimits`): CanonicalValueWithLimits is only for locally built values that never cross the v2 wire, such as workspace manifest digest inputs, with bounds the caller derives from its own limits. Its output must stay byte-identical to CanonicalValue whenever both succeed, so digests do not depend on which variant computed them.
- **Request digests exclude themselves and are domain separated** (`harnessv2.CanonicalRequestDigest`): CanonicalRequestDigest hashes the canonical request after removing only metadata.requestDigest. A domain separator and schema version are mixed in so a request digest can never be reused as another kind of content digest, such as a profile or settlement digest.
- **Only the native restore bundle gets the larger digest budget** (`harnessv2.CanonicalRequestDigest`): When digesting a request that carries a native restore bundle, only the bundle bytes receive the larger digest size budget; all other control metadata stays within the ordinary canonical JSON bound.
- **Request digest excludes raw agentConfiguration** (`harnessv2.canonicalRequestDigestJSON`): The request digest deletes the agentConfiguration field before hashing because it was added after the v1 request-digest contract and its canonical digest is already bound through profile.agentConfigurationDigest. Excluding the raw expansion keeps old and new controller-supervisor pairs wire-compatible during a rolling upgrade.
- **Harness v2 package holds only the portable wire contract** (`harnessv2`): internal/harness/v2 contains only the portable orka.harness.v2 contract: protocol types, validation, canonical request digesting, replay and fence classification, lifecycle rules, and bounded NDJSON framing. Runtime supervisors, persistence, authentication transport, and provider process management belong elsewhere.
- **Live content requires runtime confirmation** (`harnessv2.AcceptedEvent.LiveUpdates`): AcceptedEvent.LiveUpdates confirms the runtime honors LiveUpdatesHeader for the prompt, including redacting every event's content before it leaves the runtime. A consumer must not show a prompt's content live unless this confirmation is present.
- **Live updates are negotiated per prompt** (`harnessv2.LiveUpdatesHeader`): A start-prompt request sets LiveUpdatesHeader to "1" to ask for live-update kinds and fields (assistant thoughts, tool names, raw input, file edits). A runtime that does not know the header ignores it and streams the base kinds, and a runtime never sends live updates to a client that did not ask, so neither side's strict decoder meets unknown fields; a runtime that honors it confirms through AcceptedEvent.LiveUpdates.
- **Omitted content must not be treated as complete** (`harnessv2.ToolCallUpdate.ContentOmitted`): ContentOmitted reports that a content snapshot was intentionally dropped to satisfy a transport bound. Receivers must retain that truncation state rather than treating the missing content as complete.
- **Live-update tool fields are redacted** (`harnessv2.ToolCallUpdate`): A tool call's RawInput and Diffs live-update fields, and the RawInput on a permission request, are redacted before they leave the runtime and are sent only to controllers that asked for live updates. The permission request carries the input so a person deciding sees what they decide on.
- **Token usage counts are cumulative and include cache** (`harnessv2.UsageUpdate`): Harness v2 token usage counts are cumulative for the prompt by default, and InputTokens already includes cache reads and writes; cached counts are a breakdown and must never be added again. A nil cache count means unavailable, while a pointer to zero is a reported zero.
- **Session-scoped token counters need a baseline** (`harnessv2.UsageUpdate.Scope`): A token usage Scope of "session" means the counters are a running conversation total, not per prompt. Such counters need a baseline captured before the first prompt so the first delta can be attributed correctly.
- **Foundry broker identity is checked before admission** (`harnessv2.FoundryBrokerIdentity`): FoundryBrokerIdentity is obtained through the authenticated supervisor before admission because a new or replaced broker ledger cannot prove cleanup of an older ledger.
- **Boot retirement uses the supervisor only as a relay** (`harnessv2.FoundryBootRetirementRequest`): FoundryBootRetirementRequest uses the current supervisor only as an authenticated relay. Its RetiredFence names a different, previously witnessed boot and never grants that boot admission or execution authority.
- **Broker request body has its own digest** (`harnessv2.FoundryBootRetirementRequest.BrokerRequestBody`): BrokerRequestBody is the exact broker wire representation, and its byte digest is echoed in the authenticated retirement proof independently of the v2 request digest.
- **Boot retirement proof is not a prompt outcome receipt** (`harnessv2.FoundryBootRetirementProof`): FoundryBootRetirementProof certifies the broker's permanent admission seal and every owner under the retired boot. It must not be treated as a prompt outcome receipt.
- **Retirement proof digest ignores relay identity** (`harnessv2.FoundryBootRetirementProof.CanonicalProofDigest`): CanonicalProofDigest binds the durable retirement evidence independently of the relay operation identity, so a fresh retry with a new operation can prove the same sealed boot.
- **Fence binds exact boot, epoch, generations, and profile** (`harnessv2.Fence`): A harness v2 Fence binds a request to one supervisor boot, controller leadership epoch, pool generation, runtime-session generation, and immutable runtime profile. The runtime-session fields may be omitted only for pool-wide operations such as drain.
- **Stale fences are HTTP 410** (`harnessv2.CompareFence`): CompareFence returns a non-empty mismatch when a request fence differs from the expected current fence; the transport must treat any mismatch as stale and answer HTTP 410.
- **Unfinished prompts poison the RuntimeSession** (`harnessv2.runtimeSessionTransitions`): A prompt that settles without completing leaves its workspace unproven, so the RuntimeSession transition table moves it to Poisoned rather than back to a reusable state.
- **Validation may move straight to publication prepared** (`harnessv2.runtimeSessionTransitions`): The RuntimeSession transition table allows Validating to reach PublicationPrepared because a runtime may freeze and persist the publication delta within validation.
- **Cancelling may still validate a completed prompt** (`harnessv2.runtimeSessionTransitions`): The RuntimeSession transition table allows Cancelling to reach Validating because the prompt can complete before the cancellation reaches the adapter; that workspace is then validated like any completed prompt.
- **Unproven cleanup keeps the session poisoned** (`harnessv2.runtimeSessionTransitions`): When RuntimeSession cleanup cannot be proven, the session is kept in Poisoned so cleanup can be retried, rather than being dropped.
- **Deletion never interrupts publication or finalization** (`harnessv2.DeletionTransition`): DeletionTransition returns the first safe transition for a deletion request. Publication reconciliation and finalization are never interrupted; callers must let them finish before asking again.
- **MCP broker pool identity travels in headers** (`harnessv2.MCPBrokerPoolNamespaceHeader`): MCPBrokerPoolNamespaceHeader and MCPBrokerPoolUIDHeader carry the non-secret pool identity in headers so the MCP broker can resolve and verify the controller bearer before it consumes the request body.
- **Forwarding Tools are hidden from the model** (`harnessv2.MCPToolDescriptor.Forward`): An MCPToolDescriptor with Forward set is a forwarding Tool: the runtime serves it to a command-line client and never lists it to the model. Its read arguments are built by the runtime from client requests, using the fixed MCPForwardInputSchema. See [ADR 0040](0040-forwarded-cli-requests.md).
- **Denying a forwarding Tool denies its write tool** (`harnessv2.MCPToolPolicy`): Tool policy checks map a forwarding write tool back to its Tool with MCPForwardToolResource, so denying a forwarding Tool also denies the write tool derived from it, regardless of which code path built the allow and deny lists.
- **Approval waits do not consume the tool execution budget** (`harnessv2.MCPApprovalWaitTimeout`): Time spent waiting for an MCP tool approval does not count against the tool execution budget; it is bounded separately by MCPApprovalWaitTimeout. The enclosing MCP call still remains subject to cancellation and the renewable prompt lease.
- **Forwarding write tools do not need runtime approval support** (`harnessv2.MCPApprovalPolicy.NeedsRuntimeApprovals`): NeedsRuntimeApprovals is true only when an approval-required tool is called by the runtime's own MCP client, which then needs a runtime able to wait for brokered approvals. A forwarding write tool is excluded because only the supervisor's client forwarder calls it, and that forwarder holds the client's request while the broker waits.
- **Native permission mode is fixed per RuntimeSession** (`harnessv2.NativePermissions`): NativePermissions is part of the RuntimeSession's launch configuration because it selects how the provider-native tools are launched. Every prompt of a session must carry the same value.
- **Ask mode only adds prompts; it never widens policy** (`harnessv2.NativePermissionsAsk`): NativePermissionsAsk launches the provider so it requests permission before every policy-allowed native tool that acts, such as shell commands and file writes or edits. Tools outside the policy stay excluded or denied exactly as in the pre-approved mode.
- **Brokered approvals do not need ACP permission requests** (`harnessv2.MCPPolicyRequiresPermissionCapability`): MCPPolicyRequiresPermissionCapability only looks at provider-native tools in the tool policy and ignores the approval policy, because Orka decides brokered tool approvals through the MCP call itself rather than through ACP permission requests.
- **Only the controller's persisted decision approves brokered tools** (`harnessv2.MCPApprovalEvidence`): MCPApprovalEvidence is kept only so runtime-supplied grants from older runtimes get an explicit rejection. Only the controller's persisted decision authorizes a brokered tool; an ACP permission response is never approval evidence.
- **Forwarded write bodies are JSON, not strings** (`harnessv2.MCPForwardWriteInputSchema`): MCPForwardWriteInputSchema types a write's body as a JSON object or array rather than a string, so the structural redaction applied to approval previews and events reaches credential-named fields inside it.
- **Forwarding write tool names cannot collide with Tools** (`harnessv2.MCPForwardWriteSuffix`): MCPForwardWriteSuffix is ":write" because a colon cannot appear in a Kubernetes name, so a derived write tool name can never match a real Tool.
- **Forwarding Tools proxy a loopback client protocol through the broker** (`harnessv2.MCPToolForward`): For an MCPToolForward, the runtime serves Protocol on loopback and sends each client request through the broker as a call to the Tool; response references to Origin are rewritten to the runtime's local endpoint. Write marks the derived tool that carries the Tool's write requests. See [ADR 0040](0040-forwarded-cli-requests.md).
- **Forwarded writes carry their preconditions** (`harnessv2.MCPForwardRequest`): MCPForwardRequest carries IfMatch and IfNoneMatch, such as the ETag az --if-match sends, so a write the client guarded with a precondition is never sent upstream unguarded.
- **Forwarded requests cannot leave the Tool origin** (`harnessv2.MCPForwardRequest.Validate`): MCPForwardRequest.Validate keeps a forwarded request on its Tool's origin: only read or write methods, an absolute path with no dot segments, encoded separators, or characters a server could interpret differently, a well-formed query, and a JSON body only for writes.
- **Forwarding reads and writes use separate tools** (`harnessv2.MCPForwardRequest.ValidateFor`): ValidateFor requires reads to go to the forwarding Tool and writes to its derived write tool; neither accepts the other's methods, so approval and policy for writes cannot be bypassed through the read tool.
- **Forwarded responses return only allowlisted headers** (`harnessv2.ForwardResponseHeaders`): ForwardResponseHeaders is an allowlist of upstream response headers a forwarding Tool returns; every other header, including any Set-Cookie, is dropped.
- **Native session limits are opt-in via header** (`harnessv2.NativeSessionLimitsHeader`): NativeSessionLimitsHeader opts a client into the additive native-session capability limit field. Older clients decode capabilities strictly, so the field is sent only to clients that ask for it.
- **Larger JSON limit applies only to native session bundles** (`harnessv2.NativeSessionJSONLimit`): NativeSessionJSONLimit allows twice the bundle limit for base64 encoding plus the ordinary canonical JSON bound for control metadata. It applies only to native restore and capture requests, never to ordinary control JSON.
- **Native session snapshots stay out of status, events, and logs** (`harnessv2.NativeSessionSnapshot`): NativeSessionSnapshot holds private provider conversation state, so it must never be included in Task status, execution events, or diagnostic logging.
- **Capture reconciliation never starts another capture** (`harnessv2.CaptureNativeSessionRequest`): The original operation ID and request digest on CaptureNativeSessionRequest reconcile one known capture under fresh current authority. A reconciliation never starts another capture if the original is absent.
- **Update byte rate is a fixed protocol invariant** (`harnessv2.DefaultMaxUpdateBytesPerSecond`): DefaultMaxUpdateBytesPerSecond is a fixed orka.harness.v2 invariant applied to each event stream, not a negotiated ProtocolLimits value. Its exported name is kept for compatibility despite the Default prefix.
- **Event update accounting charges encoded line size** (`harnessv2.EventStreamValidator.validateNext`): validateNext charges the exact encoded line size for update-byte accounting when the caller supplies it; direct ValidateNext callers keep charging the event's compact JSON encoding, so existing callers see unchanged accounting.
- **Buffered event decoding is bounded** (`harnessv2.EventDecoder.DecodeAll`): EventDecoder.DecodeAll buffers a complete finite stream and therefore enforces MaxBufferedEvents. Streaming callers should use Decode and persist or process each event before reading the next.
- **Protocol and limit violations poison the RuntimeSession** (`harnessv2.IsPoisoningStreamError`): IsPoisoningStreamError reports protocol and limit violations that require the RuntimeSession to be poisoned rather than reused. Ordinary EOF is not poisoning, but a missing terminal event discovered by Finish is.
- **Operator exec and file access run as the child identity** (`harnessv2.OperatorExecPathTemplate`): Operator exec and operator file routes act as the RuntimeSession's child identity, never as the supervisor, and file access is limited to one regular file beneath the RuntimeSession workspace. See [ADR 0044](0044-operator-workspace-access.md).
- **Operator requests authenticate from headers alone** (`harnessv2.OperatorRequestHeader`): OperatorRequestHeader carries the base64url canonical JSON request so the supervisor can authenticate the complete operation from headers alone, before it upgrades the connection to a WebSocket or reads a body.
- **Operator file writes commit only on exact size** (`harnessv2.OperatorFileRequest.Size`): An operator file write commits only when exactly OperatorFileRequest.Size bytes arrive, so a truncated upload never replaces the target file.
- **Operator requests reject unknown fields** (`harnessv2.DecodeOperatorRequestHeader`): DecodeOperatorRequestHeader decodes strictly and refuses unknown fields, so a newer client cannot smuggle options that an older supervisor would silently ignore while still verifying the signature.
- **Path identifiers use a restricted alphabet** (`harnessv2.PathSegment`): PathSegment validates opaque path identifiers against a restricted alphabet before escaping them, which avoids router-dependent handling of encoded slashes, traversal segments, control bytes, and Unicode normalization differences.
- **Tool output keeps whitespace-only text deltas** (`harnessv2.ContentBlock.ValidateToolOutput`): ValidateToolOutput accepts non-empty whitespace-only text deltas because streamed tool output may legitimately be whitespace, while prompt and terminal-result content keep the stricter non-whitespace requirement.
- **Prompt lease renewals are bounded by the lease they renew** (`harnessv2.ValidatePromptLeaseRenewal`): A valid prompt lease renewal can arrive well after it was issued, because the controller replays an ambiguous renewal verbatim and remote renewals are rechecked after a network round trip. ValidatePromptLeaseRenewal therefore bounds the issue time by the lease being renewed rather than by arrival time; maxExtension still bounds expiry from now, and a later issue time never lengthens the lease.
- **Older runtimes keep the 512 KiB native session limit** (`harnessv2.ProtocolLimits.EffectiveMaxNativeSessionBytes`): EffectiveMaxNativeSessionBytes returns LegacyMaxNativeSessionBytes (512 KiB) when a runtime advertises no native-session limit, preserving the contract of runtimes that predate the explicit capability limit.
- **Operator access requires an advertised capability** (`harnessv2.SupportsOperatorAccess`): SupportsOperatorAccess advertises the operator exec and file routes, and callers must fail closed against any supervisor that omits it rather than attempting the routes.
- **Workspace retirement drains preserve nothing** (`harnessv2.DrainReasonWorkspaceRetirement`): DrainReasonWorkspaceRetirement drains a workspace runtime before a controller-authorized Stop or Delete. Nothing on the instance is preserved, so a later termination signal may exit promptly instead of waiting to protect data.
- **Supervisors keep serving after a worker eviction signal** (`harnessv2.DrainReasonWorkerEviction`): DrainReasonWorkerEviction is self-reported by a supervisor whose host worker began graceful termination, such as an upgrade roll, node drain, or Spot reclaim. The supervisor keeps serving so the controller can drain it and have the provider suspend its data before the eviction window ends. See [ADR 0046](0046-substrate-upgrade-and-eviction.md).
- **Worker eviction suspend window matches Substrate** (`harnessv2.WorkerEvictionSuspendWindow`): WorkerEvictionSuspendWindow is the Agent Substrate worker shutdown budget: after a worker Pod receives SIGTERM, each hosted Actor has this long to be suspended before the worker kills it. It must match Substrate's budget for eviction deadlines to be enforced correctly. See [ADR 0046](0046-substrate-upgrade-and-eviction.md).
- **Worker eviction time is reported independently of drain reason** (`harnessv2.DrainStatus.WorkerEvictionAt`): DrainStatus.WorkerEvictionAt records when the host worker signalled graceful termination, separately from Reason, which keeps the drain that first closed admission. This lets Core enforce the eviction deadline even when the signal arrives during a suspension or capacity drain. See [ADR 0046](0046-substrate-upgrade-and-eviction.md).
- **Child identity budget keeps a replacement reserve** (`harnessv2.SessionIdentityCapacity`): SessionIdentityCapacity reports the finite, never-reused child identity budget for one supervisor boot. ExhaustionReserve is deliberately excluded from admission so the controller can replace the Pod before Remaining reaches zero.
- **Native capture not started permits a fresh capture** (`harnessv2.ErrorCodeNativeCaptureNotStarted`): ErrorCodeNativeCaptureNotStarted answers a capture reconciliation whose original operation this runtime incarnation never recorded, which proves no capture started, so the controller may begin a fresh one.
- **Native capture retry requires proven writer exit** (`harnessv2.ErrorCodeNativeCaptureRetryReady`): ErrorCodeNativeCaptureRetryReady proves a capture failed after the writer exited, so a fresh operation may retry capture of the retained private tree.
- **Failed idle adapter recovery retires the session** (`harnessv2.ErrorCodePromptNotAccepted`): ErrorCodePromptNotAccepted proves idle adapter recovery failed before the prompt was submitted. The RuntimeSession is retired and is not retryable.
- **Brokered approval capability is opt-in on the wire** (`harnessv2.ProviderCapabilities`): Older controllers reject unknown capability fields, so ProviderCapabilities from a supervisor not qualified for brokered approvals must still decode against the older approval-free wire contract; new approval fields are omitted unless set.
- **Substrate actor identity comes only from SystemInfo** (`harnessv2.SubstrateActorIdentity`): SubstrateActorIdentity is read from Substrate's read-only SystemInfo volume, which is regenerated on every run and restore. It is never copied from a snapshot or trusted from template environment variables.
- **Sealed bootstrap challenges are per process** (`harnessv2.SealedBootstrapChallenge`): SealedBootstrapChallenge contains only public material, and its key and boot nonce are newly generated in each credential-free supervisor process.
- **Bootstrap receiver keys never reach durable storage** (`harnessv2.CredentialBootstrapReceiver`): CredentialBootstrapReceiver holds one process's private key, which must never go into durable storage. Full memory snapshots of such a process are prohibited because they would persist that key.
- **Sealed bootstrap payloads bind one process lifetime** (`harnessv2.SealCredentialBootstrap`): SealCredentialBootstrap encrypts the credential payload for the exact observed process and Actor lifetime, and the caller also signs the envelope with the controller-only bootstrap signing seed. A rerouted request or a replacement process, even one with the same template nonce, cannot decrypt an earlier process's payload.
- **Verify bootstrap signature before sealing a response** (`harnessv2.CredentialBootstrapReceiver.SealResponse`): SealResponse encrypts a reply for the request's ephemeral sender but does not authenticate the request; the caller must verify the bootstrap signature before asking for a response.
- **Bootstrap responses bind the exact request** (`harnessv2.CredentialBootstrapExchange.OpenResponse`): CredentialBootstrapExchange uses a response key distinct from the request key that binds the exact signed request bytes. OpenResponse accepts only a reply from the challenged process to the request that created the exchange, so replies cannot be reflected back as requests.
- **Unproven ACP settlement is outcome_unknown** (`harnessv2.MapACPStopReason`): MapACPStopReason maps an unproven ACP prompt settlement to the terminal outcome_unknown. No caller may infer success or automatically replay because of transport loss.
- **New profile lists are omitted when empty to keep digests stable** (`harnessv2.RuntimeProfile`): RuntimeProfile Toolboxes and Skills are omitted when absent so the profile serializes identically to profiles that predate them, keeping their digests unchanged. Their declared order is significant.
- **Session agent configuration is bound by the profile digest** (`harnessv2.AgentSessionConfiguration`): AgentSessionConfiguration is the resolved, non-secret Agent configuration frozen into one RuntimeSession, and its canonical digest must match the RuntimeProfile AgentConfigurationDigest.
- **Codex reasoning effort is not narrowed per model** (`harnessv2.validateAgentExecutionControls`): validateAgentExecutionControls accepts the full reasoning-effort enum for Codex, because Codex itself accepts all values even though a selected model may support only a subset.
- **Resumed sessions must find a committed checkpoint** (`harnessv2.ExpectDurableResume`): The controller sets ExpectDurableResume for sessions on a resumed workspace lineage, and the runtime fails session creation when no committed checkpoint exists rather than silently materializing a fresh baseline over lost data.
- **Resume may rebaseline only from the validated prior repository** (`harnessv2.ExpectDurableResumeFrom`): ExpectDurableResumeFrom carries the controller-validated prior repository identity of a resumed lineage that legitimately moved to a new repository, such as the fork a PR publishes to. Under ExpectDurableResume, a committed checkpoint bound to exactly that identity may be wiped and re-materialized from the new baseline; any other foreign identity still fails creation closed.
- **Resume rejects checkpoints older than the generation floor** (`harnessv2.ExpectDurableResumeMinGeneration`): ExpectDurableResumeMinGeneration is the controller's persisted floor for the committed checkpoint's session generation. A same-identity checkpoint recorded at an older generation is a stale provider restore and fails session creation closed.
- **Skill and toolbox limits are part of the profile contract** (`harnessv2.MaxRuntimeSkills`): Skill and toolbox limits (MaxRuntimeSkills, MaxRuntimeToolboxes, and related bounds) are part of the immutable runtime profile contract. Controller planning, RuntimePool projection, the deployed template, the dispatcher, and the supervisor all enforce the same shape, so changing a limit changes the contract for every one of them.
- **Skills are read only from /skills in their image** (`harnessv2.RuntimeSkillSourceRoot`): RuntimeSkillSourceRoot is the only folder inside a skill image a skill may be read from. Keeping skills under one dedicated folder keeps the copier away from kernel, device, and credential mounts.
- **Skill content limits are enforced twice** (`harnessv2.MaxRuntimeSkillEntries`): The skill copier enforces the entry, byte, and depth limits in copy mode, and the supervisor enforces all skill content limits again before projecting a skill into a session, so a bypassed copier cannot deliver an oversized skill.
- **Skill paths are always explicit in the profile** (`harnessv2.RuntimeSkill`): RuntimeSkill.Path is always explicit in the runtime profile, even when an Agent omits it, so the frozen profile digest covers the effective source folder rather than a default that could change.
- **Profile validation checks shape only** (`harnessv2.RuntimeSkill.Validate`): RuntimeSkill.Validate and RuntimeToolbox.Validate check only shape. Registry allowlisting, feature gating, and runtime support are controller policy and deliberately live outside the profile contract.
- **Partial Substrate identity projections fail closed** (`harnessv2.ReadSubstrateActorIdentity`): ReadSubstrateActorIdentity treats a missing SystemInfo projection as an ordinary Kubernetes runtime, but any partial projection fails closed rather than being treated as either.
- **Homebrew toolboxes mount at the Linuxbrew prefix** (`harnessv2.RuntimeToolboxHomebrewMountPath`): RuntimeToolboxHomebrewMountPath is the only toolbox mount path outside /opt, because dalec-homebrew packages are built with prefixes that expect /home/linuxbrew/.linuxbrew.
- **Toolboxes cannot shadow built-in /opt folders** (`harnessv2.RuntimeToolboxReservedOptNames`): RuntimeToolboxReservedOptNames lists the /opt folders built-in runtime images already populate, plus the controller-owned skill mount root. A toolbox may never mount over them, so the list must grow when a runtime image adds an /opt folder.
- **Toolbox path entries avoid shell metacharacters** (`harnessv2.RuntimeToolbox.PathEntries`): Toolbox path entries are limited to characters that are safe in PATH, in the copier's comma-separated --path-entries flag, and in the generated login profile, so no whitespace, shell metacharacters, ':' or ',' may appear anywhere in a toolbox path.
- **Toolbox order decides PATH precedence** (`harnessv2.RuntimeToolbox`): The declared order of RuntimeToolbox entries decides PATH precedence between toolboxes, so the list must never be sorted or reordered.
- **Runtime image references must be fully qualified** (`harnessv2.validateRuntimeImageReference`): validateRuntimeImageReference uses reference.ParseNamed, which accepts only the canonical form, so docker.io shorthand such as yq@sha256:... or library/yq@sha256:... is rejected and every toolbox and skill image names its registry explicitly.
- **Toolbox PATH entries never shadow system commands** (`harnessv2.RuntimeToolboxChildPath`): RuntimeToolboxChildPath appends every toolbox PATH folder, in declared order, after the base PATH, so a toolbox tool can never shadow a system command of the same name.
- **Toolbox mount overlap check is independent of path shape** (`harnessv2.runtimeToolboxMountPathsOverlap`): runtimeToolboxMountPathsOverlap must detect nested mount paths on its own even though the mountPath shape rule currently prevents them, so loosening the shape rule later cannot silently allow overlapping toolbox mounts.
- **Workspace delta rejection messages are stable** (`harnessv2.WorkspaceDeltaDisallowedPathMessage`): The messages a runtime returns when a workspace delta violates its path limits, such as WorkspaceDeltaDisallowedPathMessage, are a stable contract so the controller can recognize and report which path policy rejected the delta. Do not reword them.

### `internal/harness/v2/conformance`

- **External runtime dials are checked per connection** (`conformance.PublicAddressDialTransport`): PublicAddressDialTransport disables proxies and rejects every connection unless the resolved address is a public global unicast address outside every special-use range. The check runs per dial after DNS resolution, so it also defeats DNS rebinding between validation and dial; non-Service external runtime traffic must use it, via RequirePublicAddresses, so a hostname that resolved publicly at conformance cannot later rebind to an internal controller-reachable address.
- **Service runtime probes pin verified backend Pods** (`conformance.PinnedBackendDialTransport`): PinnedBackendDialTransport dials only verified backend ip:port targets and ignores the Service ClusterIP the endpoint URL would resolve to. Pinning the authenticated connection to the Pod backends proven by endpoint policy closes the validate-then-dial TOCTOU a caller could exploit by mutating the EndpointSlice; it round-robins across pins and fails closed when none remain.
- **Conformance checks are single attempt** (`conformance.Check`): conformance.Check probes one external runtime in a single attempt: no prompt stream is reconnected or re-executed. Strict lifecycle checks use separate completed-workspace and cancellation sessions, and each original stream is consumed through terminal settlement.
- **Backend pinning takes precedence over public-address dialing** (`conformance.Check`): Service endpoints pin to verified backends and non-Service endpoints restrict every dial to public addresses; the two modes are mutually exclusive, and pinning takes precedence so verified backends are never re-resolved through the mutable Service.
- **Conformance stream timeout differs from control timeout** (`conformance.Check`): Raw capability, authorization, and replay probes keep the control timeout, while the v2 client's original prompt stream may use the full probe budget. The client's ordinary operations still enforce WithControlTimeout.
- **Native session cap is negotiated, other limits are exact** (`conformance.validateExactCapabilities`): AgentRuntime registrations predate the optional native-session byte cap. When a registration omits it, conformance lets the cap be negotiated and bounded by the v2 client, while every registered ordinary limit must still match exactly.
- **Negative authentication probes send otherwise valid requests** (`conformance.probeMutationAuthNegatives`): Conformance negative authentication probes use an otherwise valid request and vary only authentication, so a runtime's body validation cannot mask a missing capability check regardless of the order in which it validates.
- **Negative probes clean up sessions a broken runtime admits** (`conformance.probeMutationAuthNegatives`): A broken runtime may admit a negative authentication probe, so conformance marks the probe's unique session as possibly created and cleans it up on any unexpected response, including an ambiguous transport failure.
- **Workspace probe runs before the cancellation probe** (`conformance.probeLifecycle`): Cancellation retires a session, so strict conformance proves workspace validation and publication on a separate, successfully completed prompt before running the cancellation probe.
- **Deletion request is built while the session is idle** (`conformance.probeLifecycle`): The conformance cycle checks the session generation and builds its deletion request while the session is still idle, because cancellation may retire the session before the controller can issue an explicit deletion.
- **Prompts that finish before cancellation still validate** (`conformance.probeLifecycle`): A prompt that finishes before its cancellation arrives still owes workspace validation and publication finalization before its session can retire, so strict conformance probes the completed workspace in that case.
- **Cancellation replay is safe while validation is pending** (`conformance.lifecycleProbeState.probeCompletedPromptLifecycle`): Replaying cancellation and settlement is safe while a completed session awaits workspace validation, whereas a canceled session may already be retired, so the probe allows for both.
- **Retired sessions are verified absent on the same boot** (`conformance.lifecycleProbeState.probeSessionDeletion`): When a canceled session may already be retired, conformance verifies its absence through status on the same runtime boot rather than accepting a bare 404, which a restarted runtime could also return.
- **Probe cancel and delete get separate budgets** (`conformance.lifecycleProbeState.cleanup`): Conformance cleanup gives cancel and delete each a full control-timeout budget instead of one shared fixed window, so a slow cancellation cannot starve deletion and leak a resident probe session until runtime capacity is exhausted.
- **Probe cleanup verifies deletion and retries once** (`conformance.lifecycleProbeState.cleanup`): Conformance cleanup verifies that probe session deletion succeeded and retries once on a transient failure, so a runtime that needs more than one attempt to release a session does not keep it resident.
- **Conformance timeout test proxy runs full duplex** (`conformance.TestCheckProbeTimeoutSeparatesOriginalStreamFromControls`): The probe-timeout test proxy enables full duplex because the upstream can flush acceptance before the transport's final request-body EOF check, and without full duplex the server would close that shared body when flushing the downstream response.
- **Cancellation replay tolerates completion winning** (`conformance.lifecycleProbeState.probeAcceptedPromptReplay`): Completion can win either round trip of the cancellation replay probe, so conformance keeps any settled observation and compares it with the original stream's cancellation settlement instead of failing.
- **Conformance reuses the v2 workspace governance type** (`conformance.WorkspaceGovernanceMode`): conformance.WorkspaceGovernanceMode aliases the portable v2 capability wire type; external registration adds policy around that canonical field rather than defining a duplicate JSON member.
- **Conformance never retries but deliberately replays exact identities** (`conformance.Target`): Conformance never automatically retries mutations, reconnects prompt streams, or allocates a replacement prompt identity after ambiguous acceptance. Its lifecycle probe deliberately resends exact operation identities only to verify the runtime's claimed duplicate-safe replay matrix.
- **Conformance revalidates the enrolled owner before each mutation** (`conformance.Target.BeforeMutation`): Target.BeforeMutation revalidates an enrolled physical owner before every lifecycle, negative, or replay mutation, including direct HTTP requests that bypass the v2 client.
- **Conformance results hold only sanitized observations** (`conformance.Result`): conformance.Result contains only sanitized protocol observations; authentication values, operation capabilities, prompt content, and provider output must never be stored in it.
- **Workspace probe lease is renewed by one loop only** (`conformance.lifecycleProbeState.consumeWorkspacePrompt`): The workspace probe must finish one original prompt even when provisioning outlasts its initial lease. consumeWorkspacePrompt alone owns the confirmed lease, and renewal never runs concurrently with cancellation, finalization, or cleanup.
- **Probe lease renewal is single attempt within the confirmed lease** (`conformance.lifecycleProbeState.renewWorkspacePrompt`): An unacknowledged lease renewal cannot authorize work beyond the last confirmed lease, so the conformance probe bounds each renewal attempt by that lease's expiry and never retries it.

### `internal/harness/v2/eventjournal`

- **Prompt terminal evidence excludes result content** (`eventjournal.PromptTerminalEvidence`): PromptTerminalEvidence is the durable terminal classification for one exact harness v2 prompt identity. Result content stays in ResultStore and is never copied into the public execution-event journal.
- **Recovered failures reuse the journaled reason** (`eventjournal.PromptTerminalEvidence`): PromptTerminalEvidence carries the journaled, already redacted and bounded FailureCode and FailureMessage of a Failed terminal so restart recovery projects the same durable reason the live path would have.
- **Runtime text is journaled only after its logical stream ends** (`eventjournal.State`): eventjournal.State persists public lifecycle and telemetry updates as they arrive, but untrusted assistant and tool text becomes durable only after its logical stream ends so redaction can see credential shapes split across protocol frames; chunks are kept only for same-pass deduplication. Controller takeover terminalizes accepted prompts as OutcomeUnknown instead of replaying or persisting a raw-content crash buffer.
- **Overflowing tool text is discarded, not truncated** (`eventjournal.State.omitForOverflow`): When buffered tool text overflows, the journal discards it all and persists only truncation metadata at the tool's terminal update, because a truncated prefix cannot be redacted safely when a credential spans the cutoff.
- **Journal deduplication uses a sequence high-water mark** (`eventjournal.State.HasUpdate`): Validated harness streams use strictly increasing event sequences, so HasUpdate deduplicates with one high-water mark, keeping deduplication state bounded for any prompt duration.
- **Journal redacts all later runtime text after durable text exists** (`eventjournal.Journal.Open`): Exact logical-field boundaries used for journal redaction are not persisted, and a session timeline aggregates several task streams. Once any mapped journal event or other public text event is durable, Open marks the field history saturated and all later runtime text is redacted rather than risk completing a credential fragment from an earlier turn or a pre-recovery append.
- **Controller lifecycle summaries do not trigger fail-closed redaction** (`eventjournal.Journal.Open`): Task lifecycle summary events are controller-owned status descriptions, not runtime text, so Open ignores them when deciding whether earlier public text exists; otherwise every first task turn would begin in fail-closed redaction mode.
- **Backward journal scans use fixed AfterSeq windows** (`eventjournal.Journal.FindPromptTerminal`): Per-stream sequence numbers are monotonic but may have gaps, so recovery walks backward in fixed-width AfterSeq windows of MaxExecutionEventLimit, which avoids adding a reverse-scan method to the store API.
- **Plan updates are redacted against their history** (`eventjournal.State.ProjectPlanUpdate`): ProjectPlanUpdate applies the prompt's bounded public plan-field history so a credential split across successive plan notifications is redacted from the update that would make it reconstructable.
- **Journal telemetry bound omits updates instead of failing** (`eventjournal.State.appendUpdateIfNew`): The journal's in-memory bound on open tool updates must never abort a valid prompt, so excess open-tool updates are marked processed and omitted until capacity is available.
- **Assistant chunks and reasoning are not journaled individually** (`eventjournal.State.appendUpdateIfNew`): Streamed assistant chunks only advance the journal's sequence high-water mark; the complete terminal transcript is persisted once redaction can see all chunk boundaries. Assistant reasoning is live-only and is never persisted.
- **Tool raw input and file edits are never journaled** (`eventjournal.isLiveOnlyToolUpdate`): Tool call raw input and file edits are live-only fields. Once a tool's start is durable, a non-terminal update carrying only those fields adds no telemetry and is marked processed without persisting anything.
- **Tool starts are journaled once without content** (`eventjournal.State.appendUpdateIfNew`): The journal persists one metadata-free tool start so trace consumers keep the real start time, then buffers later content-bearing tool updates until the tool's logical stream closes.
- **Logical field history saturates instead of evicting** (`eventjournal.State`): When the bounded logical-field history is full, the journal keeps everything collected so far and fails closed by redacting all later runtime text. Evicting old boundaries would let a later fragment complete a credential that consumers could reconstruct from durable events.
- **Terminal usage, transcript, and lifecycle use distinct identities** (`eventjournal.State.AppendTerminalUsageIfNew`): Terminal usage, the final assistant transcript, and prompt lifecycle events derived from the same terminal event each use a distinct journal identity, so one terminal event can own all of them without ambiguous retry reconciliation.
- **Synthetic prompt terminals are keyed by the accepted event** (`eventjournal.State.AppendPromptStreamFailureIfNew`): When the controller closes a prompt-acceptance lifecycle itself, from an observed stream failure or a proven settlement without a terminal stream event, the synthetic terminal record is anchored to the accepted event's identity so retries and recovery share one stable deduplication key.
- **Journal appends reconcile before a single retry** (`eventjournal.State.appendMappedEvent`): appendMappedEvent relies on the store's stream-scoped atomic deduplication key, and after an ambiguous append error it reconciles against the durable stream before at most one safe retry.
- **Usage attribution comes from the frozen profile** (`eventjournal.State.appendMappedEvent`): Usage attribution uses the model from the controller's frozen profile, not the runtime's free-text model field or the redacted public event. It is set on the context at the append boundary so mapped content cannot override it, and only for appends, since reconciliation reads do not carry it.
- **Tool terminals race on one key** (`eventjournal.mappedToolTerminalKey`): Real runtime tool terminal updates and synthesized recovery closures use the same prompt-and-tool-scoped key from mappedToolTerminalKey, so whichever durable outcome is written first wins.
- **Duplicate appends make later text fail closed** (`eventjournal.State.appendMappedEvent`): A duplicate or reconciled append may have a different durable winner whose public field boundaries are unknown, so the journal clears its logical-field history and redacts all later runtime text.
- **Failed append reconciliation outlives the caller deadline** (`eventjournal.Journal.reconcileFailedAppend`): An append that waited out its caller's deadline, for example behind a stalled store, leaves no time to read under that deadline. reconcileFailedAppend therefore reads under at least mappedAppendReconcileTimeout, detached from the deadline, but stops when the caller cancels its context; any retry append still runs under the caller's context.
- **Untracked tools are omitted once tracking is full** (`eventjournal.State`): Once the bounded exact set of tracked tools is full, the journal conservatively marks every otherwise untracked terminal tool as omitted for the rest of the prompt rather than persisting its text unsafely.
- **Rejected telemetry leaves its identity replayable** (`eventjournal.State`): When the journal rejects invalid usage telemetry, it must not mark that update identity as processed, so a later valid replay with the same identity can still be persisted.
- **Stream linkage comes from Orka, not the runtime** (`eventjournal.MapContext`): MapContext supplies Orka-owned stream metadata for mapped harness v2 updates; protocol events never own namespace, task name, or session linkage.
- **Journaled update identity excludes the request digest** (`eventjournal.MappedUpdateIdentity`): MappedUpdateIdentity deliberately excludes RequestDigest: the validated stream already enforces it, and journaling must not change or expose prompt digest or fencing data.
- **Provider and model fields are redacted against history** (`eventjournal.redactModelWithHistory`): Each model-bearing event publishes its provider and effective model, including configured fallbacks. redactModelWithHistory checks them together against history and fields already projected for the event, and returns every field actually published so later checks account for them.
- **Logical field history counts every public copy** (`eventjournal.logicalFieldPublicCopies`): Redaction history counts the actual locations where a logical field appears in a public record: providers and models each have two raw DTO locations, and text-only fields have bounded content and summary copies, each needing its own permutation slot. Replays of the same event identity do not add another logical field.
- **Marker copy counters leave headroom** (`eventjournal.logicalFieldBoundaries`): Each consumed public copy advances the marker search by at least one byte, and the longest current sensitive marker is 18 bytes, so the per-copy usage array has 32 slots to leave room for future markers.
- **Signed query markers match without a question mark** (`eventjournal.logicalFieldSensitiveMarkers`): The logical-field marker list includes forms such as &sig= and &signature= because signed query parameters can appear without a preceding question mark.
- **Assignment markers are sensitive only while still open** (`eventjournal.logicalFieldPWDAssignmentRe`): A complete pwd or token marker is sensitive only while it can still form an assignment key under internal/redact's sensitive assignment rule. A fixed delimiter, such as the ampersand in pwd && ls, cannot become an assignment by joining more fields, and only a delimiter reachable from the start of another public copy can complete an open key; open keys stay conservative, including quoted or whitespace tails.
- **Clipping remembers unfinished assignments** (`eventjournal.logicalFieldOpenAssignmentRe`): Assignment keys and quoted values have no fixed length in the text redactor, so logicalFieldOpenAssignmentRe records when clipping a field would discard an unfinished assignment, including the aliases and Unicode case folds internal/redact accepts; its capture group marks an unfinished quoted value.
- **Marker matching compacts ASCII whitespace runs** (`eventjournal.compactLogicalFieldWhitespace`): The text redactors accept arbitrary ASCII whitespace between header and natural-language credential parts, so compactLogicalFieldWhitespace shrinks whitespace runs in the bounded matcher representation to stop clipping from hiding an unfinished marker. It keeps line-break barriers and leaves Unicode whitespace untouched.
- **Unreachable markers are rejected before copy-aware search** (`eventjournal.logicalFieldsMayReconstructSensitiveMarker`): Sensitive-marker reconstruction first checks whether any marker is reachable without tracking copies, because the bounded copy-aware search could otherwise exhaust its work budget on benign text whose fragments cannot form a marker even with unlimited reuse.
- **Marker matching folds text like the redactor** (`eventjournal.foldLogicalFieldMarkerText`): Logical-field marker matching normalizes text the same way the redactor's case-insensitive expressions do, including Unicode folds and ASCII whitespace in natural-language API key text; only the conservative fallback also folds line breaks into spaces.
- **Exact permutation tracking is bounded with a conservative fallback** (`eventjournal.permutedLogicalFieldSubsetsSensitive`): Exact permutation tracking of logical fields is bounded by maxLogicalFieldPermutationFields. Histories can legitimately hold a full 128-entry plan plus a later update, so exceeding the limit is not treated as sensitive by itself; the matcher falls back to the conservative marker reachability check also used when the candidate work cap is exhausted.
- **Safe provider and model survive summary masking** (`eventjournal.mapUsageUpdateWithHistory`): When mapping usage, provider and model values that are safe against history are preserved before the new summary is checked, because the summary's trailing "tokens" may complete an assignment or exhaust the conservative search budget, and masking it must not needlessly discard independently safe metadata.
- **Oversized transcripts are dropped entirely** (`eventjournal.MapAssistantTranscript`): MapAssistantTranscript never keeps a prefix once the complete assistant stream exceeded its bound, because a credential may span the discarded cutoff; only truncation metadata is persisted.

- **SSE scanner sees only delivered bytes** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): The SSE scanner attaches on the write side so it sees only bytes the child actually received; a marker read upstream but never delivered must not count.
- **Flush the SSE scanner before the verdict** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): A stream can end on an unterminated line, so the SSE scanner's residual buffer is scanned before deciding the stream's outcome.
- **Child disconnects are not upstream evidence** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): A child disconnect alone is not upstream evidence: a partially delivered SSE response still needs a terminal marker, while zero-byte and partial non-SSE relays stay unaccounted.
- **Leave partial non-SSE bodies unaccounted** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): A partially delivered non-SSE body proves nothing about the inference outcome, so it stays unaccounted; an unaccounted request can neither mask an earlier failure nor certify success.
- **Broken 2xx bodies count as failures** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): A 2xx whose body overran the response limit or broke mid-stream upstream delivered no usable result, so it is recorded as a failure and upstreamFailureUnrecovered cannot mistake it for success.
- **Only local cancellation waits for courtesy cancel** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): The relay holds only locally cancelled termination for courtesy cancellation; an HTTP/SSE error, completed result, or protocol or limit failure keeps its own meaning.
- **Success requires full delivery and a terminal marker** (`supervisor.providerProxy.relayUpstreamResponseWithCancellation`): A success is accounted only once the whole body reached the child, and a streamed response must also carry the provider's terminal success marker, so a truncated 2xx cannot mask an earlier failure.
- **SSE terminal scanner semantics** (`supervisor.sseTerminalErrorScanner`): sseTerminalErrorScanner watches a relayed event stream for an explicit terminal result, because providers can fail after a 200 and a clean EOF without a success marker only proves truncation. Markers are matched in a bounded rolling window of compacted line bytes; model content carries markers JSON-escaped and cannot spoof them.
- **Latch SSE failures at end of line** (`supervisor.sseTerminalErrorScanner.pendingMarker`): sseTerminalErrorScanner latches a matched error marker only once the whole line is seen, so the recorded detail carries the complete error payload instead of the prefix up to the marker.
- **Match SSE markers on whitespace-stripped lines** (`supervisor.sseTerminalErrorEventMarkers`): SSE markers are matched against whitespace-stripped lines so spaced and unspaced JSON match identically; content deltas still cannot spoof them because quotes inside model text arrive JSON-escaped and stripping whitespace does not unescape.
- **Clamp provider output limits to the profile** (`supervisor.clampProviderOutputLimit`): clampProviderOutputLimit enforces the immutable profile's model output limit on Codex, Claude, and Copilot requests, because an untrusted ACP child with a prompt-scoped proxy credential must not exceed the reviewed token bound by inflating or omitting the field; OpenCode is normalized separately with the same rule.
- **Classify provider routes before reading the body** (`supervisor.providerRequestRoute`): providerRequestRoute classifies a request by path and method alone, before the body is read, so proxy-side rejections of inference requests can be accounted in issuance order.
- **Stale cancellations do not touch the successor prompt** (`supervisor.providerProxySession.deactivateWithCause`): deactivateWithCause for a previous prompt ID may neither revoke the successor prompt's gate nor attach a cancellation hold to it.
- **Provider proxy rejects upstream tokens too short to redact** (`supervisor.ProviderProxyConfig.normalized`): ProviderProxyConfig.normalized rejects an upstream bearer token that is too short to be redacted from events by its exact value, because a short value would either leak or cause redaction of unrelated text.
- **Model output is possible only after a non-error inference response starts** (`supervisor.providerProxySession`): The provider proxy records the moment a prompt's first non-error inference response begins relaying, because model output can only be derived from such a response; error responses never mark a prompt as having produced model output.

Rejections on metadata routes carry no inference evidence.
- **Upstream detail sanitizer drops separators instead of spacing them** (`supervisor.sanitizeProviderUpstreamDetail`): sanitizeProviderUpstreamDetail removes control and separator characters rather than replacing them with spaces, so a credential wrapped across lines reassembles and the redactor still recognizes it; prose may join across the removed separators.

- **Upstream test handlers drain the request body** (`supervisor.TestProviderProxyChildCancelDuringStreamedSuccessCountsAsSuccess`): Streaming upstream test handlers drain the request body first so the HTTP server's background read can observe the proxy closing the upstream connection and cancel the request context.

- **Session operation records outlive capability expiry by a skew margin** (`supervisor.operationReplayRetentionSlack`): operationReplayRetentionSlack keeps a session operation record and its stored response 30s past the request capability expiry, preserving replay classification across the clock-skew edge without retaining expired capabilities for the whole life of a resident session.
- **Tombstones are retained by time, never evicted by count** (`supervisor.tombstoneRetention`): tombstoneRetention must exceed the maximum operation-capability lifetime plus clock skew so a replay with a still-valid capability is classified against its tombstone; after it, the capability layer rejects the replay. Every tombstone in the window is kept because the never-reused UID/GID allocator bounds their count, and count-based eviction would reopen valid create capabilities to replay.
- **Late cancellation records are kept apart from the deletion tombstone** (`supervisor.sessionTombstone`): sessionTombstone stores late cancellation operations in a separate map so replays of the explicit deletion keep returning the original immutable wire tombstone.
- **Tombstones mark sessions retired by drain cleanup** (`supervisor.sessionTombstone`): sessionTombstone.drainCleaned records that a session was retired by drain cleanup rather than an authenticated delete, so a fresh prompt for it can be reported as provably never accepted.
- **Retired prompts keep settlement proof only** (`supervisor.retiredPromptSettlement`): retiredPromptSettlement keeps a prompt's settlement proof but never its input, output, or capabilities, and lives as long as the session tombstone rather than the admission capability, which can expire while a renewed prompt is still running.
- **Create rejection messages exclude workspace contents and secrets** (`supervisor.failedCreateReplay`): rejectedMessage is a permanent, caller-visible rejection of the create request and must never contain workspace contents or secrets.
- **Workspace rejections expose only fixed public messages** (`supervisor.workspaceRejectedError`): workspaceRejectedError.publicMessage is always one of the fixed acp.*Message constants the controller surfaces; the free-form detail is only logged, so workspace contents never reach Task status.
- **Relaunch workspace validation runs as the session child** (`supervisor.validateWorkspaceAsSessionChild`): validateWorkspaceAsSessionChild re-runs workspace validation for an idle adapter restart under the child's UID/GID, because the tree and its private 0700 write-intent workspace belong to the child and the supervisor has no DAC_OVERRIDE; running as itself it would retire every clean session. The check inspects entries without following them, so child changes can only make it fail and retire the session.
- **Operator admission closes before an adapter relaunch** (`supervisor.Server.quiesceOperatorsBeforeRelaunch`): quiesceOperatorsBeforeRelaunch closes operator admission and waits for every admitted operator to exit before an exited adapter is replaced, because operator commands run as the session child and could change what the provider loads between the workspace check and the launch. Admission reopens only when the replacement accepts the triggering prompt; a failed restart retires the session with admission closed.
- **Leaving an operator-admitting state kills all operators** (`supervisor.sessionState`): sessionState.operators holds admitted operator processes, and any transition out of an operator-admitting state revokes and kills all of them.
- **Codex text without a message ID is buffered separately** (`supervisor.promptState`): promptState.untagged collects text Codex sends without a message ID since the last named chunk, such as a /review result, so it is not lost or misattributed.
- **Prompt cancel failures keep only a bounded classification** (`supervisor.promptState`): promptState.cancelInferenceFailure stores only the bounded supervisor classification, never a raw child error, because PromptSettlement does not carry the terminal event's failure detail.
- **Redaction streams hold back a possible credential prefix** (`supervisor.redactionStream`): Each prompt's redactor replaces session credentials in every emitted event, and its redaction streams hold back any chunk suffix that could begin a credential until the next chunk or stream end, so a credential split across chunks is still redacted.
- **Session operation journals reserve a slot for deletion** (`supervisor.ensureSessionOperationCapacityLocked`): ensureSessionOperationCapacityLocked keeps one journal slot for explicit deletion and makes a live session reject fresh mutations before the protocol limit, because tombstones retain every still-replayable operation and evicting valid replay records would break replay classification.
- **Session identity allocator state lives on the durable workspace** (`supervisor.newServer`): Under a durable workspace root, the UID/GID allocator high-water mark is stored in .session-identity on the durable volume, because the session base directory dies with a data-only cold suspension and a cold-booted supervisor would otherwise reuse the pre-suspension session's UID/GID. See [ADR 0027](0027-substrate-data-only-suspension.md).
- **Native-session capabilities are hidden from old clients** (`supervisor.Server.handleCapabilities`): Capabilities responses zero MaxNativeSessionBytes and SupportsNativeSessions for clients that did not opt in, preserving strict decoding by old controllers during controller/runtime upgrades.
- **Runtime status requires a single-use operation capability** (`supervisor.Server.handleStatus`): Status discloses Task, prompt, permission, and fence identifiers, so it requires proof of the operation-capability secret bound to this runtime profile in addition to the controller bearer, with a single-use nonce so a captured token cannot be replayed within its TTL.
- **Failed creates are tombstoned after identity allocation** (`supervisor.Server.tombstoneFailedCreateLocked`): A create that fails after UID/GID allocation is tombstoned so a replay of the same request is classified as a duplicate instead of consuming another never-reused identity on every retry and exhausting the pool's range; a genuine new attempt advances the session generation and is not blocked.
- **rejectTombstonedSessionCreateLocked releases the lock when it handles a request** (`supervisor.Server.rejectTombstonedSessionCreateLocked`): rejectTombstonedSessionCreateLocked is called with s.mu held; when it returns true it has already unlocked s.mu and written the response, so the caller must return immediately.
- **Unknown operations on a tombstoned session fail closed** (`supervisor.Server.rejectTombstonedSessionCreateLocked`): A create for a tombstoned session UID/generation whose operation was never recorded on it is rejected with Gone/stale fence instead of resurrecting the session.
- **Fresh creates are fenced before identity allocation** (`supervisor.Server.handleCreateSession`): A fresh create has no operation record or tombstone to classify, but its fence must still match the current supervisor before any UID/GID is allocated.
- **Creates consult the deletion tombstone before allocating identity** (`supervisor.Server.handleCreateSession`): Session creation checks the deletion tombstone before admitting a new OS identity, so a create replayed after the session was deleted never recreates it and re-runs the prompt.
- **Workspace rejections are non-retryable** (`supervisor.Server.handleCreateSession`): A create rejected because the workspace is unsupported returns a non-retryable invalid-request error, because retrying the same workspace cannot succeed and each retry would consume another child identity.
- **Only the repository workspace lives on the durable volume** (`supervisor.Server.createSession`): Under a durable workspace root, only one logical session's repository workspace lives on the provider's durable volume so a data-only cold suspension preserves exactly it; all other session paths stay ephemeral. Committed content resumes without re-materialization, and the recorded repository binding must match the declared baseline so continuation never silently switches source content. See [ADR 0027](0027-substrate-data-only-suspension.md).
- **Durable workspace data key is stable across checkpoint seeding** (`supervisor.Server.createSession`): A dedicated provider workspace keeps DurableWorkspaceKey as its data key when a checkpoint seeds a new RuntimeSession; runtime identities and the UID/GID allocator stay independent, and only the workspace directory name is stable.
- **Durable resume without a durable root fails closed** (`supervisor.Server.createSession`): When the controller asserts a session resumes a committed durable checkpoint, a runtime without a durable workspace root fails the create as resume-lost instead of running on a fresh tree.
- **Empty durable volume on expected resume fails closed** (`supervisor.Server.createSession`): If the provider returns an empty or replacement volume when a durable resume is expected, creation fails as resume-lost instead of materializing the baseline, which would silently lose checkpoint-only changes. The one exception is a repository-identity transition that staged its record durably before wiping; a retry may materialize that same staged target fresh.
- **Durable resume continuity uses session-level identity** (`supervisor.Server.createSession`): Durable resume continuity is judged on the stable session-level repository identity, not the Task-scoped baseline, because a no-repository continuation carries a fresh Task UID and a verified publication legitimately advances the validated revision.
- **Stale durable snapshots fail closed** (`supervisor.Server.createSession`): A committed durable checkpoint whose recorded session generation is older than ExpectDurableResumeMinGeneration is a stale snapshot; creation fails as resume-lost because diffing it against the newest baseline would let the next publication drop or revert newer edits.
- **Resumed durable trees are reclaimed before baseline capture** (`supervisor.Server.createSession`): A resumed durable tree still has the previous child's ownership and 0700 modes, and the supervisor lacks DAC_OVERRIDE, so acp.ReclaimSessionOwnership runs before the resumed baseline is captured; finalization then hands it to the new session's fresh child identity.
- **Durable checkpoints bound to an unexpected repository fail closed** (`supervisor.Server.createSession`): When a committed checkpoint binds a repository identity that matches neither the resumed lineage nor a controller-authorized prior identity, creation fails as resume-lost instead of wiping it, because wiping would destroy preserved data and run the continuation on a clean baseline.
- **Repository-identity transitions are staged durably before wiping** (`supervisor.Server.createSession`): A verified publication transition (for example to a PR fork) wipes the stale durable tree and re-materializes from the new baseline, but the authorization is first staged durably with acp.MarkDurableWorkspaceTransitionAuthorized; otherwise a failure between wipe and commit would leave a resumed lineage with no committed marker and every retry would fail closed.
- **Resumed baselines are reconstructed from the verified repository baseline** (`supervisor.Server.createSession`): On durable resume the publication baseline is reconstructed from the controller-verified repository baseline, not captured from the checkpoint tree, because the checkpoint may hold unpublished pre-suspension edits from a failed or cancelled Task that the next delta must include.
- **Session skills are materialized before ownership finalization** (`supervisor.materializeSessionSkills`): Skills are copied into the session tree before ownership is finalized so each private copy belongs only to this session's identity; Claude's skills go to a shared plugin folder that no session identity owns.
- **Workspace identity is recorded and held open before ownership handoff** (`supervisor.Server.createSession`): recordSessionWorkspaceIdentity pins the workspace directory identity and holds it open for the session because operator file copies reopen it by path after the child runs, and a deleted workspace's inode number could be reused by a child-created directory. It must precede the ownership handoff, since a 0700 child-owned root is not traversable by a supervisor without CAP_DAC_OVERRIDE.
- **Durable resume marker is invalidated just before the child spawns** (`supervisor.Server.createSession`): acp.MarkDurableSessionWorkspaceResumePending runs immediately before the provider child (the durable tree's only writer) can spawn, so earlier failures leave the committed checkpoint reusable on retry, while failures after it wipe the tree because the child may have modified it; the final commit restores the marker.
- **Durable workspace binding commits only after full initialization** (`supervisor.Server.createSession`): acp.CommitDurableSessionWorkspace runs only after the session is fully initialized, so a part-way failure leaves the binding pending and the next creation wipes and re-materializes instead of reusing state a failed create or partly started provider may have modified; a resume recommits here, retiring its pending record.
- **Abandoned creates must prove the child is gone** (`supervisor.Server.createSession`): When creation fails after the credential-bearing child started, its deletion must be proven before the creation is abandoned; otherwise a surviving descendant would be untracked by any session and pool lifecycle decisions would proceed over it.

- **Durable checkpoint wipes need the exact prior identity** (`supervisor.durableResumeTransitionAuthorized`): durableResumeTransitionAuthorized allows a committed checkpoint that mismatches the resumed baseline to be wiped and re-materialized only when the controller asserted the exact prior repository identity of a verified publication transition and the checkpoint binds precisely that identity.

- **Supervisor GenAI telemetry never captures content** (`supervisor.supervisorTelemetryEnvironmentSafe`): The supervisor deliberately ignores the GenAI content-capture setting: spans and metrics derived from the ACP stream never carry prompt, completion, tool argument, or tool result content.
- **Telemetry error-handler tests run in a subprocess** (`supervisor.TestSupervisorTelemetrySamplingAndRecovery`): The OpenTelemetry SDK's first SetErrorHandler call permanently changes previously returned delegators, so tests that exercise the asynchronous error path run in a subprocess to keep that state out of other tests.
- **Toolbox architecture check uses a dedicated UID** (`supervisor.toolboxCheckUID`): toolboxCheckUID (64022) is a fixed unprivileged identity for the image-volume architecture check, distinct from the session identity range and the init-container identities.
- **Root never opens or runs toolbox contents** (`supervisor.VerifyToolboxes`): VerifyToolboxes checks at startup that every toolbox mount path and path entry is a real folder using lstat only, so root opens and runs nothing; with image volumes an unprivileged child verifies the ELF architecture of the tool folders.
- **Unknown toolbox mount methods fail closed** (`supervisor.VerifyToolboxes`): VerifyToolboxes knows only the copy and imageVolume mount methods and fails closed on anything else, because skipping the unprivileged check would trust unsanitized image-volume contents.
- **Toolbox folders are re-added to PATH via ~/.profile** (`supervisor.writeToolboxLoginProfile`): writeToolboxLoginProfile writes ~/.profile in a fresh session home because Codex runs commands through bash -lc and Debian's /etc/profile resets PATH for non-root users, which would drop every toolbox folder; the file only appends folders from the frozen profile and never names files inside a toolbox.
- **Toolbox check drops to an unprivileged identity** (`supervisor.toolboxCheckSysProcAttr`): toolboxCheckSysProcAttr runs the toolbox check as toolboxCheckUID when the supervisor is root so root never parses toolbox files; a non-root supervisor (tests) runs it as itself.
- **Toolbox check clears supplementary groups** (`supervisor.toolboxCheckSysProcAttr`): toolboxCheckSysProcAttr sets an empty Groups list to clear the supervisor's supplementary groups, including group 0, so the check sees exactly what an unprivileged identity can read, matching the session launcher.
- **Supervisor and controller compute identical profile digests** (`harnessv2.RuntimeProfile`): The supervisor must compute exactly the runtime profile digest the controller computes for the same profile and toolbox list, otherwise fence checks reject the runtime.
- **Supervisor operation spans are authorized and content-free** (`supervisor.Server.traceOperation`): traceOperation runs only after controller and operation authorization, parents spans to individual HTTP operations rather than the reusable runtime session, and exports no request content, capability, header, URL, or raw error.
- **Supervisor trace extraction ignores ambient context and baggage** (`supervisor.Server.traceOperation`): traceOperation clears any server ambient parent before extracting so missing or invalid headers cannot inherit another request's context, and it uses W3C TraceContext only, excluding baggage.
- **Trace propagation survives disabled exporting** (`supervisor.Server.traceOperation`): When the supervisor tracer is disabled, traceOperation still returns the extracted context so propagation to delegated Tasks keeps working.
- **Workspace validation messages never include agent-controlled paths** (`supervisor.boundedWorkspaceValidationMessage`): boundedWorkspaceValidationMessage is forwarded into controller structured logs, so it carries only the operation and safety category and never an agent-controlled path, which could be named after a credential.

## Consequences

- These decisions are still in force. A change that breaks one must supersede that
  entry in a new ADR.
- Symbols get renamed. When an entry's symbol no longer exists, search for the behavior it
  describes.
- Entries recovered from test comments record why a test is shaped the way it is, so the test
  stays honest. A later ADR may supersede them once the tests explain themselves.
