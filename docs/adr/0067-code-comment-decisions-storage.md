# 67. Decisions recovered from code comments: storage

Date: 2026-11-22

## Status

Accepted. This record is a catalog produced by the comment ban in
[ADR 0062](0062-code-carries-no-comments.md). Each entry was a code comment that recorded a
non-obvious decision in `internal/store`, `internal/storageclient`, `internal/storageconfig`, and `pkg/storage`. The comment was deleted, and the decision now lives here.

## Context

Round 2 of the comment cleanup classified every comment left after
[ADR 0063](0063-code-comment-decisions-round-1.md). In `internal/store`, `internal/storageclient`, `internal/storageconfig`, and `pkg/storage` it found 1083 distinct decisions
that a reader of the code alone could get wrong. Comments that stated the same rule in several
places are merged into one entry. Where an earlier ADR already records a decision, the entry
links it.

## Decision

Each entry names the symbols it governs, so `rg '<symbol>'` finds the code. Entries are
grouped by package and ordered by source position as of round 2.

### `internal/storageclient`

- **Storage client owns Orka policy above providers** (`storageclient.Client`): storageclient.Client is Orka's only entry point to application storage: Orka callbacks (memory proposal application, task data access, scan ingestion) run in the client with no provider transaction open, and redaction, payload sanitization, usage attribution and snapshot-key sealing happen before any provider call so providers only store safe, sealed bytes and never hold the key. Every contract write runs under a WriteEnvelope attached below the sealing step, so a retry with the same envelope resends the identical sealed request.
- **State, artifacts and embedded must be one store** (`storageclient.New`): storageclient.New rejects a client whose State, Artifacts and Embedded providers are not provably one store (ErrSplitEmbeddedStore), because fenced artifact writes must land on the store whose cleanup generations fence them.
- **Fences are bound after the client is built** (`storageclient.Client.BindFences`): storageclient.Client.BindFences exists because the controller epoch manager is constructed after the storage client: the Kubernetes control store it uses persists through that client. Until fences are bound, writes wait and then fail with ErrNotReady; the source can be bound only once.
- **sameStore never compares uncomparable values** (`storageclient.sameStore`): storageclient.sameStore treats values that == cannot compare, including comparable types holding uncomparable interface fields, as different stores so New rejects them instead of panicking; do not replace it with a plain == comparison.
- **Provider clock skew gates writes** (`storageclient.Client.CheckClocks`): storageclient.Client.CheckClocks refuses new writes to a dataset with ErrNotReady while its provider clock is beyond storagev1.MaxClockSkew even at the edge of round-trip uncertainty, and lifts the refusal on a later in-bounds check. Leases are decided on Orka's clock, so the check only bounds the provider clock's own uses (operation age, receipt retention, filled-in times). Providers are described concurrently and each result applies as soon as it answers, so an unresponsive provider never delays another dataset's check or the lifting of its refusal.
- **Unreported clocks never clear a reported skew** (`storageclient.clockClaims.clearUnclaimed`): In storageclient.clockClaims, a Describe response without ObservedAt never claims a dataset and clears its skew only while holding the claims lock, so when two bindings describe the same dataset an unreported clock can neither suppress nor undo the refusal set by the binding that did report a skew.
- **Connector custody seal formats are a stored format** (`storageclient.Client (connector custody)`): storageclient seals connector custody under the snapshot key in the exact formats the embedded store wrote before, so existing datasets open unchanged: credentials as JSON under a fresh 32-byte AES-256-GCM data key bound to Connection UID, namespace, name, subject digest and provider, with that data key sealed under the snapshot key bound to the Connection UID; consent PKCE verifiers and parked completions sealed under the snapshot key bound to every plain field. JSON field names of the sealed bodies are part of the format. Decisions that need plaintext (commit state, retirement, grant and consent sequence) are made in the client, which reads custody, decides, seals and sends a conditional command, re-reading up to connectorCommitAttempts times when the provider reports a concurrent change. See [ADR 0033](0033-user-connectors.md).
- **Completion commit marker is sealed** (`storageclient.sealedConnectorCompletionPayload`): storageclient.sealedConnectorCompletionPayload seals the consent authority digest and the Committed marker inside the completion body, and a commit re-seals the completion with the marker bound to the same plain fields, so only a holder of the snapshot key can turn a committed completion back into a fresh write.
- **Connector seals bind every fenced plain field** (`storageclient.connectorConsentAdditionalData`): storageclient.connectorConsentAdditionalData and connectorCompletionAdditionalData bind the sealed verifier or payload to every plain field the callback and completion fences read, including the OAuth authority digest, mode, name, provider, expiry and consent sequence, so an altered record no longer opens and cannot steer the code exchange to a different endpoint.
- **Connector open errors carry no plaintext** (`storageclient.openConnectorCredential`): storageclient.openConnectorCredential and the other connector open paths must never include decrypted token material in returned errors, since errors are logged and surfaced to callers.
- **Unopenable completions count as uncommitted** (`storageclient.judgeConnectorCompletions`): storageclient.judgeConnectorCompletions counts a parked completion it cannot open as not committed: it can never be committed, so it is only ever replaced or dropped, never treated as a recovery record.
- **Replaced connector material is retired for revocation** (`storageclient.connectorRetirementFor`): storageclient.connectorRetirementFor keeps replaced connector custody sealed for later revocation because only Orka held a copy and neither a refresh nor a re-consent makes the upstream provider forget the previous material; it returns nil when nothing is left to revoke.
- **Identical replacement tokens retire nothing** (`storageclient.connectorRetirementFor`): storageclient.connectorRetirementFor retires nothing when the replacement carries the same access token, refresh token and revocation digest (providers that re-issue long-lived material on re-consent), because the current record is revoked at disconnect and duplicates would only multiply provider revocation calls.
- **Dropped refresh tokens are kept until disconnect** (`storageclient.connectorRetirementFor`): storageclient.connectorRetirementFor keeps a replaced record until disconnect when the replacement does not carry its refresh token or when a re-consent replaced the whole grant, because refresh-token rotation does not promise immediate upstream invalidation; only a replacement that keeps the same refresh token leaves just the old access token to revoke until it expires.
- **Custody reads refuse other Connections' records** (`storageclient.Client.readConnectorCustody`): storageclient.Client.readConnectorCustody rejects any record the provider returns for a different Connection UID, so a connector decision never counts, retires or commits another Connection's material.
- **Grant sequence never repeats after shred** (`storageclient.Client.PutConnectorCredential`): storageclient.Client.PutConnectorCredential numbers grants from a per-Connection LastGrantSequence counter that outlives the credential record, so a grant created after a shred never reuses an earlier grant number that approvals may be bound to.
- **Sealed grant sequence is authoritative** (`storageclient.Client.GetConnectorCredentialGrant`): The provider's plain GrantSequence column exists only so the provider can order grants and is not authenticated. storageclient.Client.GetConnectorCredentialGrant and openStoredConnectorCredential take the grant and its scopes from the sealed record and refuse custody whose plain column disagrees with the sealed value.
- **Grant read uses the tombstone-checked record** (`storageclient.Client.GetConnectorCredentialGrant`): storageclient.Client.GetConnectorCredentialGrant opens the grant from the same custody read that passed the tombstone check; a second read could return material from before a disconnect that committed after that check.
- **Refresh carries the stored grant forward** (`storageclient.Client.ReplaceConnectorCredential`): storageclient.Client.ReplaceConnectorCredential carries the stored grant sequence forward regardless of what the caller supplied; only a consent commit starts a new grant.
- **Refresh checks the tombstone before the version** (`storageclient.Client.ReplaceConnectorCredential`): storageclient.Client.ReplaceConnectorCredential refuses a tombstoned Connection before checking the version fence: a disconnect fences custody before reading the material to revoke, so a refresh landing afterwards must not add a rotated credential outside that revocation set, and a stale writer retires nothing.
- **Refresh retirement depends on refresh-token rotation** (`storageclient.Client.ReplaceConnectorCredential`): A refresh in storageclient.Client.ReplaceConnectorCredential retires the replaced record through connectorRetirementFor as a non-consent write: when the refresh keeps the same refresh token, the replaced record is kept for revocation only until its access token expires; when it rotates the refresh token, the old one may still be honored upstream, so the replaced record is kept until disconnect.
- **Retired record lifetime follows its tokens** (`storageclient.Client.RetireConnectorCredential`): storageclient.Client.RetireConnectorCredential keeps a retired record with a refresh token until disconnect; without a refresh token it lives until the access token expires, and an already expired one is not retained.
- **Consent sequence, not callback arrival, orders commits** (`storageclient.Client.CreateConnectorConsent`): storageclient.Client.CreateConnectorConsent gives each consent the Connection's next consent sequence, sealed with its verifier; completions and commits follow this order rather than callback arrival, so an older consent's tokens never replace a newer consent's committed grant.
- **One uncommitted completion per Connection** (`storageclient.Client.CreateConnectorCompletion`): storageclient.Client.CreateConnectorCompletion refuses a completion from a consent older than the committed grant or an already parked completion and replaces older uncommitted completions, so a Connection parks at most one uncommitted completion at a time.
- **Completions are refused after disconnect** (`storageclient.Client.CreateConnectorCompletion`): storageclient.Client.CreateConnectorCompletion refuses tombstoned custody because a callback that was mid-exchange during a disconnect must not park tokens for the disconnected Connection UID.
- **Expired completions stay listed for revocation** (`storageclient.Client.ListConnectorCompletionsForConnection`): storageclient.Client.ListConnectorCompletionsForConnection includes expired completions because their tokens may still be live upstream and must be revoked at disconnect; completions that cannot be opened are skipped.
- **A completion is committed at most once** (`storageclient.Client.CommitConnectorCompletion`): storageclient.Client.CommitConnectorCompletion reads custody, judges the parked completion, decides retirement and seals the new grant and committed completion into one conditional command, so a completion another API replica committed meanwhile is never committed again, which would take another grant and replay material a newer consent may have replaced.
- **Completion expiry is judged at commit time** (`storageclient.Client.CommitConnectorCompletion`): storageclient.Client.CommitConnectorCompletion checks a parked completion's expiry when preparing each attempt and sends a fresh Now so the provider judges expiry again at commit, so a commit that stalled after the read or past the deadline redeems nothing.
- **Committed completions remain recovery records** (`storageclient.Client.prepareConnectorCommit`): When storageclient.Client.prepareConnectorCommit commits a grant, uncommitted completions from older consents are removed because they can never commit afterwards, while committed completions stay as recovery records until their status lands.
- **Key activation verifies all retained connector records** (`storageclient.Client.verifyRetainedConnectorCustody`): storageclient.Client.verifyRetainedConnectorCustody authenticates every retained connector record (current and retired data keys, unexpired consent verifiers, parked completion payloads) with a candidate snapshot key before activation, so linked accounts remain usable and revocable after a key change.
- **Expired consents do not block key activation** (`storageclient.Client.verifyRetainedConnectorCustody`): storageclient.Client.verifyRetainedConnectorCustody skips expired pending consents because they hold no token and can never be used, so a key that cannot open them may still be activated.
- **Key verification pages native records one at a time** (`storageclient.nativeSessionVerificationPageSize`): Key activation pages retained snapshots eight at a time (snapshotVerificationPageSize) and native session records one at a time (nativeSessionVerificationPageSize) because snapshot bodies have no fixed size limit and native session records can hold large bundles.
- **Snapshot key stays inside keyCustody** (`storageclient.keyCustody`): storageclient.keyCustody holds the snapshot key as an AES-256-GCM AEAD; every sealed record format uses a fresh random nonce and binds the record's identity through associated data, and the raw key never leaves this type.
- **Open rejects wrong-length nonces** (`storageclient.keyCustody.open`): storageclient.keyCustody.open rejects a nonce of the wrong length before calling the AEAD, which would otherwise panic on provider-supplied data.
- **Snapshot key activation verifies retained data** (`storageclient.Client.ActivateSnapshotKey`): storageclient.Client.ActivateSnapshotKey installs a key only after it authenticates every retained sealed snapshot, native session and connector custody record, so a dataset never accumulates records sealed under different keys and linked accounts stay usable and revocable. Startup activates the key before any consumer uses the client; until then sealed operations fail closed with ErrSnapshotKeyNotActive.
- **Native seal verification skips read checks** (`storageclient.verifyNativeSessionSeal`): storageclient.verifyNativeSessionSeal authenticates a retained native session record and its digest without the stricter checks a read applies, so key activation accepts every record an earlier release could have stored.
- **Writes wait only for their own dataset's fence** (`storageclient.FenceSource`): storageclient.FenceSource, implemented by the controller epoch manager, opens each dataset's controller epoch fence only once that dataset's own epoch advance succeeds, so a storage write waits only for the fence of the dataset it targets.
- **Write retries stay within the operation lifetime** (`storageclient.DefaultRetryHorizon`): storageclient retries of one write end DefaultRetryHorizon after its first ErrUnavailable or ErrOutcomeUnknown, or at the call's deadline if earlier, and always before the operation is storagev1.MaxOperationAge minus storagev1.MaxClockSkew old so every retry is within the operation's lifetime. The first attempt runs under the call's deadline alone so a long write is not cut short.
- **A write's own fence parameter goes in its envelope** (`storageclient.writeCall.fence`): When a contract write method takes a controller epoch fence as a parameter, storageclient.writeCall.fence carries it and the envelope uses that fence, because the method's fence is authoritative for the write rather than the fence source's current one.
- **Operation IDs are UUIDv7** (`storageclient.newOperationID`): storageclient.newOperationID uses UUIDv7 so operation IDs sort by creation time; background resolution relies on operation ID order to settle unresolved operations oldest first.
- **Fence wait failures are ErrNotReady** (`storageclient.operations.writeFence`): storageclient.operations.writeFence returns ErrNotReady even when the caller's context ends before the fence opens, so callers can distinguish a write that never started from a definite failure.
- **Envelope ownership and operation creation** (`storageclient.operations.run`): storageclient.operations.run sends a write whose context already carries an envelope exactly once and unchanged, assigning no identity or time; such a caller must stamp them before computing the digest, and the client refuses unstamped requests with ErrValidation. Otherwise run waits for the target dataset's fence, refuses the write while that dataset has an unknown outcome or out-of-bounds clock, and creates one operation (new ID, digest over current arguments, issue time matching filled-in record times, next sequence) that every retry reuses with the same arguments.
- **Envelope IssuedAt matches filled-in record times** (`storageclient.operations.withIssueTime`): storageclient.operations.withIssueTime carries the time the client fills into a write's records through the context so the write envelope's IssuedAt is that same time and the request digest is computed over the stamped records.
- **Write retry and resolution semantics** (`storageclient.operations.drive`): storageclient.operations.drive retries the same envelope after ErrUnavailable (nothing committed) or ErrOutcomeUnknown (may have committed). A retry the horizon ends in flight may have committed, so it is resolved like ErrOutcomeUnknown; a retry the caller's own deadline ends returns the context error without resolution unless an earlier attempt's outcome was unknown. Any other error settles the operation as refused, unless an earlier attempt was unknown, in which case drive resolves the operation.
- **Clock-skew refusals are not-ready** (`storageclient.operations.drive`): When a provider refuses a write for clock skew, storageclient.operations.drive reports ErrNotReady, also when it ends an attempt after an unknown outcome and resolution finds the operation aborted, because the store refuses this controller's writes only until the clocks agree.
- **Retry horizon uses one timer per deadline** (`storageclient.operations.retryBounds`): storageclient.operations.retryBounds caps the retry horizon before MaxOperationAge minus MaxClockSkew because providers refuse older envelopes and their clock may run that far ahead. When the call's deadline comes first, retries run under the call's context alone (capAt zero), since a second timer for the same instant could end an attempt first and misreport the call's own deadline as the horizon's.
- **Unknown outcomes never look like definite failures** (`storageclient.operations.resolve`): storageclient.operations.resolve replays a committed operation with the same envelope to read its result, adds an operation it cannot settle to its dataset's unresolved set, and returns an error that matches only ErrOutcomeUnknown, never the underlying refusal or resolution error, so no caller treats a possibly committed write as a definite failure.
- **Aborted transient writes are safe to rerun** (`storageclient.operations.resolve`): When storageclient.operations.resolve finds an operation aborted (nothing committed, never will) and only transient failures ended the attempts, the error also matches ErrUnavailable so callers may safely rerun it; when a refusal ended the attempts, that refusal stays matchable instead.
- **Unsettleable operations do not block writes** (`storageclient.operations.resolve`): An operation whose ResolveOperation fails with a definite refusal (storageclient.unsettleable) is not added to the unresolved set, because retrying cannot settle it; it does not block the dataset, and its outcome is reported as unknown.
- **Replays honor Task data fences** (`storageclient.operations.replay`): storageclient.operations.replay re-attempts a committed operation with its original envelope to read the result; a replay is served regardless of the current controller epoch fence but not past a Task data fence that cleanup or Job revocation moved since, and every refusal yields ErrOutcomeUnknown so the caller does not re-authorize and repeat a committed operation.
- **Unknown outcomes block a dataset's new writes** (`storageclient.operations.requireSettled`): storageclient.operations.requireSettled refuses new writes with ErrNotReady while any write to the same dataset has an unknown outcome, so nothing that depends on that outcome runs before it is settled.
- **Gateway duplicate lookup sanitizes like admission** (`storageclient.Client.GetGatewayEventDuplicate`): storageclient.Client.GetGatewayEventDuplicate sanitizes the candidate exactly as AdmitGatewayEvent sanitizes a stored event, so a repeat of an admitted event matches its stored, redacted form.
- **Client enqueue mirrors Gateway service text rules** (`storageclient.Client.EnqueueGatewayMessage`): storageclient.Client.EnqueueGatewayMessage redacts message text before the provider stores it, as the Gateway service does, so a direct caller cannot store a credential either; like the service it refuses text over protocol.MaxInterimTextBytes or not valid UTF-8, before or after redaction, instead of truncating it, and leaves already redacted text unchanged.
- **Client assigns identities and times before the digest** (`storageclient (identity.go)`): storageclient assigns the identities and record times a provider would otherwise assign once per operation, before the request digest is computed and using the operation's IssuedAt, so every retry sends the same request and no provider clock or ID generator decides what Orka stores. A caller that supplies its own write envelope owns the request: the client sends it unchanged and refuses with ErrValidation a request lacking a stamp or one that redaction, bounding or other preparation (protect.go, gateway.go) would change.
- **SendMessage updates the caller only on success** (`storageclient.Client.SendMessage`): storageclient.Client.SendMessage stamps a copy of the message and copies the stored ID and creation time back to the caller's message only after the write succeeds, so a write whose outcome stays unknown leaves the caller's message as passed.
- **Caller-keyed transcript messages are left as is** (`storageclient.identifySessionMessages`): storageclient.identifySessionMessages gives a UUIDv7 ID and timestamp only to messages without an ID; a message with an ID is the caller's natural key and keeps a zero timestamp, because providers match a repeat without comparing a zero timestamp and filling one would turn a later repeat into a mismatch. It copies the slice when it changes anything.
- **Dropped finding IDs use the provider's drop_ format** (`storageclient.Client.CreateDroppedFinding`): storageclient.Client.CreateDroppedFinding assigns IDs that hash the diagnostic and its creation time in the same drop_ format the provider would generate, so client- and provider-assigned IDs stay compatible.
- **Memory proposal apply authorizes outside provider transactions** (`storageclient.Client.ApplyMemoryProposal`): storageclient.Client.ApplyMemoryProposal resolves the target memory by ID, has Orka authorize that exact memory (AuthorizeExistingMemory, and AuthorizeMemoryChange for every consolidation target) with no provider transaction open, then commits only while the proposal still resolves to the same target, re-resolving and re-authorizing when a concurrent application changed it, so a caller never receives an existing memory it was not authorized to read.
- **Proposal targets are immutable** (`storageclient.Client.ApplyMemoryProposal`): storageclient.Client.ApplyMemoryProposal reads the proposal after resolving the target and relies on a proposal's type and targets never changing, so that read names exactly the memories this application changes.
- **Applied memories are redacted again** (`storageclient.memoryFromProposal`): storageclient.memoryFromProposal re-applies the current redaction rule when building a memory from a stored proposal, so a proposal stored under an older rule cannot become an unredacted memory.
- **Execution-event store metrics are recorded by the client** (`storageclient (metrics.go)`): storageclient records Orka's execution-event store metrics (appends, store reads, payload redaction and truncation) and providers record none, so every provider, including one in another process, reports the same series in Orka's registry and nothing is counted twice.
- **Native session seal format is stable** (`storageclient.nativeSessionAAD`): storageclient seals a native session record as its whole JSON encoding with associated data (storageclient.nativeSessionAAD) binding namespace, Session name, owner UID and the encoding's digest; the provider stores the same facts in plain fields for enforcement and the client checks them against the plaintext on open. The format matches earlier releases so existing datasets open unchanged.
- **Native read limit is the absolute ceiling** (`storageclient.validateNativeRecord`): storageclient.validateNativeRecord parses the bundle only for writes; authenticated reads already proved the bytes match what was inspected at write time and are bounded only by the absolute ceiling, while new captures and imports use the configured SetNativeSessionMaxBytes policy, so lowering the limit never makes existing checkpoints unreadable.
- **Staged native imports carry no runtime ownership** (`storageclient.validateNativeRecord`): storageclient.validateNativeRecord refuses a staged native import that carries runtime ownership; its transcript boundary may still advance when a non-success prompt carries it across a terminal marker.
- **Capture retry digest ignores creation time** (`storageclient.nativeCaptureRequestDigest`): storageclient.nativeCaptureRequestDigest excludes the record's creation time so retries of the same native capture produce the same request identity.
- **Imported native snapshots bind ownership later** (`storageclient.Client.GetNativeSession`): An imported native snapshot has no Orka owner until SessionControl binds the transcript, so storageclient.Client.GetNativeSession sets the requested owner UID on the returned record, and provider and runtime metadata are rebound at runtime creation.
- **Native checkpoints are monotonic** (`storageclient.Client.SaveNativeSession`): storageclient.Client.SaveNativeSession relies on the provider preserving monotonic checkpoints and immutable named operation outcomes, so an old capture cannot replace newer conversation history.
- **Imports reserve a new Session** (`storageclient.Client.StageNativeSessionImport`): storageclient.Client.StageNativeSessionImport has the provider reserve a new Session before staging, so a caller can never replace a Session owned by another call, even an empty one.
- **Carried checkpoints advance only the boundary** (`storageclient.sealCarriedNativeSession`): storageclient.sealCarriedNativeSession advances only the transcript boundary of the stored native checkpoint: a failed, cancelled or lost prompt produced no new native state, so the stored bytes, source operation and runtime generation must match exactly.
- **Providers never receive usage attribution** (`storageclient.providerContext`): storageclient.providerContext masks the controller's usage attribution in the context once the client has derived usage from it, so a provider receives only the derived, redacted usage observation; cancellation and transaction values are kept.
- **Scan ingestion commits one conditional command** (`storageclient.Client.ApplyScanTaskIngestion`): storageclient.Client.ApplyScanTaskIngestion resolves the receipt and run with ordinary reads, runs validate (a live Kubernetes check) and apply with no provider transaction open, then commits the recorded reads and writes with the run update and receipt in one conditional command that applies only while the run and every read record are unchanged; otherwise it returns ErrPreconditionFailed, changes nothing, and the caller repeats from fresh state.
- **Ingestion callbacks get only commit-recordable methods** (`storageclient.scanIngestionRecorder`): storageclient.scanIngestionRecorder refuses every SecurityStore method whose effect it cannot record as a step of the ingestion's single commit (errScanIngestionUnsupported), and the refusal fails the ingestion.
- **Scan ingestion recorder semantics** (`storageclient.scanIngestionRecorder`): storageclient.scanIngestionRecorder records each read with the result the callback saw and each write as a commit step; writes take effect only at commit, reads of records an earlier recorded write may have changed are answered by a provider preview that applies the provider's own write semantics, and callbacks receive copies so mutating a returned record cannot change what the commit checks. Only the fingerprint finding-ID default and threat model sanitization are written back to the caller.
- **Any finding write invalidates all finding reads** (`storageclient.scanIngestionRecorder.dirtyFindings`): In storageclient.scanIngestionRecorder any recorded finding write marks all findings dirty, because an upsert matches by fingerprint and duplicate marking re-points descendants, so later finding reads must go through a provider preview.
- **Uncheckable ingestion reads fail closed** (`storageclient.scanIngestionRecorder`): When storageclient.scanIngestionRecorder cannot record a read in a form the commit can check, it fails the ingestion rather than committing writes based on an unchecked read.
- **Execution snapshot seal format is stable** (`storageclient.snapshotAdditionalData`): storageclient seals execution snapshot bodies with AES-256-GCM under the snapshot key, with associated data (storageclient.snapshotAdditionalData) binding Task UID, digest and schema version so a body copied to another identity fails to open; the format matches earlier releases so existing datasets open unchanged.
- **Task data access registers only after authorization** (`storageclient.Client.WithAuthorizedTaskDataAccess`): storageclient.Client.WithAuthorizedTaskDataAccess lets the provider resolve the cleanup fence and authorizes the caller against live Kubernetes state with no provider transaction open; each fence-checking call then refuses once cleanup or Job revocation invalidates the authorization. A Task without a registration is registered only after a first successful authorization, so unauthenticated requests cannot create one, and the caller is then authorized again against the registered fence; a registration this call created is released when access fails.
- **Trusted task data access leaves no registration** (`storageclient.Client.WithTaskDataAccess`): storageclient.Client.WithTaskDataAccess registers a Task only for the duration of trusted controller access, so cleanup of other Tasks does not refuse it while no registration is left behind for a Task that may already be finalized.
- **Uncertain fenced writes stay uncertain** (`storageclient.Client.withTaskDataAccess`): storageclient.Client.withTaskDataAccess tracks in the context whether a write had an unknown outcome, so the result stays ErrOutcomeUnknown even if a handler translates the error, and reauthorization never turns an uncertain write into a new operation.
- **Task data fence is checked before access** (`storageclient.Client.withTaskDataAccess`): storageclient.Client.withTaskDataAccess checks the Task data fence before running access as well as in every fenced call, so access that ends up calling no fence-checking method is still fenced.
- **Moved fences override translated refusals** (`storageclient.Client.withTaskDataAccess`): When access fails, storageclient.Client.withTaskDataAccess rechecks the fence and returns ErrTaskDataCleanupChanged or ErrTaskJobRevoked if it moved, even when the caller translated the refused call into its own error, so the caller reauthorizes instead of surfacing the refusal as a failure.
- **Turn finalization is decided in the client** (`storageclient.Client.commitSessionTurnFinalization`): storageclient turn finalization reads, decides and seals in the client and commits conditionally in the provider; the client assigns the IDs of the transcript messages the finalization appends so it knows the resulting transcript boundary and can seal native state against it, and the provider commits only if the transcript and stored native record still match what the client read.
- **Transcript message IDs keep the embedded format** (`storageclient.newTranscriptMessageID`): storageclient.newTranscriptMessageID produces transcript message IDs in the format the embedded store has always used for messages it appends itself, keeping client- and store-assigned IDs indistinguishable.
- **Native finalization admits two shapes** (`storageclient.validateNativeFinalization`): storageclient.validateNativeFinalization admits native state only as a fresh capture committed with a canonical assistant result, or the Session's existing checkpoint carried across a non-success outcome marker.
- **Repeated finalization seals nothing** (`storageclient.Client.sealTurnNativeSession`): storageclient.Client.sealTurnNativeSession returns nil when the turn is already finalized, so the provider only compares the recorded finalization, as it would for a repeated request.
- **Task token usage uses report attribution rules** (`storageclient.Client.TaskTokenUsage`): storageclient.Client.TaskTokenUsage gets only counter observations from the provider and applies Orka's attribution rules itself, so a Task's token totals match exactly what the usage report attributes.
- **Out-of-range usage never blocks finalization** (`storageclient.Client.CommitSessionTurnFinalization`): storageclient.Client.CommitSessionTurnFinalization attributes prompt-attempt usage before the provider adds it to Session token counters on first finalization; totals beyond the exact reporting range are left out of the counters rather than blocking finalization.
- **Derived usage is stored atomically with its event** (`storageclient.deriveExecutionEventUsage`): storageclient.deriveExecutionEventUsage attaches the usage observation derived from the sanitized event and caller attribution to the event so the provider records both atomically; an observation Orka code already attached is kept, and provider and model names are redacted either way.
- **Write watermark advances run as fenced client writes** (`storageclient.Client.Datasets`): storageclient.Client.Datasets hands the controller epoch manager each contract's provider so it can advance every dataset; reads and the epoch advance reach the provider unchanged, but AdvanceWriteWatermark runs as a write of the client under the contract's fence and envelope.
- **Write retries recheck the dataset fence** (`storageclient.operations.admitRetry`): Before each retry, storageclient.operations.admitRetry waits until the serving dataset's fence is open, no longer than fenceWait and never past the retry horizon, because a fence can close after it opened (a storage recovery hold, or a recheck after restart or switch) and a retry must never reach a dataset a new write could not. A fence reported closed (ErrNotReady), or one still closed when fenceWait ends while the call is live, refuses the retry with ErrNotReady; when the call or its horizon ends during the wait, any error that does not report the fence closed is treated as that end, and the caller ends retries as between attempts.

### `internal/storageclient/internal/envelopegen`

- **Write-back decorators copy the record per attempt** (`envelopegen.Generate`): The generated envelope decorators (envelopegen) override every catalog write so it runs through the storage client's operation runner; for writes that take a record pointer the provider may fill in, each attempt gets a fresh copy of the caller's record so every attempt sends the request its digest covers, and the caller's record receives the successful attempt's copy only after the write succeeds. The copy is shallow because providers write back only a record's own fields, never into slices, maps or records those fields refer to.
- **Writes served by every contract use the provider's own fence** (`envelopegen.Generate`): envelopegen generates decorators where a write that every contract part serves, such as AdvanceWriteWatermark, runs under the fence of the decorated provider's own dataset; a write tagged with another contract is rejected at generation time.

### `internal/storageclient/storagefault`

- **Fault errors mirror real provider error contracts** (`storagefault.Fail`): storagefault.Fail tests should use storagev1.ErrUnavailable for an unreachable store, ErrUnauthenticated for rejected credentials and ErrIncompatible for an incompatible provider. A migrating dataset refuses only writes with ErrNotReady, so a Fail(ErrNotReady) fault must match write kinds (Match.Kinds) to model it faithfully.
- **An ended context always wins over a delay or release** (`storagefault.delayAction.apply`): storagefault.delayAction.apply and Hang.apply re-check ctx.Err() after the timer or release branch fires, because select picks randomly when both are ready. A call whose context has ended must always be abandoned with ErrUnavailable and never reach the provider, so the extra check must stay.
- **Only lost-response calls get private argument copies** (`storagefault.cloneArgument`): When storagefault.LoseResponse applies, the generated wrappers mark the context (lostResponseContextKey) and pass the provider a deep copy from cloneArgument, because a provider may write output through input pointers or mutate nested maps and slices, and a lost response must not disclose fields a remote caller could not have received. Delivered responses keep the original argument references so pointer, slice and map aliasing behaves exactly like the unwrapped provider. Unexported fields such as time.Time internals keep their value from the shallow copy.
- **Storage faults interact with client write retries** (`storagefault`): The storage client retries a write that fails with ErrUnavailable or loses its response, with the same envelope, until the call deadline or storageclient.DefaultRetryHorizon, so a storagefault fault that fails a write once is absorbed; tests expecting a write to fail through an outage must give the call a short deadline. Every provider-interface method is wrapped by generated wrappers (wrappers_gen.go, regenerate with go generate), and a test fails if a catalog method is missed.
- **Embedded wrapper probes through the state contract** (`storagefault.Injector.WrapEmbedded`): storagefault.Injector.WrapEmbedded assigns Describe and HealthCheck to storagev1.StateContract because the storage client probes an embedded store through its state binding, and returns one embedded store so both contracts stay on one store. To fault the artifacts binding probes of the same store, tests wrap it again with WrapArtifacts on the same injector.
- **Fault-injected clients keep an unwrapped epoch fence** (`storagefault.NewEmbeddedClient`): storagefault.NewEmbeddedClient builds the client's controller-epoch fence (storageclienttest.FollowDataset) from the raw store, so injected faults reach the client's calls but never its fence. It validates the raw store with storageclient.NewEmbedded before wrapping, because the wrapper would hide a nil backend. Sealed calls still need Client.ActivateSnapshotKey first and fail with ErrSnapshotKeyNotActive before reaching the injector.

### `internal/storageclient/storagefault/internal/wrappergen`

- **Generated imports use the reflected package name** (`wrappergen.generator.typeName`): wrappergen.generator.typeName derives a package's identifier from reflect's type string rather than the last element of its import path, because a package name can differ from its path (harnessv2 does), and the generated wrappers would otherwise reference a nonexistent identifier.

### `internal/storageconfig`

- **Storage configuration loading is offline and source-neutral** (`storageconfig`): storageconfig builds the same Config from either the default flags (both contracts on embedded SQLite at --store-path) or a --storage-config file rendered by the Helm chart, so startup, validation and status never depend on the source. Loading never contacts a storage backend; Secret references are resolved separately through a direct Kubernetes reader before application storage opens.
- **Storage configuration digest is source-independent and secret-free** (`storageconfig.Config.Digest`): storageconfig.Config.Digest is "sha256:" plus the hex SHA-256 of the canonical encoding of every binding's backend, SQLite path, endpoint, TLS settings and Secret references, and never Secret values. It ignores where the configuration came from, so default flags and a file binding both contracts to the same SQLite path yield the same digest.
- **Embedded SQLite path comes only from --store-path** (`storageconfig.EmbeddedSQLiteSource`): storageconfig.EmbeddedSQLiteSource.Path is an installation setting taken from --store-path, never from the storage configuration file, so a configuration file cannot redirect the controller's embedded database.
- **Storage configuration reasons are stable API** (`storageconfig.Reason`): storageconfig.Reason values are stable CamelCase strings that status, Events and logs report unchanged, so renaming one is a user-visible compatibility break.
- **Storage configuration errors never include Secret values** (`storageconfig.Error`): storageconfig.Error messages name flags, fields, Secrets and keys but never Secret values, because they flow into status, Events and logs.
- **Adapter bindings fail closed until a wire transport exists** (`storageconfig.Config.RequireEmbeddedSQLite`): storageconfig.Config.RequireEmbeddedSQLite returns the SQLite path only when every contract binds to embedded SQLite; a contract bound to an adapter fails with ReasonAdapterTransportUnavailable because the controller has no storage wire transport yet, and it never silently substitutes SQLite for a configured adapter.
- **Storage configuration digest encoding is versioned by domain** (`storageconfig.digestDomain`): storageconfig.digestDomain prefixes the canonical encoding so configuration digests never collide with other Orka SHA-256 values. Any change to canonicalConfig's encoding (bindings in Contracts order, fixed field order, source kind and file path excluded) requires a new domain string, and golden digests in load_test.go pin the current one.
- **Storage configuration files are capped at 1 MiB** (`storageconfig.MaxFileBytes`): storageconfig.MaxFileBytes is 1 MiB because that is the largest ConfigMap Kubernetes stores, and the file is normally mounted from one.
- **Adapter URLs follow the AgentRuntime endpoint rule** (`storageconfig.adapterURLPattern`): storageconfig.adapterURLPattern accepts only https:// URLs without whitespace, userinfo credentials, query or fragment, the same endpoint form AgentRuntime registrations use; validateAdapterURL never echoes the rejected URL because it could carry credentials.
- **Storage config file and --store-backend are mutually exclusive** (`storageconfig.storeBackendFlag`): storageconfig.storeBackendFlag records whether --store-backend was set explicitly so Load can reject a configuration that selects storage both through --storage-config and the backend flag.
- **Storage configuration files are decoded strictly** (`storageconfig.parse`): storageconfig.parse accepts exactly one YAML document with exact field names and rejects unknown and duplicate fields, so no setting is silently ignored. requireOneDocument exists because the strict decoder reads only the first document, and a later one would go unvalidated and outside the digest.
- **Empty TLS blocks normalize away before digesting** (`storageconfig.cloneAdapter`): An adapter's empty tls block means the same as no tls block, so normalization drops it before the configuration digest is computed; otherwise two equivalent configurations would have different digests.
- **Adapter bearer tokens share the AgentRuntime token floor** (`storageconfig.MinBearerTokenBytes`): storageconfig.MinBearerTokenBytes is 32, the same minimum AgentRuntime controller tokens use, and validateBearerToken also requires visible ASCII so the token fits an Authorization header unchanged.
- **Storage Secrets resolve through the uncached API reader** (`storageconfig.Config.Resolve`): storageconfig.Config.Resolve must be given the manager's API reader, which reads directly from the API server, because resolution runs before the informer cache starts and must not wait for it. A configuration bound only to embedded SQLite makes no API calls.
- **Each Secret is read once per resolution** (`storageconfig.secretReader`): storageconfig.secretReader caches each Secret for one resolution so an adapter's CA bundle and bearer token come from the same Secret version when they share a Secret.

### `internal/store`

- **Execution snapshots are sensitive, sealed and immutable** (`store.AgentExecutionSnapshot`): store.AgentExecutionSnapshot is the immutable non-secret executable input for one Task binding. Raw credentials and TxTokens are prohibited, but the body (resolved prompts, Skill content, repository identities, endpoint metadata, policy configuration) is still sensitive: the storage client seals it with Orka's key before a provider stores it, fails closed when no key is active, and the body must never enter logs, events, metrics or ordinary API output.
- **Snapshot persistence is idempotent per Task UID and digest** (`store.AgentExecutionSnapshotStore.PersistAgentExecutionSnapshot`): store.AgentExecutionSnapshotStore.PersistAgentExecutionSnapshot keys snapshots by Task UID and digest: re-persisting an identical snapshot succeeds, the same key with different content returns ErrDuplicateMismatch, and the digest must equal CanonicalAgentExecutionSnapshotDigest(Body).
- **Snapshot deletion requires released references** (`store.AgentExecutionSnapshotStore.DeleteAgentExecutionSnapshots`): store.AgentExecutionSnapshotStore.DeleteAgentExecutionSnapshots removes every snapshot for a Task UID without checking references; callers must first prove all binding, attempt, lineage, finalizer and retention references are released.
- **Connector custody tombstones are permanent per Connection UID** (`store.ErrConnectorCustodyTombstoned`): Disconnecting a Connection tombstones its UID permanently: TombstoneConnectorCustody fences the UID before its material is read for revocation, and every later commit, completion or retire for that UID fails with store.ErrConnectorCustodyTombstoned, so a late consent completion can never recreate custody. Rows stay readable for revocation until DeleteConnectorCredential removes them and their wrapped keys.
- **Connector completion commit is sealed and atomic** (`store.ConnectorCompletion.Committed`): store.ConnectorCompletion is parked sealed until the verified owner commits it with the one-time completion nonce the completing browser received. Committed is sealed into the parked payload and replaced atomically with the custody write, so a retry after a failed status update resumes that commit (ErrConnectorCompletionCommitted) instead of writing the parked tokens again over a newer commit, and no plain field can flip it.
- **Connector grants are ordered by consent sequence** (`store.ConnectorCredential.GrantSequence`): Custody assigns each consent a Sequence when it starts, and completions carry it, so commits follow consent order rather than callback arrival; a completion from a consent older than one already parked or committed fails with store.ErrConnectorConsentSuperseded, so an older consent's tokens never replace a newer grant. store.ConnectorCredential.GrantSequence is assigned when a grant commits (never on a refresh), rises monotonically for the Connection's lifetime even across a shred, and is mirrored to Connection status so authority frozen under one grant is refused against custody a later consent replaced.
- **Connector tokens are sealed per record and bound to their Connection** (`store.ConnectorCredentialStore`): store.ConnectorCredential plaintext exists only in controller memory. The storage client seals each record's token material under its own data key, itself sealed under the snapshot key, and every store.ConnectorCredentialRef field is AEAD additional data, so a row copied to another Connection, subject or provider fails to open. Every Put, Replace or commit seals the new record under a freshly minted data key, so no two records share a key; a fresh key alone does not make earlier ciphertext unreadable. When connectorRetirementFor decides the replaced material may still need revocation, the previous record moves with its wrapped data key into retired custody, stays openable (and verifyRetainedConnectorCustody checks its data key when the snapshot key rotates), and lives until it ages out of its revocable window, is dropped by the cap on refresh-retired rows, or is deleted at disconnect. Only deleting a record deletes its sealed data key, making that ciphertext unrecoverable. See [ADR 0033](0033-user-connectors.md).
- **Connector authority and revocation identity are frozen at consent** (`store.ConnectorConsent.AuthorityDigest`): store.ConnectorConsent records the provider OAuth authority digest and revocation digest (client plus revocation endpoint, without the token endpoint) when consent starts. The callback refuses to exchange the code with a different authority, completion refuses a provider whose full authority digest (client identity plus tool destinations) changed, and both digests are sealed with the tokens so refresh and revocation always target the issuing client and a revocation endpoint moved during the consent window is never handed the credential.
- **Connector refresh writes are version-fenced** (`store.ConnectorCredential.Version`): store.ConnectorCredential.Version is the custody record version set on read; ReplaceConnectorCredential and ShredConnectorCredential write only while the row is still at that version and return ErrConflict otherwise, so a concurrent re-consent is never overwritten by material derived from an older refresh token.
- **Superseded connector material is retained for revocation** (`store.ConnectorCredentialStore.RetireConnectorCredential`): Material obtained for a Connection that cannot become its current row, such as a refresh that lost to a consent, is retired rather than dropped: it stays sealed until disconnect revokes it (with a refresh token the row lives until disconnect, otherwise until the access token expires). ListConnectorCompletionsForConnection includes expired parked completions so the reconciler can revoke tokens that were never committed before dropping them.
- **Shredding connector material keeps the UID reusable** (`store.ConnectorCredentialStore.ShredConnectorCredential`): store.ConnectorCredentialStore.ShredConnectorCredential deletes material without tombstoning the UID, for a link the provider revoked that the person may re-consent to. It still truncates the log when the row is missing and returns ErrNotFound, so callers treat ErrNotFound as already shredded.
- **Connector PKCE verifiers stay server-side and single-use** (`store.ConnectorConsent`): store.ConnectorConsent keeps the PKCE verifier server-side, sealed, and single-use: the OAuth state carries only a random single-use Nonce, and ConsumeConnectorConsent removes the consent atomically, reporting expired consents as ErrNotFound. See [ADR 0033](0033-user-connectors.md).
- **Omitted token scope means exactly the requested scopes** (`store.ConnectorConsent.Scopes`): When a token response omits scope, store.ConnectorConsent.Scopes (the scopes the consent requested) are taken as the granted set, never a later configured set, so a configuration change during consent cannot widen a grant.
- **Prompt credential bindings are normalized separately** (`store.NormalizePromptAttemptForCreate`): store.NormalizePromptAttemptForCreate does not inspect CredentialBindings; every backend that persists them must also call store.NormalizePromptCredentialBindings, which sorts them by role, validates each against the attempt namespace and rejects duplicate roles.
- **PromptAttempt reclamation waits for finalization barriers** (`store.PromptAttemptRetentionStore`): store.PromptAttemptRetentionStore reclaims Task-owned PromptAttempt records only after the broader durable control plane has crossed its finalization barriers, through a prepare step followed by reclaim.
- **Branch claim cleanup is limited to claims this call inserted** (`store.BranchClaimStore.CreateBranchClaimWithResult`): store.BranchClaimStore.CreateBranchClaimWithResult reports whether this exact call inserted the claim so callers clean up only creations they actually won, never a claim an idempotent retry or concurrent caller created.
- **External-effect authorization reads one exact identity** (`store.ExternalEffectIdentityReader`): Kubernetes-backed authorization paths use store.ExternalEffectIdentityReader.GetExternalEffectByIdentity instead of broad LIST reads so a just-committed in-flight lease is observed without cache or list races.
- **OutcomeUnknown is a terminal prompt state** (`store.IsTerminalPromptExecutionState`): store.IsTerminalPromptExecutionState treats PromptExecutionOutcomeUnknown as terminal on purpose: a prompt whose acceptance cannot be proven must never be replayed, so no further execution transition is permitted from it. See [ADR 0017](0017-harness-coexistence-architecture.md).
- **Pre-submission recovery requires proof of non-acceptance** (`store.PromptAttemptPreSubmissionRecovery`): store.PromptAttemptPreSubmissionRecovery may refresh Reserved or reset an attempt back to Reserved under a controller epoch only when it crossed no prompt acceptance boundary; resubmitting requires proof that the prompt was not accepted, otherwise the prompt could run twice.
- **PromptAttempt reclamation re-proves terminal barriers** (`store.ReclaimPromptAttemptsRequest`): store.ReclaimPromptAttemptsRequest removes every PromptAttempt of one immutable deleting Task only after the store re-proves the terminal barriers; the store derives the newest attempt itself and verifies the caller's expected final identity rather than trusting it as deletion authority. Projected mode requires an exact delivered terminal projection; Unbound covers the crash window where a queued attempt was persisted before Task.status.execution and is authoritative discovery, recording a durable NoAttempt marker when none exists so retries stay crash-safe; NoAttempt is limited to failures proven to happen before any durable attempt existed. ContinuitySession distinguishes SessionTurn-backed tasks from standalone runtime-session identities, which also populate PromptAttempt.SessionUID.
- **Session mutation lease generations are never reused** (`store.SessionMutationLease`): store.SessionMutationLease.Generation is monotonic for the immutable SessionUID and never reused, so every fence on a stale lease generation fails rather than acting for a newer owner.
- **Session lineage is claimed in the lease CAS** (`store.AcquireSessionMutationLeaseRequest.Lineage`): store.AcquireSessionMutationLeaseRequest.Lineage is established or verified in the same Kubernetes RuntimeSessionControl status CAS that records the acquired lease, and the Kubernetes-authoritative store requires it, so a lease can never exist without verified lineage.
- **Session turn finalization is atomic** (`store.FinalizeSessionTurnRequest`): store.FinalizeSessionTurnRequest finalizes the turn, optionally appends canonical transcript entries, snapshots the publication receipt, updates the verified baseline, releases the matching lease and enqueues the terminal projection in one atomic operation, so no partial finalization is observable.
- **Finalization resume cannot be redirected** (`store.ResumeSessionTurnFinalizationRequest`): store.ResumeSessionTurnFinalizationRequest resumes only the Kubernetes and outbox activation tail of a SessionTurn whose SQLite finalization is already durable; the immutable key, PromptAttempt identity and finalization digest must match so a caller cannot redirect recovery to a different turn.
- **Branch claim reclamation is exact and idempotent** (`store.ReclaimBranchClaimRequest`): store.ReclaimBranchClaimRequest removes only the exact available claim the caller observed: reconciliation-blocked claims are never reclaimable and Session claims are reclaimed only by Session lifecycle code. A missing claim, or one whose immutable owner or request identity was already replaced, is an idempotent success, but every mutable fence must still match before an existing claim is deleted.
- **Forge intent is persisted before forge calls and receipts before terminal status** (`store.SetPublicationPRIntentRequest`): store.SetPublicationPRIntentRequest persists the exact forge tuple after the deterministic commit SHA is known and before any forge API call, and store.SetPublicationPRReceiptRequest commits the exact forge receipt while the Publication is still Verifying and before terminal status is exposed, so a crash never leaves an unrecorded PR or a terminal status without its receipt.
- **External-effect operation IDs are never reused** (`store.ExternalEffectIdentity`): store.ExternalEffectIdentity is the canonical idempotency identity for an external effect, and its operation ID must never be reused for different input; ReserveExternalEffect returns the existing record only for the same request digest.
- **ApprovalTaskUID is a discovery binding only** (`store.ExternalEffect.ApprovalTaskUID`): store.ExternalEffect.ApprovalTaskUID binds a Kubernetes Task, with a discovery label for approval recovery, when Tasks share a RuntimeSession aggregate; legacy records receive only the label so their spec is preserved, and other backends may ignore it. It never changes the canonical identity, grants no execution authority, and does not make the record subject to Task garbage collection.
- **Controller epoch mutation interlock is not a transaction** (`store.ControllerEpochMutationStore`): store.ControllerEpochMutationStore acquires a bounded epoch Lease interlock before a short Kubernetes mutation callback, but it is not a cross-resource transaction: an ambiguous request can still complete after the callback returns or the Lease expires, so callers must keep target UID and resourceVersion preconditions and immutable ownership checks, and neither timeout nor expiry proves completion. The callback must not invoke another control-store mutation or wait for a runtime or network operation to settle. Acquisition contention wraps ErrControllerEpochMutationContention and ErrConflict, and confirmed authority loss must never carry the contention marker.
- **Event sanitization metrics are recorded once from final state** (`store.SanitizeExecutionEventPayloadFields`): store.SanitizeExecutionEventPayloadFields applies the shared redaction and truncation contract and the storage client applies it to every appended event before any provider call, but it records no metrics because it runs more than once per logical event (the harness mapper, then the storage client on append) and a worker may already have redacted the payload in another process. The storage client records the redaction and truncation metric exactly once per newly appended event using store.ExecutionEventPayloadSanitizationSignals, which derives the signals from the final persisted payload.
- **Gateway session cleanup operations bind the physical Session** (`store.GatewaySessionCleanupOperation`): store.GatewaySessionCleanupOperation derives its operation identity from namespace, Session name, Session UID, Gateway UID and binding UID, so ingress recognizes cleanup completions without reusing deleted names or erasing archive receipts that older Tasks still need.
- **WorkAction IDs use a length prefix, not a hash** (`store.RepositoryMonitorWorkActionID`): store.RepositoryMonitorWorkActionID prefixes the command ID length so the command and action components stay unambiguous; command identifiers are not credentials, so password-style hashing was deliberately not used.
- **Native session state reads require the exact Session UID** (`store.NativeSessionStore`): store.NativeSessionStore persists sealed native provider state separately from public Task artifacts and Session projections; reads require the exact canonical Session UID and transcript boundary, and an empty UID read exposes only a staged, not-yet-bound import to the authorized migration export API. The storage client seals records before a provider sees them.
- **Native capture digest excludes the transcript boundary** (`store.NativeSessionCaptureDigest`): store.NativeSessionCaptureDigest binds only immutable finalization input and excludes the transcript boundary, because the finalization itself produces that boundary and the sealer applies it afterwards.
- **Session runtime cleanup runs outside the epoch lock** (`store.SessionRuntimeCleanupFunc`): store.SessionRuntimeCleanupFunc retires resident runtime state after the durable cleanup intent has fenced new work and before Session authority is removed. It runs outside the controller-epoch mutation lock, so runtime mutations must revalidate the supplied fence and short receipt writes must acquire that lock.
- **Session turn persistence never touches Kubernetes control rows** (`store.SessionTurnPersistenceStore`): store.SessionTurnPersistenceStore is the database half of SessionControlStore: the storage client persists turn rows, transcript entries, native state and deferred outbox records over a provider's SessionTurnRecordStore, but never reads or mutates Kubernetes-authoritative control rows. CommitSessionTurnFinalizationRequest commits only database-owned data atomically, and the coordinating Kubernetes store updates control records after that transaction commits; NativeSession is plaintext and the storage client seals it before a provider sees it.
- **Turn token usage is counted once** (`store.CommitSessionTurnFinalizationRequest.InputTokens`): store.CommitSessionTurnFinalizationRequest.InputTokens and OutputTokens are added to the Session's token counters only by the first finalization of a turn; a repeated finalization adds nothing, so retries never double-count usage.
- **Temporary storage errors are retried, never final** (`store.IsTemporaryStorageError`): store.IsTemporaryStorageError groups ErrNotReady (fence not open, an earlier outcome still resolving, or clock skew), ErrUnavailable (nothing committed) and ErrOutcomeUnknown (neither success nor failure). Callers retry later, as a reconciler requeue or HTTP 503, and never treat such an error as a definite failure of the work or report success.
- **Memory proposal authorization runs outside provider transactions** (`store.MemoryProposalStore.ApplyMemoryProposal`): store.MemoryProposalStore.ApplyMemoryProposal is implemented by the storage client as the contract's resolve followed by a conditional commit, running Orka's authorization callbacks between them with no provider transaction open. MemoryProposalApply.AuthorizeExistingMemory authorizes the exact existing memory an application would return or link and runs again for each new target after a concurrent change; new memories are covered by the caller's separate create permission. AuthorizeMemoryChange runs for every memory a consolidation proposal targets.
- **Scan ingestion is an optimistic conditional commit** (`store.SecurityStore.ApplyScanTaskIngestion`): store.SecurityStore.ApplyScanTaskIngestion runs validate before apply and again just before commit, with neither inside a store transaction. apply must use the supplied recording store and perform no external mutations; its writes take effect only if the commit succeeds and their errors may surface later. When another writer changed a record apply read, ingestion returns ErrPreconditionFailed and changes nothing, and the caller must repeat from fresh state rather than re-running apply on state it mutated.
- **Task data access is fenced against finalizer cleanup** (`store.ErrTaskDataCleanupChanged`): store.ErrTaskDataCleanupChanged means concurrent Task data cleanup moved past an authorization; the caller must retry with fresh authorization. store.TaskDataAccessStore.WithAuthorizedTaskDataAccess resolves the cleanup fence, runs live Kubernetes authorization with no provider transaction open, then runs access with the fence and authorized Job identities in its context; each fence-checking store method checks the fence in its own transaction and returns ErrTaskDataCleanupChanged or ErrTaskJobRevoked once cleanup or revocation passed. Calls are separate operations, so repeated writes inside access must be idempotent, request bodies must be fully read first, and Kubernetes writes inside access must keep their own preconditions because they are checked only before access runs.
- **Usage attribution is controller-owned and masked from providers** (`store.UsageAttribution`): store.UsageAttribution is controller-owned accounting context attached only to an execution event append; the storage client derives the usage observation from the event plus this context and masks the attribution before calling the provider. A worker "usage" report counts only when the authenticated TaskUID is set, and Model, frozen from the controller's runtime profile, replaces the runtime's free-text model field so a runtime cannot misattribute usage.
- **Storage recovery holds read as a temporary outage** (`store.ErrStorageRecoveryRequired`): store.ErrStorageRecoveryRequired is returned while the installation is held for storage recovery, and errors carrying it (store.StorageHoldError) also match ErrNotReady, so callers treat the hold as a temporary storage outage: they neither repeat an action nor report success.
- **Storage acknowledgements follow dataset success** (`store.StorageAcknowledgement`): store.StorageAcknowledgement records, per storage contract, the controller epoch and highest write watermark the dataset stored, each recorded only after the dataset returned success, so a lower value later read from the dataset proves acknowledged writes were lost.
- **Storage record writes are epoch-fenced** (`store.StorageRecordStore`): Every store.StorageRecordStore write commits only while its fence is the controller epoch the record holds, and otherwise returns ErrFenced, which also matches ErrConflict; a write refused by a recorded storage recovery hold returns ErrConflict.
- **Storage acknowledgements never move backward** (`store.StorageRecordStore.RecordStorageAcknowledgement`): RecordStorageAcknowledgement and RecordStorageWatermark never lower the epoch or watermark already recorded for the same contract and dataset (a contract now served by another dataset is replaced), and both are refused while a storage recovery hold is recorded.
- **Storage acknowledgements never move backward** (`store.StorageRecordStore.RecordStorageWatermark`): RecordStorageWatermark raises the recorded watermark of every contract the dataset serves and never lowers one, and it is refused while a storage recovery hold is recorded.

### `internal/store/kube`

- **Branch claim reclamation is exact and idempotent** (`store.ReclaimBranchClaimRequest`): store.ReclaimBranchClaimRequest removes only the exact available claim the caller observed: reconciliation-blocked claims are never reclaimable and Session claims are reclaimed only by Session lifecycle code. A missing claim, or one whose immutable owner or request identity was already replaced, is an idempotent success, but every mutable fence must still match before an existing claim is deleted.
- **Broker fence reads do not sync the epoch mirror** (`kube.Store.GetControllerEpochFence`): kube.Store.GetControllerEpochFence reads and validates the authoritative fence without synchronizing the inspection mirror, because unrelated control-store mutations legitimately change the Lease resourceVersion while leaving epoch authority intact; broker authorization paths use this read-only form.
- **Controller epoch CAS proves freshness and reconciles crash tails** (`kube.Store.CompareAndSwapControllerEpoch`): kube.Store.CompareAndSwapControllerEpoch treats a same-holder, same-digest retry of an already committed target epoch as idempotent even when the caller's expected values are stale. Creating the ControllerEpoch inspection object is the API-server-serialized proof that the control store is genuinely fresh; a pre-existing object, even with blank status, may be a restored authority whose Lease has not been applied yet and must never authorize epoch reuse. Before returning an idempotent target or advancing again, it reconciles an authenticated prior CAS crash tail, consumes the one-shot epoch-1 initialization marker, and establishes the immutable Lease UID binding.
- **Installation identity is the ControllerEpoch object UID** (`kube.Store.ControllerEpochInstallationID`): kube.Store.ControllerEpochInstallationID returns the UID of the ControllerEpoch object, created once when the installation's first controller acquires the epoch; it is stable for the installation's life and identifies the installation that owns every storage dataset Orka advances.
- **Controller epoch mutation interlock is not a transaction** (`store.ControllerEpochMutationStore`): store.ControllerEpochMutationStore acquires a bounded epoch Lease interlock before a short Kubernetes mutation callback, but it is not a cross-resource transaction: an ambiguous request can still complete after the callback returns or the Lease expires, so callers must keep target UID and resourceVersion preconditions and immutable ownership checks, and neither timeout nor expiry proves completion. Acquisition contention wraps ErrControllerEpochMutationContention and ErrConflict, and confirmed authority loss must never carry the contention marker.
- **Approval cleanup scope comes from the immutable spec binding** (`kube.ExternalEffectReferencesTask`): kube.ExternalEffectReferencesTask scopes approval cleanup to the Task recorded in the effect's immutable spec ApprovalTaskUID, because continuation Tasks share a RuntimeSession aggregate that alone cannot identify whose approval must settle. Only that spec binding may exclude another Task's effect; legacy discovery labels (added by labelApprovalExternalEffect only after the immutable request binding is checked, under the reserve operation's epoch guard) can add candidates but never override the conservative aggregate check or substitute for validating the approval binding and saved receipt. None of this grants execution authority or makes the effect subject to Task garbage collection.
- **External-effect authorization reads one exact identity** (`store.ExternalEffectIdentityReader`): Kubernetes-backed authorization paths use store.ExternalEffectIdentityReader.GetExternalEffectByIdentity instead of broad LIST reads so a just-committed in-flight lease is observed without cache or list races.
- **Outbox operations are fenced by the Kubernetes controller epoch** (`kube.Store.EnqueueOutboxProjection`): kube.Store's outbox methods (EnqueueOutboxProjection, ClaimOutboxProjections, CompleteOutboxProjection) validate the Kubernetes controller epoch first and then let the SQLite adapter persist, atomically claim, or complete/retry/dead-letter the exact claim, without consulting SQLite's own control records.
- **PromptAttempt reclamation uses a durable marker** (`kube.Store.ReclaimPromptAttempts`): kube.Store.PreparePromptAttemptReclamation proves the deletion barriers and persists a durable marker before any PromptAttempt is removed; ReclaimPromptAttempts performs the same preflight and creates the marker if missing, deletes the final attempt last so partial Kubernetes deletion stays retryable, and removes the marker with exact object preconditions once every authorized attempt is gone. A later projected retry with no marker or candidates is treated as already complete. Before a continuity Session is bound, the standalone Task projection is proven through the marker, and because the final PromptAttempt ID cannot be reconstructed after deletion, the Task-scoped completion receipt treats it as a wildcard; the immutable marker and completion digest still revalidate the full request.
- **Read-only APIs share the control store's Session name mapping** (`kube.RuntimeSessionControlObjectName`): kube.RuntimeSessionControlObjectName exposes the control store's deterministic Session-to-object name mapping so read-only API surfaces never compute it themselves and drift from the control store's identity mapping.
- **Session cleanup persists intent before runtime retirement** (`kube.Store.ReclaimSession`): kube.Store.ReclaimSession persists a durable cleanup intent before retiring the runtime, which fences new authority for the deleting Session. Runtime I/O holds only the per-Session lock (sessionCleanupLockSet serializes retries of one Session while the global epoch slot is released); reclamation then reacquires the same controller epoch and revalidates the entire intent before removing authority. The intent is marshaled to an immutable JSON copy before runtime code runs, which also preserves the persisted equivalence of omitted and empty optional slices.
- **Gateway Session cleanup has a separate retention-only entry point** (`kube.Store.ReclaimGatewaySession`): kube.Store.ReclaimGatewaySession is the only entry point for Gateway-owned Session cleanup; the generic Session deletion API cannot opt into Gateway cleanup or replay its durable intents, even with knowledge of the exact Gateway operation, and returns ErrGatewayOwnedSession.
- **Legacy Gateway rows fall back to the Gateway Session UID** (`kube.Store.ResumeSessionCleanups`): Gateway rows created before the transcript UID binding have no Session UID of their own, so cleanup falls back to the Gateway's recorded SessionUID; the SQLite cleanup transaction still requires every stored turn to prove that UID.
- **Session lease acquisition updates the Lease before status** (`kube.Store.AcquireSessionMutationLease`): kube.Store.AcquireSessionMutationLease acquires the next monotonic lease generation by first CAS-updating the coordination Lease and then mirroring the exact Lease revision into RuntimeSessionControl status, so status never claims a lease the Lease does not hold.
- **Pre-prompt lease release commits SessionControl first** (`kube.Store.ReleaseSessionMutationLease`): kube.Store.ReleaseSessionMutationLease aborts an exact pre-prompt lease only after the caller has independently established that no SessionTurn was persisted. SessionControl commits first, and retries finish clearing the coordination Lease by matching the durable release operation.
- **Session reconciliation holds a Lease across both CAS writes** (`kube.Store.ReconcileSessionControl`): kube.Store.ReconcileSessionControl establishes the independently observed baseline and returns both SessionControl and BranchClaim to Available while holding a Session Lease in reconciliation mode across the two status CAS operations; retries finish any partially committed reconciliation with the same operation.
- **Session lineage is established only with lease acquisition** (`kube.Store.completeExistingSessionLineage`): Session lineage is never accepted on SessionControl creation (normalizeSessionControlForCreate rejects it); it is established with mutation Lease acquisition. kube.Store.completeExistingSessionLineage handles an idempotent retry whose exact coordination Lease is already mirrored but has no lineage, and appending lineage stays fenced by that exact Lease and one RuntimeSessionControl status CAS.
- **Cross-store SessionTurn finalization protocol** (`kube.Store.FinalizeSessionTurn`): kube.Store.FinalizeSessionTurn validates all Kubernetes-authoritative fences and terminal receipts, atomically commits SQLite turn, transcript and deferred outbox data, CAS-updates the Kubernetes BranchClaim and SessionControl and releases the Lease, then activates the SQLite outbox projection. Every step is idempotent so a restart after any committed boundary resumes the same finalization instead of replaying transcript or publication effects; ResumeSessionTurnFinalization completes only the Kubernetes and outbox tail and reloads all timing, digest, terminal, publication and projection inputs from the persisted turn and outbox record.
- **Archived turn evidence is readable only after Session deletion** (`kube.Store.GetSessionTurnCleanupReceipt`): kube.Store.GetSessionTurnCleanupReceipt returns archived finalization evidence only while the completed Session's authoritative Kubernetes resources remain absent, so archived receipts never compete with live control records.
- **Bound PromptAttempts outlive newer unbound attempts** (`kube.Store.verifySessionCleanupBeforePromptAttemptDeletion`): A newer PromptAttempt may settle before binding to its Session, but every older bound attempt still owns frozen runtime cleanup authority, so none may be removed until Session deletion has archived all of that evidence.
- **Kubernetes is authoritative for ACP control records** (`kube`): Package kube implements the hard-cutover DurableControlStore: Kubernetes is authoritative for controller, Session, prompt, publication and branch state, with controller epochs and Session mutation ownership serialized by coordination.k8s.io Leases and the CR status resourceVersion as the CAS token for every other transition. SQLitePersistence (satisfied by the storage client, which seals native session state) stores only SessionTurn, transcript and outbox data; no database control row is authoritative, and SQLite's controller_epochs table is only a mirror it checks fences against.
- **Authoritative control reads use an uncached reader** (`kube.WithAPIReader`): kube.WithAPIReader configures the uncached reader for authoritative control records; controller-runtime cached clients remain the writer but must not be trusted for immediate read-after-write recovery decisions.
- **Storage holds and acknowledgements outlive epochs** (`kube.Store controller epoch mirror`): When the Kubernetes store mirrors a new controller epoch into the ControllerEpoch status, it carries over the storage acknowledgements, any storage recovery hold, and the conditions, because they belong to the installation rather than to one epoch.
- **Epoch mutation interlock refuses recorded storage holds** (`kube.Store.lockControllerEpochMutation`): kube.Store.lockControllerEpochMutation refuses the interlock with a store.StorageHoldError while a storage recovery hold is recorded, unless allowHeld is set. It reads the ControllerEpoch object between the Lease read and the Lease update that takes the interlock, so a hold recorded under the interlock in between makes that update conflict and the next pass sees it.
- **Storage hold wait test uses a distinct Store** (`kube TestStorageHoldWaitsForAControlStoreChangeInProgress`): TestStorageHoldWaitsForAControlStoreChangeInProgress records the hold through a distinct kube.Store so the durable Lease interlock, not one Store's local queue, is what makes HoldStorage wait; reusing the same Store would not test the cross-process guarantee.
- **Storage records are read without the cache** (`kube.Store.GetStorageRecord`): kube.Store.GetStorageRecord reads the ControllerEpoch object through the API reader, not the cache, so a hold another process recorded and an operator's acknowledgement are seen at once.
- **Storage holds are recorded under the epoch mutation interlock** (`kube.Store.HoldStorage`): kube.Store.HoldStorage records a storage recovery hold under the controller epoch mutation interlock, waiting while another control-store change holds it, so every change either finishes before the hold is recorded or sees the hold and is refused.
- **Interlock waits return only the context's end** (`kube.Store.waitForControllerEpochMutation`): kube.Store.waitForControllerEpochMutation returns only ctx's error when it gives up, never the interlock contention, because contention matches ErrConflict and would read to callers as a definite refusal.
- **Storage hold release retries match the exact release** (`kube.Store.ReleaseStorageHold`): kube.Store.ReleaseStorageHold lets a retry of a release whose status update committed but whose response was lost succeed without writing again only when the ControllerEpoch object, under the same fence, shows exactly that release: no hold, the operator's acknowledgement of that hold ID, the condition the release set, and exactly the acknowledgements it recorded, with times compared to the second as the API server stores them. Anything else is a conflict, and the fence check ensures no other controller epoch's release is taken for this one.
- **Storage record writes fail when the schema drops them** (`kube.Store.updateStorageRecord`): An API server still serving an older ControllerEpoch schema accepts a status update but drops the storage fields it does not know, which would let a hold or acknowledgement vanish. kube.Store.updateStorageRecord therefore checks with storageRecordKept that the returned status keeps what was written (ignoring times, which the API server stores to the second) and fails the write otherwise.
- **Storage hold messages fit the CRD limit** (`kube.truncateMessage`): kube.truncateMessage keeps status messages within 1024 bytes because the ControllerEpoch schema allows no more; raising the limit requires changing the CRD.

### `internal/store/sqlite`

- **Session lineage CHECK keeps its released form** (`sqlite.agentExecutionSchemaStatements`): agentExecutionSchemaStatements keeps the session lineage CHECK constraint exactly as released so existing SQLite stores keep their layout without a table rebuild. Only orka.harness.v2 lineages are written even though the CHECK still admits older values.
- **SQLite stores sealed snapshots without the key** (`sqlite.Store.CreateSealedAgentExecutionSnapshot`): Agent execution snapshots arrive sealed by the storage client. The SQLite store keeps the nonce and ciphertext as opaque bytes and must never receive or hold the snapshot encryption key.
- **Sealed snapshot pages probe for more by key only** (`sqlite.Store.ListSealedAgentExecutionSnapshots`): ListSealedAgentExecutionSnapshots detects a following page with a key-only EXISTS query instead of fetching limit+1 rows, so a full page never reads one extra record's sealed bytes.
- **Snapshot retention cutoff is strict** (`sqlite.Store.ListAgentExecutionSnapshotMetadataBefore`): ListAgentExecutionSnapshotMetadataBefore uses a strict less-than cutoff so a retention pass can reuse one stable timestamp without collecting records created exactly at that boundary.
- **Snapshot reference counts come from one statement** (`sqlite.Store.CountAgentExecutionSnapshotReferences`): CountAgentExecutionSnapshotReferences reads every reference count in a single SQL statement so all counts come from one consistent SQLite snapshot; splitting it into several queries would let deletions race the counts.
- **Single snapshot deletion carries no lifecycle policy** (`sqlite.Store.DeleteAgentExecutionSnapshot`): DeleteAgentExecutionSnapshot deletes exactly one keyed snapshot and performs no lifecycle policy; reference and retention decisions belong to the caller. It is separate from the Task-scoped DeleteAgentExecutionSnapshots, which must keep its broad behavior.
- **AHP clientId stays bound to its first user** (`sqlite.Store.PutAHPClient`): PutAHPClient binds a clientId to the first user that registers it and only updates negotiated fields afterward; another user presenting the same clientId must not take over its record or replay state.
- **Sign-in session uniqueness is checked before pruning** (`sqlite.Store.CreateAuthSession`): CreateAuthSession runs requireAuthSessionUnused before pruneAuthSessions because pruning would delete an ended session with the same ID or token hash and let the insert succeed. Reordering them would let an ended session's token become valid again.
- **Ended sign-in sessions still reserve their ID and hash** (`sqlite.requireAuthSessionUnused`): requireAuthSessionUnused rejects a new sign-in session whose ID or token hash matches any stored session, ended or not, because reusing an ended session's hash would make its old token valid again.
- **A sign-in session renews at most once** (`sqlite.Store.RenewAuthSession`): RenewAuthSession revokes the live session and inserts its successor in one transaction, so a session token can be renewed at most once and two concurrent renewals cannot both mint successors. See [ADR 0037](0037-github-sign-in.md).
- **Branch claim reclamation deletes only the exact claim** (`sqlite.Store.ReclaimBranchClaim`): ReclaimBranchClaim deletes only the exact available Task-owned claim. A missing claim or one whose immutable owner and request identity was replaced counts as already reclaimed, and every other mismatch is a conflict so stale recovery cannot delete a live claim.
- **Connector custody is sealed and crypto-shredded** (`sqlite.connectorSchemaStatements`): The SQLite connector store receives token material, consent verifiers and completion payloads already sealed by the storage client and never sees plaintext; it decides conditional commands only from plain columns. Deleted custody is crypto-shredded: secure_delete zeroes freed pages and the write-ahead log is truncated so its frames do not outlive the records. See [ADR 0033](0033-user-connectors.md).
- **Only re-consent retired grants count toward the consent bound** (`sqlite.connectorSchemaStatements`): In connector_retired_credentials, consent_grant marks a grant that a re-consent replaced, and only those rows count toward the per-Connection MaxRetiredConnectorConsentGrants bound; refresh-rotated grants are bounded separately.
- **Connector consents are numbered and committed monotonically** (`sqlite.connectorSchemaStatements`): connector_consent_sequences numbers each Connection's consents in issued and records in committed the newest consent whose tokens became custody, so an older consent can never be committed over a newer one.
- **Connector grant and version counters outlive shredded records** (`sqlite.Store.putConnectorCredentialTx`): putConnectorCredentialTx numbers grants and versions from per-Connection counters stored outside the credential row, so a credential recreated after a crypto-shred never reuses a grant number or a version that a stale fenced write could still hold.
- **Refresh is refused after a disconnect tombstone** (`sqlite.Store.ReplaceSealedConnectorCredential`): A disconnect tombstones connector custody before it reads the material to revoke, so ReplaceSealedConnectorCredential refuses a refresh on a tombstoned Connection; otherwise a rotated credential could land outside the revocation set.
- **Connector replacement checks the version fence before retiring** (`sqlite.Store.ReplaceSealedConnectorCredential`): ReplaceSealedConnectorCredential checks the expected version fence before it retires the current credential, so a stale writer fails without moving any custody into the retired set.
- **Refresh-rotated connector grants are dropped, never revoked** (`sqlite.Store.retireConnectorCredentialTx`): retireConnectorCredentialTx keeps replaced custody sealed exactly as stored so disconnect can revoke it, but keeps refresh-rotated grants only up to a bound so a long-lived Connection cannot grow custody or disconnect revocations without limit. The oldest are dropped, never revoked: providers that rotate refresh tokens already invalidate the old one, and revoking a rotated token can revoke the whole grant at providers that detect reuse.
- **Explicitly retired refresh material shares the refresh bound** (`sqlite.Store.RetireSealedConnectorCredential`): RetireSealedConnectorCredential retires material as a refresh grant (consentGrant false) so it falls under the refresh-retired bound; a store that keeps failing replacement therefore cannot grow connector custody without limit.
- **Tombstoning clears custody receipts** (`sqlite.Store.TombstoneConnectorCustody`): TombstoneConnectorCustody removes no custody row but clears the operation receipts that hold sealed results for the Connection, and marks a pending WAL truncation so their log copies are removed after the commit.
- **Connector sequence counters are reaped with expired tombstones** (`sqlite.reapConnectorTombstonesTx`): reapConnectorTombstonesTx deletes a Connection's grant and version counters only together with its tombstone after ConnectorTombstoneRetention, so counters survive shreds long enough to fence stale writes while create/delete churn still cannot grow the store without bound.
- **Connector shred always truncates the WAL after commit** (`sqlite.Store.ShredConnectorCredential`): A connector shred is a crypto-shred only once the WAL frames that carried the row are gone, so ShredConnectorCredential truncates the log after the operation commits whether or not this call removed the row, including on replays, letting a retry after a busy log finish the job.
- **Shred reports remaining versions in the same transaction** (`sqlite.Store.shredConnectorCredentialTx`): shredConnectorCredentialTx checks for a record at another version inside the delete's transaction; reading after that transaction would report a grant committed in between as a conflict, which matches no serial order.
- **Shredded custody needs a WAL checkpoint and truncate** (`sqlite.Store.truncateWAL`): truncateWAL checkpoints and truncates the write-ahead log because secure_delete only zeroes the row in the main database file; WAL frames still carrying a deleted custody row's wrapped data key and ciphertext must not outlive the deletion. See [ADR 0033](0033-user-connectors.md).
- **WAL truncation is deferred while a transaction is open** (`sqlite.Store.truncateWAL`): The SQLite store uses one connection, so truncateWAL cannot checkpoint while the context carries a transaction or write operation; it sets pendingWALTruncate and the next custody operation finishes it.
- **Custody operations finish pending WAL truncations first** (`sqlite.Store.finishPendingWALTruncate`): Every connector custody operation calls finishPendingWALTruncate first, so a shredded row's WAL frames never outlive the next custody operation even when the caller of the deletion did not retry.
- **Connector consent commits follow issue order** (`sqlite.Store.CreateSealedConnectorConsent`): The storage client picks the Connection's next consent sequence and binds it into the sealed verifier's additional data; CreateSealedConnectorConsent only validates that the request carries exactly the next sequence (ErrConflict otherwise, which the client retries), records it as issued, and stores the consent. Commits are ordered by that sequence, not by the order OAuth callbacks arrive.
- **One pending consent per Connection** (`sqlite.Store.CreateSealedConnectorConsent`): CreateSealedConnectorConsent deletes any earlier pending consent for the Connection before inserting the new one, so repeated authorize calls cannot grow connector_consents within the consent TTL.
- **Expired connector completions are reaped by the reconciler** (`sqlite.Store.CreateSealedConnectorCompletion`): CreateSealedConnectorCompletion does not purge expired completions; the Connection reconciler reaps them, and their tokens are left to expire rather than revoked.
- **Consumed completion results live in receipts until custody removal** (`sqlite.Store.ConsumeSealedConnectorCompletion`): ConsumeSealedConnectorCompletion truncates the WAL copy of the consumed sealed tokens after commit; with an operation envelope the receipt keeps the sealed result until the Connection's custody is removed or the receipt expires.
- **Completion lifetime is judged again at commit** (`sqlite.Store.CommitSealedConnectorCompletion`): CommitSealedConnectorCompletion rejects a parked completion whose expiry is not after both the request time and the current wall clock, so a commit that stalled past the deadline redeems nothing.
- **Re-consent retired grants are pruned before the bound is counted** (`sqlite.Store.CommitSealedConnectorCompletion`): CommitSealedConnectorCompletion keeps grants a re-consent superseded so disconnect can revoke them, bounded so repeated relinking cannot grow custody without limit; it prunes records with nothing left to revoke first so they never count toward that bound.
- **Connector pages probe with one extra full row** (`sqlite.connectorPage`): connectorPage reads one extra whole row to detect a following page because connector records are small; unlike agent execution snapshots, a key-only probe is not needed.
- **Controller epoch advance is serialized with writes** (`sqlite.Store.AdvanceControllerEpoch`): The SQLite store has one connection, so AdvanceControllerEpoch is serialized with every write operation: a write that checked the previous fence has committed or rolled back before the advance runs, and every later write checks the new fence. A multi-connection store would need an explicit lock to keep this guarantee.
- **Controller epoch mirror only moves forward** (`sqlite.Store.SyncControllerEpochMirror`): SyncControllerEpochMirror records the Kubernetes-authoritative controller epoch that fences SQLite payload mutations. It may move a stale mirror forward after a crash between authoritative acquisition and mirror persistence, but never rewinds it or replaces conflicting evidence at the same epoch.
- **Database file lock is taken before opening SQLite** (`sqlite.lockDatabaseFile`): lockDatabaseFile takes a non-blocking advisory lock beside the SQLite database before sql.Open and schema setup run, so a second process can never open or migrate a database another process is serving.
- **CanBootstrapSnapshotKey is narrow** (`sqlite.DatasetInfo`): DatasetInfo.CanBootstrapSnapshotKey is true only for a never-bootstrapped, newly created dataset with no application, artifact or control records. It is not a general emptiness check and never grants permission to replace an installation's dataset.
- **Dataset bootstrap state comes from durable history** (`sqlite.Store.DatasetInfo`): Store.DatasetInfo reads durable bootstrap history while the caller holds the process lock and never relies on a file-existence check. An interrupted first start can resume bootstrap only if no application data has appeared meanwhile.
- **Record detection uses sqlite_schema object type** (`sqlite.datasetHasRecords`): datasetHasRecords finds tables by sqlite_schema type rather than by parsing CREATE statements, because a validated layout may contain equivalent SQL with different whitespace or quoted names.
- **Dataset metadata is synchronized with a full checkpoint** (`sqlite.synchronizeDatasetMetadata`): The store runs SQLite in NORMAL synchronous mode, which does not sync each WAL commit, so synchronizeDatasetMetadata runs PRAGMA wal_checkpoint(FULL) before startup relies on dataset identity or completed bootstrap history. Ordinary writes keep NORMAL mode, and a busy or incomplete checkpoint is a startup failure, even on a retry whose earlier transaction already committed.
- **Empty binding state may carry an epoch-recorded installation** (`sqlite.bindingStateNone`): An empty store_dataset.binding_state means BindDataset has not bound the dataset: it belongs to no installation, or only to the installation a controller epoch advance recorded in installation_id. Such a dataset is still unclaimed for that installation.
- **Inconsistent dataset bindings fail closed** (`sqlite.readDatasetBinding`): readDatasetBinding refuses a store_dataset row whose binding columns contradict one another and never repairs it, so corruption or tampering cannot silently rebind a dataset.
- **Dataset binding check and bind are one step** (`sqlite.Store.BindDataset`): BindDataset reserves SQLite's writer before reading the stored binding; with the store's single connection, the check and the bind are therefore atomic with respect to every other call.
- **Bootstrap completion follows snapshot key activation** (`sqlite.Store.CompleteDatasetBootstrap`): CompleteDatasetBootstrap records successful snapshot key activation before controller consumers start; startup calls it only after the storage client has activated the key, which authenticates retained sealed records and enforces permitted rotation. It synchronizes the WAL before returning so the flag survives host failure.
- **Failed post-commit synchronization is ErrOutcomeUnknown** (`sqlite.synchronizeCommittedDataset`): synchronizeCommittedDataset reports a WAL checkpoint failure after a dataset metadata change committed as ErrOutcomeUnknown rather than a refusal; the caller repeats the identical request, which replays the change and synchronizes again.
- **Dataset binding changes run alone and always synchronize** (`sqlite.Store.changeDatasetBinding`): changeDatasetBinding refuses to run inside another transaction because binding outcomes must be durable and cannot be rolled back by an enclosing task-data transaction. It synchronizes the WAL after every successful call, including no-ops, so a retry after a failed synchronization still makes the binding durable.
- **Execution event appends skip the mutex inside a Task transaction** (`sqlite.Store.appendExecutionEventWithPlan`): When an enclosing Task transaction already owns SQLite's writer, execution event appends do not take executionEventMu: an ordinary append holding the mutex while waiting for that writer would deadlock. The single writer alone serializes sequence IDs in that case, and such appends are not retried.
- **Execution event dedupe matches identity, not content** (`sqlite.sameExecutionEventIdentity`): sameExecutionEventIdentity matches a deduplicated append to the stored event only by Task, Session and tool call, with empty fields matching anything. Type, content and summary may differ because competing outcomes share one key so the first durable outcome wins, and Orka may re-derive an event under newer redaction rules.
- **Dedupe lookup repeats the partial index predicate** (`sqlite.executionEventByDedupeKeySQL`): executionEventByDedupeKeySQL includes dedupe_key <> '' because SQLite uses a partial index only when the query's WHERE clause implies the index's own, and a bound parameter does not. Without that term the lookup scans every event in the stream inside the append's write transaction, so appends get slower as the stream grows.
- **Session event pages read one snapshot** (`sqlite.Store.ListSessionExecutionEvents`): ListSessionExecutionEvents reads the latest sequence watermark, the retained Session cursor and the page in one read snapshot, so a concurrent append or stream deletion cannot produce a page and latest sequence that never existed together.
- **Stream heads are read in one indexed snapshot query** (`sqlite.Store.GetLatestExecutionEventSeqs`): GetLatestExecutionEventSeqs reads stream heads through the existing sequence index in one snapshot per batch, without scanning historical events or issuing one query per stream.
- **Execution event redaction happens above the store** (`sqlite.Store.appendExecutionEventWrite`): Orka redacts and bounds execution event payloads above the storage client; the SQLite store only requires that structured content is valid JSON and treats whitespace-only content as no content.
- **Gateway message counts pin join order with CROSS JOIN** (`sqlite.gatewayMessageCountSQL`): gatewayMessageCountSQL uses CROSS JOIN so SQLite reads events first through the Task identity index before probing deliveries; a reorderable join can scan the namespace's whole delivery history while holding the store's single connection.
- **Gateway message enqueue reuses the task-data writer** (`sqlite.Store.EnqueueGatewayMessage`): EnqueueGatewayMessage serializes eligibility, dedupe, quota and insertion with terminal projection and cleanup by reusing the authorized task-data writer; nesting BeginTx would deadlock because the store uses a single SQLite connection.
- **Gateway message replays are receipt lookups** (`sqlite.Store.enqueueGatewayMessageWrite`): A replayed gateway message enqueue is a receipt lookup, even after closure or quota exhaustion; it neither requeues the delivery nor consumes another lifetime quota slot.
- **Gateway message delivery IDs hash identity, never text** (`sqlite.gatewayMessageDeliveryID`): gatewayMessageDeliveryID hashes a length-delimited identity of namespace, namespace UID, event ID, Task UID and request ID, shared by admission and budget replay detection. - **Gateway delivery created_at is a logical clock** (`sqlite.advanceGatewayDeliveryOrderTx`): advanceGatewayDeliveryOrderTx makes created_at a persisted per-event logical admission clock for messages and their terminal successor, assigned under the writer and strictly advancing even when wall clocks tie or go backwards. Retention keeps all of an event's delivery evidence until every row can be removed.
- **Transcript-only gateway cleanup retires no runtime authority** (`sqlite.reclaimGatewayTranscriptTx`): reclaimGatewayTranscriptTx keeps gateway retention working when no ACP coordinator is configured and handles only transcripts with no ACP identity or records. - **Gateway Session continuations never reuse physical names** (`sqlite.resolveGatewaySessionNameTx`): resolveGatewaySessionNameTx follows completed Session incarnations to a successor name instead of reusing their physical names. - **Gateway Task runtime tool policy is frozen once** (`sqlite.Store.FreezeGatewayEventTaskRuntimeAllowedTools`): FreezeGatewayEventTaskRuntimeAllowedTools records the external runtime allowed-tools policy for the deterministic Task and keeps the first value, so crash recovery never rebuilds the Task from mutable live policy.

- **Gateway Task cleanup receipts key on Task UID** (`sqlite.Store.GetGatewayTaskCleanupReceipt`): GetGatewayTaskCleanupReceipt never consults bounded deduplication history or current Gateway and Binding objects; the original Task UID stays authoritative when names or external event IDs are reused.

- **Session name filter trims in SQL and rechecks in Go** (`sqlite.Store.sessionUsageTasks`): Session names compare without surrounding whitespace of any kind: SQL trims what strings.TrimSpace does so only rows of a wanted session are read, and Go repeats the comparison. Names pass as one JSON array so the query keeps one shape regardless of count.
- **Late Tasks are filtered before decoding** (`sqlite.Store.sessionUsageTasks`): Tasks that started after startedBy are excluded in SQL before decoding so they do not count against limit and cannot push the lookup past the caller's budget. started_at is the first-written start, which later snapshots keep. A zero startedBy sets no cut-off; the Unix epoch is a real one.
- **Usage JSON times are normalized to UTC** (`sqlite.utcUsageTimes`): sqlite.utcUsageTimes converts usage record times to UTC before storing and again on read, because JSON keeps the zone a time was written in; reading also normalizes rows written before this rule.
- **utcUsageTimes clones phase history** (`sqlite.utcUsageTimes`): sqlite.utcUsageTimes clones PhaseHistory before converting times because the slice may share its backing array with the caller's record.
- **Usage pruning expires whole inactive cohorts** (`sqlite.Store.PruneUsage`): sqlite.Store.PruneUsage expires only whole, inactive work cohorts and never trims early attempts from a retained request. Cumulative counter baselines remain until the counter itself expires, so retention cannot turn an old total into new usage.
- **Usage work stays active while anything is live** (`sqlite.Store.pruneUsageWrite`): A usage work is retained while any Task is nonterminal, a linked PR is open, or a recent model observation belongs to it; sqlite.Store.pruneUsageWrite deletes only works with none of these.
- **Closed PRs stay in the usage refresh list** (`sqlite.Store.ListUsagePullRequestLinks`): sqlite.Store.ListUsagePullRequestLinks keeps returning closed pull requests for refresh because a closed PR can reopen; only confirmed merges stop needing refreshes.
- **Whole-object replacements are ordered by write stamp** (`sqlite.writeStamp`): sqlite.writeStamp is the epoch and sequence of a write envelope; results and artifacts store the stamp of the write that stored them, and a replacement applies only when its stamp is greater. Rows written before schema version 5 carry (0, 0), so the first stamped write replaces them. Unstamped writes, which only package tests make, replace unconditionally.
- **Write stamps refuse sequences SQLite cannot store** (`sqlite.writeStampFrom`): A write envelope sequence is unsigned but SQLite stores the stamp as a signed integer, so sqlite.writeStampFrom refuses a sequence that does not fit instead of wrapping it into a stamp that would order before every other write.
- **Inbox batches count identifier bytes too** (`sqlite.scanMessageBatch`): sqlite.scanMessageBatch stops before the message that would take an inbox batch past store.MaxMessageBatchBytes, keeping at least one message unless it alone exceeds the wire-safe budget. It charges both content and oversized identifier bytes against the budget because legacy rows stored before the send-time caps may exceed them, and a consuming read must never commit a batch that cannot fit in one wire response.
- **SQLite reports durability from its live synchronous mode** (`sqlite.Store.Describe`): sqlite.Store.Describe runs SQLite in WAL mode and reports local-buffered under synchronous=NORMAL (the default; commits survive a process restart but not a host or storage failure before the WAL syncs) and local-fsync under FULL or EXTRA (every commit syncs, which limits the single writer on slow storage). It reads the mode the connection actually uses, reports a new incarnation each time the store opens, and always reports the dataset ready because the schema is upgraded while the store opens under its process lock.
- **SQLite write watermark moves with the dataset file** (`sqlite.Store.AdvanceWriteWatermark`): sqlite.Store.AdvanceWriteWatermark keeps the write watermark as a column of the dataset's identity row, so it moves with the dataset: a copy restored from an older file holds the older value, which is how Orka detects lost acknowledged writes.

### `pkg/storage/v1`

- **Session lineage generation is its own counter** (`storagev1.SessionLineage`): SessionLineage.LineageGeneration is independent of the Session mutation-lease generation and of any v2 RuntimeSession generation; ordinary first use establishes generation 1. Do not reuse or compare it against lease or RuntimeSession generations.
- **Lineage claims run under the Session lease serialization** (`storagev1.ClaimSessionLineageRequest`): ClaimSessionLineageRequest atomically establishes or verifies a Session lineage, and callers must issue it under the same serialization that acquires the Session mutation lease. Otherwise two concurrent first-use Tasks could establish different runtime identities for one Session.
- **Only proven-fresh Sessions may create lineage** (`storagev1.ClaimSessionLineageRequest.EstablishIfAbsent`): ClaimSessionLineageRequest.EstablishIfAbsent may be true only when the caller has proven the Session is fresh, or the Session is a controller-owned Gateway Session whose first message was admitted atomically. Setting it elsewhere would let a later Task silently establish a lineage for a Session that already ran.
- **Session lineage store is a projection of Kubernetes authority** (`storagev1.SessionLineageStore`): SessionLineageStore persists a projection of the Kubernetes-authoritative Session protocol and runtime lineage. A projection failure may block dispatch, but it never changes or releases the Kubernetes lineage or Lease authority.
- **Lineage projection mismatches are conflicts, not overwrites** (`storagev1.SessionLineageStore.ProjectSessionLineage`): SessionLineageStore.ProjectSessionLineage idempotently stores the exact authoritative record; any mismatch returns ErrConflict and must be repaired explicitly. The SQLite store never decides which lineage owns a Session.
- **AHP tokens are stored as hashes only** (`storagev1.AHPToken`): storagev1.AHPToken holds only a hash of the connection token secret (TokenHash); the token itself is never stored, as ADR 0034 requires. See [ADR 0034](0034-agent-host-protocol-api.md).
- **AHP backend records stay server-side** (`storagev1.AHPRecord`): storagev1.AHPRecord is a session backend's own per-user record, such as a project or the Orka objects behind a session. Clients never see these records directly, so they must not be returned through AHP client-facing state.
- **Zero AHP journal limit means unbounded** (`storagev1.AHPJournalLimits`): In storagev1.AHPJournalLimits a zero MaxEntries or MaxBytes leaves the journal unbounded by that measure rather than keeping nothing; ADR 0034 records that replay is bounded by count and bytes. See [ADR 0034](0034-agent-host-protocol-api.md).
- **AHP store methods touch only one user's state** (`storagev1.AHPStore`): Every storagev1.AHPStore method that takes a user key reads or changes only that user's state, so one user never reads another's; only tokens and clients are not keyed by user. Byte values are opaque to the provider and must be returned exactly as stored. See [ADR 0034](0034-agent-host-protocol-api.md).
- **Creating an AHP token prunes old ended tokens** (`storagev1.AHPStore.CreateAHPToken`): storagev1.AHPStore.CreateAHPToken returns ErrConflict when the ID or hash already exists. It keeps only the MaxAHPEndedTokensPerUser newest of the user's tokens that were revoked or had expired by the new token's CreatedAt and deletes older ones.
- **AHP revocation is owner-scoped and keeps the first time** (`storagev1.AHPStore.RevokeAHPToken`): storagev1.AHPStore.RevokeAHPToken returns ErrNotFound unless the user owns the token, so callers cannot probe other users' tokens, and revoking again keeps the first revocation time.
- **AHP clients stay bound to their first user** (`storagev1.AHPStore.PutAHPClient`): storagev1.AHPStore.PutAHPClient returns ErrConflict and changes nothing when the clientId already belongs to another user, which prevents clientId hijacking (ADR 0034). Each user keeps at most MaxAHPClientsPerUser clients; recording another forgets the least recently updated. See [ADR 0034](0034-agent-host-protocol-api.md).
- **AHP journal appends compare and swap the sequence** (`storagev1.AHPStore.AppendAHPJournal`): storagev1.AHPStore.AppendAHPJournal atomically appends entries numbered previousSeq+1 onward, stores channel states, advances the user's sequence and prunes to the limits. It returns ErrConflict and changes nothing if the user's sequence is no longer previousSeq.
- **AHP journal reads report gaps** (`storagev1.AHPStore.ReadAHPJournal`): storagev1.AHPStore.ReadAHPJournal returns entries after afterSeq in order from one snapshot. complete is false when some entries were pruned, or, with no entries, when afterSeq is negative or past the user's sequence, so the host sends fresh snapshots instead of an incomplete replay.
- **AHP prefix matches are literal** (`storagev1.AHPStore.ListAHPChannels`): storagev1.AHPStore.ListAHPChannels and DeleteAHPRecords match the prefix literally, so providers must escape LIKE or glob wildcards rather than treat the prefix as a pattern.
- **Updating an AHP session keeps its backend** (`storagev1.AHPStore.PutAHPSession`): storagev1.AHPStore.PutAHPSession on an existing catalog entry updates only the summary and modification time; the session's backend and creation time are kept, so a put cannot move a session to another backend.
- **Sign-in session tokens are stored as hashes** (`storagev1.AuthSession`): storagev1.AuthSession is an Orka sign-in session issued after GitHub sign-in (ADR 0037); only a hash of its token is stored, never the token itself. See [ADR 0037](0037-github-sign-in.md).
- **Sign-in identity uses the numeric GitHub user ID** (`storagev1.AuthSession.Subject`): storagev1.AuthSession Issuer and Subject are the person's verified identity: GitHub and their numeric user ID, never their login, because a login can be renamed and reused by someone else.
- **Creating a sign-in session prunes and caps sessions** (`storagev1.AuthSessionStore.CreateAuthSession`): storagev1.AuthSessionStore.CreateAuthSession drops every session revoked or expired by the new session's CreatedAt and keeps only the person's MaxAuthSessionsPerSubject most recently issued sessions, ending the oldest. It returns ErrConflict and changes nothing when the ID or hash already exists.
- **Sign-in session revocation keeps the first time** (`storagev1.AuthSessionStore.RevokeAuthSession`): storagev1.AuthSessionStore.RevokeAuthSession is idempotent: revoking an already revoked session keeps the first revocation time, and an unknown session returns ErrNotFound.
- **A sign-in session renews at most once** (`storagev1.AuthSessionStore.RenewAuthSession`): storagev1.AuthSessionStore.RenewAuthSession revokes a session live at the given time and stores its successor in one transaction, after dropping sessions that ended by then. It returns ErrConflict and changes nothing when the session is revoked, expired or unknown, so one session renews at most once (ADR 0037). See [ADR 0037](0037-github-sign-in.md).
- **Detached datasets refuse writes until rebound** (`storagev1.ErrDatasetDetached`): storagev1.ErrDatasetDetached, which matches ErrNotReady, is returned for any envelope-carrying write or controller epoch advance on a dataset its installation detached; nothing is committed, and writes resume only after the installation binds it again (docs/development/storage-contracts.md, Installation binding).
- **A detached dataset still belongs to its installation** (`storagev1.DatasetDetached`): storagev1.DatasetDetached marks a dataset its installation left, for example after a storage switch; the dataset still belongs to that installation, reads keep working, and writes and controller epoch advances return ErrDatasetDetached.
- **Epoch-advance bindings have no record and generation 0** (`storagev1.DatasetBinding`): A storagev1.DatasetBinding recorded by the controller epoch advance has an empty RecordUID and SwitchGeneration 0: the dataset belongs to the installation, which has not bound it itself yet. Bindings made by BindDataset always have a RecordUID and a SwitchGeneration of at least 1.
- **Binding key fingerprints are equality-only identifiers** (`storagev1.DatasetBinding.KeyFingerprint`): storagev1.DatasetBinding.KeyFingerprint identifies the snapshot key that seals the dataset's records; Orka derives it from the key, it is never key material, and providers compare it only for equality.
- **BoundAt may be zero** (`storagev1.DatasetBinding.BoundAt`): storagev1.DatasetBinding.BoundAt is the provider clock when the dataset reached its State, and is zero when the provider cannot tell, so callers must not treat a zero time as invalid.
- **Fresh binding requires a provably empty dataset** (`storagev1.BindFresh`): storagev1.BindFresh binds only a new-origin, unclaimed dataset that holds no record of any kind, including control records such as a controller epoch or operation receipt, and whose bootstrap is incomplete. A provider that cannot prove the dataset holds no record must refuse the mode (docs/development/storage-contracts.md).
- **Embedded binding requires the provider's process lock** (`storagev1.BindEmbedded`): storagev1.BindEmbedded binds an unclaimed embedded dataset the provider opened under its own process lock, in any bootstrap state; only an embedded provider accepts it, and any other provider returns ErrValidation.
- **Migrated binding requires a finished import** (`storagev1.BindMigrated`): storagev1.BindMigrated binds an unclaimed dataset imported from another provider only after its import finished (origin DatasetOriginMigrated, state DatasetReady).
- **Adopt binds only unclaimed or self-detached datasets** (`storagev1.BindAdopt`): storagev1.BindAdopt takes over a dataset that already holds data only when it is unclaimed or detached from the same installation at a lower switch generation.
- **Rebind moves an owned dataset forward only** (`storagev1.BindRebind`): storagev1.BindRebind moves a dataset the same installation already owns (bound, detached, or recorded by the epoch advance at generation 0) to a higher switch generation, for example when a storage switch returns to it or a recovered installation replaces its record.
- **Key fingerprint updates follow proof under the new key** (`storagev1.UpdateBindingKeyRequest`): storagev1.UpdateBindingKeyRequest is sent only after Orka proved that the dataset's sealed records authenticate under the new snapshot key; the provider records the fingerprint and does not check the records itself.
- **Binding conflicts carry the stored binding** (`storagev1.BindingConflictError`): storagev1.BindingConflictError matches ErrConflict, commits nothing, and carries the dataset's stored binding (nil when unbound) so callers can tell another installation, another record, and a detached dataset apart without another read.
- **Dataset binding is create-once, unfenced and generation-ordered** (`storagev1.DatasetBindingStore`): storagev1.DatasetBindingStore writes are administrative and unfenced because BindDataset establishes identity before any fence exists; every method is atomic, linearizable per dataset, durable on return, refuses by committing nothing, and returns the stored result unchanged for an identical repeat (ErrOutcomeUnknown when commit or durability is unknown). BindDataset first returns an identical existing binding unchanged, then refuses datasets owned by another installation, then enforces the mode precondition, and only BindRebind at a higher generation or UpdateBindingKeyFingerprint changes a same-installation binding. Binding records the installation for the controller epoch advance and makes SyncControllerEpochMirror refuse it; see docs/development/storage-contracts.md, Installation binding.
- **GetDatasetBinding reports epoch-advance bindings** (`storagev1.DatasetBindingStore.GetDatasetBinding`): storagev1.DatasetBindingStore.GetDatasetBinding returns a binding recorded by the controller epoch advance as well as one made by BindDataset, and ErrNotFound only when the dataset is unbound.
- **Detach moves the switch generation forward only** (`storagev1.DatasetBindingStore.DetachDatasetBinding`): storagev1.DatasetBindingStore.DetachDatasetBinding requires the dataset to belong to the request's installation at a lower generation, keeps the installation and key fingerprint, and returns an already detached binding with the same record UID and generation unchanged; anything else is a BindingConflictError. Because the generation only increases, a delayed detach cannot undo a later change.
- **Dataset bootstrap completion never reverts** (`storagev1.DatasetBindingStore.CompleteDatasetBootstrap`): storagev1.DatasetBindingStore.CompleteDatasetBootstrap records that Orka activated the dataset's snapshot key; it is idempotent, independent of the binding, and never reverts, so a completed dataset can no longer be bound with BindFresh or receive a newly minted key.
- **Connector custody is sealed in Orka and committed by conditional commands** (`storagev1.SealedConnectorCustodyStore`): Connector token material, pending consents and parked completions are sealed by Orka before a provider sees them (custody under a per-record data key wrapped by Orka's snapshot key, verifiers and completion payloads under Orka's key), and each seal binds the record identity and plain fields through associated data, so a provider stores only opaque nonces and ciphertexts (ADR 0033). Decisions needing plaintext are made in Orka, which reads ConnectorCustody, decides, seals and sends a conditional command naming the custody version, next grant or consent sequence and judged completion digests; the provider commits only if those still hold and otherwise returns ErrConflict, while enforcing plain-field rules (tombstones, consent order, sequence counters, expiry, retired bounds) itself. See [ADR 0033](0033-user-connectors.md).
- **Retired consent grants are capped, refresh grants evicted** (`storagev1.MaxRetiredConnectorConsentGrants`): storagev1.MaxRetiredConnectorConsentGrants bounds the re-consent-replaced grants a Connection keeps for revocation at disconnect, and a commit past it returns ErrConnectorRetiredLimit so no grant is silently forgotten. MaxRetiredConnectorRefreshGrants instead drops the oldest refresh-rotated grants first.
- **Connector tombstones last 24 hours** (`storagev1.ConnectorTombstoneRetention`): storagev1.ConnectorTombstoneRetention is 24 hours because a tombstone only has to fence consents and completions in flight at disconnect, which expire after minutes, and a Connection UID is never reused. Providers drop the Connection's sequence counters together with its tombstone.
- **Connector disconnect is permanent per UID** (`storagev1.ErrConnectorCustodyTombstoned`): storagev1.ErrConnectorCustodyTombstoned is returned for writes to a disconnected Connection UID; deletion is permanent per UID so a late consent completion can never recreate custody.
- **Older consents never replace newer grants** (`storagev1.ErrConnectorConsentSuperseded`): storagev1.ErrConnectorConsentSuperseded is returned for a completion from a consent older than one already parked or committed for the Connection, so an older consent's tokens never replace a newer grant.
- **Sealed value digest encoding is fixed** (`storagev1.SealedValueDigest`): storagev1.SealedValueDigest is the canonical sha256 over the nonce length as an 8-byte big-endian integer, the nonce and the ciphertext; the length prefix prevents nonce/ciphertext boundary ambiguity, and providers and Orka must compute it identically for conditional commands.
- **Plain custody fields are re-checked against the seal** (`storagev1.SealedConnectorCredential`): storagev1.SealedConnectorCredential plain fields only help Orka find and judge the record; Orka binds the identity fields into the seal and checks the grant sequence against the plaintext when it opens the record, so a provider cannot alter them undetected.
- **Custody versions never repeat** (`storagev1.SealedConnectorCredential.Version`): storagev1.SealedConnectorCredential Version and UpdatedAt are set by the provider: Version from a per-Connection counter that never repeats, even after the record is shredded, and UpdatedAt from the request's time. Values sent in a request are ignored, so a stale version can never match a new record.
- **Replaced connector tokens are kept for revocation** (`storagev1.SealedRetiredConnectorCredential`): storagev1.SealedRetiredConnectorCredential keeps token material that a later write replaced, or that could not become custody, sealed under its own data key so disconnect can still revoke it upstream.
- **Zero RevocableUntil keeps retired material until disconnect** (`storagev1.SealedRetiredConnectorCredential.RevocableUntil`): For storagev1.SealedRetiredConnectorCredential and ConnectorRetirement, RevocableUntil is when nothing is left to revoke; zero keeps the record until disconnect rather than expiring it.
- **Consent verifiers are sealed with their plain fields** (`storagev1.SealedConnectorConsent`): storagev1.SealedConnectorConsent seals the PKCE verifier, and its associated data binds every plain field, so a provider cannot swap a consent's identity, scopes or sequence.
- **Consent nonce is the single-use OAuth state** (`storagev1.SealedConnectorConsent.Nonce`): storagev1.SealedConnectorConsent.Nonce is the single-use identifier carried in the OAuth state; consuming the consent removes it so a callback cannot be replayed.
- **Consent scopes keep their order** (`storagev1.SealedConnectorConsent.Scopes`): storagev1.SealedConnectorConsent.Scopes are OAuth scope tokens, which never contain whitespace, and providers must return them in the stored order because the seal's associated data binds them.
- **Completion commit state lives inside the seal** (`storagev1.SealedConnectorCompletion`): storagev1.SealedConnectorCompletion parks token material until the Connection's owner commits it; whether it was committed is sealed inside the payload, and the associated data binds every plain field, so no provider-visible field can flip it.
- **Connector custody is read from one snapshot** (`storagev1.ConnectorCustody`): storagev1.ConnectorCustody holds every custody record of one Connection read from one snapshot, and Orka decides connector writes from it; providers must not assemble it from separate reads.
- **Grant sequence outlives the credential** (`storagev1.ConnectorCustody.LastGrantSequence`): storagev1.ConnectorCustody.LastGrantSequence is the sequence the Connection's last grant took and outlives the credential record, so a shred-and-reconsent cannot reuse an old grant sequence.
- **New grants must take the next grant sequence** (`storagev1.PutSealedConnectorCredentialRequest`): storagev1.PutSealedConnectorCredentialRequest requires Credential.GrantSequence to equal LastGrantSequence + 1; otherwise another grant was taken since Orka read the custody and the provider returns ErrConflict.
- **Refresh replacement is version-fenced** (`storagev1.ReplaceSealedConnectorCredentialRequest`): storagev1.ReplaceSealedConnectorCredentialRequest replaces the current custody of the same grant, as a refresh does; the provider commits only while the stored record is at ExpectedVersion and the grant sequence matches.
- **New consents take the next consent sequence** (`storagev1.CreateSealedConnectorConsentRequest`): storagev1.CreateSealedConnectorConsentRequest replaces any earlier pending consent of the Connection and requires Consent.Sequence to equal IssuedConsentSequence + 1, otherwise ErrConflict; consents that expired before Now are dropped.
- **Parking a completion is conditional on the judged set** (`storagev1.CreateSealedConnectorCompletionRequest`): storagev1.CreateSealedConnectorCompletionRequest carries the parked completions Orka judged (ExpectedCompletions) and the uncommitted older ones it replaces; the provider commits only if the Connection's completions are still exactly ExpectedCompletions.
- **Completion commit is triple-fenced** (`storagev1.CommitSealedConnectorCompletionRequest`): storagev1.CommitSealedConnectorCompletionRequest carries a payload Orka opened, judged uncommitted and re-sealed as committed, plus its retirement and drop choices. The provider commits only if custody is still at ExpectedCredentialVersion (zero for none), the grant sequence is LastGrantSequence + 1, and the completions are still exactly ExpectedCompletions.
- **Replace keeps identity and checks refusals in order** (`storagev1.SealedConnectorCustodyStore.ReplaceSealedConnectorCredential`): storagev1.SealedConnectorCustodyStore.ReplaceSealedConnectorCredential replaces only the sealed bytes and expiry, keeping identity fields, and refuses in order with ErrConnectorCustodyTombstoned, ErrNotFound, then ErrConflict for another version. It first drops retired records whose RevocableUntil is not after Now, and a non-consent record retired until disconnect counts toward MaxRetiredConnectorRefreshGrants.
- **Uncommittable material is retired for revocation** (`storagev1.SealedConnectorCustodyStore.RetireSealedConnectorCredential`): storagev1.SealedConnectorCustodyStore.RetireSealedConnectorCredential keeps material that cannot become custody sealed for revocation, with RetiredAt from the request and ConsentGrant false; it refuses tombstoned Connections and applies the same expiry pruning and refresh bound as ReplaceSealedConnectorCredential.
- **Disconnect fences writes before reading for revocation** (`storagev1.SealedConnectorCustodyStore.TombstoneConnectorCustody`): storagev1.SealedConnectorCustodyStore.TombstoneConnectorCustody fences the Connection before its material is read for revocation, so later writes return ErrConnectorCustodyTombstoned while records stay readable. It is idempotent, prunes tombstones older than ConnectorTombstoneRetention, and clears sealed results held by operation receipts so a replayed write returns ErrConflict instead of resurrecting material.
- **Shred deletes custody without a tombstone** (`storagev1.SealedConnectorCustodyStore.ShredConnectorCredential`): storagev1.SealedConnectorCustodyStore.ShredConnectorCredential deletes current custody only at expectedVersion and leaves no tombstone so the person may consent again; it clears receipt-held sealed results like TombstoneConnectorCustody.
- **Deleting custody also tombstones the Connection** (`storagev1.SealedConnectorCustodyStore.DeleteConnectorCredential`): storagev1.SealedConnectorCustodyStore.DeleteConnectorCredential deletes current and retired custody, tombstones the Connection, succeeds for missing records, and clears receipt-held sealed results like TombstoneConnectorCustody.
- **Custody listing supports key verification** (`storagev1.SealedConnectorCustodyStore.ListSealedConnectorCredentials`): storagev1.SealedConnectorCustodyStore.ListSealedConnectorCredentials pages every current custody record by Connection UID so Orka can authenticate all retained custody with its key before key decisions (see docs/development/storage-contracts.md).
- **Orka judges a consumed consent's expiry** (`storagev1.SealedConnectorConsentStore.ConsumeSealedConnectorConsent`): storagev1.SealedConnectorConsentStore.ConsumeSealedConnectorConsent removes and returns the consent for a nonce after dropping consents expired before now; Orka still judges the expiry of the one it receives.
- **Parking refuses superseded consents** (`storagev1.SealedConnectorConsentStore.CreateSealedConnectorCompletion`): storagev1.SealedConnectorConsentStore.CreateSealedConnectorCompletion returns ErrConnectorCustodyTombstoned for a disconnected Connection and ErrConnectorConsentSuperseded for a consent sequence not after CommittedConsentSequence.
- **Completion commit is atomic with ordered refusals** (`storagev1.SealedConnectorConsentStore.CommitSealedConnectorCompletion`): storagev1.SealedConnectorConsentStore.CommitSealedConnectorCompletion, in one transaction, retires replaced custody when asked, stores the new grant, replaces the payload, records the committed consent and drops listed completions. Refusals, in order: ErrConflict when what Orka read changed; ErrNotFound for a completion expired at Now or at the provider's time inside the transaction; ErrConnectorConsentSuperseded; ErrConnectorRetiredLimit after pruning expired retired records; ErrConnectorCustodyTombstoned. A refused commit changes nothing.
- **Dropping consents clears receipt results** (`storagev1.SealedConnectorConsentStore.DeleteConnectorConsentsForConnection`): storagev1.SealedConnectorConsentStore.DeleteConnectorConsentsForConnection drops every pending consent and parked completion of a Connection and clears receipt-held sealed results, as TombstoneConnectorCustody does, so replays cannot return stale sealed material.
- **Controller epoch mirrors never choose ownership** (`storagev1.ControllerEpochMirror`): storagev1.ControllerEpochMirror receives the exact epoch acquired from the Kubernetes-authoritative ControllerEpochStore. Mirrors are subordinate fencing records for SQLite payload transactions and never select or advance controller ownership themselves.
- **Epoch advance installation ID before binding** (`storagev1.AdvanceControllerEpochRequest.InstallationID`): storagev1.AdvanceControllerEpochRequest.InstallationID is the UID of the installation's ControllerEpoch object until Orka records its installation, and afterwards the installation ID it binds datasets to through DatasetBindingStore.
- **Epoch advances require the acknowledged epoch** (`storagev1.AdvanceControllerEpochRequest.AcknowledgedEpoch`): storagev1.AdvanceControllerEpochRequest.AcknowledgedEpoch is the last epoch the installation durably acknowledged for the dataset; before changing anything the provider atomically checks that its stored epoch is at least this value (absent counts as zero) and otherwise returns ErrNotReady. This preserves rollback evidence across failed takeovers and controller crashes.
- **Controller epoch advance is forward-only and installation-bound** (`storagev1.ControllerEpochAdvancer`): storagev1.ControllerEpochAdvancer replaces SyncControllerEpochMirror: once a dataset is advanced Orka never syncs it again, and a provider refuses SyncControllerEpochMirror on an installation-bound dataset with a FencedError. AdvanceControllerEpoch refuses another dataset (ErrDatasetMismatch), another installation or lower epoch (FencedError), a detached dataset (ErrDatasetDetached), a differing equal epoch (ErrConflict), and a stored epoch below AcknowledgedEpoch (ErrNotReady, atomically), commits nothing on refusal, allows forward jumps because Kubernetes may advance several times without a store advance, records the installation on first success, and is linearized with fenced writes so no older-fenced write commits after it returns. It carries no WriteEnvelope or receipt and is idempotent by epoch and request digest; at takeover Orka advances each bound dataset and opens its fence only after that dataset's advance succeeds (docs/development/storage-contracts.md).
- **Epoch fences are checked inside the mutation transaction** (`storagev1.ControllerEpochFence`): storagev1.ControllerEpochFence fences a mutation to one exact controller epoch and holder, and providers must check both values in the same transaction as the durable mutation, never in a separate read.
- **Durability class decides automatic continuation after failover** (`storagev1.DurabilityClass`): storagev1.DurabilityClass states what an acknowledged write survives, and Orka uses it to decide whether automatic continuation after a provider failover is safe. synchronous-replicated loses no acknowledged write on failover; local-fsync survives process and host restarts with no failover; local-buffered survives a process restart but may lose recent writes on host or storage failure; async-replicated may lose acknowledged writes on failover.
- **Provider limits are floors set by the contract** (`storagev1.ProviderLimits`): storagev1.ProviderLimits must report at least the sizes the contract defines: an artifacts.v1 provider at least MaxArtifactBytes and a state.v1 provider at least MaxResultBytes, with zero for a contract part it does not serve.
- **Receipt retention has a contract minimum** (`storagev1.ProviderLimits.ReceiptRetention`): storagev1.ProviderLimits.ReceiptRetention is at least MinReceiptRetention, or zero only for a provider that keeps no operation receipts yet.
- **Large receipt results are rebuilt from records** (`storagev1.ProviderLimits.MaxReceiptResultBytes`): storagev1.ProviderLimits.MaxReceiptResultBytes caps the result kept with an operation receipt; for a larger result the provider reads it again from the records the write made, so a replay still returns the original result.
- **Migrating datasets still serve replays** (`storagev1.DatasetMigrating`): While a dataset is storagev1.DatasetMigrating, new writes return ErrNotReady and commit nothing until the migration finishes, but a replay of a committed operation is still served and reads keep working; DatasetImporting refuses new writes the same way.
- **Incompatible datasets are untouched until replaced** (`storagev1.DatasetIncompatible`): storagev1.DatasetIncompatible marks a dataset whose schema the provider cannot serve although it can read its identity, for example after a newer provider migrated it forward. The provider then reads and writes nothing: every call except Describe returns ErrIncompatible and commits nothing, and the state never changes on its own; an operator replaces the provider or the dataset.
- **Dataset emptiness is reported conservatively** (`storagev1.DatasetBootstrap.Empty`): storagev1.DatasetBootstrap.Empty is true only when the provider proves the dataset holds no application record; a provider may report false whenever it cannot prove emptiness cheaply, which makes fresh binding fail closed.
- **Storage contract revisions are additive** (`storagev1.ProviderInfo.ContractRevision`): storagev1.ProviderInfo.ContractRevision is the highest revision of ContractVersion whose obligations the provider meets, at least 1; revisions are additive, so revision N meets every earlier obligation, and passing the shared suite meets ContractRevision.
- **Dataset IDs survive moves and restores** (`storagev1.ProviderInfo.DatasetID`): storagev1.ProviderInfo.DatasetID identifies the dataset independently of its location and is stable for the dataset's lifetime, surviving a move or restore, so bindings follow the data rather than the address.
- **Orka never interprets provider schema versions** (`storagev1.ProviderInfo.SchemaVersion`): storagev1.ProviderInfo.SchemaVersion is the provider's own schema version and is opaque to Orka beyond equality; the provider's State, DatasetIncompatible or ErrIncompatible, is the verdict on whether it can serve the schema.
- **Optional storage families are detected, not assumed** (`storagev1.ProviderInfo.Capabilities`): storagev1.ProviderInfo.Capabilities lists optional families beyond Contracts, such as ExportCapability; Orka detects them here rather than assuming them.
- **Incarnation signals a possible database restart** (`storagev1.ProviderInfo.Incarnation`): storagev1.ProviderInfo.Incarnation changes whenever the serving database may have restarted or switched nodes so Orka can validate the dataset again before trusting it; it is never empty and stays stable between calls otherwise.
- **Describe reports provider time in UTC** (`storagev1.ProviderInfo.ObservedAt`): storagev1.ProviderInfo.ObservedAt is the provider clock in UTC when Describe ran, so Orka can estimate clock skew between itself and the provider.
- **Describe works before binding and is unfenced** (`storagev1.ProviderDescriber`): storagev1.ProviderDescriber.Describe is read-only, may take about a second, and answers for a dataset Orka has not bound, bootstrapped or advanced, so it carries no write envelope and is never fenced. It returns ErrUnavailable, ErrUnauthenticated, or ErrIncompatible when it cannot report on the dataset at all; Orka treats ErrIncompatible and State DatasetIncompatible as the same verdict that the provider cannot serve the dataset.
- **Request digest domain changes with the encoding** (`storagev1.requestDigestDomain`): storagev1.requestDigestDomain separates request digests from every other digest Orka computes, and any change to the RequestDigest encoding must change this domain string so old and new digests can never collide.
- **Request digest depth limit stops pointer cycles** (`storagev1.maxRequestDigestDepth`): storagev1.maxRequestDigestDepth bounds nesting at 64 levels, which also stops a pointer cycle from recursing forever; deeper typed values return ErrValidation.
- **Request digests use a stable canonical Go-value encoding** (`storagev1.RequestDigest`): storagev1.RequestDigest digests the method name and each argument after the context (never the WriteEnvelope) by walking Go values, so json:"-" fields count, and the encoding is stable across additive contract changes and process boundaries: struct fields in declaration order by Go name with zero values omitted (so new unset fields do not change the digest), zero values kept in positional slots, non-nil pointers to zero values encoded, maps in encoded-key order, times as UTC seconds plus nanoseconds, all NaNs equal and -0 as 0, and dynamic values as canonical JSON with sorted keys and numbers kept exactly as written. Servers recomputing it must decode dynamic values losslessly (UseNumber or json.RawMessage); a float64-decoded copy that rewrote a number digests differently and fails closed rather than matching another request. Unexported fields, channels, functions, complex numbers, invalid JSON, unencodable dynamic values and nesting beyond 64 levels return ErrValidation.
- **Map key ties are broken by value** (`storagev1.RequestDigest`): When storagev1.RequestDigest sorts map entries, keys that encode the same, such as NaN keys, are ordered by their encoded values so the digest stays deterministic.
- **Request digest test vectors are pinned** (`storagev1.TestCanonicalJSONIsPinned`, `storagev1.RequestDigest`): storagev1 request digest tests pin canonical JSON and digest bytes exactly, so a change to key sorting, escaping, number text or the node encoding shows up as a failing test rather than silently different request digests; a changed expected value means every stored receipt digest changed meaning and requires a new requestDigestDomain.
- **Times digest as seconds and nanoseconds** (`storagev1.RequestDigest`): storagev1.RequestDigest encodes times as Unix seconds plus nanoseconds rather than UnixNano, because UnixNano is undefined outside the years 1678 to 2262 and distinct extreme times would otherwise collide.
- **Dataset mismatch is not retryable** (`storagev1.ErrDatasetMismatch`): storagev1.ErrDatasetMismatch means a request named a dataset other than the provider's; nothing was committed and the caller is bound to the wrong dataset, so retrying cannot succeed.
- **Clock skew makes the store not ready** (`storagev1.ErrClockSkew`): storagev1.ErrClockSkew is returned for a write issued more than MaxClockSkew ahead of the provider clock; nothing was committed, and the caller treats the store as not ready until the clocks agree again.
- **Write envelope checks run in a fixed order inside the commit** (`storagev1.WriteEnvelope`): storagev1.WriteEnvelope is attached by the storage client to every MethodWrite (never reads or MethodAdmin), and the provider checks it in the committing transaction in this order: dataset ID (ErrDatasetMismatch); an existing receipt with the same method and digest replays the original outcome even under a stale fence, after still checking any Task data fence, while a differing receipt returns ErrDuplicateMismatch and an aborted one ErrOperationAborted; IssuedAt within MaxOperationAge and MaxClockSkew; dataset ready and not detached; Fence equal to the dataset's epoch, linearized with AdvanceControllerEpoch; method preconditions; then the change and receipt written together. A refusal commits nothing and records no receipt; each dataset has its own fence opened after its own advance; an explicit ControllerEpochFence parameter must equal Fence or ErrValidation (docs/development/storage-contracts.md).
- **Request digest is computed once and rechecked across processes** (`storagev1.WriteEnvelope.RequestDigest`): storagev1.WriteEnvelope.RequestDigest never covers the envelope; the storage client computes it once from the first attempt's arguments and every retry resends them unchanged. An in-process provider compares it with the receipt without recomputing, while a transport crossing a process boundary recomputes it from the decoded request and refuses a mismatch with ErrValidation.
- **Retries keep the original IssuedAt** (`storagev1.WriteEnvelope.IssuedAt`): storagev1.WriteEnvelope.IssuedAt is the controller clock when the operation was created, and every retry repeats it, so MaxOperationAge bounds the whole operation rather than each attempt.
- **Whole-object replacements are ordered by issue** (`storagev1.WriteEnvelope.Sequence`): storagev1.WriteEnvelope.Sequence is the operation's issue order within Fence, starting at 1 and repeated by retries; with Fence.Epoch it forms the order stamp that orders whole-object replacements such as SaveResult and SaveArtifact by issue rather than commit, so a delayed older write cannot overwrite a newer one.
- **Receipt retention outlasts every acceptable retry** (`storagev1.MinReceiptRetention`): storagev1.MinReceiptRetention must exceed MaxOperationAge + MaxClockSkew, because a receipt recorded at provider time C may be retried by an operation the provider still accepts until C + MaxClockSkew + MaxOperationAge.
- **Event usage is recorded atomically with the append** (`storagev1.ExecutionEvent.Usage`): storagev1.ExecutionEvent.Usage is a usage observation Orka derived from the event; a newly appended event records it in the same transaction as RecordUsage would and the append fails if recording fails, a deduplicated append that returns an existing event records nothing, and reads never return it.
- **Retried usage reports keep the first observation time** (`storagev1.ExecutionEventUsage.KeepFirstObservedAt`): storagev1.ExecutionEventUsage.KeepFirstObservedAt makes the provider keep the ObservedAt of an observation already recorded under the same namespace and ID before comparing them, so a usage report retried under a new event stays idempotent instead of conflicting.
- **Whitespace-only event content means no content** (`storagev1.ExecutionEventStore`): storagev1.ExecutionEventStore requires event content to be valid JSON when present, and providers store and return whitespace-only content as no content.
- **Latest event sequences come from one snapshot** (`storagev1.ExecutionEventStore.GetLatestExecutionEventSeqs`): storagev1.ExecutionEventStore.GetLatestExecutionEventSeqs reads only the requested streams, in bounded batches, all from one snapshot; keys are trimmed stream IDs and absent streams report sequence zero.
- **Grouped event appends are all-or-nothing** (`storagev1.GroupedExecutionEventStore`): storagev1.GroupedExecutionEventStore appends several deduplicated events in order in one transaction, each behaving as AppendExecutionEventIfAbsent including terminal approval conflicts, and appends none when any fails. Orka uses it for evidence that must not be recorded in part, such as a recovered approval decision and its execution outcome.
- **Event deduplication matches identity, not content** (`storagev1.DeduplicatingExecutionEventStore`): storagev1.DeduplicatingExecutionEventStore scopes a caller key to the event stream; a repeat returns the existing event with appended=false when Task, Session and tool call match (an empty field on either side matches), otherwise ErrDuplicateMismatch. Type, content and summary may differ, because competing outcomes of one step share a key so the first durable outcome wins and Orka may re-derive events after restart under newer redaction rules; terminal approval events are separately limited to one per approval.
- **Repeated plan events leave the plan unchanged** (`storagev1.AtomicExecutionEventPlanStore`): storagev1.AtomicExecutionEventPlanStore persists a deduplicated event and its plan projection in one transaction, and a repeated event key returns the existing event without changing the current plan projection.
- **Truncation lengths are measured after redaction** (`storagev1.ExecutionEventTruncation`): storagev1.ExecutionEventTruncation original lengths are measured after redaction so truncation metadata cannot reveal the size of a redacted secret.
- **Unknown event severities become info** (`storagev1.NormalizeExecutionEventSeverity`): storagev1.NormalizeExecutionEventSeverity deliberately coerces empty or unsupported severities to info rather than rejecting them, so event producers can be permissive while stores and APIs persist a stable severity value.
- **Session timelines are never appended directly** (`storagev1.IsValidExecutionEventStreamType`): storagev1.IsValidExecutionEventStreamType accepts only the task stream for persistence: session timelines are an aggregated read model over task streams, never a direct append target.
- **Pending Session cleanup defers Gateway admission** (`storagev1.ErrGatewaySessionCleanupPending`): storagev1.ErrGatewaySessionCleanupPending is returned by Gateway admission while a Session cleanup intent is retiring the target Session's previous incarnation; nothing is committed and the caller retries the event later. It is deliberately distinct from ErrConflict, which rejects the event.
- **Gateway cleanup proof is internal authority** (`storagev1.GatewaySessionCleanupProof`): storagev1.GatewaySessionCleanupProof freezes the owner and retention boundary of one Gateway transcript; it is internal cleanup authority and must never be exposed or accepted as a Session API flag.
- **Cleanup eligibility is rechecked at intent time** (`storagev1.GatewaySessionCleanupCandidate`): A storagev1.GatewaySessionCleanupCandidate only identifies an inactive retained transcript; providers check eligibility again in the transaction that persists its cleanup intent, so a listing is never authority to clean up.
- **Cleanup pages advance over skipped rows** (`storagev1.GatewaySessionCleanupPage`): storagev1.GatewaySessionCleanupPage reports progress through raw candidate rows, including rows skipped for malformed ownership, so the cursor always advances; Complete means fewer than Limit rows were scanned, and a full final page requires one more empty read.
- **Gateway Task cleanup receipts outlive event compaction** (`storagev1.GatewayTaskCleanupReceipt`): storagev1.GatewayTaskCleanupReceipt preserves exact event-to-Task ownership after retention compacts the event. It authorizes requesting ordinary Task deletion but does not replace runtime, Session or Task finalizer cleanup evidence, and it is kept until an uncached Kubernetes read proves the exact Task UID is gone.
- **Only event compaction writes cleanup receipts** (`storagev1.GatewayTaskCleanupReceiptStore`): storagev1.GatewayTaskCleanupReceiptStore is read-only durable retention evidence: the only writer is event compaction, so Task metadata can never manufacture a receipt.
- **Receipts are removed only after uncached absence proof** (`storagev1.GatewayTaskCleanupReceiptMaintenanceStore`): storagev1.GatewayTaskCleanupReceiptMaintenanceStore removes only receipts whose exact Tasks no longer exist, and callers must establish absence with an uncached Kubernetes read; elapsed retention or a cached miss is not sufficient.
- **Gateway expiry and its error delivery commit together** (`storagev1.GatewayExpiryProjection`): storagev1.GatewayExpiryProjection expires one event and creates its visible error delivery in one transaction so a crash can never leave external users without a response.
- **Gateway message budget reads reserve nothing** (`storagev1.GatewayMessageBudget`): storagev1.GatewayMessageBudget is a read-only snapshot, not an admission reservation; enqueue must enforce the limit again when it writes.
- **Gateway interim messages derive identity from the durable event** (`storagev1.GatewayMessageEnqueue`): storagev1.GatewayMessageEnqueue admits one bounded nonterminal message for an exact Task and event: routing and delivery identity come only from the durable event and RequestID, and callers must authorize the live Task and Gateway identity before entering the writer. ReplayOnly permits only receipt recovery when readiness denies admission, MaxMessages and MaxAttempts are positive controller policy never taken from workers, and replays compare identity and Text, not retry policy or request time (ADR 0032). See [ADR 0032](0032-gateway-interim-delivery.md).
- **ReplayOnly is a controller-only bit** (`storagev1.GatewayMessageEnqueue.ReplayOnly`): storagev1.GatewayMessageEnqueue.ReplayOnly is a controller-only control bit that is never persisted and never accepted from workers.
- **Storage contract never imports Orka internals** (`storagev1.TestContractPackagesDoNotImportOrkaInternals`): pkg/storage/v1 and its provider suite must be usable by a separately built provider, so neither may depend on Orka's internal packages; TestContractPackagesDoNotImportOrkaInternals enforces it.
- **Memory generation counts content changes, not recalls** (`storagev1.Memory`): storagev1.Memory.Generation is 1 at creation and increases by one for every change to content, tags, provenance, Disabled or Deleted, but never for a recall; only RecordMemoryRecall changes LastRecalledAt and RecalledCount. Consolidation proposals name the generation they read so applying them fails once the memory changed, and SupersededBy names the memory that replaced this one after a merge or supersede (ADR 0051). See [ADR 0051](0051-offline-memory-consolidation.md).
- **Only agent recalls count as memory recalls** (`storagev1.MemoryRecall`): storagev1.MemoryRecall is recorded only when an agent's recall_memory call returns memories, never when Orka injects memories into a prompt or an operator lists them.
- **Recall ID bound matches the largest recall** (`storagev1.MaxMemoryRecallIDs`): storagev1.MaxMemoryRecallIDs equals the largest recall a provider returns, so every real recall fits in one RecordMemoryRecall; change both together.
- **Proposal apply targets carry no memory content** (`storagev1.MemoryProposalApplyTarget`): storagev1.MemoryProposalApplyTarget names what applying a proposal would return without any memory content, and Orka authorizes its MemoryID before committing; ProposalStatus and AppliedMemoryID are the version the commit checks.
- **Applied memories are built and redacted by Orka** (`storagev1.MemoryProposalApplication.Memory`): storagev1.MemoryProposalApplication.Memory is set only when the target names no existing memory; Orka builds it from the proposal and redacts it, and the provider sets its namespace, source and source proposal and assigns an ID when missing.
- **Memory store contract** (`storagev1.MemoryStore`): storagev1.MemoryStore receives content Orka already redacted. CreateMemory assigns missing IDs and MemorySourceManual, refuses IDs reused across namespaces and duplicate SourceProposalIDs with ErrConflict, and always stores RecalledCount 0, Generation 1 and no SupersededBy. All access is namespace-scoped; UpdateMemory ignores Generation and SupersededBy and bumps Generation only when a replaced field changes; DeleteMemory soft-deletes and disables. RecordMemoryRecall accepts at most MaxMemoryRecallIDs, counts each distinct live ID once per operation, ignores deleted or unknown IDs because deletion can race a recall, and never changes UpdatedAt or list order since a recall is not an update.
- **Memory proposals apply through a two-step conditional command** (`storagev1.MemoryProposalStore`): storagev1.MemoryProposalStore creates only pending proposals with no review or apply outcome, validates consolidation targets (merge at least two, supersede exactly one, retire at least one, distinct IDs at generation 1 or more), and lets review record accepted or rejected exactly once on a pending unapplied proposal; a review never applies. Applying is two steps so Orka can authorize the exact memory before any content leaves the provider: ResolveMemoryProposalApplication returns a content-free target, and CommitMemoryProposalApplication re-resolves and applies only if it still equals Target (else ErrPreconditionFailed), so racing applications create one memory. Consolidation applies only while every target is live and at the named generation (else ErrConflict, stale), never adopts a memory that merely names it as source, and marks merged or superseded targets deleted, disabled and superseded in the same transaction.
- **Each consolidation mode has its own cursor** (`storagev1.MemoryConsolidationRun`): storagev1.MemoryConsolidationRun keeps a separate cursor per mode in each namespace, so a dry run never consumes the Sessions a proposing run has yet to read (ADR 0051). See [ADR 0051](0051-offline-memory-consolidation.md).
- **Consolidation input is pinned and then cleared** (`storagev1.MemoryConsolidationRun.Input`): storagev1.MemoryConsolidationRun.Input is recorded when the run begins, at most MaxMemoryConsolidationInputBytes; a resumed worker reads the same input and completion is checked against it. Because it holds transcript excerpts, the provider clears it once the run completes, is skipped or is abandoned.
- **Abandoned consolidation runs are final** (`storagev1.MemoryConsolidationAbandoned`): storagev1.MemoryConsolidationAbandoned marks a running run whose lease ended and that another run took over; it can neither resume nor complete.
- **Consolidation runs hold a two-hour lease** (`storagev1.MemoryConsolidationRunLease`): storagev1.MemoryConsolidationRunLease (2 hours) is how long a running run blocks another from beginning in its namespace, so a run whose Task died stops blocking once it is older.
- **Memory consolidation store contract** (`storagev1.MemoryConsolidationStore`): storagev1.MemoryConsolidationStore.BeginMemoryConsolidationRun is idempotent per namespace and TaskUID, refuses a new run while another unexpired run of any mode is running (ErrConflict) so two runs never propose over the same memories, returns ErrPreconditionFailed when a same-mode run completed past WindowStart because the cursor moved, marks lease-expired runs abandoned in the same transaction, and writes the stored run back so a retry keeps its window and input. CompleteMemoryConsolidationRun records the report, clears Input and creates all proposals atomically, only for propose-mode non-skipped runs; ReleaseMemoryConsolidationRun abandons and clears Input (and Report and unneeded rows on deletion) without moving cursors. ListMemoryConsolidationSessions never returns gateway Sessions, and the cursor is the latest completed window end or the earliest start. Begin, Complete, Get and ListSessions check a Task data fence because Input holds transcripts, and operation receipts keep no copy of Input or Report so they never outlive the run (ADR 0051). See [ADR 0051](0051-offline-memory-consolidation.md).
- **Method kind decides envelope, fence and receipt** (`storagev1.MethodKind`): storagev1.MethodKind classifies provider methods: MethodRead changes nothing and carries no envelope or receipt; MethodWrite carries a WriteEnvelope, commits only under the current fence and leaves a receipt with its change; MethodAdmin establishes the fence, settles operations or binds the dataset, carries no envelope and is not fence-checked.
- **Writes wait only for their own dataset's fence** (`storagev1.MethodInfo.Contract`): storagev1.MethodInfo.Contract names the contract part (StateContract or ArtifactsContract) whose provider serves a method, or is empty for methods every part serves such as Describe; Orka fences writes per dataset, so a write waits only for the fence of the dataset serving its own contract.
- **Natural keys make re-run writes idempotent** (`storagev1.MethodInfo.NaturalKey`): storagev1.MethodInfo.NaturalKey lists, comma-separated as $N.field paths (N counts arguments after the context from 1), the request values by which a provider recognizes a repeat of a write's effect: while the keyed record or tombstone is kept, a new operation with the same key returns the stored outcome or fails with ErrConflict or ErrDuplicateMismatch. An empty key means only same-operation retries are safe through the receipt, and a new operation repeats the effect unless the write is idempotent by state, such as a delete.
- **Call classes isolate scheduling and bulk transfers** (`storagev1.CallClass`): storagev1.CallClass sets a storage call's deadline, retry rule and shared concurrency limit, and network transports carry bulk calls on their own connection so a large transfer cannot delay a health check queued behind it.
- **Control calls must get through under saturation** (`storagev1.CallControl`): storagev1.CallControl marks calls that check or establish a binding or its ownership, such as HealthCheck, Describe, AdvanceControllerEpoch and the dataset binding methods, which act before a fence exists; they must get through when every other class is saturated.
- **Stream reads have their own call class** (`storagev1.CallStream`): storagev1.CallStream is never assigned by the catalog; a poller chooses it for an otherwise interactive read so the number of open streams cannot use up the interactive concurrency limit.
- **The method catalog is authoritative** (`storagev1.Methods`): storagev1.Methods lists every method of StateProvider, ArtifactProvider, OperationReceiptStore, ControllerEpochAdvancer and DatasetBindingStore so storage clients, transports and the shared suite tell reads from writes and bulk from ordinary calls from the catalog, never by guessing from names.
- **IsLocked is classified as a write** (`storagev1.methodCatalog`): storagev1.methodCatalog classifies IsLocked as a write despite its read-style name, because it clears a Task lock it finds expired.
- **Sealed snapshot and native session calls are bulk** (`storagev1.methodCatalog`): storagev1.methodCatalog classifies sealed snapshot bodies and native session record calls as CallBulk because each can reach several megabytes and must not share the interactive connection.
- **Only active work actions hold a dedupe key** (`storagev1.WorkActionStatusQueued`): Among one monitor's work actions sharing a non-empty DedupeKey, at most one may be in an active status (queued, leased, running, retry_pending). Finished statuses (succeeded, failed, blocked, cancelled, completed) hold no key and storagev1.RepositoryMonitorStore.MarkWorkActionRetryPending never reopens them; completed means the action was coalesced into another active action at creation.
- **AllNamespaces is never client-settable** (`storagev1.GitHubMutationRecordFilter.AllNamespaces`): storagev1.GitHubMutationRecordFilter.AllNamespaces enables controller-wide mutation audit lookup only for internal callers; API list handlers stay namespace-scoped and must never populate it from client input.
- **Expired operations stay unsettled** (`storagev1.ErrOperationExpired`): A write issued more than storagev1.MaxOperationAge before the provider clock returns ErrOperationExpired and commits nothing; callers must not retry it, and rerunning the logical work is a new operation. Because an earlier attempt may have committed, this refusal does not settle an unknown outcome; when ResolveOperation finds no record older than MinReceiptRetention minus MaxClockSkew, the outcome is permanently unknown and the work is held for recovery rather than repeated or reported as success.
- **Aborted operations are final** (`storagev1.ErrOperationAborted`): storagev1.ErrOperationAborted means ResolveOperation recorded the operation as aborted: nothing committed and nothing ever will under that operation ID. Running the logical work again is a new operation and a deliberate caller choice.
- **Operation age bounds new writes only** (`storagev1.MaxOperationAge`): storagev1.MaxOperationAge limits how long after IssuedAt a provider accepts a new write for an operation; a replay of an already committed operation is served for as long as its receipt is retained.
- **Receipt retention exceeds operation age plus skew** (`storagev1.MinReceiptRetention`): storagev1.MinReceiptRetention must exceed MaxOperationAge plus MaxClockSkew so a receipt outlives every retry the provider can still accept.
- **Large receipt results may be re-read** (`storagev1.MaxReceiptResultBytes`): storagev1.MaxReceiptResultBytes is the largest result a provider must keep with a receipt; for larger results it may keep only record identifiers and re-read the records on replay.
- **Operation outcomes carry no result** (`storagev1.OperationOutcome`): storagev1.OperationOutcome records only the settled state of an operation; to read the typed result of a committed operation the caller retries the write with the same envelope and receives it as a replay.
- **Aborted outcomes have a zero fence** (`storagev1.OperationOutcome.Fence`): storagev1.OperationOutcome.Fence is the envelope fence of the committing write and is zero for an operation ResolveOperation aborted.
- **Outcome IssuedAt source** (`storagev1.OperationOutcome.IssuedAt`): storagev1.OperationOutcome.IssuedAt is the committing write's envelope IssuedAt, or for an aborted operation the IssuedAt of the ResolveOperation request that aborted it.
- **Resolve uses IssuedAt to interpret missing receipts** (`storagev1.ResolveOperationRequest.IssuedAt`): storagev1.ResolveOperationRequest.IssuedAt must be the operation's original envelope IssuedAt; the provider uses it to decide whether a missing receipt proves the operation never committed or whether the receipt may already have been pruned.
- **Operation receipt contract** (`storagev1.OperationReceiptStore`): Every enveloped write records a receipt atomically with its change, and a retry with the same operation ID, method, and request digest returns the original outcome without changing anything; no-op successes also get receipts, refusals leave none, receipts never hold plaintext protected data, and removing sealed custody clears a stored result so replay returns ErrConflict. After an unknown outcome only a replayed commit, ErrOperationAborted, or ResolveOperation settles the operation, never a later refusal. Receipt check, commit, and abort are atomic per operation ID with age measured on the provider clock, and imported datasets must carry receipts or take a new dataset ID so ResolveOperation never reports a committed operation as aborted.
- **ResolveOperation proves absence only within retention** (`storagev1.OperationReceiptStore.ResolveOperation`): storagev1.OperationReceiptStore.ResolveOperation returns a committed outcome or durably records an abort, may be called by any controller even with a stale fence because it only prevents change, and returns ErrNotReady without recording during migration or import. A missing receipt proves non-commit only while retention still covers it, so when IssuedAt is older than MinReceiptRetention minus MaxClockSkew it returns ErrOperationExpired, and IssuedAt more than MaxClockSkew ahead returns ErrClockSkew. Providers whose clock can regress must extend retention by a bound on cumulative regression or use a durable non-regressing clock.
- **Receipt pruning touches only receipts** (`storagev1.OperationReceiptStore.PruneOperationReceipts`): storagev1.OperationReceiptStore.PruneOperationReceipts removes at most limit receipts and aborted records older than retention on the provider clock and never removes records other families keep, such as Session cleanup completions or gateway tombstones; a limit below 1 returns ErrValidation.
- **Outbox persistence trusts the Kubernetes fence** (`storagev1.OutboxPersistenceStore`): storagev1.OutboxPersistenceStore is the SQLite-only outbox adapter used behind a Kubernetes epoch fence; its methods persist records but must not treat a SQLite controller_epochs row as authoritative.
- **Protected records are sealed by Orka** (`storagev1.SealedAgentExecutionSnapshot`): Execution snapshots, native session state, and connector custody are sealed by Orka with AES-256-GCM under a fresh nonce, binding record identity into the associated data; providers store nonce and ciphertext as opaque bytes and never hold the key or plaintext. Providers decide conditional commits only from plain metadata stored beside the sealed bytes, and Orka authenticates that metadata against the plaintext when opening a record.
- **Snapshot digest is over plaintext** (`storagev1.AgentExecutionSnapshotKey.Digest`): storagev1.AgentExecutionSnapshotKey.Digest is the canonical sha256 digest of the plaintext snapshot body, not of the sealed ciphertext, so snapshot identity is stable across re-sealing.
- **Snapshot create never overwrites** (`storagev1.SealedAgentExecutionSnapshotStore.CreateSealedAgentExecutionSnapshot`): CreateSealedAgentExecutionSnapshot returns ErrConflict and changes nothing when a snapshot with the same key exists; only Orka, after reading and opening the stored snapshot, decides whether the request was a repeat.
- **Sealed listings are ordered and page-bounded** (`storagev1.SealedAgentExecutionSnapshotStore.ListSealedAgentExecutionSnapshots`): ListSealedAgentExecutionSnapshots returns retained snapshots ordered by Task UID and digest, 1 through MaxSealedRecordPageSize per page, so Orka can authenticate every retained record with its key before serving; an invalid cursor returns ErrValidation and providers hold at most one page of large records at a time.
- **Snapshot deletion requires released references** (`storagev1.SealedAgentExecutionSnapshotStore.DeleteAgentExecutionSnapshots`): DeleteAgentExecutionSnapshots removes every snapshot for a Task UID without checking references; the caller must first prove all binding, attempt, lineage, finalizer, and retention references are released.

- **SessionTurns retain all snapshots of their Task** (`storagev1.AgentExecutionSnapshotReferenceCounts`): storagev1.AgentExecutionSnapshotReferenceCounts counts every durable reference that can retain a snapshot; SessionTurns store no snapshot digest, so each retains every snapshot scoped to its immutable Task UID.
- **Retention listing order** (`storagev1.AgentExecutionSnapshotLifecycleStore.ListAgentExecutionSnapshotMetadataBefore`): ListAgentExecutionSnapshotMetadataBefore returns snapshots created strictly before the cutoff, ordered by creation time, Task UID, and digest.
- **Snapshot reference counts are one consistent read** (`storagev1.AgentExecutionSnapshotLifecycleStore.CountAgentExecutionSnapshotReferences`): CountAgentExecutionSnapshotReferences must count prompt attempts (matched by Task UID and digest) and SessionTurns (matched by Task UID only) from one consistent view so retention never deletes a referenced snapshot.
- **Exact snapshot delete is caller-guarded** (`storagev1.AgentExecutionSnapshotLifecycleStore.DeleteAgentExecutionSnapshot`): DeleteAgentExecutionSnapshot idempotently deletes one exact Task UID and digest key; the caller must first prove all references and the configured retention interval have cleared.
- **Native session plain fields are authenticated mirrors** (`storagev1.SealedNativeSession`): storagev1.SealedNativeSession repeats facts from inside the sealed record in plain fields so the provider can enforce ownership, transcript boundaries, and monotonic history without opening it; Orka checks those fields against the plaintext when opening the record.
- **Empty SessionUID marks a staged import** (`storagev1.SealedNativeSession.SessionUID`): storagev1.SealedNativeSession.SessionUID is the canonical Session owner, and is empty only for a staged import no Session has bound yet; such an import also has no runtime generation.
- **Native capture retry identity** (`storagev1.SaveSealedNativeSessionRequest`): SaveSealedNativeSessionRequest.RequestDigest is computed by Orka from the plaintext record excluding its creation time; a repeated source operation with the same digest succeeds without change, and with another digest returns ErrDuplicateMismatch.
- **Import receipt time is Session creation time** (`storagev1.StageSealedNativeSessionImportRequest`): StageSealedNativeSessionImportRequest reserves a new Session and stages a sealed import for its first Task; the receipt's CreatedAt is also the new Session's creation time.

- **Native record reads are owner and boundary checked** (`storagev1.SealedNativeSessionStore.GetSealedNativeSession`): GetSealedNativeSession returns a record only when sessionUID is the canonical owner and the record covers the current transcript; it returns ErrNotFound without a record, ErrConflict for another owner, deleted name, or stale boundary, and ErrGatewayOwnedSession for gateway Sessions. An empty sessionUID reads only an unbound import.
- **Native captures are monotonic** (`storagev1.SealedNativeSessionStore.SaveSealedNativeSession`): SaveSealedNativeSession requires the record to cover the Session's current transcript and to advance the runtime generation or transcript boundary over the stored record, otherwise it returns ErrConflict.
- **Import staging is atomic and refuses reused names** (`storagev1.SealedNativeSessionStore.StageSealedNativeSessionImport`): StageSealedNativeSessionImport creates the Session and stores the record with its receipt in one transaction; a repeat returns the stored receipt only when the request digest matches, and a name that exists, is being cleaned up, or was deleted with native state returns ErrConflict.
- **Turn records follow Kubernetes lease validation** (`storagev1.CreateSessionTurnRecordRequest`): A CreateSessionTurnRecordRequest is persisted only after Kubernetes has validated the exact SessionControl mutation lease and PromptAttempt binding.
- **Deferred turn projection waits for Kubernetes** (`storagev1.ActivateSessionTurnProjectionRequest`): ActivateSessionTurnProjectionRequest releases the deferred terminal outbox record only after Kubernetes SessionControl and BranchClaim finalization has committed.
- **Finalization basis is one consistent snapshot** (`storagev1.SessionTurnFinalizationBasis`): storagev1.SessionTurnFinalizationBasis returns the turn, the Session's transcript boundary, and the stored native record from one consistent snapshot, which Orka reads before sealing a turn's native state.

- **Turn token usage is added once** (`storagev1.SealedSessionTurnFinalization.InputTokens`): The first storagev1.SealedSessionTurnFinalization adds InputTokens and OutputTokens to the Session's counters; a repeated finalization adds nothing.

- **Turn creation is idempotent** (`storagev1.SessionTurnRecordStore.CreateSessionTurnRecord`): CreateSessionTurnRecord returns the stored turn when repeated with the same immutable input.
- **Turn finalization replay rule** (`storagev1.SessionTurnRecordStore.CommitSealedSessionTurnFinalization`): CommitSealedSessionTurnFinalization returns the finalized turn for a repeat with the same terminal data and ErrConflict for different data.
- **Storage extension contract semantics** (`storagev1 (package)`): orka.storage.v1 splits into state.v1 (all database-owned state except public Task artifacts, keeping records that must commit together) and artifacts.v1, with no operation spanning both; provider methods take no Go callbacks, hold no transaction open while Orka works, and keep Kubernetes authority, authorization, and orchestration in Orka, using a resolve step plus a conditional command that returns ErrPreconditionFailed (ErrConflict for sealed families) when the target changed. Every method is atomic and linearizable per dataset, multi-record reads come from one snapshot, ErrUnavailable means nothing committed while a possibly committed write returns ErrOutcomeUnknown, caller-supplied times are preserved to the nanosecond in UTC because some are bound into encryption associated data, and every write carries a WriteEnvelope checked in the committing transaction. Datasets are bound once to one installation, and the package's JSON tags serve Orka's API rather than storage, so cross-process providers must define their own wire records instead of encoding these structs with encoding/json.
- **Contract revisions gate mandatory obligations** (`storagev1.ContractRevision`): storagev1.ContractRevision increments whenever every provider gains a new mandatory obligation (checked by the shared storagetest suite), so Orka can refuse an outdated provider with one precise reason instead of failing at the first missing method; optional families are announced through ProviderInfo.Capabilities instead. Revision 8, for example, orders whole-object SaveResult and SaveArtifact replacement by the envelope's (Fence.Epoch, Sequence) write stamp and caps results at MaxResultBytes.
- **Outbox backlog reads never claim** (`storagev1.OutboxBacklogReader`): storagev1.OutboxBacklogReader counts unsettled outbox projections without claiming them, because the planned-upgrade drain barrier uses it to prove the outbox is empty without disturbing delivery.
- **Session creation time identifies an incarnation** (`storagev1.SessionCreationReader`): A Session deleted and recreated under the same name gets a new creation time, so the value from storagev1.SessionCreationReader identifies one Session incarnation.
- **Scan ingestion is one conditional command** (`storagev1.ScanIngestionStore`): Orka resolves a scan run and receipt with ordinary reads, validates the live RepositoryScan identity, and computes an ordered list of read and write steps; the provider then commits the steps, run update, and receipt in one transaction only while every read still returns what Orka saw, with no transaction open while Orka computes. Reads that follow earlier writes use PreviewScanTaskIngestion, which runs the steps with the provider's own semantics and discards them, so a preview returns exactly what the commit will see.
- **Each ingestion step names one operation** (`storagev1.ScanIngestionStep`): Exactly one operation field of storagev1.ScanIngestionStep is set, and each has the meaning of the SecurityStore method it names.
- **Read steps carry the observed result** (`storagev1.ScanIngestionStep.Expect`): A commit requires storagev1.ScanIngestionStep.Expect on every read step and compares it with the read's result when the step runs; a preview ignores it.
- **Read result NotFound semantics** (`storagev1.ScanIngestionReadResult`): storagev1.ScanIngestionReadResult sets NotFound when the read returned ErrNotFound and otherwise fills the field of the read's type; write steps have an empty result.
- **Ingestion step times derive from At** (`storagev1.ScanIngestionPreview.At`): Where a provider would read its clock while running ingestion step i, it uses At plus i nanoseconds; a preview and the commit that follows use the same At so their results match.
- **Ingestion read equality rule** (`storagev1.ScanIngestionReadsEqual`): storagev1.ScanIngestionReadsEqual compares field by field with empty and absent lists equal and times equal by instant, and counts every persisted field including JSON-omitted ones such as Finding.TargetKey and Finding.DecisionAt; wire formats must carry those fields and cross-process providers must compare decoded results with the same rule.
- **Run equality includes cancellation fields** (`storagev1.ScanRunsEqual`): storagev1.ScanRunsEqual compares the stored run with ExpectedRun including the cancellation fields that are not in the JSON form, so a cancellation request blocks a stale commit.
- **Scan commit refusal rules** (`storagev1.ScanIngestionStore.CommitScanTaskIngestion`): CommitScanTaskIngestion returns false and changes nothing when the receipt exists or the run is terminal or cancellation-requested, returns ErrValidation for mismatched run identity or steps outside the ingestion's namespace or RepositoryScan, ErrConflict for a run of another RepositoryScan, and ErrPreconditionFailed unless the stored run and every read Expect still match. It applies writes, run update, and receipt in one transaction, so two commits computed against the same run cannot both apply.
- **Scan ingestion binds one Task incarnation** (`storagev1.ScanTaskIdentity`): storagev1.ScanTaskIdentity binds ingestion to one Kubernetes Task incarnation and scan run so a recreated Task cannot reuse an earlier ingestion.
- **Ingestion receipt is the source for follow-up work** (`storagev1.ScanTaskIngestion`): storagev1.ScanTaskIngestion is committed with the Task's results and run counters, and follow-up work reads this receipt instead of parsing and counting results again.
- **Scan runs bind admitting configuration** (`storagev1.ScanRun.RepositoryScanUID`): storagev1.ScanRun.RepositoryScanUID and RepositoryScanGeneration bind the run to the configuration that admitted it; empty values identify legacy history.
- **Cancellation fences scan progress** (`storagev1.ScanRun.CancellationVersion`): storagev1.ScanRun.CancellationVersion fences cleanup attempts, and once cancellation is requested ordinary progress updates must never resume the run.
- **Patch failure reasons are operator-safe** (`storagev1.PatchProposal.Reason`): storagev1.PatchProposal.Reason holds an operator-facing failure explanation that must never include credentials or agent-controlled text, and is empty while pending or succeeded.
- **Publication evidence is bound atomically** (`storagev1.PatchPublicationEvidence`): storagev1.PatchPublicationEvidence is the immutable governed-publication tuple bound atomically when a patch proposal reaches pr_opened.
- **Pull request evidence is non-secret** (`storagev1.PatchPullRequestEvidence`): storagev1.PatchPullRequestEvidence is the exact non-secret forge receipt bound to a PatchPublicationEvidence record and must never carry secrets.
- **Scan cancellation intent precedes cleanup** (`storagev1.SecurityStore.RequestScanRunCancellation`): RequestScanRunCancellation persists cancellation intent and bumps run.CancellationVersion before any external cleanup, and CompleteScanRunCancellation must match that version.
- **Session cleanup uses a durable cross-store intent** (`storagev1.SessionCleanupPersistenceStore`): storagev1.SessionCleanupPersistenceStore is the SQLite half of the cross-store Session cleanup protocol; its durable intent closes the crash window between deleting Kubernetes control records and deleting the transcript.
- **Cleanup receipts are read only for reclamation** (`storagev1.SessionTurnCleanupReceiptStore`): storagev1.SessionTurnCleanupReceiptStore reads Task-owned finalization evidence after Session deletion, and ordinary turn and outbox reads never consult these receipts.
- **Transcript-only cleanup intents** (`storagev1.SessionCleanupIntent`): An empty SessionUID in storagev1.SessionCleanupIntent denotes a transcript-only, non-ACP Session, and SQLite refuses that form when ACP SessionTurns exist.
- **SQLite cleanup follows Kubernetes reclamation** (`storagev1.CompleteSessionCleanupRequest`): storagev1.CompleteSessionCleanupRequest deletes SQLite-owned state only after the authoritative Kubernetes cleanup plan has been reclaimed.
- **Deleted Session names are never reused** (`storagev1.SessionCleanupCompletion`): storagev1.SessionCleanupCompletion is a durable tombstone kept after the Session row and intent are atomically removed; Session names are not reusable because stale DELETE retries could not otherwise tell a new Session instance from the deleted one.
- **Cleanup receipts keep exact evidence only** (`storagev1.SessionTurnCleanupReceipt`): storagev1.SessionTurnCleanupReceipt keeps only finalization evidence needed by Task reclamation and deliberately omits prompt and transcript content; Payload is bytes rather than json.RawMessage so encoding preserves the exact immutable projection bytes, including whitespace.
- **Only Delivered receipts authorize reclamation** (`storagev1.SessionTurnCleanupReceipt.Validate`): SessionTurnCleanupReceipt.Validate proves archived metadata pins one exact terminal projection; DeadLetter receipts are retained as evidence, but callers must still require Delivered before authorizing Task reclamation.
- **Legacy receipts without publication receipt stay readable** (`storagev1.SessionTurnCleanupReceipt.Validate`): SessionTurnCleanupReceipt.Validate accepts older turns that name a publication without retaining its receipt so archives stay readable, but such a receipt can never authorize delivery compatibility.
- **Established empty soul digest means no soul** (`storagev1.SessionSoulState`): storagev1.SessionSoulState describes the pinned Task revision or first canonical message revision (the first assistant message for gateway conversations); Established with an empty Digest means an explicitly no-soul conversation.
- **Soul MessageCount includes unbound failures** (`storagev1.SessionSoulState.MessageCount`): storagev1.SessionSoulState.MessageCount counts all visible messages, including unbound failures.
- **FirstMessageID skips anchors and unbound turns** (`storagev1.SessionSoulState.FirstMessageID`): storagev1.SessionSoulState.FirstMessageID excludes hidden anchors and attested unbound Gateway turns so the controller can still require the current event to be first.
- **Soul reads check the Task lock** (`storagev1.SessionSoulReader`): storagev1.SessionSoulReader reads only bounded revision metadata while checking the caller still owns the legacy Task lock, so retaining the revision across Task cleanup needs no schema or transcript changes.
- **Soul identity is pinned before execution** (`storagev1.SessionSoulWriter`): storagev1.SessionSoulWriter durably pins ordinary AI Session identity under the exact Task lock before execution, writing only digest metadata and never persona text; an empty digest pins the absence of a soul so a later turn cannot opt in, and the owner must hold the Session lock at owner.Now.
- **Soul digest metadata is not prompt text** (`storagev1.SessionSoulDigestMetadata`): storagev1.SessionSoulDigestMetadata is controller-authored prompt revision metadata, never model instruction text, and follows the canonical transcript lifecycle.
- **Unbound marker requires literal true** (`storagev1.SessionSoulUnboundMetadata`): storagev1.SessionSoulUnboundMetadata marks a controller-authored Gateway AI error that failed before soul binding; only the literal "true" on a canonical error without digest metadata counts as unbound, and absence preserves legacy identity.
- **Configuration mismatch is not lease contention** (`storagev1.ErrSessionConfigurationMismatch`): storagev1.ErrSessionConfigurationMismatch marks an immutable Session configuration conflict, not lease contention, so callers must not retry it as they would ErrConflict.
- **Replay-only admission preserves the gate error** (`storagev1.ErrGatewayMessageReplayOnly`): When receipt-only gateway admission finds no existing message it returns storagev1.ErrGatewayMessageReplayOnly, and the caller must return its original live admission gate error rather than this one.
- **ErrUnavailable guarantees nothing committed** (`storagev1.ErrUnavailable`): Providers return storagev1.ErrUnavailable only when nothing was committed, which makes retrying the same operation safe.
- **Unknown outcomes are settled, not repeated** (`storagev1.ErrOutcomeUnknown`): After storagev1.ErrOutcomeUnknown the caller must neither report success nor repeat the action as a new operation; it may only retry with the same operation ID and request digest or settle the outcome with OperationReceiptStore.ResolveOperation.
- **Fenced writers stop** (`storagev1.ErrFenced`): storagev1.ErrFenced means the caller's controller epoch or owner fence is stale and it has lost the authority the write required, so it must stop rather than retry.
- **Precondition failures disclose nothing** (`storagev1.ErrPreconditionFailed`): On storagev1.ErrPreconditionFailed nothing is applied and nothing the command would have returned is disclosed; the caller resolves the target again, repeats any authorization for the new target, and retries.
- **Authentication failures require credential reload** (`storagev1.ErrUnauthenticated`): storagev1.ErrUnauthenticated commits nothing and retrying with the same credentials fails again, so the caller reloads its credentials before retrying; in-process providers never return it.
- **Incompatibility is permanent until replacement** (`storagev1.ErrIncompatible`): storagev1.ErrIncompatible commits nothing and cannot succeed on retry until the provider or the dataset is replaced.
- **Precondition failures also match ErrConflict** (`storagev1.PreconditionFailedError`): storagev1.PreconditionFailedError matches both ErrPreconditionFailed and ErrConflict so callers that branch on concurrent changes keep handling a changed target correctly.
- **Validation messages are client-safe** (`storagev1.ValidationError`): storagev1.ValidationError carries a message that is safe to return to API clients while still matching ErrValidation via errors.Is, so providers must never put sensitive detail in it.
- **Health checks are cheap dataset probes** (`storagev1.HealthChecker`): storagev1.HealthChecker.HealthCheck must reach the dataset rather than only the provider process, take no write lock, and finish in tens of milliseconds because Orka calls it every few seconds with a short deadline; it works before dataset binding or epoch advance and returns nil, ErrUnavailable, ErrNotReady (migrating or importing), ErrUnauthenticated, or ErrIncompatible.
- **Results are replaced in issue order** (`storagev1.ResultStore`): storagev1.ResultStore.SaveResult replaces a stored result only when its WriteEnvelope (Fence.Epoch, Sequence) stamp is greater than the stored one; an older or equal stamp still succeeds and leaves a receipt but changes nothing, so an older retry never overwrites a newer result whichever commits last. DeleteResult removes the stamp so a later save always stores, a Task-scoped writer's TaskDataFence refuses writes after cleanup, and data over MaxResultBytes returns ErrTooLarge.
- **Prompt result receipts enable takeover repair** (`storagev1.PromptResultReceipt`): storagev1.PromptResultReceipt preserves the exact result bytes behind a fenced prompt settling transition and is immutable per PromptAttempt, so a controller takeover can repair a result write interrupted after the durable control-plane transition.
- **Result receipts precede Settling** (`storagev1.PromptResultReceiptStore`): storagev1.PromptResultReceiptStore persists the attempt-bound result receipt before the corresponding PromptAttempt enters Settling.
- **Session leases use the request's controller time** (`storagev1.SessionStore`): Providers decide whether a Session lock or chat turn reservation expired only by comparing its stored expiry with the time the request carries, never their own clock; the commit-time fence makes an early reclaim after takeover harmless, the request time is covered by the request digest so retries are judged at the original time, and a zero request time returns ErrValidation.
- **Session paging order** (`storagev1.SessionStore.ListSessionsPage`): ListSessionsPage returns sessions newest first by creation time then name, strictly after the cursor (nil for the first page), skipping excludeType when set, and reports whether more rows exist.
- **Live leases block Session deletion** (`storagev1.SessionStore.DeleteSession`): DeleteSession returns ErrConflict while an unexpired chat turn reservation or transient Task lock holds the Session at now; expired leases do not block deletion.
- **AcquireLock reclaims expired leases** (`storagev1.SessionStore.AcquireLock`): AcquireLock gives the Session a durable lock for one Task incarnation, reclaiming a transient lock or chat turn reservation expired at now and returning ErrConflict for a live one.
- **IsLocked has a reclaim side effect** (`storagev1.SessionStore.IsLocked`): IsLocked reports whether another Task incarnation or a chat turn reservation holds the Session at now, and clears a transient Task lock that has expired at now.
- **Transcript search filters before limiting** (`storagev1.SessionStore.SearchTranscript`): SearchTranscript excludes gateway sessions and applies the result limit only after filtering by the authorized session names, so unauthorized matches cannot consume or reveal result slots.
- **Chat turn reservations can create the Session** (`storagev1.AcquireChatTurnRequest.Session`): When AcquireChatTurn creates the Session, it gets the request Session's type and cancellation state and its CreatedAt, or Now when CreatedAt is zero.
- **Turn commit requires a live reservation** (`storagev1.CommitSessionTurnRequest.Now`): CommitSessionTurn requires the turn's reservation to expire after the request's Now, judged on the controller clock.
- **Chat turn commits are fenced by message count** (`storagev1.SessionTurnCommitter`): storagev1.SessionTurnCommitter atomically commits a chat turn's transcript messages with token usage only while ExpectedMessageCount still matches the session revision observed after acquiring the turn lease; leases follow SessionStore rules.
- **Session writes name the exact lock owner** (`storagev1.SessionOwnerWrite`): storagev1.SessionOwnerWrite names the exact Task or transient owner holding the Session lock and the controller time of the request; a transient lock expired at Now no longer authorizes the write.
- **Session writes are owner-fenced** (`storagev1.FencedSessionWriteStore`): storagev1.FencedSessionWriteStore binds transcript and token writes to the exact active lock owner, and AppendMessagesWithLock and UpdateTokenCountsWithLock return a FencedError when the owner no longer holds the lock at owner.Now, so a stale owner cannot write after takeover.
- **Token usage and lock release are one write** (`storagev1.FencedSessionWriteStore.ReleaseLockWithTokenUsage`): ReleaseLockWithTokenUsage adds a finished owner's token usage and releases its lock in one write, so a replayed completion cannot count usage twice.
- **Artifacts are replaced in issue order** (`storagev1.ArtifactStore`): storagev1.ArtifactStore never shares a transaction with state.v1 records; SaveArtifact replaces a stored file only when its WriteEnvelope (Fence.Epoch, Sequence) stamp is greater than the stored file's, an older write succeeds without change, and DeleteArtifacts removes the files with their stamps.
- **Artifact listing is byte-ordered** (`storagev1.ArtifactStore.ListArtifacts`): ListArtifacts returns a Task's artifact metadata ordered by filename in byte order, independent of database collation.
- **Retry parking only touches active actions** (`storagev1.RepositoryMonitorStore.MarkWorkActionRetryPending`): MarkWorkActionRetryPending atomically checks that the work action is active and only then sets status and phase to retry_pending, replaces RunID, BlockedReason, and Error, clears CompletedAt, and sets UpdatedAt from the provider clock, leaving lease fields untouched; for any other status it changes nothing and returns false so a completion that committed first is never undone, and a missing action returns ErrNotFound.
- **Inbox reads are bounded** (`storagev1.MaxMessageBatch`): storagev1.MaxMessageBatch caps how many messages one ListUnreadMessages or ConsumeMessages call returns, so readers with a longer backlog read it over several calls.
- **Message IDs are monotonic and never reused** (`storagev1.Message.ID`): storagev1.Message.ID is provider-assigned, increases in storage order, and is never reused, so a replayed ConsumeMessages that re-reads its messages by ID cannot return a later message.

- **Broadcasts have one shared read flag** (`storagev1.MessageStore`): A Task's inbox in storagev1.MessageStore holds unread messages of its namespace and parent Task addressed to it or broadcast with "*", excluding its own; a broadcast has one read flag, so the first sibling to consume it marks it read for all.

- **Shared counters need other Tasks' observations** (`storagev1.TaskUsageObservationReader.ListTaskCounterObservations`): ListTaskCounterObservations returns every Task's observations of each counter the Task observed, ordered by observed time then provider record order, because other Tasks' observations of a shared counter are baselines that keep their usage out of this Task's share.
- **Usage observation rules apply on every path** (`storagev1.ValidateUsageObservation`): Providers enforce storagev1.ValidateUsageObservation both in RecordUsage and for observations carried by execution events.
- **Token counts fit exact JSON integers** (`storagev1.MaxUsageTokenCount`): storagev1.MaxUsageTokenCount is 2^53-1, the largest integer JSON clients such as the UI represent exactly.
- **Usage work IDs are deterministic per issue** (`storagev1.UsageWorkID`): storagev1.UsageWorkID derives the ID only from namespace, monitor UID, repository, kind, and number so retries and follow-up commands for one issue share one work ID.
- **Durability class decides automatic recovery after a switch** (`storagev1.DurabilityClass`): storagev1.DurabilityClass states what a successful write, committed together with its operation receipt, survives, and Orka uses it to decide whether to continue after detecting a restart or switch through ProviderInfo.Incarnation: synchronous-replicated continues once the dataset validates again; local-fsync and local-buffered have no automatic switch, so a restart is validated and work continues; async-replicated stops all work until an operator acknowledges recovery because the switch may have lost acknowledged writes. In every class, a dataset holding a lower controller epoch or write watermark than Kubernetes recorded has lost acknowledged writes and Orka stops all work until an operator acknowledges recovery; for local-buffered a host failure looks like a restart, so that is the only way such a loss is detected.
- **State providers report the exact message content limit** (`storagev1.ProviderLimits.MaxMessageContentBytes`): A state.v1 provider reports exactly MaxMessageContentBytes in ProviderLimits.MaxMessageContentBytes, because a provider that accepts larger message content breaks the inbox batch budget (MaxMessageBatchBytes); a provider that does not serve state.v1 reports zero.
- **Schema migrations serialize with the epoch advance** (`storagev1.DatasetMigrating`): A provider enters storagev1.DatasetMigrating in a transaction that takes the same lock as AdvanceControllerEpoch, so writes in progress finish first, then records the new schema version and returns to DatasetReady. A dataset left migrating by a crash refuses new writes until the migration runs again, and concurrent migrations serialize.
- **Dataset migration requires export.v1 on both providers** (`storagev1.ExportCapability`): A provider reports storagev1.ExportCapability (export.v1) only when it implements DatasetExporter, DatasetImporter and MigrationMarkerStore for every contract part it serves, and Orka migrates a dataset only between providers that both report it.
- **Dataset export is a field-for-field copy** (`storagev1.DatasetExporter`): storagev1.DatasetExporter reads records in their canonical encoding because behavioral methods cannot copy a dataset: they assign sequences, IDs and times, apply quotas and deduplication, and some records have no public writer. The export carries provider-assigned values, every time to the nanosecond, domain tombstones, natural-key receipts and sealed records as opaque stored bytes. It reads no snapshot across pages, so Orka exports while writes are stopped and compares both datasets' counts and digests before using the copy.
- **Export pages keep one stable record order** (`storagev1.DatasetExporter.ExportRecords`): ExportRecords returns a family's records in an order the provider chooses but keeps from page to page, so the pages of one export hold every record exactly once.
- **Imports refuse records beyond target limits** (`storagev1.ImportRecordsRequest.Records`): A provider may refuse an import batch larger than it accepts at once with ErrTooLarge, committing nothing, and Orka resends in smaller batches; a one-record batch within ProviderLimits is always accepted. A record beyond the target's limits (MaxResultBytes, MaxMessageContentBytes, MaxArtifactBytes) returns a TooLargeError so a target with lower limits refuses the import instead of truncating it, and a message whose identifiers exceed MaxControlIdentifierBytes returns ErrValidation as SendMessage would, so an imported inbox still fits a consumed batch in one response.
- **Dataset imports are unfenced admin operations** (`storagev1.DatasetImporter`): storagev1.DatasetImporter methods other than GetImportProgress are MethodAdmin: they carry no write envelope and are not checked against a fence because the dataset has no controller yet. Each is atomic, durable when it returns, returns ErrOutcomeUnknown when the provider cannot tell whether it committed, and is safe to repeat. An import moves the dataset from empty through DatasetImporting to DatasetReady with origin DatasetOriginMigrated, or back to empty on abort; while importing, every write, the controller epoch advance, BindDataset and MarkDatasetMigrated return ErrNotReady.
- **Imports start only on an empty new dataset** (`storagev1.DatasetImporter.BeginImport`): BeginImport requires a dataset that serves every requested contract part and reports origin DatasetOriginNew, ready, bootstrap incomplete and empty, no binding, no migration marker, and no controller epoch, write watermark or records; otherwise it returns ErrConflict. It mints a new dataset ID; a repeat of the request that began the current import returns its session, and any other request during an import returns ErrConflict.
- **Import batches are sequenced and reference checks wait** (`storagev1.DatasetImporter.ImportRecords`): ImportRecords commits one batch atomically: a batch after the family's last committed batch commits, a batch at or before it is a repeat that succeeds unchanged only if every record is held with the same body, and a conflicting body, duplicate key with different bodies, or skipped sequence returns ErrConflict and commits nothing. Because references between families can be circular or self-referential, a provider never refuses a record whose referent has not arrived; any reference checks run in CompleteImport.
- **Completed imports start with fresh sequences and stamps** (`storagev1.DatasetImporter.CompleteImport`): CompleteImport verifies every family's count and digest against the manifest, moves every provider-assigned sequence past both its imported head and the largest imported value, and leaves the dataset ready with origin DatasetOriginMigrated, unbound, with no controller epoch and a write watermark of zero. Results and artifacts keep no write stamp from the source, whose controller epochs are not copied, so the first enveloped write replaces them; only an explicit storage switch later binds the dataset with BindMigrated.
- **Aborted imports mint a fresh dataset ID** (`storagev1.DatasetImporter.AbortImport`): AbortImport discards every imported record and the session and returns the dataset to empty, unbound and ready with origin DatasetOriginNew and a dataset ID it has never reported before, so nothing can mistake it for the aborted import's dataset.
- **Migrated contract parts refuse writes on the source** (`storagev1.MigrationMarkerStore`): storagev1.MigrationMarkerStore marks a source dataset's migrated contract parts so the source cannot become their active writer again unnoticed. While a contract part is marked, every write method of it returns ErrDatasetMigrated (which matches ErrNotReady) until an explicit rollback clears the marker; reads, exports, replays (which still check a carried Task data fence) and the other contract part are unaffected. AdvanceWriteWatermark returns ErrDatasetMigrated only once every served contract part is marked, and marker changes never advance the watermark.
- **Importing datasets are never migration sources** (`storagev1.MigrationMarkerStore.MarkDatasetMigrated`): MarkDatasetMigrated returns the stored marker for a repeat to the same target and ErrConflict for another target, and returns ErrNotReady for a dataset that is importing, so an aborted import leaves no marker behind.
- **Migration targets are marked at most once** (`storagev1.MigrationMarkerStore.ClearMigrationMarker`): ClearMigrationMarker is used only by an explicit migration rollback. Because an import fills only a DatasetOriginNew dataset, a rolled-back target (origin migrated) is never filled again and a later migration copies into a new dataset ID; the caller therefore never re-marks a cleared target, so a retried clear whose first outcome was unknown cannot remove a newer marker.
- **Export times keep the instant, not the zone** (`storagev1.ExportTime`): storagev1.ExportTime fields are encoded exactly to the nanosecond but keep only the instant, not the time.Time location; ExportFamilySchema.Decode returns them in UTC. Providers and tests must compare exported times by instant, never by zone.
- **Nullable export fields keep absence distinct from zero** (`storagev1.ExportField.Nullable`): storagev1.ExportField.Nullable marks a field that may be absent, which is distinct from its zero value; a provider that stores an absent value as SQL NULL must export nil, not the zero value, so a copy round-trips absence.
- **Export key fields are unique and never nullable** (`storagev1.ExportField.Key`): The storagev1.ExportField.Key fields of a family together identify a record: no two records of a family have equal key fields, and a key field is never nullable, so the record Key encoding is always defined and unique.
- **Export encoding version changes with its fields** (`storagev1.ExportFamilySchema.Version`): storagev1.ExportFamilySchema.Version must be incremented whenever a family's fields change, because it is part of the encoding name both sides of an import and its digests check.
- **Export records have one canonical encoding** (`storagev1.ExportFamilySchema.Encode`): An exported record is encoded as the field count (unsigned varint), then each field in schema order as one tag byte and its value: strings and bytes as an unsigned varint length plus the bytes, integers as a signed varint, booleans as one byte 0 or 1, and times as the signed varint of Unix seconds plus the unsigned varint of nanoseconds; an absent nullable field is the tag alone. Each record has exactly one encoding so equal records have equal bytes and digests, and a record Key is the same encoding of the key fields alone in base64url without padding.
- **Export decoding refuses non-canonical records** (`storagev1.ExportFamilySchema.Decode`): storagev1.ExportFamilySchema.Decode accepts only a record of its family and encoding whose body is the canonical encoding and whose Key matches its key fields, returning ErrValidation otherwise; a lenient decoder would let two different byte strings stand for one record and break digest equality.
- **Export digests use their own domain strings** (`storagev1.exportRecordDomain`): storagev1.exportRecordDomain and exportFamilyDomain prefix export digests so they never collide with any other digest Orka computes; changing an export encoding must change these domain strings.
- **Family digests are order-independent** (`storagev1.FamilyDigester`): storagev1.FamilyDigester computes a family's digest as SHA-256 over the family's encoding name, the record count and the sorted SHA-256 digests of each record (over its encoding and body), so exporter and importer reach the same digest whatever order records arrive in.
- **Manifest digest follows schema order** (`storagev1.ManifestDigest`): storagev1.ManifestDigest digests each family's FamilyDigest in ExportSchemas order, whatever order the manifest lists them, and refuses with ErrValidation any entry naming an unknown or duplicate family, an old encoding, a negative count or a non-canonical digest.
- **Export families copy contract state, not provider internals** (`storagev1.exportSchemas`): storagev1.exportSchemas lists every state.v1 and artifacts.v1 family in import order (Sessions before their records; other references may be circular), field for field what the contract requires, including provider-assigned IDs, tombstones, receipts and sealed records as opaque bytes, named by the embedded SQLite provider's columns. AHP tokens and auth sessions copy only token hashes so issued credentials stay valid; sequence_heads carries each sequence's last issued value so an import never reissues a value a client may have seen; security_scan_runs.admission_seq, auth_sessions.issued_seq and execution_events.session_seq carry orders a provider may keep implicitly. Operation receipts, the controller epoch mirror, write watermark, result/artifact write stamps (imported as (0, 0)), dataset identity and installation binding, and the embedded store's duplicate Kubernetes control records are deliberately not exported.
- **Export fixtures use nanoseconds and a non-UTC zone** (`storagev1_test.exampleValues`): Export test fixtures (storagev1_test.exampleValues, storagetest.exportExampleTime) build times with nanoseconds in a zone other than UTC, so an encoding that rounds precision or keeps the location is caught.
- **Storage module requires only wire dependencies** (`storagev1_test.TestStorageModuleRequiresOnlyTheWireDependencies`): An adapter that imports orka.storage.v1 inherits the storage module's requirements, so TestStorageModuleRequiresOnlyTheWireDependencies keeps them limited to gRPC, protobuf, the google.rpc status types and the assertion library the shared suite uses.
- **Write watermark calls run in the control class** (`storagev1.methodCatalog`): storagev1.methodCatalog classifies AdvanceWriteWatermark and GetWriteWatermark as CallControl, because the watermark detects lost acknowledged writes and must keep working even while ordinary traffic saturates the store.
- **Migration calls run in the background class** (`storagev1.methodCatalog`): storagev1.methodCatalog classifies export, import and migration-marker calls as CallBackground: a migration copies a dataset while writes are stopped and its batches can carry whole results and artifacts, so they must not delay health checks or interactive calls.
- **Storage export surface and wire-preservation rules** (`storagev1 (package)`): A storagev1 provider that reports ExportCapability also implements DatasetExporter, DatasetImporter and MigrationMarkerStore, copying a whole dataset while writes are stopped in the canonical ExportSchemas encoding with sealed records as opaque bytes; the import gets a new dataset ID with origin DatasetOriginMigrated and its source in ProviderInfo.Source, and the source marks each moved part so it refuses writes. Records crossing the orka.storage.v1 wire must not depend on nil versus empty slices or maps, must use valid UTF-8 strings, and times within 0001-01-01..9999-12-31 UTC where the zero time.Time means no time and a *time.Time keeps nil apart from a pointer to zero. Orka validates a binding with Describe before use and periodically, probes it with HealthCheck in between, and uses LookupMethod's CallClass so long transfers never delay health checks.
- **Inbox batches are bounded by content bytes** (`storagev1.MaxMessageBatchBytes`): storagev1.MaxMessageBatchBytes (4 MiB) bounds the content one ListUnreadMessages or ConsumeMessages call returns: a batch stops before the message that would pass it and always holds at least one message from a non-empty inbox. It is at least MaxMessageContentBytes so any stored message fits alone, and with each of a message's four identifiers capped at MaxControlIdentifierBytes a full MaxMessageBatch batch carries at most 2 MiB of identifiers, staying under the wire message limit so a consumed batch can always be sent.
- **SendMessage writes back identity and enforces limits** (`storagev1.MessageStore.SendMessage`): storagev1.MessageStore.SendMessage writes the assigned ID and creation time back into the message, and a replay writes back the same ones and stores nothing; content over MaxMessageContentBytes returns TooLargeError and an identifier over MaxControlIdentifierBytes returns ErrValidation, both storing nothing.
- **Inbox reads return at least one message** (`storagev1.MessageStore.ListUnreadMessages`): storagev1.MessageStore.ListUnreadMessages returns the oldest unread messages by ID, changes nothing, stops before MaxMessageBatchBytes and always yields at least one message from a non-empty inbox; a limit of zero selects MaxMessageBatch and a negative or larger limit returns ErrValidation.
- **ConsumeMessages marks exactly what it returns** (`storagev1.MessageStore.ConsumeMessages`): storagev1.MessageStore.ConsumeMessages marks exactly the messages it returns as read, so a message the byte budget left out stays unread. A replay returns the same messages and marks nothing more, omits messages deleted in between by sender or parent cleanup, and under a Task data fence that cleanup or a Job revocation moved since it is refused with that fence's error.
- **Write watermark detects lost acknowledged writes** (`storagev1.WriteWatermarkStore`): Orka advances each bound dataset's write watermark with a fenced write about once a minute and records the returned value in Kubernetes; a dataset reporting a lower value lost acknowledged writes or was restored from an older copy with the same identity, so Orka stops work and waits for an operator instead of resuming. storagev1.WriteWatermarkStore is required on both providers because each dataset holds its own watermark.
- **Watermark advances once per operation** (`storagev1.WriteWatermarkStore.AdvanceWriteWatermark`): storagev1.WriteWatermarkStore.AdvanceWriteWatermark is an enveloped write that increases the watermark by exactly one under the current fence, and a replay of the same operation returns the original value without advancing again.

### `pkg/storage/v1/storagetest`

- **AHP prefix deletes treat wildcards literally** (`storagetest.runAHP`): DeleteAHPRecords matches its prefix literally: SQL LIKE wildcards such as '_' or '%' in the prefix must not match other characters, so deleting prefix "s1_" must leave "s10/" records. The storagetest AHP case checks this so SQL providers escape the prefix.
- **Ended auth sessions are pruned on the next write** (`storagetest.runAuthSessions`): RevokeAuthSession only marks a session ended and prunes nothing; the next auth-session write drops every session that has ended, whether revoked or expired. The storagetest auth-session cases hold providers to this so a revoked session stays visible until a later write.
- **Artifacts-only providers may hold an advance-recorded binding** (`storagetest.requireUnclaimed`): requireUnclaimed accepts either no binding or the binding an epoch advance records (the suite's installation at generation 0 with no record), because the suite gives an artifacts-only provider its first epoch through an advance in order to store a record. Such a dataset is still unclaimed by any installation.
- **Write catalog compares observations** (`storagetest.writeCase`): Each writeCase runs against fresh providers: setup prepares records without an envelope, args supplies the call arguments, and observe captures the state the write changes. Comparing observations before and after proves that a refused write changed nothing and that a replay returned the original result without a second change.
- **Write case arguments are rebuilt per attempt** (`storagetest.writeCase.args`): writeCase.args returns fresh arguments for every attempt so a write that fills in a record it was passed starts from the same request each time; the fence argument lets methods that also take a fence parameter receive the envelope's fence.
- **afterCommit makes replay detection observable** (`storagetest.writeCase.afterCommit`): writeCase.afterCommit changes the written state after the first commit, for example by writing a deleted record again, so the receipt check can prove a replay returns the original outcome without rerunning the write. Without it an idempotent write would hide a second execution.
- **Catalog writes run under a bounded context** (`storagetest.callWriteContext`): callWriteContext bounds each catalog write with writeCallTimeout so a provider that waits on itself (for example a nested transaction on the same connection) fails the test instead of hanging the suite.
- **Replay outcomes compare by canonical digest** (`storagetest.requireSameOutcome`): requireSameOutcome compares canonical RequestDigest values of the original and replayed outcomes, so an empty slice or map and a nil one count as the same result; a deep-equal comparison would fail providers that legitimately round-trip empties as nil.
- **Missing-envelope checks bypass the suite wrapper** (`storagetest.runMissingEnvelopes`): runMissingEnvelopes prepares and observes through the suite's wrapper but sends the unenveloped write to the raw provider through callWriteContext, because the wrapper would otherwise attach an envelope. Every catalog write must refuse a call without an envelope and change nothing.
- **Detached-dataset checks observe only while bound** (`storagetest.runWriteDetached`): runWriteDetached observes state only while the dataset is bound, because some observers call catalog writes that change nothing, such as IsLocked, and a detached dataset refuses those too once they carry a write envelope.
- **Concurrent reads are paced to overlap every write** (`storagetest.readDuringWrites`): readDuringWrites makes each write wait until a read starts after the previous write, so reads overlap the whole workload even when a provider could otherwise finish every write before any reader runs and hide snapshot bugs.
- **Stream-head snapshot case uses 1024 streams** (`storagetest.runConcurrency`): The stream-head snapshot case appends to 1024 streams so a provider that reads heads in bounded batches reads the first and last streams in different queries, exposing a non-snapshot read.
- **Parking must not reopen a completed action** (`storagetest.runConcurrency`): In the park-versus-complete race one caller completes the action and the others park it; a provider whose park reads before the completion and writes after it would reopen the action, so park must be atomic with its check.
- **Session event page and latest sequence share one snapshot** (`storagetest.sessionEventPagesSnapshot`): sessionEventPagesSnapshot records each round's first event sequence; because a round appends two events and then deletes the stream, any snapshot with an empty page must report a latest sequence of zero or a round's second event, never a first event that was still stored.
- **Session UID stays fenced across cleanup intent replacement** (`storagetest.cleanupFenceSnapshot`): In cleanupFenceSnapshot, once a round's cleanup intent is stored its Session UID must remain fenced, first by the intent and then by the completion that replaces it; a reader must never see the UID unfenced in between.
- **Claim renewal returns a still-dispatching event** (`storagetest.gatewayClaimRenewalSnapshot`): In gatewayClaimRenewalSnapshot each round claims a new event and then retries it past base, so a renewal at base must either fail or return the event still dispatching under the same owner.
- **Cleanup identity binding never conflicts** (`storagetest.cleanupIdentityBinding`): Binding a cleanup identity to a Session created during the call must succeed or report the Session missing; a conflict matches no serial order because nothing else binds or fences these Sessions.
- **Session deletion must not succeed after a lock grant** (`storagetest.lockDuringDelete`): When lock acquisition races deletion of the same Session, acquisition must succeed or report the Session missing, and a deletion must not succeed once a lock on the Session was granted; a delete may instead fail with ErrConflict. Any other result matches no serial order.
- **Identical usage replays succeed across retention pruning** (`storagetest.usageReplayDuringRetention`): An identical replay of a usage observation must be recorded whether it lands before or after retention prunes the original, so any error from RecordUsage while retention removes observations matches no serial order.
- **Conditional commands replace provider callbacks** (`storagetest.conditional`): Providers apply conditional commands instead of running Go callbacks: Orka resolves a target, authorizes or computes in its own process with no provider transaction open, and the provider applies the command only while the resolved target and version still match.
- **Losing memory application does not return the winner** (`storagetest.conditional`): A CommitMemoryProposalApplication against a stale target must not return the memory another caller created, because the caller was authorized to create a memory, not to read the winner's.
- **Connector custody records stay opaque to providers** (`storagetest.connector`): Connector custody records carry sealed bytes the provider cannot read; providers must store them exactly and decide every conditional command only from the plain fields and the expectations Orka sends.
- **Connector completion fixture expiry uses the real clock** (`storagetest.connectorCompletionExpiry`): connectorCompletionExpiry is derived from time.Now because completion redemption also checks the provider clock, so the fixture must stay live while connectorNow keeps the rest of the fixtures deterministic.
- **Connection shred classifies inside its delete transaction** (`storagetest.shredDuringGrants`): A shred fenced on a Connection's version must delete it or report it missing; a conflict matches no serial order. A provider that decides a no-op shred by reading the record outside the delete's transaction misreports a grant made in between as a conflict.
- **Fence rejections also match ErrConflict** (`storagetest.requireFenced`): A stale-fence rejection must match both storagev1.ErrFenced and storagev1.ErrConflict, because existing Orka callers detect fence failures through ErrConflict.

- **Self-enveloping callers stamp times before digesting** (`storagetest.runLostResponses`): A caller that supplies its own write envelope must stamp the record's creation time before computing the request digest, otherwise a retry digests a different request and is refused as a reused operation ID.

- **Only synchronous-replicated providers declare failovers** (`storagetest.DurabilityHarness.Failovers`): storagetest.DurabilityHarness.Failovers is empty for local-fsync, local-buffered and async-replicated providers and non-empty for synchronous-replicated ones; an async-replicated switch may lose acknowledged writes, which the durability cases do not allow, and Orka holds the installation after one instead.
- **Failovers start while writes are held in the database** (`storagetest.DurabilityHarness.HoldWrites`): storagetest.DurabilityHarness.HoldWrites, required with failovers, makes the next writes wait inside the database (as behind a row lock) so the suite starts each failover with writes in flight; the failover ends the wait and every held write must have returned by the time the failover returns.
- **Durability cases require writes, receipts and ownership to survive** (`storagetest.WithDurability`): storagetest.WithDurability checks that after a restart and each declared failover every catalog write is present with its receipt, a replay returns the original outcome without a second change, and the dataset keeps identity, controller epoch, installation and write watermark; each failover changes the reported incarnation, and in-flight writes settle through ResolveOperation as their errors promised.
- **Resolve the receipt before replaying after a switch** (`storagetest.runDurableWrite`): storagetest.runDurableWrite resolves a write's receipt before replaying it after a restart or failover, because a replay would record a lost receipt again and hide the loss.
- **In-flight write errors decide how they settle** (`storagetest.runWritesDuringFailover`): In storagetest.runWritesDuringFailover a write that returned nil must survive with its receipt; one refused with ErrUnavailable or ErrNotReady must settle as aborted, because those errors promise nothing committed and a caller may repeat the action as a new operation; only ErrOutcomeUnknown may settle either as committed or aborted, and an aborted write is refused if it arrives late.
- **Parallel suites need isolated datasets and harnesses** (`storagetest.Parallel`): storagetest.Parallel runs the suite's families concurrently, so the factory must be safe for concurrent use and each dataset isolated (such as a schema per case); a harness that restarts or fails over a database the families share would disconnect the others, so such a suite must omit Parallel.
- **Digest-recomputing transports expect ErrValidation** (`storagetest.RecomputesRequestDigests`): storagetest.RecomputesRequestDigests tells the suite that the named methods cross a transport that recomputes each write's request digest and refuses a mismatch with ErrValidation, so receipt cases expect ErrValidation where an in-process provider returns ErrDuplicateMismatch; the suite must also run in process to cover the provider's own receipt comparison.
- **Export suite uses tiny pages and batches** (`storagetest.exportPageLimit`): storagetest.exportPageLimit (2) and importBatchRecords (3) are deliberately tiny so every export spans several pages and every import several batches, exercising cursors and batch sequences; raising them would silently drop that coverage.
- **Export suite uses tiny pages and batches** (`storagetest.importBatchRecords`): storagetest.exportPageLimit (2) and importBatchRecords (3) are deliberately tiny so every export spans several pages and every import several batches, exercising cursors and batch sequences; raising them would silently drop that coverage.
- **Shortened-manifest request is built by hand** (`storagetest.RunExportImport`): storagetest.RunExportImport builds the shortened-manifest request directly instead of digesting it, because for a provider that serves only artifacts.v1 the shorter manifest is empty and an empty manifest has no digest.
- **Import batches may be refused as too large** (`storagetest.RunExportImport`): A provider may refuse any import batch of two or more records with ErrTooLarge, and a refused batch commits nothing; storagetest.RunExportImport accepts either outcome and callers split the batch.
- **Duplicate records in one import batch count once** (`storagetest.RunExportImport`): Two copies of one record in a single ImportRecords batch count once; a provider that takes one record at a time may refuse the pair with ErrTooLarge instead.
- **Refused import batches split under the same sequence** (`storagetest.importDataset`): storagetest.importDataset resends a batch the provider refuses with ErrTooLarge as two halves under the same batch sequence, as the contract permits, and with replay set repeats each family's first batch to check idempotence.
- **Record picker tolerates key-only custom seeds** (`storagetest.firstRecord`): storagetest.firstRecord prefers a record with a field outside its key but falls back to any record, so a provider's custom seed that only fills key-only families still runs the cases.
- **Changed export values keep their size** (`storagetest.changedRecord`): storagetest.changedRecord changes a string by replacing a rune with one of the same UTF-8 width and a byte slice by changing a byte, so a value at a size bound such as MaxControlIdentifierBytes stays valid and the change is the only difference.
- **Typed errors may be values or pointers** (`storagetest.typedError`): storagetest.typedError accepts a typed error such as TooLargeError whether a provider returns it as a value or a pointer, since the contract allows both.
- **Export fixtures use nanoseconds and a non-UTC zone** (`storagetest.exportExampleTime`): Export test fixtures (storagev1_test.exampleValues, storagetest.exportExampleTime) build times with nanoseconds in a zone other than UTC, so an encoding that rounds precision or keeps the location is caught.
- **Export surface bypasses the envelope wrapper** (`storagetest.exporter`): Export, import and migration-marker calls carry no write envelope, so storagetest.exporter sends them to the provider the factory returned rather than the suite's envelope wrapper, while suiteExport keeps the wrapped provider for a seed's ordinary writes so they get envelopes.
- **Export surface bypasses the envelope wrapper** (`storagetest.suiteExport`): Export, import and migration-marker calls carry no write envelope, so storagetest.exporter sends them to the provider the factory returned rather than the suite's envelope wrapper, while suiteExport keeps the wrapped provider for a seed's ordinary writes so they get envelopes.
- **Export seed deletes sequence maxima** (`storagetest.seedStateExport`): storagetest.seedStateExport deletes the records holding the highest message ID and session event sequence after reading the heads, so an import that continued sequences from the remaining records instead of the copied sequence heads would reuse a value and fail.
- **Order fixtures sort keys opposite to the implicit order** (`storagetest.runStateExportImport`): The export contract fixtures give scan runs and auth sessions IDs that sort opposite to admission or issuance (with equal creation times), so an import that rebuilt admission_seq or issued_seq from key order would reverse them and fail.
- **Dataset state is checked before the fence** (`storagetest.runStateExportImport`): A write to a dataset being imported must be refused with ErrNotReady: the provider checks dataset state before the controller epoch fence, since the importing dataset holds no epoch yet.
- **Imports reset write stamps** (`storagetest.runImportedWriteOrder`): Result and artifact write stamps are relative to the source's controller epochs, which are not copied, so an import stores none and the target's first write under its own fence replaces an imported object whatever stamp the source held, while a writer bound to the source or holding a superseded fence cannot.
- **Export cursors always name a key** (`storagetest.memoryExport.ExportRecords`): A provider never issues an export cursor without a key: a page that returns no record returns no cursor, so the reference provider refuses an empty-key cursor as one it could not have issued.
- **Reference export provider never aliases caller buffers** (`storagetest.memoryExport`): storagetest.memoryExport copies record bodies on import and export, keeping the bytes it validated rather than the caller's buffer and giving each page its own copy, as a provider that copies records over the network does.
- **Grouped-write cases fail the naturally last part** (`storagetest.runGroupedWrites`): storagetest.runGroupedWrites makes the part a provider would naturally write last collide with a stored record, so a provider that writes a group in order without rolling back earlier parts leaves a visible part and fails.
- **A dataset belongs to its first installation** (`storagetest.runInstallations`): A dataset belongs to the installation whose controller first advanced it: a second installation pointed at the same dataset can neither advance nor write to it, and the first installation keeps writing; storagetest.runInstallations enforces this.
- **Maintenance harness declares refused reading writes** (`storagetest.MaintenanceHarness.RefusesReadingWrites`): storagetest.MaintenanceHarness.RefusesReadingWrites declares that a provider also refuses, while its dataset is migrating, catalog writes the suite observes through, such as IsLocked (which clears an expired lock); those cases are then compared during migration only through their catalog reads.
- **Migrating datasets refuse new writes but serve replays and reads** (`storagetest.WithMaintenance`): While a dataset is migrating every catalog write is refused with ErrNotReady and changes nothing, a replay of a committed operation and reads are still served, Describe reports DatasetMigrating and ResolveOperation records nothing new; once ready again the refused operation commits. storagetest.WithMaintenance checks this.
- **Migration read check uses the write watermark** (`storagetest.requireReadServed`): storagetest.requireReadServed checks that reads are served during migration with GetWriteWatermark because it is the one read every provider serves for both contracts, covering cases that have no read of their own.
- **Message budget fixtures count bytes** (`storagetest.runMessageBudget`): storagetest.runMessageBudget builds content from a two-byte rune so a provider that counts characters instead of bytes against MaxMessageContentBytes fails.
- **Message batches must fit one response including identifiers** (`storagetest.runMessageBudget`): storagetest.runMessageBudget sends two messages with huge identifiers that each fit one request but not together in one response, so a provider must also count identifier bytes when it cuts a batch.
- **Protocol cases follow storage-contracts numbering** (`storagetest.protocolRun`): storagetest.protocolRun drives only the store half of each Kubernetes control protocol, numbered (P3, P4, P5, P7) as in docs/development/storage-contracts.md; Kubernetes performs the other steps, which the cases name but do not run.
- **Protocol steps survive retries, reruns and delayed controllers** (`storagetest.runProtocols`): storagetest.runProtocols requires every store step of the outbox, Session cleanup, prompt result receipt and Gateway Task cleanup protocols to return the original outcome on retry, be recognized by its natural key or changed state when rerun as a new operation, and refuse without change a step a replaced controller issued after takeover.
- **Outbox claims have no natural key** (`storagetest.runOutboxProtocol`): An outbox projection claim is not recognized by a natural key: rerun as a new operation before its lease expires it finds nothing due, so a claim whose outcome stays unknown only delays the record until its lease expires.
- **Session cleanup intent fences the Session** (`storagetest.runSessionCleanupProtocol`): A pending Session cleanup intent blocks new work on the Session and fences its UID; after completion the UID stays fenced and the name of a Session with a Kubernetes identity stays reserved.
- **Transcript-only Sessions may be recreated after cleanup** (`storagetest.runTranscriptCleanupProtocol`): The exception to Session name reservation: a transcript-only Session, which has no Kubernetes identity, may be created again once its cleanup completed.
- **Harnesses receive the unwrapped provider** (`storagetest.harnessProvider`): storagetest.harnessProvider gives a durability or maintenance harness the provider its factory returned, not the suite's envelope wrapper, and rewrapHarnessProvider wraps any replacement provider the harness returns the same way.
- **Watermark order is Value, not AdvancedAt** (`storagev1.WriteWatermark.AdvancedAt`): storagev1.WriteWatermark.AdvancedAt is the provider's wall clock and may step back between advances; only Value carries the order, so callers and tests must never order watermarks by AdvancedAt.

### `pkg/storage/v1/wire`

- **Storage wire blob framing** (`wire (blob framing)`): A streaming storage RPC carries one blob field in the direction it streams: the first message carries every other field and at most MaxChunkBytes of the blob, and each later message carries only the next non-empty part of the blob in the same field. The blob's total size and SHA-256 digest travel as the HeaderBlobSize and HeaderBlobSHA256 headers so the receiver can refuse an oversized blob before reading it and verify the reassembled bytes before using them.
- **Reassembled blobs never create missing parent records** (`wire.restoreBlob`): wire.restoreBlob stores a non-empty reassembled blob only into parent messages the first stream message already carried and fails otherwise; it never creates a record the sender left out, so framing cannot change the meaning of the request.
- **Blob reassembly never reads past the declared size** (`wire.reassemble`): wire.reassemble never reads more than the size the stream declared in HeaderBlobSize, and its callers check that declared size against their blob limit before calling it, so an oversized stream is refused before its bytes are buffered.
- **Blob buffers grow with received parts** (`wire.reassemble`): wire.reassemble caps its initial buffer at four chunks and grows it as parts arrive instead of preallocating the declared size, so a stream that declares a large blob and then stalls holds only the bytes it has actually sent.
- **Both wire sides check strings for valid UTF-8** (`wire.firstInvalidString`): wire.firstInvalidString finds the first string that is not valid UTF-8 because protobuf refuses to encode such a string; the client checks a request before sending it and the server checks a response before answering, so the failure is reported as a clear storage error naming the field instead of an opaque marshalling failure.
- **Storage client connections never retry writes themselves** (`wire.DialOptions`): wire.DialOptions installs the send-evidence stats handler and configures no gRPC retries (grpc-go keeps only transparent retries of attempts the server never processed), no proxy, keepalive, and the message size limits. A connection built from these options directly may also carry caller interceptors, so on it every transport failure of a write is reported as an unknown outcome rather than not sent.
- **A bound storage client refuses other datasets' responses** (`wire.ClientConfig.Dataset`): wire.ClientConfig.Dataset names the dataset every call except Describe and HealthCheck carries in its request header; a client without one may call only those two to learn the dataset. A bound client refuses any other call's response that does not come from its dataset, while Describe reports whichever dataset the server serves, as it does in process, and the caller compares its DatasetID.
- **The client uses only RPCs and fields the server's revision has** (`wire.ClientConfig.ServerRevision`): wire.ClientConfig.ServerRevision is the server's protocol revision from its Describe; the client calls an RPC or sets a request field only when that revision is at least the one that introduced it, and zero means the library's own ProtocolRevision.
- **Send evidence is trusted only on Dial connections** (`wire.Client`): wire.Client keeps the underlying *grpc.ClientConn for its main and bulk connections only when the caller passed a connection from Dial directly, and trusts send evidence only on such a connection; on any wrapped connection a write's transport failure is an unknown outcome.
- **Dial accepts no extra gRPC options** (`wire.DialConfig`): wire.DialConfig deliberately takes no other gRPC dial options, so no caller interceptor can sit between a Client and grpc-go and send a call where its send evidence cannot see it; otherwise a write reported as not sent might have been sent.
- **Storage connections require caller-configured transport security** (`wire.DialConfig.TransportCredentials`): wire.DialConfig.TransportCredentials are required and Dial refuses a config without them, but Dial does not inspect them, so the caller is responsible for configuring TLS 1.3.
- **Dial marks every call as covered by send evidence** (`wire.Dial`): wire.Dial's only interceptors mark each call on the connection as covered by send evidence, so a write that sent nothing, including one that failed before any attempt, is reported as not sent (ErrUnavailable) instead of an unknown outcome.
- **Only Dial connections can prove a write was never sent** (`wire.NewClient`): wire.NewClient can tell a request that was never sent from one that may have been only when conn, and config.Bulk for streaming RPCs, is a connection from Dial passed directly rather than wrapped; over any other connection a write's transport failure is reported as ErrOutcomeUnknown.
- **Calls are checked before anything is sent** (`wire.Client.prepare`): wire.Client.prepare sends nothing when a request is invalid, larger than the limit, or names an RPC the server's revision lacks. A write carries the WriteEnvelope from its context, a read or administrative call never carries one, and any call carries the TaskDataFence from its context.
- **A call with a done context is reported as not sent** (`wire.Client.prepare`): wire.Client.prepare reports a call whose context is already done as ErrUnavailable (not sent) because gRPC starts no attempt for it, so the caller may safely retry instead of resolving an unknown outcome.
- **Write envelopes must name the bound dataset** (`wire.Client.prepare`): wire.Client.prepare refuses, before sending, a write whose WriteEnvelope names a dataset other than the bound client's, because the server checks a write against the dataset the call names, so an envelope for another dataset could commit there while the response names the bound one.
- **Responses from another dataset are refused** (`wire.Client.checkServed`): wire.Client.checkServed refuses a response, or a storage error that answers for the server's dataset, that a bound client received from a dataset other than its own, which a server that checks the request's dataset header never sends. A write or administrative call that got such an answer reached a server serving another dataset, so its outcome is unknown.
- **Undecodable responses never look like refusals** (`wire.Client.responseError`): wire.Client.responseError reports a successful call whose response cannot be decoded as ErrOutcomeUnknown for a write or administrative call, since it may have committed, and as a plain error for a read. The decode error is kept as text only so the call never looks like a refused request with a typed storage error.
- **Newer request parameters are refused, not silently dropped** (`wire.Client.checkNewerParameter`): wire.Client.checkNewerParameter refuses before sending a call that sets a parameter newer than the server's protocol revision, because that server would silently ignore it; a zero value or empty list or map is not sent anyway and is allowed.
- **Out-of-range durations are refused, not saturated** (`wire.durationFromWire`): The wire duration decoder checks the seconds against the time.Duration range and returns a validation error instead of calling durationpb.AsDuration alone, because AsDuration silently saturates at the range limits and would store a different value than the sender wrote.
- **Servers decode JSON numbers exactly** (`wire.jsonFromWire`): wire.jsonFromWire decodes numbers as json.Number when exact is set, as a server does for a request, so the provider stores them and the request digest covers them exactly as the caller wrote them. A client decoding a response uses the types encoding/json produces, matching what an in-process provider that stores JSON text returns.
- **Text crossing a trust boundary is sanitized** (`wire.sanitizeText`): wire.sanitizeText drops invalid UTF-8 and control characters and truncates to a byte limit for any text that crosses a trust boundary into status, logs, or errors, so a peer cannot inject log lines or unbounded messages.
- **Storage wire transport contract** (`wire (package)`): Package wire carries orka.storage.v1 over gRPC: the Go contract in pkg/storage/v1 stays the source of semantics, the .proto files under pkg/storage/proto are the wire source of truth, and wiregen generates one RPC per contract method and one wire message per record, failing when any Go parameter, result, or record field (including json:"-" fields) has no wire counterpart. Writes carry their WriteEnvelope and every call its TaskDataFence as binary request headers; the server recomputes a write's request digest from the decoded request, refuses calls that name no dataset or another dataset (except Describe and HealthCheck) before the provider runs, and errors travel as google.rpc.ErrorInfo reasons. Per-call send evidence classifies transport failures: a request that never left the process is ErrUnavailable, a write or administrative call that may have been sent is ErrOutcomeUnknown, and blobs move in MaxChunkBytes parts that the server checks against the declared size and digest before calling the provider.
- **Only statuses in the storage ErrorInfo domain come from the server** (`wire.ErrorDomain`): wire.ErrorDomain (storage.orka.ai) is the google.rpc.ErrorInfo domain of every status the server library produces; a status without an ErrorInfo in this domain came from the gRPC library or a proxy, so the client classifies it as a transport failure rather than a contract error.
- **ErrorInfo reasons identify contract errors** (`wire (ErrorInfo reasons)`): The storage wire identifies a contract error by its ErrorInfo reason, not its gRPC code, because two contract errors can share a code; the code is advisory only.
- **Servers refuse fields they do not know** (`wire.ReasonUnsupportedField`): wire.ReasonUnsupportedField refuses a request that carries a field the server does not know, so an older server never silently ignores a newer precondition and commits a write the caller meant to guard.
- **Provider errors on writes are unknown outcomes** (`wire.ReasonProviderError`): wire.ReasonProviderError reports a provider error that is not a contract error, or a provider panic; a write that fails this way may have committed, so the client reports it as ErrOutcomeUnknown.
- **Infrastructure outcomes take precedence in error encoding** (`wire.outcomeReasons`): wire.outcomeReasons (ErrOutcomeUnknown, ErrUnavailable) are matched before every other contract error, so an error that also matches a family sentinel keeps its infrastructure outcome and a possibly committed write is never reported as a plain refusal.
- **Error sentinel order resolves multi-matches** (`wire.sentinelReasons`): wire.sentinelReasons order matters only for an error that matches several sentinels: a sentinel comes before one it wraps, such as ErrDatasetDetached or ErrDatasetMigrated before ErrNotReady, and family errors come before the generic errors they resemble, so the most specific reason crosses the wire.
- **Typed errors cross the wire without provider text** (`wire.contractStatus`): wire.contractStatus encodes a typed contract error such as TooLargeError from its sanitized typed fields only, never the provider's wrapping text, which could quote stored values.
- **Typed contract errors are matched in value and pointer form** (`wire.asTyped`): wire.asTyped finds a typed contract error in an error chain in both its value and pointer form, because the contract's typed errors have value receivers and a provider may return either; matching only one form would leak or misclassify the other.
- **Typed error messages match the in-process message** (`wire.typedMessage`): wire.typedMessage sends the message of the typed error itself so the client's errors.As finds the same message an in-process caller finds; a provider that wrapped the bare sentinel sends its error's text, and a pointer to the typed error is treated like the value so its wrapping text never crosses.
- **Provider error text never crosses the wire** (`wire.providerErrorStatus`): wire.providerErrorStatus reports an error that is not a contract error without its text, because that text can quote stored values; only a correlation ID crosses, tying the status to the server's log entry.
- **Some refusals carry no dataset** (`wire.refusedBeforeDataset`): wire.refusedBeforeDataset lists the reasons a server can send before its dataset check or without knowing its dataset (authentication, contract and request checks, admission, the dataset check itself, and a provider that cannot describe its dataset), so the client does not require a dataset header on them.
- **Dataset-scoped errors must come from the client's dataset** (`wire.answersForDataset`): wire.answersForDataset marks a storage status that answers for the server's dataset, so the client requires it to name the client's dataset as a successful response must; a NOT_FOUND or refused write from another dataset says nothing about the client's own.
- **An unimplemented RPC is incompatible, not unknown** (`wire.decodeError`): wire.decodeError maps a server that does not serve an RPC to ErrIncompatible rather than an unknown outcome, because nothing ran on the server.
- **Unknown error reasons are treated as provider errors** (`wire.decodeReason`): wire.decodeReason treats PROVIDER_ERROR and any reason the client does not know the same way: a write or administrative call becomes ErrOutcomeUnknown because it may have committed, so a newer server's reason never looks like a safe refusal.
- **Dataset migration refusals stay safe for older clients** (`wire.ReasonDatasetMigrated`): A write refused because its contract part migrated travels as the DATASET_MIGRATED reason and decodes to storagev1.ErrDatasetMigrated, which matches ErrNotReady and is a definite refusal. A client from before the reason existed decodes it as an unknown reason, which for a write is an unknown outcome, so no client ever reports the refused write as committed.
- **Send evidence errs toward unknown outcomes** (`wire.EvidenceHandler`): wire.EvidenceHandler records for each Client call whether any attempt reached grpc-go's stats.OutHeader, the point where request headers could leave the process; a call that never reached it sent nothing, and a header queued but not flushed counts as possibly sent so the classification can turn a harmless failure into an unknown outcome but never the reverse. The absence of that point is evidence only on a connection Dial built, which admits no caller interceptors; on any other connection every transport failure of a write is an unknown outcome.
- **Only covered calls can prove nothing was sent** (`wire.sendEvidence`): wire.sendEvidence.covered shows a call reached the only interceptor of a connection Dial built and that the connection is the Client's own, so nothing sits between the client and grpc-go and every attempt, transparent retries included, carries the record. A covered call without sent evidence therefore sent nothing, even one that never reached an attempt (a closed connection or a deadline spent in name resolution), while an uncovered call, such as one through a wrapper connection, is always possibly sent.
- **Evidence coverage is marked only on the Client's own Dial connection** (`wire.coverEvidence`): wire.coverEvidence is the only unary client interceptor of a connection Dial builds and marks a call as covered just before grpc-go starts it, and only when the call runs on that connection and the Client called it directly, so a call routed any other way is never treated as provably unsent.
- **Send evidence is pinned by grpc-go behavior tests** (`wire.EvidenceHandler`): The wire send-evidence tests deliberately exercise grpc-go itself with faults injected below the gRPC layer (refused dials, resets, raw HTTP/2 GOAWAY over plaintext TCP), because wire.EvidenceHandler's not-sent classification depends on grpc-go internals; they must keep running on every grpc-go upgrade rather than be removed as third-party tests.
- **List streams split unbounded lists into ordered parts** (`wire.splitList`): A server-streaming read whose response marks a repeated field with the list option splits that list across messages of at most MaxListPartBytes of encoded items, because a list the contract does not bound may not fit in one message; a single larger item travels alone. The header HeaderListCount declares the total item count, the first message carries every other response field plus the first part, and each later message carries only the next part with at least one item, in order, so the client rebuilds the list exactly.
- **Splitting a list shares fields and items** (`wire.splitList`): wire.splitList sets the first message's other fields from the response and appends the response's own items to each part instead of cloning them, so splitting a long list allocates only the parts. Do not replace this with proto.Clone or per-item copies; TestSplitListSharesTheItems enforces the allocation bound.
- **Streaming handlers rely on checkedStream for the duration limit** (`wire.checkedStream`): Streaming handlers such as Server.sendList and the blob upload and download paths send and receive through the call's checkedStream, which bounds every SendMsg and RecvMsg by the call's duration limit. They add no deadline of their own, and must keep using the stream they were given rather than an unwrapped one, or a stalled peer holds the slot forever.
- **List streams fail closed on the client** (`wire.Client.list`): wire.Client.list returns a list only when the whole stream succeeds and carries exactly the declared item count; a stream that ends with an error, ends short, carries more than declared or breaks framing fails the call, so a partial list is never returned. It stops reading as soon as the stream exceeds the declared count instead of buffering whatever else the server sends.
- **Check the served dataset only after the first message** (`wire.Client.list`): wire.Client.list reads the first message before calling checkServed, because a refused call carries its status instead of a response and has no serving-dataset headers. Checking the headers first would turn every refusal into a dataset mismatch instead of its real typed error.
- **Split allocation bound is 1.5 per item** (`wire.TestSplitListSharesTheItems`): wire.TestSplitListSharesTheItems allows fewer than 1.5 allocations per item because appending through protoreflect costs one allocation per item, while copying the items would cost at least one more each; the bound separates sharing from copying.
- **Raise the protocol revision for new RPCs or request fields** (`wire.ProtocolRevision`): wire.ProtocolRevision is the orka.storage.v1 wire revision; a release must raise it whenever it adds RPCs or request fields, because clients call an RPC or send a newer field only to servers of at least the revision that introduced it.
- **Dataset travels in a binary header on every non-Dataset call** (`wire.HeaderDataset`): The contract and revision headers travel on every request and response, and every call except the Dataset service's Describe and HealthCheck, which a client uses to learn its dataset, must name the dataset it expects in wire.HeaderDataset. The header is binary (-bin) because a dataset ID may hold any UTF-8 text and gRPC text headers carry only printable ASCII.
- **Blob size and digest header format** (`wire.HeaderBlobSize`): wire.HeaderBlobSize and wire.HeaderBlobSHA256 describe the whole blob a streaming RPC carries, as decimal bytes and lowercase hex SHA-256; an upload sends them as request headers and a download as response headers, so the receiver can refuse an oversized blob before reading it. Separately built adapters depend on this exact format.
- **Blob chunks are capped at 1 MiB for fair flow control** (`wire.MaxChunkBytes`): wire.MaxChunkBytes caps the blob bytes one streaming message carries at 1 MiB so a large transfer moves in small messages that share HTTP/2 flow control fairly with other calls, instead of one message monopolizing the window.
- **Default blob limit covers the contract's largest values** (`wire.DefaultMaxBlobBytes`): wire.DefaultMaxBlobBytes (64 MiB) is the blob limit a client or server uses unless configured otherwise, chosen to cover the contract's largest values such as MaxResultBytes and MaxArtifactBytes; lowering it below those would refuse contract-conforming data.
- **Only reads are safe to report as plain transport failures** (`wire.method.mayChange`): wire.method.mayChange treats every write and administrative call as possibly state-changing, so a transport failure after its request may have been sent is reported as ErrOutcomeUnknown rather than a retryable failure; only reads never change state.
- **Overloaded calls are refused before any work** (`wire.Limits.MaxConcurrent`): wire.Limits.MaxConcurrent caps the calls of each call class a Server runs at once; a call over its class's limit is refused with OVERLOADED before the provider runs and before an upload's blob is read, so shedding costs no provider work or blob buffering.
- **Duration limit covers the whole call** (`wire.Limits.MaxDuration`): wire.Limits.MaxDuration caps the whole call of a class: describing the providers for its dataset check, every message a streaming call receives or sends, and the provider's work; a shorter caller deadline still applies. An upload or download that does not finish in time ends as UNAVAILABLE, except that a write whose response cannot be sent in time after the provider ran is OUTCOME_UNKNOWN, since it may have committed.
- **State and artifacts providers of one server share a dataset** (`wire.ServerConfig.Artifacts`): A wire.Server needs at least one of ServerConfig.State and ServerConfig.Artifacts; when both are set they must serve the same dataset and State answers Describe for both, and every RPC of a contract part the server does not serve answers UNIMPLEMENTED.
- **Storage authentication runs in the gRPC tap and fails closed** (`wire.ServerConfig.Authenticator`): wire.ServerConfig.Authenticator authenticates every call in the gRPC transport tap, before its request is decoded and whatever method it names. A call served through a transport that runs no tap, such as grpc.Server.ServeHTTP, is refused as unauthenticated rather than served unauthenticated; without an Authenticator the library authenticates nothing.
- **Server logs never carry request or response messages** (`wire.ServerConfig.Logger`): wire.ServerConfig.Logger receives one entry per call and the text of provider errors the server does not forward to clients, which can quote stored values, so it must be treated as sensitive; it never receives request or response messages.
- **Server blob limit may not fall below contract limits** (`wire.ServerConfig.MaxBlobBytes`): wire.NewServer refuses a ServerConfig.MaxBlobBytes below storagev1.MaxResultBytes with a state provider or below storagev1.MaxArtifactBytes with an artifacts provider, because those providers must store values of at least those sizes and a smaller wire cap would refuse contract-conforming data. An artifact is also capped at the artifacts provider's own MaxArtifactBytes.
- **Only the newest description changes the serving dataset** (`wire.Server.publish`): wire.Server numbers descriptions as they start (describeSeq) and publish lets only a description newer than the last published one change the serving dataset, under publishMu, so a slow description can never restore a dataset that a newer one replaced or dropped, and a call is not checked against a superseded description.
- **Storage gRPC servers serve only storage services** (`wire.Server.ServerOptions`): wire.Server.ServerOptions supplies tap authentication before decoding, the protocol interceptors, message size limits, keepalive enforcement that admits the client's pings, and a maximum connection age so long-lived connections spread across adapter replicas; callers add TLS. A gRPC server built with them authenticates every call and refuses any method the storage protocol does not define, so no handler runs without the protocol checks.
- **Adapters refresh descriptions at startup and periodically** (`wire.Server.Refresh`): wire.Server describes its providers before the first call that needs a dataset and again for every read or administrative call that names one, but writes use the last description, so an adapter must call Server.Refresh at startup and periodically to notice a dataset change, such as a database replaced under it, before the next write.
- **Describe reports only contract parts the server registers** (`wire.Server.describe`): wire.Server.describe reports only the contract parts that its providers report and that it actually registers, plus the artifact limit it enforces, so a client never accepts an endpoint whose methods are unimplemented.
- **Inconsistent descriptions drop the serving dataset** (`wire.Server.publish`): wire.Server.publish clears the serving dataset after a description that names no single dataset, so no call is admitted until a consistent description succeeds, while a description that merely fails, such as a timeout, publishes nothing and leaves the last dataset in place.
- **Tap authentication does not depend on the method table** (`wire.Server.tap`): wire.Server.tap authenticates every call before its request is read without recognizing the method, so a path the method table does not name is never served unauthenticated, and marks the context so the interceptors can verify the tap ran.
- **Authentication errors are never logged** (`wire.Server.tap`): wire.Server.tap logs a failed authentication without the authenticator's error, because the authenticator saw credential-bearing metadata and its error may quote it.
- **Protocol refusals happen before the provider runs** (`wire.Server.intercept`): wire.Server.intercept applies every protocol check before the provider sees a unary call, so any refusal it returns means nothing was committed; checks that run after the provider must not reuse refusal reasons.
- **Every authenticated response names contract, revision and dataset** (`wire.Server.intercept`): wire.Server.intercept answers every authenticated call, including a refused one, with the contract, revision and, once known, the serving dataset; an admitted call answers with the dataset it was checked against, or the newly described one for Describe, so clients can tell which dataset an answer belongs to.
- **Oversized responses are reported as provider errors** (`wire.Server.intercept`): wire.Server.intercept reports a response over MaxMessageBytes as PROVIDER_ERROR, because gRPC would otherwise refuse it with a bare status the client cannot tell from a transport failure, making a read look safe to retry. The contract's message budgets keep conforming providers under the limit.
- **checkedStream bounds and revalidates every streaming call** (`wire.checkedStream`): wire.checkedStream gives a streaming handler the call's checked context and bounds every receive and send by it, including the download request receive gRPC makes before the handler runs; it refuses any request message with an unknown field and revalidates the serving dataset right after receiving the request, so a dataset switch while waiting for the request cannot serve data under the old dataset header.
- **A write response sent late is an unknown outcome** (`wire.checkedStream.SendMsg`): wire.checkedStream.SendMsg reports a write whose response could not be sent within the time limit as OUTCOME_UNKNOWN, because a write sends its response only after the provider ran and may already have committed.
- **Dataset checks run inside admission and the duration cap** (`wire.Server.admit`): wire.Server.admit checks the contract header, admits the call within its class's concurrency limit, caps its duration, then checks its dataset and decodes its envelope and Task data fence; the dataset check runs inside the admission and the cap so a slow provider description holds a slot and ends at the cap instead of queueing calls without limit. admit owns the admission until it returns successfully, so a refused call or a provider that panics while described has already released it.
- **Revision 1 clients get UNAVAILABLE instead of OVERLOADED** (`wire.Server.admit`): wire.Server.admit answers an over-limit call from a client below overloadedSince with UNAVAILABLE instead of OVERLOADED, because a revision 1 client does not know OVERLOADED and would take the refusal of a write as an unknown outcome.
- **admit frees a copy of its release function** (`wire.Server.admit`): wire.Server.admit releases the admission through a copy (free) on refusal or panic, because returning a refusal clears the named release result before deferred calls run; using release directly in the defer would leak the slot.
- **Calls whose admission outlasts the limit start no work** (`wire.Server.admit`): wire.Server.admit refuses as UNAVAILABLE a call whose time limit passed during admission, since a provider that ignores its context can describe the dataset after the limit; the call then starts no provider work.
- **Servers serve every older protocol revision** (`wire.checkContract`): wire.checkContract refuses only calls missing the orka.storage.v1 contract header or a protocol revision; a server serves every older revision, so revision bumps must stay backward compatible.
- **Write envelopes must name the call's dataset** (`wire.withEnvelope`): wire.withEnvelope refuses an envelope on a read or administrative call and refuses a write envelope for any dataset other than the one the call names, because the provider could commit it there while the response names the call's dataset. An envelope naming no dataset is passed through for the provider to refuse as it does in process.
- **Servers recompute write request digests** (`wire.Server.checkDigest`): wire.Server.checkDigest refuses, before the provider runs, a write whose envelope's RequestDigest differs from the digest of the request the server decoded, so an operation ID can never be bound to a request other than the one its client digested.
- **Reads redescribe; writes use the last description** (`wire.Server.servingDataset`): wire.Server.servingDataset describes the providers again before every read or administrative call that names a dataset, so a provider whose dataset changed never answers for the old one; a write is checked against the last description because the provider rechecks its envelope's dataset, and Describe or HealthCheck naming none needs no dataset. A switch while the provider runs the call is not detected, an open gap in the provider contract.
- **Unexpected Describe errors read as unavailable** (`wire.Server.checkDataset`): wire.Server.checkDataset forwards a failed Describe only as UNAVAILABLE, UNAUTHENTICATED or INCOMPATIBLE, which clients accept from a server that has not checked its dataset; any other error, such as a cold replica's ErrNotReady or providers disagreeing on their dataset, is reported as UNAVAILABLE because it would otherwise read as an answer for another dataset.
- **Responses name the dataset the call was admitted against** (`wire.Server.responseHeader`): wire.Server.responseHeader names the dataset an admitted call was checked against, falling back to the serving dataset only for unadmitted calls, so a write's response names the dataset it ran against even when a newer description replaced or cleared the serving dataset after admission.
- **Uploads reach the provider only when complete and verified** (`wire.Server.receiveUpload`): wire.Server.receiveUpload calls the provider only after the client ends the stream and the reassembled blob matches its declared size and SHA-256 digest, so a refused, truncated or corrupted upload never reaches the provider.
- **Abandon blocked stream operations when the call ends** (`wire.withinCall`): wire.withinCall runs a blocking stream operation in a goroutine and returns when the call's context ends, because gRPC ends a stream only when its handler returns, so this is the only way a duration-capped call stops waiting for a stalled peer. The abandoned operation fails once the handler returns; callers must not touch its message afterwards.
- **Streams timing out before the provider are unavailable** (`wire.streamError`): wire.streamError reports a stream that ran out of time before the provider ran as UNAVAILABLE rather than an unknown outcome, because nothing was committed.
- **Unrecognized provider errors cross without their text** (`wire.Server.providerError`): wire.Server.providerError forwards a contract error's reason but logs any other provider error with a correlation ID and reports it as PROVIDER_ERROR without its text, because the text can quote stored values.
- **Encode failures never claim nothing happened** (`wire.Server.encodeError`): wire.Server.encodeError reports a provider result the server cannot encode as a provider error, never with a contract reason that tells the client nothing happened, because the call may already have committed.
- **Provider panics are logged without their value** (`wire.Server.panicked`): wire.Server.panicked reports a provider panic as a provider error with a correlation ID and never logs the raw panic value, which may contain credential-like strings.
- **Servers refuse unknown request fields** (`wire.hasUnknownFields`): The storage server refuses any request, or any message of a request stream, carrying a field it does not know anywhere in its message tree (UNSUPPORTED_FIELD, via wire.hasUnknownFields), so an older server never silently ignores a newer precondition a client sent.
- **Providers, not the server library, refuse writes without envelopes** (`wire.withEnvelope`): The wire server library forwards a write that carries no envelope to the provider unchanged; refusing it is the provider's job, which the conformance suite's missing-envelopes family checks over the wire. Do not add a server-side refusal that would hide a provider that fails to enforce it.
- **Plaintext test loopback only for below-TLS fault injection** (`wire.serveInsecure`): The wire tests' serveInsecure helper serves without TLS and is reserved for tests that inject transport faults below TLS; every other test uses wiretest, which always uses TLS so the protocol is exercised as deployed.
- **Wire integers outside int range are refused** (`wire.intFromWire`): wire.intFromWire refuses a protobuf int64 outside the architecture's int range, so a 32-bit server never silently truncates a 64-bit client's limit or count.
- **Blank raw JSON is an absent field** (`wire.rawJSONToWire`): wire.rawJSONToWire carries json.RawMessage bytes unchanged, but empty or whitespace-only bytes are an absent field, because they are zero in a request digest and no content to a provider.
- **The dataset's owner answers Ownership** (`wire.datasetProvider.owner`): Operation receipts, the controller epoch, the dataset binding and the write watermark are one record per dataset, so a server serving both contract parts answers Ownership from its state provider, as it answers Describe, and an artifacts-only server asks its artifacts provider.
- **Ownership is refused when providers disagree on the dataset** (`wire.datasetProvider.owner`): When the artifacts provider reports a different dataset from the state provider, even one that changed since the last description, an Ownership call is refused before any provider runs, so an artifacts write is never resolved, fenced or bound against the state provider's records.

### `pkg/storage/v1/wire/adapterkit`

- **Storage adapters serve TLS 1.3 with authenticated clients** (`adapterkit (package)`): adapterkit.Serve wraps the wire server with what a separately deployed storage adapter needs: TLS 1.3 with a serving certificate reloaded from disk, client authentication by bearer token, mTLS client certificate or both, per-class concurrency limits that shed load with OVERLOADED, liveness/readiness/metrics on a separate plain HTTP port, and a graceful stop; providers use SettleContext to finish a commit already sent after the caller's context ends.
- **Default adapter limits shed only abnormal load** (`adapterkit.DefaultLimits`): adapterkit.DefaultLimits admit more calls per class than an Orka controller sends by default, so shedding happens only under abnormal load, and they keep control calls such as health checks apart from storage traffic.
- **CallStream is not limited by the adapter** (`adapterkit.limitedClasses`): adapterkit.limitedClasses holds only the classes the method catalog assigns; a poller chooses CallStream itself and the server cannot tell those calls apart, so CallStream gets no per-class limit.
- **One adapter serves one dataset** (`adapterkit.Config.Artifacts`): adapterkit.Config requires at least one of State and Artifacts, and when both are set they must serve the same dataset.
- **Probe port is plain HTTP without credentials** (`adapterkit.Config.ProbeAddress`): adapterkit serves /healthz, /readyz and /metrics on a separate plain HTTP port that carries no stored data and needs no credentials, so kubelet probes can reach it; it must never expose request or response content.
- **Bearer tokens rotate through a reloaded directory** (`adapterkit.Config.BearerTokenDir`): adapterkit.Config.BearerTokenDir accepts any token in a regular file whose name starts with "token" (whitespace trimmed) and reloads the set when files change, so a token rotates by adding a second Secret key, moving clients and removing the first, without a restart.
- **mTLS clients need an allowed SAN** (`adapterkit.Config.ClientCAFile`): With adapterkit.Config.ClientCAFile a client certificate must chain to the reloaded CA bundle, which may hold old and new CAs during rotation, and carry one of AllowedClientURIs or AllowedClientDNSNames as a subject alternative name.
- **Adapter authentication is mandatory** (`adapterkit.Config`): adapterkit.Config must enable at least one of bearer tokens and mTLS; when both are configured a call must pass both.
- **Shutdown timeout should exceed settle timeout** (`adapterkit.Config.ShutdownTimeout`): When adapterkit.Config.ShutdownTimeout passes, Serve closes every remaining connection and returns without waiting for running handlers, including one settling a commit with SettleContext, so it should be set above SettleTimeout to let such commits settle.
- **Adapter logs carry no content or credentials** (`adapterkit.Config.Logger`): adapterkit never passes request or response content, credential values, provider error text or panic values to its logger, because provider errors can carry backend details such as connection-string credentials; readiness failures log only a fixed reason from readinessReason.
- **Serve owns the listeners it is given** (`adapterkit.Serve`): adapterkit.Serve owns and closes the listeners in its Config, including when it fails before serving.
- **Serve does not wait for grpcServer.Serve** (`adapterkit.Serve`): adapterkit.Serve does not wait for grpcServer.Serve to return, because it returns only once a stop completes and a handler still settling a commit can delay that past the grace period.
- **Probe server bounds reads and idle connections** (`adapterkit.probeReadTimeout`): adapterkit's probe server sets probeReadTimeout to bound a whole request, including a body discarded after a handler that never reads it, and probeIdleTimeout to close idle keep-alive connections, so a stalled or idle peer never holds a probe connection open.
- **Forced stop closes tracked connections itself** (`adapterkit.stopGracefully`): adapterkit.stopGracefully lets calls finish for up to the timeout, then closes every connection the trackedListener accepted, including ones still in their TLS handshake, and returns without waiting for handlers; grpc GracefulStop holds the server lock while waiting for handlers so even Stop can block behind it, and Stop waits for in-handshake connections before closing any.
- **Forced stop closes tracked connections itself** (`adapterkit.trackedListener`): adapterkit.stopGracefully lets calls finish for up to the timeout, then closes every connection the trackedListener accepted, including ones still in their TLS handshake, and returns without waiting for handlers; grpc GracefulStop holds the server lock while waiting for handlers so even Stop can block behind it, and Stop waits for in-handshake connections before closing any.
- **Draining adapters never report ready again** (`adapterkit.readiness.mu`): adapterkit.readiness.mu orders each check's result against drain, so a readiness check that finishes after the adapter starts stopping never reports ready again.
- **Adapter logs carry no content or credentials** (`adapterkit.readinessReason`): adapterkit never passes request or response content, credential values, provider error text or panic values to its logger, because provider errors can carry backend details such as connection-string credentials; readiness failures log only a fixed reason from readinessReason.
- **Provider panics make the adapter not ready** (`adapterkit.readiness.probe`): adapterkit.readiness.probe recovers a provider panic during Describe or HealthCheck and reports not ready instead of ending the process; the next check runs as usual and can make it ready again.
- **Failed credential reloads keep the last good set** (`adapterkit.Config.BearerTokenDir`): A token file adapterkit cannot inspect is a failed reload, not a removed token, and a CA bundle with any malformed entry never replaces the trusted CAs: the adapter keeps its last good credentials and reports the failure, so a broken rotation never drops access or trust.
- **Failed credential reloads keep the last good set** (`adapterkit.Config.ClientCAFile`): A token file adapterkit cannot inspect is a failed reload, not a removed token, and a CA bundle with any malformed entry never replaces the trusted CAs: the adapter keeps its last good credentials and reports the failure, so a broken rotation never drops access or trust.
- **Client certificates are verified on every call** (`adapterkit.Config.ClientCAFile`): Because a connection outlives its handshake, adapterkit verifies the client certificate again on every call, so removing its CA from the bundle or the certificate expiring stops an already open connection.
- **Tests rewrite the CA bundle only after startup** (`adapterkit_test.TestServeReverifiesClientCertificatesOnEveryCall`): TestServeReverifiesClientCertificatesOnEveryCall waits for the adapter to be ready before rewriting the CA bundle, because a rewrite before the startup load could hand it a partly written file.
- **Adapter credential reload keeps the last good value** (`adapterkit.credentialStore`): adapterkit.credentialStore reloads the serving certificate, bearer tokens, and client CAs from their files when they change; a file that no longer parses keeps the previous value and is reported through metrics, so a broken rotation never drops working credentials. The exception is a bearer token directory with no tokens left, which accepts no token so removed credentials stop authenticating.
- **Missing credentials at startup fail Serve** (`adapterkit.loadCredentials`): adapterkit.loadCredentials fails Serve when any configured credential is missing or invalid at startup; the keep-the-last-good-value rule applies only to later reloads, so an adapter never starts serving without a valid certificate, token set, or client CA pool.
- **Credential fingerprints are recorded only after use** (`adapterkit.credentialStore.changed`): adapterkit.credentialStore.changed only compares a file's fingerprint and records nothing; credentialStore.loaded records it once the parsed credential is stored. Recording in changed would mark a file that failed to parse as loaded, so it would never be retried until its content changed again.
- **A missing bearer token directory revokes every token** (`adapterkit.credentialStore.reloadTokens`): adapterkit.credentialStore.reloadTokens treats a missing bearer token directory as no tokens mounted and replaces the cached set with an empty one, so removed credentials stop authenticating instead of the last loaded tokens staying valid.
- **Unreadable token files keep the last good token set** (`adapterkit.credentialStore.reloadTokens`): adapterkit.credentialStore.reloadTokens returns an error and keeps the previous token set when a token file exists but cannot be inspected or read; only a file that is truly absent counts as removed, so a transient filesystem error does not refuse every call.
- **Only regular token files are read** (`adapterkit.credentialStore.reloadTokens`): adapterkit.credentialStore.reloadTokens reads only token* entries that stat to regular files, because a mounted Kubernetes Secret links each key to a regular file while the projection also creates its own directories that must be skipped.
- **Client CA bundles are all-or-nothing** (`adapterkit.parseCABundle`): adapterkit.parseCABundle refuses the whole PEM bundle when any block is malformed or not a certificate, unlike x509.CertPool.AppendCertsFromPEM which keeps whatever parses, so a rotation bundle with one broken entry never replaces a working pool and silently drops a CA still in use.
- **CA bundle parsing counts every BEGIN marker** (`adapterkit.parseCABundle`): adapterkit.parseCABundle compares the number of -----BEGIN markers with the number of parsed certificates because pem.Decode silently skips a block it cannot decode; without the count a corrupted block would vanish instead of failing the bundle.
- **Adapter TLS reads current credentials per handshake** (`adapterkit.credentialStore.serverTLS`): adapterkit.credentialStore.serverTLS allows only TLS 1.3 and loads the current serving certificate and, with mTLS, the current client CA pool on every handshake through GetCertificate and GetConfigForClient, so credential rotation takes effect without restarting the adapter.
- **Every configured adapter authentication method must pass** (`adapterkit.credentialStore.Authenticate`): adapterkit.credentialStore.Authenticate requires every configured method (bearer token and client certificate) to pass for each call, and it never logs or returns a credential value in errors.
- **Client certificates are re-verified on every call** (`adapterkit.credentialStore.authenticateCertificate`): adapterkit.credentialStore.authenticateCertificate verifies the client leaf again on every call against the current client CA bundle and the current time, because the TLS handshake only checked the CAs of its time and a connection outlives it; a removed CA or an expired certificate must stop a connection that is already open.
- **Adapter metric labels take only bounded values** (`adapterkit.metrics`): adapterkit.metrics labels only bounded values: protocol method names, gRPC codes, ErrorInfo reasons, and credential names. Never add a label from caller-controlled data such as dataset names, keys, or error messages, because that would make metric cardinality unbounded.
- **Metrics are rendered to a string before writing** (`adapterkit.metrics.exposition`): adapterkit.metrics.exposition renders the metrics into a string while holding the lock and the probe handler writes the response after the lock is released, so a slow or stalled scrape never delays the storage calls that record metrics.
- **Providers finish sent commits after caller cancellation** (`adapterkit.SettleContext`): adapterkit.SettleContext returns a context that keeps the call's values but not its cancellation, bounded by Config.SettleTimeout (DefaultSettleTimeout outside Serve). A provider uses it only for a commit it has already sent and the work that settles it, because a cancelled client reports an unknown outcome and later retries or resolves the same operation, which needs that commit and its receipt to settle one way or the other; it must never be used to start new work for a caller that has gone.

### `pkg/storage/v1/wire/internal/wiregen`

- **The storage contract imports only the standard library** (`wiregen.loadContract`): wiregen.loadContract type-checks pkg/storage/v1 with the go/types source importer and no module loader, which works only because the contract imports nothing but the standard library; adding a non-standard import to the contract requires changing the generator's loader.
- **wiregen reads the protocol revision from source** (`wiregen.loadProtocolRevision`): wiregen.loadProtocolRevision parses the wire package's ProtocolRevision constant from source instead of importing the package, so the generator never compiles the package it writes and still runs when generated files are stale or broken.
- **wiregen fails on any contract and wire mismatch** (`wiregen (command)`): Command wiregen reads the Go contract with go/types and the wire descriptors from storagepb and writes zz_generated.mapping.go, zz_generated.service.go, and wiretest/zz_generated.overlay.go. It fails, writing nothing, when a contract method has no RPC or an RPC no method, when an RPC's kind or contract part differs from the method catalog, when any parameter, result, or record field (including json:"-" fields) has no wire counterpart or the reverse, when a type pair is not in the mapping table, or when revision annotations are inconsistent; the wire deliberately has no ignore-this-field option.
- **Wire parameters map by name, results by position** (`wiregen.builder.buildMethod`): wiregen.builder.buildMethod maps Go parameters to request fields by name, so renaming a parameter fails generation until the wire changes and two swapped string parameters cannot go unnoticed; results map by position to response fields in field-number order.
- **RPC kinds must match the method catalog** (`wiregen.builder.checkCatalog`): wiregen.builder.checkCatalog requires an RPC's wire kind annotation and contract part to equal the storage method catalog's, because the kind decides whether a call carries a write envelope and how its transport failure is classified; it takes the call class from the catalog and requires any RPC that streams a blob to be a bulk call.
- **A framed message has exactly one blob location** (`wiregen.blobPaths`): wiregen.blobPaths accepts as a blob only a singular bytes field outside any oneof, reached through singular message fields, so every framed message names exactly one place for its blob and the runtime framing in wire.blobPathOf can rely on a single path.
- **Write requests cannot gain revision-gated fields** (`wiregen.builder.bindParams`): wiregen.builder.bindParams refuses a since revision annotation on any request field of a write, because a write's request digest covers every parameter and an older server that does not take the field could not recompute the digest; only reads and administrative calls can gain newer request fields.
- **Decoded byte fields are never nil** (`wiregen.fromWire`): The generated wire decoding (wiregen.fromWire) turns a nil bytes value into an empty slice because protobuf decodes empty bytes as nil, so a present record keeps the empty value a provider may require, exactly as it would receive in process.
- **List streams stay on their call class's connection** (`wiregen.renderService`): The generated client sends a list-streaming RPC on the connection of the call's own class rather than the bulk connection, because a list is metadata, not a blob; only blob streams move to the bulk connection.
- **Named types match aliases too** (`wiregen.isNamed`): wiregen.isNamed matches a type path.name whether it is declared as a defined type or an alias, because encoding/json.RawMessage is an alias in some Go releases.

### `pkg/storage/v1/wire/wiretest`

- **wiretest mirrors a deployed adapter connection** (`wiretest (package)`): Package wiretest serves storage providers over an in-memory gRPC loopback with TLS 1.3 from a test CA, bearer authentication, the server library and the generated client, sending streaming calls on a second bulk connection as a remote client does. It deliberately has no plaintext mode, so conformance over the wire always exercises the deployed transport.
- **wiretest overlays route only wire families through gRPC** (`wiretest.State`): wiretest.State and wiretest.Artifacts return providers whose families with wire RPCs go through the generated client and server, while every other family is served by the provider in process until it gains its RPCs, so suite results over the wire cover only the families listed by Methods and ArtifactsMethods.
- **Release blocked provider calls before wiretest cleanup** (`wiretest.Dial`): wiretest.Dial and wiretest.Serve stop the server when the test ends and stopping waits for every provider call still running, so a test whose provider blocks a call must release it first, either in the test itself or in a cleanup registered after Dial or Serve, which runs before theirs; otherwise the test hangs.
- **Loopback stop waits for running handlers** (`wiretest.serve`): wiretest.serve builds its gRPC server with grpc.WaitForHandlers(true) so Stop waits for running handlers, and a provider method a cancelled call left running has returned before the test closes the provider.
- **Test PKI is created once per process** (`wiretest.material`): wiretest.material holds a process-wide test certificate authority, server certificate and bearer token, created once so each per-case loopback stays cheap instead of generating keys for every test.

## Consequences

- These decisions are still in force. A change that breaks one must supersede that
  entry in a new ADR.
- Entries were recovered from comments in bulk, and a few original comments were stale or
  overstated. If an entry disagrees with the code, treat that as a bug in the entry: confirm the
  intended behavior, then fix the code or supersede the entry in a new ADR.
- Symbols get renamed. When an entry's symbol no longer exists, search for the behavior it
  describes.
- Entries recovered from test comments record why a test is shaped the way it is, so the test
  stays honest. A later ADR may supersede them once the tests explain themselves.
