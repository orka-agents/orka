# 68. Decisions recovered from code comments: the other platform packages

Date: 2026-11-22

## Status

Accepted. This record is a catalog produced by the comment ban in
[ADR 0062](0062-code-carries-no-comments.md). Each entry was a code comment that recorded a
non-obvious decision in the remaining `internal/` packages and the `workers/` outside ACP. The comment was deleted, and the decision now lives here.

## Context

Round 2 of the comment cleanup classified every comment left after
[ADR 0063](0063-code-comment-decisions-round-1.md). In the remaining `internal/` packages and the `workers/` outside ACP it found 780 distinct decisions
that a reader of the code alone could get wrong. Comments that stated the same rule in several
places are merged into one entry. Where an earlier ADR already records a decision, the entry
links it.

## Decision

Each entry names the symbols it governs, so `rg '<symbol>'` finds the code. Entries are
grouped by package and ordered by source position as of round 2.

### `internal/admission`

- **AgentHost admission trusts only the request's UserInfo** (`admission.AgentHostValidator`): admission.AgentHostValidator authorizes an AgentHost's template and token Secret against AdmissionRequest.UserInfo, never against identity fields in the submitted object, so a caller cannot claim someone else's permissions by writing them into the spec. See [ADR 0035](0035-agent-hosts.md).
- **AgentHost selections are checked only when they can change** (`admission.AgentHostValidator.Handle`): admission.AgentHostValidator.Handle checks githubTokenFrom only on creation because the field is immutable, so updates never re-run the Connection host check. See [ADR 0036](0036-agent-hosts-from-connections.md).
- **AgentHost updates that select nothing new skip authorization** (`admission.AgentHostValidator.Handle`): templateRef is immutable, so admission.AgentHostValidator.Handle checks template use only on creation and checks the token Secret only when it changes. Updates that change no selection, such as the controller removing its finalizer, must still pass after the original caller's permission is revoked.
- **Naming an AgentHost token Secret requires read access** (`admission.AgentHostValidator.Handle`): The AgentHost controller copies the named GitHub token Secret into the host, so admission.AgentHostValidator.Handle requires the caller to be allowed to get that Secret; otherwise naming it would leak a Secret the caller cannot read.
- **Connection-fed AgentHosts are controller-only and skip template use** (`admission.AgentHostValidator.admitConnectionHost`): admission.AgentHostValidator.admitConnectionHost admits a Connection-fed AgentHost only from a controller identity and only with the template the Connection's provider names. The operator naming that template in the provider is the grant, so no template use check applies. See [ADR 0036](0036-agent-hosts-from-connections.md).
- **code_exec Jobs must set a seccomp profile explicitly** (`config/admission ai-worker identity protection policy`): The AI worker identity protection policy rejects code_exec Jobs with no seccompProfile, because an unset profile runs Unconfined on nodes without kubelet seccompDefault.
- **AI worker may manage only code_exec ServiceAccounts** (`config/admission ai-worker identity protection policy`): The AI worker identity protection policy lets the AI worker create or delete only code_exec's own marked ServiceAccounts, because replacing a platform ServiceAccount with one of the same name would inherit its RoleBindings. A platform account whose name happens to match the code_exec prefix stays protected.
- **Only the token controller writes controller token Secrets** (`config/admission controller_serviceaccount_protection policy`): The controller ServiceAccount protection policy lets only the token controller update an existing controller ServiceAccount token Secret, whatever the change, because the response to an update returns the token to the writer.
- **Running controller Pods keep their spec** (`config/admission controller_serviceaccount_protection policy`): The controller ServiceAccount protection policy freezes the spec of running controller Pods, because an image swap or an added ephemeral container would run other code with the controller's projected token.
- **Exec and attach into controller Pods are refused for everyone** (`config/admission controller_serviceaccount_protection policy`): The controller ServiceAccount protection policy refuses exec and attach into controller Pods for every user, because a command there could read the mounted controller token. Exec into other Pods in the namespace, or in other namespaces, is untouched.
- **Controller Pod matching tolerates truncated generated names** (`config/admission controller_serviceaccount_protection policy`): Generated Pod names keep only the first 58 characters of "<deployment>-<hash>-", so the controller ServiceAccount protection policy must still recognize controller Pods when a deployment name of 58 or more characters loses its trailing hyphen.
- **Manifest checks reject unknown API identities** (`admission.strictDecodeOrkaDocument`): admission.strictDecodeOrkaDocument skips only known Kubernetes and Kustomize kinds and rejects unknown apiVersion/kind pairs, so a misspelled Orka group in a shipped or documented manifest fails the test instead of silently bypassing strict decoding.
- **Core skips provider kinds instead of importing provider SDKs** (`admission.strictDecodeOrkaDocument`): Workspace provider schemas are served and validated by separately installed provider modules, so admission.strictDecodeOrkaDocument skips the listed provider kinds rather than importing a provider SDK into core.
- **Documented manifests opt out with a skip marker** (`admission.TestDocumentedManifestsDecodeStrictly`): admission.TestDocumentedManifestsDecodeStrictly strict-decodes every Orka manifest in YAML fences and kubectl heredocs in docs. A deliberately invalid block opts out with an HTML comment `<!-- orka:skip-strict-decode reason -->` on the line before its opening fence.
- **Controller usernames are a second fence behind RBAC** (`admission.ExecutionModeConfig`): admission.ExecutionModeConfig lists exact controller usernames. Namespace-scoped RBAC stays the primary authorization boundary; these usernames are a second fail-closed identity fence for controller-owned writes. See [ADR 0018](0018-static-harness-modes-and-namespace-isolation.md).
- **Namespace claim and workspace Lease checks are VAPs** (`admission.RegisterExecutionModeWebhooks`): admission.RegisterExecutionModeWebhooks registers only the static execution-mode boundary; namespace claim immutability and ACP workspace coordination Lease ownership are enforced by ValidatingAdmissionPolicies in config/admission, not by this webhook. See [ADR 0018](0018-static-harness-modes-and-namespace-isolation.md).
- **Omitted Agent contractVersion means the namespace mode** (`admission.Agent execution-mode validator`): A namespace is immutably bound to one execution mode, so an Agent with no contractVersion runs in that mode, and an explicit contractVersion must agree with it. See [ADR 0018](0018-static-harness-modes-and-namespace-isolation.md).

The garbage collector may still orphan it. See [ADR 0039](0039-agent-identities.md).

- **Only the controller removes the continuation link finalizer** (`admission.TaskProvenanceValidator.Handle`): The continuation link finalizer keeps a continuation Task visible until its parked predecessor records it, so only the controller may remove it. Removing it early lets a deleted continuation look as if it was never created, and recovery would start the same work again. See [ADR 0041](0041-data-only-parked-turns.md).

A missing Agent declares none, but any other read failure is returned so admission fails closed.
- **Task coordination ancestry is fixed by its creator** (`admission.changedTaskCoordinationFields`): A Task's creator establishes its coordination ancestry and, for a chat Task, its chat Session incarnation. admission.changedTaskCoordinationFields rejects later metadata updates that would move a worker into another Task's scope or detach a Task from the chat whose deletion stops its delegated calls.

### `internal/agentidentity`

- **OBO user tokens must be audienced to the blueprint** (`agentidentity.requireAudience`): agentidentity.requireAudience checks that a requester's token is addressed to the identity's blueprint client ID, so a Connection linked for another client can never be exchanged. The token comes from Orka's own custody, so only its claims are read; Entra verifies the signature during the exchange. See [ADR 0039](0039-agent-identities.md).
- **Entra authority canonicalization never folds the path** (`agentidentity.EntraConfig.authority`): agentidentity.EntraConfig.authority canonicalizes the authority by trimming space and a trailing slash and lower-casing scheme and host, but keeps the path as given because URL paths are case-sensitive.
- **Agent use enforcement flag asserts policies are installed** (`agentidentity.Config.AgentUseAuthorization`): agentidentity.Config.AgentUseAuthorization mirrors --agent-use-authorization-enabled, which identity-bound Agents require. Setting it asserts that the agent-use ValidatingAdmissionPolicies are installed (the Helm value installs both together); the controller does not detect the policies itself. See [ADR 0039](0039-agent-identities.md).
- **Objects created before enforcement began get no identity claim** (`agentidentity.Config.EnforcedSince`): agentidentity.Config.EnforcedSince is when the controller's current unbroken period of Agent use enforcement began, by the API server's clock. Objects created before it may have been created while the check was off, so no identity claim covers them. See [ADR 0039](0039-agent-identities.md).
- **Identity binding waits for the enforcement period** (`agentidentity.Config.Enforcement`): When agentidentity.Config.Enforcement is set, the enforcement period starts only once this controller leads, and no identity binding is decided until then. See [ADR 0039](0039-agent-identities.md).
- **Entra tenant and blueprint IDs must be bare GUIDs** (`agentidentity.Config.Validate`): agentidentity.Config.Validate requires the Entra tenant ID and blueprint client ID to be bare GUIDs, because the issuer sends them to Entra as they are and surrounding space would reach Entra.
- **Entra authority may not carry query or fragment delimiters** (`agentidentity.Config.Validate`): agentidentity.Config.Validate refuses an authority with a query or fragment, including a bare "?" or "#", because even an empty query or fragment changes the token endpoint built from the authority.
- **Non-default Entra authority is part of the issuer instance** (`agentidentity.Config.Instance`): agentidentity.Config.Instance appends a non-default Entra authority to the issuer instance frozen into Task bindings, because tokens come from the authority and restarting against another one must fail bound Tasks closed. The public cloud authority stays implicit.
- **Enforcement marker Lease is read only for creation time** (`agentidentity.EnforcementLeaseName`): The orka-agent-use-enforcement Lease (agentidentity.EnforcementLeaseName) marks an unbroken period of Agent use enforcement. It carries no holder; only its creation time, set by the API server, is read. See [ADR 0039](0039-agent-identities.md).
- **Only a leader-created marker can continue an enforcement period** (`agentidentity.enforcementLeaderAnnotation`): Only an enforcement marker carrying agentidentity.enforcementLeaderAnnotation can continue a period: a controller creates it after winning leadership, so the leader it replaced, which may not have checked Agent use, no longer serves requests. See [ADR 0039](0039-agent-identities.md).
- **Non-enforcing controllers end the enforcement period** (`agentidentity.EndEnforcementPeriod`): A controller that does not enforce Agent use calls agentidentity.EndEnforcementPeriod before serving any request and again once it leads, since an enforcing leader may have started a period in between. Errors are returned so the caller refuses to run, because a marker left in place would let a later enforcing leader trust the gap. See [ADR 0039](0039-agent-identities.md).
- **Enforcement marker records leader Lease UID and count** (`agentidentity.enforcementTransitionAnnotation`): agentidentity.enforcementTransitionAnnotation records "<uid>/<count>" of the leader election Lease under the last enforcing leader that kept the period. The UID keeps a recreated leader Lease, whose count starts over, from matching an old count. See [ADR 0039](0039-agent-identities.md).
- **Leader holder is matched by hostname prefix** (`agentidentity.LeaderLease.HolderPrefix`): agentidentity.LeaderLease.HolderPrefix matches this process's leader holder identity by hostname, because controller-runtime names a holder by hostname plus a random suffix and a process that loses leadership exits, so a current holder with this Pod's hostname is this process.
- **Leader transition count fences enforcement periods** (`agentidentity.LeaderLease.transition`): agentidentity.LeaderLease.transition returns the leader Lease's UID and transition count only while this process holds it; leader election advances the count whenever the holder changes, before the new leader runs anything. See [ADR 0039](0039-agent-identities.md).
- **Enforcement periods continue only across adjacent enforcing leaders** (`agentidentity.StartEnforcementPeriod`): agentidentity.StartEnforcementPeriod is called each time an enforcing controller wins leadership, never before. It continues the marker's period only when the recorded leader transition count is its own or the one just before it, so any leader in between, such as one that did not check Agent use, forces a new period; without leader election every start begins a new period. See [ADR 0039](0039-agent-identities.md).
- **Enforcement period is shared by all Config copies** (`agentidentity.EnforcementPeriod`): agentidentity.EnforcementPeriod is held by pointer so every copy of Config shares it, and a period started after leadership reaches every reconciler.
- **Issuer outages are distinct from refusals** (`agentidentity.ErrIssuerUnavailable`): agentidentity.ErrIssuerUnavailable marks an issuer that could not answer (timeout, network failure, throttling, or server error) as opposed to one that refused the identity; callers may retry it later, while a refusal is kept.
- **Entra tokens use the blueprint flow** (`agentidentity.EntraIssuer`): agentidentity.EntraIssuer acquires agent identity tokens with the blueprint flow: the blueprint authenticates with the controller's federated credential and receives an exchange token for one agent identity (fmi_path), which that identity then presents to get a token for the target resource. See [ADR 0039](0039-agent-identities.md).
- **Federated credential is read on every call** (`agentidentity.EntraIssuer.Credential`): agentidentity.EntraIssuer.Credential defaults to reading the projected ServiceAccount token file on every call, because the kubelet rotates it.
- **Missing federated token is an outage** (`agentidentity.FileCredential`): agentidentity.FileCredential treats a missing or empty projected token as ErrIssuerUnavailable: Entra was never asked, so the failure says nothing about the identity and must be retried rather than kept as a refusal.
- **Exchange token proves blueprint parentage** (`agentidentity.EntraIssuer.ExchangeToken`): Obtaining agentidentity.EntraIssuer.ExchangeToken's exchange token proves the agent identity is a child of the configured blueprint. See [ADR 0039](0039-agent-identities.md).
- **Identity verification never uses the token cache** (`agentidentity.EntraIssuer.VerifyIdentity`): agentidentity.EntraIssuer.VerifyIdentity asks Entra for the identity's own token past the cache, and never caches or returns it, because a cached token can be up to five minutes old and treating it as proof would let an Agent edit renew trust in an identity Entra has since disabled.
- **Identity tokens are cached per policy UID and generation** (`agentidentity.EntraIssuer.appToken`): agentidentity.EntraIssuer.appToken caches tokens under the outbound policy UID and generation that asked for them, so an edited or recreated policy never reuses its predecessor's token. See [ADR 0039](0039-agent-identities.md).
- **On-behalf-of tokens are cached per policy and user** (`agentidentity.EntraIssuer.OnBehalfOfToken`): agentidentity.EntraIssuer.OnBehalfOfToken caches under the policy and the user token, so an edited or recreated policy, or another requester, never reuses it. The user token must be audienced to the blueprint, which Entra also enforces. See [ADR 0039](0039-agent-identities.md).
- **Entra resource is kept exactly as configured** (`agentidentity.entraScope`): agentidentity.entraScope appends /.default to the resource exactly as configured, because a resource registered with a trailing slash, such as https://database.windows.net/, needs it to select that audience.
- **Token cache lifetime and shared fetch rules** (`agentidentity.EntraIssuer.cached`): agentidentity.EntraIssuer.cached keeps an entry at most five minutes and never past a minute before the token expires. Concurrent misses share one fetch run under a context no caller can cancel, bounded by entraFlightDeadline, so a caller that gives up does not fail the others; a failed fetch is returned to every waiter and nothing is cached.
- **Token request errors carry only Entra's error code** (`agentidentity.EntraIssuer.requestToken`): agentidentity.EntraIssuer.requestToken returns errors that carry only Entra's error code, never a credential or the response body.
- **Entra token requests never follow redirects** (`agentidentity.EntraIssuer.requestToken`): agentidentity.EntraIssuer.requestToken disables redirects because following one would replay the form, which carries the federated credential or the blueprint's exchange token, to wherever the response points. Entra's token endpoint never redirects, so a 3xx counts as the issuer being unavailable.
- **Unreadable token responses are outages** (`agentidentity.EntraIssuer.requestToken`): agentidentity.EntraIssuer.requestToken treats an answer that is not a token response, such as a proxy's HTML page or a truncated body, as ErrIssuerUnavailable, because it says nothing about the identity and must not be kept as a refusal for an hour.
- **Only known Entra OAuth errors refuse an identity** (`agentidentity.EntraIssuer.requestToken`): agentidentity.EntraIssuer.requestToken treats only OAuth errors Entra defines as refusing the identity; 5xx, 429, temporarily_unavailable, server_error, and unknown answers such as a proxy's JSON are outages that must not be kept as refusals.
- **Only known OAuth error codes are passed through** (`agentidentity.entraOAuthErrorCode`): agentidentity.entraOAuthErrorCode returns a known OAuth error code or "unknown_error", because the value comes from the issuer or a proxy and reaches Agent status, errors, and a metric label.
- **Unknown token lifetime disables caching** (`agentidentity.parseExpiresIn`): agentidentity.parseExpiresIn accepts expires_in as a number or numeric string and treats an unknown lifetime as zero, so the token is used once and never cached.
- **Identity tokens require Agent use enforcement** (`agentidentity.Source.AgentIdentityToken`): agentidentity.Source.AgentIdentityToken issues no token unless Agent use authorization is enforced, because an identity claim that outlived a restart without the check must not get tokens. See [ADR 0039](0039-agent-identities.md).
- **Verification uses the identity's own fresh token** (`agentidentity.Source.Verify`): agentidentity.Source.Verify proves an identity with the identity's own token for a cloud-neutral resource, fetched fresh, because Entra still issues the blueprint's exchange token for a disabled agent identity.

### `internal/agentruntimepolicy`

- **Registered AgentRuntime stays the tool policy authority** (`agentruntimepolicy.RuntimeRefPolicy`): agentruntimepolicy.RuntimeRefPolicy is the registered harness-v2 policy a generated Task must request explicitly; the AgentRuntime remains the policy authority, not the generated Task.

### `internal/cli/client`

- **Native session transfers never follow redirects** (`client.Client.nativeSessionRequest`): The CLI native-session client copies its HTTP client and disables redirect following so portable conversation data is only ever sent to, and read from, the server the operator explicitly selected. Error results carry only the HTTP status, never response bodies, so conversation data never reaches error output. Native-session request errors report only the HTTP status code and never echo the response body, keeping portable conversation data out of CLI error output.
- **Operator exec argv travels in the stream, not the URL** (`client.Client.OperatorExec`): OperatorExec sends the command argv as the first stream message rather than as query parameters or headers, so argv never lands in URLs, proxy logs, or header-based audit trails.
- **Operator exec fails closed on local I/O errors** (`client.pumpOperatorStdin`, `client.Client.OperatorExec`): Only a real end of local stdin is announced to the remote command; any other read error ends the exec with failure, because announcing EOF would let the remote command finish on truncated input and report success. Likewise, if local stdout/stderr cannot be written, OperatorExec returns an error and closes the stream (stopping the command) regardless of the remote exit status, since lost output means the exec did not succeed. When OperatorExec cannot write remote output locally it returns an error and closes the stream, stopping the command, so a lost transfer is never reported as success even if the remote command exits 0.

### `internal/codexstate`

- **Codex native-session bundles exclude credentials and config** (`codexstate`, `codexstate.Capture`): The codexstate package moves only the supported SessionKit bundle between Orka and local Codex homes; provider configuration and credentials always remain the caller's responsibility. Capture requires a stopped source writer and retains only manifest and rollout bytes, never authentication files, configuration, or native databases. codexstate.Capture requires a stopped source writer and copies only manifest and rollout bytes, never authentication, configuration, or native databases.
- **MaxBundleBytes is an Orka transport limit** (`codexstate.MaxBundleBytes`): codexstate.MaxBundleBytes reuses harnessv2.DefaultMaxNativeSessionBytes as Orka's transport bound for native-session bundles; it is not SessionKit's own storage limit and must not be raised to match it.
- **Native session unsupported vs retryable outcomes** (`codexstate.ErrUnsupported`, `codexstate.captureSourceUnavailable`): codexstate.ErrUnsupported marks only stopped conversations outside the supported format or transport bounds; I/O failures and uncertain outcomes are deliberately distinct errors because they remain retryable. A session with no readable rollout, or an absent/unreadable home or file, is terminal unsupported because Capture only runs after the writer and its descendants stopped, so a retry cannot change the answer, while timeouts and other I/O errors stay retryable. codexstate.captureSourceUnavailable treats a missing or unreadable rollout, home, or file as terminal unsupported, because Capture only runs after the writer and descendants stop; timeouts and other I/O failures remain retryable.
- **Only encrypted-content rejection allows transcript fallback** (`codexstate.classifyNativeFormatError`): codexstate.classifyNativeFormatError maps only SessionKit's known rejection of encrypted content (raised before an inspection manifest is produced) to the optional transcript fallback; every other format error stays a hard failure.
- **Path containment compares file identity** (`codexstate.within`): codexstate.within compares existing paths by file identity so aliases such as symlinked parents cannot hide an overlap between paths; only a root that does not exist yet falls back to cleaned lexical ancestry.
- **Native session install is journaled and idempotent** (`codexstate.Install`): codexstate.Install records one immutable plan before publishing and reconciles that same plan on retries, so a retried install cannot diverge. The journal directory must be private and outside the Codex home so the installed client cannot read or tamper with it.

### `internal/connectors`

- **Controller validates connector tool arguments before attaching credentials** (`connectors.ValidateToolArguments`): connectors.ValidateToolArguments checks a tool call's arguments against the Tool's declared JSON Schema in the controller before a person's credential is attached; the worker that produced the arguments is not trusted to have honored the schema. An empty payload is judged as the empty object, matching how the executor treats it, so parameterless calls are validated rather than refused as malformed. An empty arguments payload is validated as {} because the executor treats it that way, so the judged and executed inputs match.
- **Tool argument numbers must be exactly representable as float64** (`connectors.ValidateToolArguments`): ValidateToolArguments decodes numbers as float64 because the schema library judges json.Number as a string, which would let integer constraints pass for any value. Because the raw arguments, not the decoded copy, are executed, numbersExactlyRepresentable refuses any argument number whose float64 copy does not print back (shortest round-trip form) as the same decimal value, e.g. 9007199254740993. Schema constants (const, enum, bounds) also decode through float64, so a schema containing a number float64 cannot hold exactly is refused outright; otherwise an argument equal to the rounded value would pass a constraint the provider never declared.
- **Built-in connector tools accept only github.com credentials** (`connectors.ProviderIssuesGitHubCredentials`, `connectors.builtinConnectorIssuerHost`, `connectors.ValidateProviderSpec`): Catalog built-in connector tools always send their credential to the fixed audience https://api.github.com (BuiltinConnectorToolAudience), so only a ConnectorProvider whose OAuth endpoints are github.com's may declare them. GitHub Enterprise Server issues tokens for its own API host, which the built-ins never call, so GHES providers are refused. builtinConnectorIssuerHost is github.com because GitHub Enterprise Server issues tokens for its own API host, which the built-in tools never call.
- **Built-in connector tool classes are fixed by the catalog** (`connectors.builtinConnectorTools`, `connectors.ValidateProviderSpec`): connectors.builtinConnectorTools fixes each built-in's class by what it does with the linked-account credential (read-class only reads, write-class mutates the forge); a provider cannot declare a different class, since a write tool declared read would skip approval and readOnly hiding, and a built-in outside the catalog cannot be declared because it would ignore the credential and run under something else. check_pr_review_marker is excluded because its marker secrets and trusted author are Task environment the controller does not hold, so a brokered run would judge markers against the wrong configuration. Provider validation admits only built-ins that consume the linked credential, and only with their catalog class, since an ignored credential or a write tool declared read would run under a different credential or skip approval and readOnly rules.
- **Built-in tool timeouts set credential freshness** (`connectors.BuiltinConnectorToolTimeout`, `connectors.BuiltinPollingToolTimeout`): Each catalog built-in has a fixed maximum duration (BuiltinToolTimeout 2m; BuiltinPollingToolTimeout 11m for check_pull_request_ci, covering its maximum poll wait plus a bounded final status check). The credential source refreshes any token that would expire within that duration before the call starts, so the credential stays valid for the whole call. BuiltinPollingToolTimeout is 11 minutes because check_pull_request_ci may poll up to its maximum wait plus a bounded final status check.
- **Infrastructure hosts are always denied for connector endpoints** (`connectors.PrivateEndpointDialContext`, `connectors.InfrastructureHostDenied`, `connectors.InfrastructureAddressDenied`): Even with the fixture-only private-endpoint allowance (--connectors-allow-private-endpoints), connector OAuth and tool endpoints may never resolve to infrastructure hosts such as cloud metadata, kubernetes.default, or the literal KUBERNETES_SERVICE_HOST address, and plain http stays refused, so an OAuth client secret or a person's token can never reach them. InfrastructureHostDenied and InfrastructureAddressDenied refuse, allowance or not, cloud metadata services and the Kubernetes API service under any cluster domain, including the literal KUBERNETES_SERVICE_HOST address so aliases or DNS rebinding to it are refused. At dial time the whole IPv4 link-local range (169.254.169.254, EKS Pod Identity 169.254.170.23), the IPv6 metadata address fd00:ec2::254, and Alibaba Cloud's 100.100.100.200 (in shared address space, which the private allowance would otherwise permit) are denied; PrivateEndpointDialContext enforces this whatever name resolved to them.
- **Connector OAuth callback URI must match registration exactly** (`connectors.CallbackPath`): connectors.CallbackPath is the fixed path appended to the operator's callback base URL; the result must equal the redirect URI registered with the provider exactly, so changing the path breaks every existing provider registration.
- **Connection identity uses exact subject digests** (`connectors.SubjectDigest`): connectors.SubjectDigest hashes issuer and subject exactly as verified (no trimming or normalization: claims are opaque, so a differently spaced subject is a different person) to bind sealed credential material to its owner without storing the raw subject beside the ciphertext. Callers reject blank values separately.
- **Connection index labels are not authoritative** (`connectors.ListSubjectConnectionsAuthoritative`, `connectors.ConnectionLabels`): The orka.ai/connection-subject and orka.ai/connector-provider labels only index Connections (set by the API at creation and repaired by the controller). Fail-closed decisions use ListSubjectConnectionsAuthoritative, which lists all Connections in the namespace and matches the spec's requester exactly, so an object created outside the API or with its label stripped can never look unlinked. ConnectionLabels are set by the API at Connection creation and repaired by the controller; they are an index only.
- **Connector provider names are digested when not valid labels** (`connectors.ConnectionProviderLabelValue`): ConnectionProviderLabelValue uses the provider name when it is a valid label value and a digest otherwise, because an object name may be 253 characters while a label value is limited to 63.
- **AgentHosts record their ConnectorProvider explicitly** (`connectors.AgentHostProviderAnnotation`): An AgentHost created for a Connection carries the orka.ai/connector-provider annotation because the Connection name keeps only a prefix of a long provider name, and both the provider and Connection may be deleted while the host is kept.
- **Connection names are deterministic per person and provider** (`connectors.ConnectionName`): connectors.ConnectionName derives a deterministic name from provider, issuer, and subject so a person has at most one Connection per provider; the digest covers the full provider name so providers sharing a long prefix still get distinct names after truncation.
- **OAuth consent state is HMAC-signed** (`connectors.SignState`): connectors.SignState binds the consent nonce to the controller's state key (at least MinStateKeyBytes) because the state travels through the person's browser and the provider; the signature stops a forged callback from probing the consent table.
- **Resolved OAuth provider config stays in controller memory** (`connectors.OAuthProviderConfig`): connectors.OAuthProviderConfig holds a provider's resolved client secret and must never be persisted, logged, or written to any API object; it exists only in controller memory.
- **OAuth scope omission differs from an empty grant** (`connectors.TokenResponse.ScopePresent`): TokenResponse.ScopePresent distinguishes an omitted scope field, which RFC 6749 section 5.1 defines as granting the requested scopes, from an explicitly empty one, which grants nothing. A JSON null scope is neither and is refused rather than collapsed into the omitted case. A present scope field must be a JSON string; JSON null is refused rather than treated as omitted.
- **OAuth provider errors are sanitized** (`connectors.OAuthError`): connectors.OAuthError carries only the HTTP status and a sanitized error code, never the provider response body, and transport errors are reduced to a generic message because they can embed URLs with query material. Provider transport errors are replaced with a generic sanitized message because they may embed URLs whose query material must not leak.
- **invalid_grant revokes the Connection** (`connectors.OAuthError.IsInvalidGrant`): When the provider rejects the grant itself (IsInvalidGrant), the stored material is unusable, so the Connection is marked revoked instead of retried.
- **Connector OAuth endpoints must be public unless fixture allowance** (`connectors.OAuthClient`, `connectors.OAuthClient.allowPrivate`, `connectors.SetAllowPrivateEndpoints`): connectors.OAuthClient reaches only public HTTPS endpoints. The fixture-only --connectors-allow-private-endpoints allowance (OAuthClientOptions.AllowPrivateEndpoints) permits private and cluster-local HTTPS endpoints through PrivateEndpointDialContext, which still refuses infrastructure addresses; when it is set, the public-address check on token and revocation URLs is skipped because the dialer enforces the infrastructure block list. Production configurations cannot enable it. OAuthClient.allowPrivate skips the public-address URL check only because PrivateEndpointDialContext enforces the infrastructure block list at dial time.
- **Connector OAuth client dials directly, never via proxy** (`connectors.NewOAuthClient`): NewOAuthClient's default transport dials only public addresses, follows no redirects, bounds response size and time, and deliberately uses no proxy: through a CONNECT proxy the public-address dialer would validate only the proxy hop, letting a hostname that resolves to a private address bypass the endpoint check. The OAuth client never uses an HTTP proxy, because the public-address dialer would only validate the proxy hop and a private-resolving hostname could bypass the check.
- **Rotated refresh tokens must be persisted** (`connectors.OAuthClient.Refresh`): OAuthClient.Refresh may return a new refresh token from providers that rotate them; callers must persist it, since the old one becomes invalid.
- **Tokens are revoked only at their issuing host** (`connectors.OAuthClient.Revoke`, `connectors.ValidateProviderSpec`): OAuthClient.Revoke (RFC 7009) succeeds immediately when the provider has no revocation URL, so callers must not treat success as proof the provider invalidated the token. When a revocation URL exists, the token is sent only if it is on the same host and port as the token endpoint (SameEndpointHost), so a token never leaves for a host other than its issuer. Revoke re-checks SameEndpointHost at call time, mirroring provider validation, so a token is only sent to the host that issued it.
- **Token responses that cannot authenticate are refused** (`connectors.OAuthClient.parseTokenResponse`): Token responses are refused unless the access token matches the RFC 6750 b64token grammar and token_type is bearer, because credentials are injected verbatim as an Authorization bearer header and anything else would yield a Ready link that can never authenticate. Only token_type bearer is accepted, since any other type would produce a Ready link that never authenticates.
- **Granted scope lists are bounded** (`connectors.maxGrantedScopes`): maxGrantedScopes and maxGrantedScopeBytes bound the scope list a token response may carry, far above any real grant, because the granted list is copied into Connection status and a provider must not be able to make that object unwritable. Each configured scope is likewise capped at maxScopeBytes (256) so scopes can't push the authorization URL past browser and proxy limits. maxGrantedScopes and maxGrantedScopeBytes are set far above any real provider grant; they exist to keep Connection status writable.
- **expires_in is bounded to avoid overflow** (`connectors.maxExpiresInSeconds`): maxExpiresInSeconds caps expires_in at ten years so converting seconds to time.Duration cannot overflow into an expiry in the past.
- **Endpoint host rules are re-checked at call time** (`connectors.OAuthClient.post`): The OAuth client reapplies provider-validation host rules before any DNS lookup or dial, so an endpoint stored before a rule existed or that bypassed admission is refused rather than left to DNS resolution; the fixture allowance relaxes only general private and cluster-local names, never infrastructure hosts.
- **Credential tokens are capped at 16 KiB** (`connectors.maxCredentialTokenBytes`): maxCredentialTokenBytes caps a single token at 16 KiB; real bearer tokens are far smaller, so larger material is refused as not a credential.
- **Granted scopes split on spaces and commas** (`connectors.parseGrantedScopes`, `connectors.validScopeToken`): Granted scope strings are split on both spaces (RFC 6749) and commas, because GitHub reports scopes comma-delimited ("repo,gist"). This cannot fabricate a grant because validScopeToken refuses commas inside configured scope names, so no required scope can be produced by splitting a single comma-bearing token. validScopeToken refuses commas in configured scopes even though RFC 6749 allows them, because GitHub delimits granted scopes with commas and a configured comma-bearing scope could be fabricated by splitting a single issued scope.
- **Malformed expires_in is an error** (`connectors.parseExpiresIn`): parseExpiresIn accepts expires_in as a positive integer JSON number or decimal string; absent or null means no expiry was reported, but a present zero, negative, fractional, or malformed value is an error so it can never silently become a non-expiring credential.
- **OAuth 200 responses with error bodies are rejections** (`connectors.OAuthClient.ExchangeCode`): GitHub returns HTTP 200 with an error body for failed token exchanges, so the OAuth client treats any token response carrying an error field as a rejection with a sanitized code.
- **Task requester stamps are UID-bound HMACs** (`connectors.requesterStampDomain`, `connectors.RequesterStamp`, `connectors.RequesterStampValid`, `connectors.SealRequesterStamp`): connectors.RequesterStamp computes a domain-separated HMAC (domain orka.requester-stamp.v1, key at least MinRequesterStampKeyBytes) over the Task's server-assigned UID and the verified requester. Because the UID is assigned at creation, SealRequesterStamp patches the stamp onto the live object after creation, so the stamp cannot be transplanted onto another Task, even one re-created with the same name. RequesterStampValid treats every Task as unstamped when no key is configured, so provenance fails closed. RequesterStamp binds the server-assigned Task UID, so a stamp is sealed only after creation and cannot be reused on a re-created Task of the same name.
- **Linked Connection status is computed in one place** (`connectors.ApplyLinkedStatus`): connectors.ApplyLinkedStatus is the single routine both the API (right after a custody commit) and the controller (finishing a commit whose status write was lost) use to record a successful consent, so they never disagree. Granted scopes are judged against what the mode requires now, so a provider expanded after consent began leaves the link Pending until the person consents again. Each commit raises the grant sequence so a snapshot or approval bound to one grant can tell a re-link of the same object apart. Connection status mirrors the custody grant of the committed material and raises the grant sequence on every commit, so approvals or snapshots bound to one grant can detect a re-link.
- **Connector validation messages never echo credentials** (`connectors.Issue`): Everything in package connectors is status-safe: Issue messages become public provider status and must never carry a credential, a credential-bearing URL, a header name that looks like a credential, a duplicated scope value, or schema library error text (which can quote schema values and $ref URLs). Duplicate-scope errors omit the scope value because the message becomes public status.
- **Connector authorization URL size bounds** (`connectors.maxEndpointURLBytes`, `connectors.maxAuthorizeParameterValueBytes`, `connectors.ValidateProviderSpec`): Connector validation bounds every component that rides in the browser's authorization URL: each scope (256 bytes, matching the bound on provider-reported scopes), the readWrite scope set's encoded total, client_id (256), static authorize parameter values (512) and their encoded total, endpoint and HTTP tool URLs (2048), and static endpoint queries. Together with the flow's own parameters they keep an authorization URL under the 8 KiB request target that common servers and proxies accept. maxAuthorizeParameterValueBytes and maxAuthorizeParametersEncodedBytes keep static authorize parameters from pushing the authorization URL past browser, proxy, and provider limits.
- **Flow-owned OAuth parameters are reserved** (`connectors.reservedAuthorizeParameters`, `connectors.validateURL`, `connectors.validateEndpointQuery`): Parameters the consent flow sets (code, code_verifier, grant_type, state, redirect_uri, and similar) may not be overridden by provider authorize parameters or appear as static query on an OAuth endpoint, so a preconfigured state, redirect URI, or secret can never ride along in public configuration. Tool URLs may use such names because a tool API may use names like state as filters. validateURL applies the same host rules to OAuth endpoints and HTTP tool URLs, but only OAuth endpoints refuse flow-owned query names, since a tool's API may legitimately use names such as state as filters.
- **Connector endpoints must name public hosts** (`connectors.hostDenied`, `connectors.deniedHostSuffixes`, `connectors.validateURL`, `connectors.validDNSName`): connectors.hostDenied rejects endpoint hosts equal to or under denied cluster-internal and metadata names, names extending them with more labels (kubernetes.default.svc.example), names under cluster-local, mDNS, and other non-public suffixes, any <service>.<namespace>.svc.<domain> name, and single-label names, which Pod DNS search domains complete to cluster Services (kubernetes, orka-api). Hosts must be ASCII (punycode) because clients IDNA-normalize forms such as ideographic full stops to loopback, must be syntactically valid DNS names, and must not be non-canonical numeric spellings (127.1, 2130706433, 0x7f000001) that resolvers accept but net.ParseIP rejects, since the authorize URL is opened by the browser rather than the guarded dialer. deniedHostSuffixes covers cluster-local service names under any cluster domain, mDNS, and other non-public name spaces that never resolve to a public provider.
- **HTTP tools may not set hop-by-hop headers** (`connectors.reservedToolHeaders`): Provider HTTP tool definitions may not set hop-by-hop headers (Connection, Keep-Alive, Proxy-Connection, TE, Trailer, and similar) because Connection could nominate the injected Authorization header for removal by an intermediary and all of them are invalid on HTTP/2.
- **Tool header names are validated as RFC 9110 tokens** (`connectors.validHeaderToken`): validHeaderToken checks header names against the RFC 9110 token grammar required by net/http, because http.CanonicalHeaderKey returns invalid names unchanged and canonical-form equality alone would accept them.
- **Connector provider names are limited to 63 characters** (`connectors.maxProviderNameLength`): ConnectorProvider names are limited to 63 characters (maxProviderNameLength) because the provider name is a label value on every Connection.
- **Impossible Secret references are invalid specs** (`connectors.ValidateProviderSpec`): A client secret reference whose name or key no Secret could ever have is rejected as an invalid spec instead of failing every resolution as a transient error.
- **Credential-like parameter names are refused** (`connectors.credentialLikeParameter`): credentialLikeParameter compares names lowercased with underscores folded to hyphens and again with all separators removed, so concatenated aliases such as Authentication, X-Accesskey, or awsaccesskeyid are caught.
- **HTTP connector tools may not reuse built-in names** (`connectors.ValidateProviderSpec`): Tool selection and execution are name-based, so an HTTP connector tool named like an Orka built-in is rejected to prevent shadowing in either direction.
- **Forwarding connector tools are single-origin and read-class** (`connectors.validateForwardingTool`): validateForwardingTool limits a forwarding tool to one origin and no declared arguments (its arguments are the runtime's fixed request shape). It is class read; writes require both forward.writes and the Tool's write permission, and are only made through a readWrite link.
- **Connector tool parameter schemas must match execution** (`connectors.validateToolParameters`): validateToolParameters requires an object-typed root because LLM tool definitions accept only that shape and without an explicit root type JSON Schema accepts non-object inputs the HTTP executor cannot map. It resolves the whole schema as execution does, so nested shapes execution would reject are refused, and refuses schemas whose numbers float64 cannot hold exactly since execution would then accept no call at all. The schema root type is required because without it JSON Schema accepts non-object inputs that the HTTP executor cannot map onto request arguments.
- **Curated HTTP tool URLs are fixed destinations** (`connectors.validateHTTPTool`): Curated HTTP tool URLs may not contain template syntax because the URL is the exact destination the person consented to, and templates would let call arguments rewrite its path or query.
- **Agent-host providers resolve only with a valid template** (`connectors.ResolveProviderReferences`): A provider that serves agent hosts is ready only once its Relay template exists, passes agenthost.ValidateTemplate, and reaches each host only through its owner's account; otherwise every host it provisions would fail, so the provider is not offered meanwhile. A template the AgentHost reconciler would refuse keeps the provider unresolved.
- **ConnectionLinked is a status view, not a release check** (`connectors.ConnectionLinked`): ConnectionLinked requires Ready, ProviderResolved, and ScopesGranted, with the controller-owned conditions observing the current generation so a mode change or provider loss fails closed. Because status trails the provider by one reconcile, any caller that releases token material must also load the provider and verify ProviderAccepted, the authority digest sealed with the credential, and the scopes the mode requires, as the credential-injection path does.
- **Connector consent fences** (`connectors.ProviderAuthorityDigest`, `connectors.ProviderIssuerDigest`, `connectors.ProviderRevocationDigest`, `connectors.providerIssuerParts`): ProviderAuthorityDigest is a length-prefixed (injective) SHA-256 digest over the provider UID, client ID, client secret reference, auth method, endpoints, static authorize parameters (which can select the resource server, e.g. an Auth0 audience), curated HTTP tool destinations and static headers, forwarding and write capabilities, declared parameter schemas, built-in declarations, and agent-host service. It changes whenever a held token would belong to a different client, target a different resource, or be sent elsewhere, forcing renewed consent; scopes are judged separately by ScopesGranted. ProviderIssuerDigest excludes tool destinations and authorize-only parameters so a retargeted tool still lets a held token be refreshed or revoked by its issuing client, and ProviderRevocationDigest covers only the OAuth client and revocation URL so disconnect still revokes after the token endpoint moves; both are sealed with every credential. Turning a tool into a forwarding tool or letting it write moves the authority digest, because a forwarding tool reaches any read path on its origin.

### `internal/connectors/credential`

- **Agent host credential release** (`credential.HostCredential.Refreshable`, `credential.Source.HostCredential`, `credential.Source.CheckHostLink`): HostCredential.Refreshable reports whether custody holds a refresh token; because GitHub issues refresh tokens only alongside expiring access tokens, it distinguishes an expiry GitHub set from a deadline Orka chose for a non-expiring token it was handed. Source.HostCredential releases only the access token for an agent host (refreshing first if it expires within the horizon); the refresh token never leaves custody. It shares the tool path's per-grant single-flight refresh, so a host and a tool call never refresh the same grant twice and either's refresh replaces the other's token. Every link check runs again before release, because a disconnect that began after the first read tombstones custody without the custody read noticing, and the provider may stop serving hosts or a re-consent may replace material while a refresh is in flight.
- **Agent host link verdicts** (`credential.Source.hostLink`, `credential.Source.hostConnection`, `credential.providerVerdict`, `credential.checkProvider`): An agent host keeps the template it was created from: pointing the provider at another template affects only hosts created afterwards, and the existing host is fed again once the person consents to the change. hostLink orders its checks so a settled provider refusal (including deletion) ends the link without reading custody, so a storage outage cannot keep a host running after its provider refused it. An unobserved or inconclusive provider status is retryable only after custody is read, because missing credentials already prove the link ended. A mismatch with a provider just read and accepted is a verdict; a failed provider read is retried, never treated as a refusal. Once provider and custody are checked directly, a lagging or failed-read Connection status stops no host.
- **Linked-account credentials resolve only in the controller** (`credential`): Package credential resolves a person's linked-account access token for a tool call, refreshing lazily with single-flight per Connection grant and writing rotated material back to custody; it runs only in the controller, never in workers or runtimes.
- **Credential authorization reads are uncached** (`credential.Source.reader`, `credential.Source.loadLiveConnection`): Source.reader returns the uncached API reader when configured so identity, generation, and readiness checks never trust a lagging informer cache; a generation change after dispatch must be seen before the watch catches up or the frozen-binding check could pass against stale readiness. Status writes still use the cached Client. loadLiveConnection reads through the uncached reader so a post-dispatch generation change is seen before the watch catches up.
- **Connector credential resolution fences** (`credential.Source.ResolveConnectionCredential`, `credential.frozenGrantHolds`, `credential.Source.validateProvider`, `credential.checkProvider`): ResolveConnectionCredential refuses a write-class tool on a readOnly link before reading custody, so a call that can never run never refreshes, rotates, or shreds the credential. Custody, not only status, is fenced to the grant frozen at dispatch (frozenGrantHolds): a consent that committed between the Connection read and the custody read holds another grant's material, which this Task never bound, including after a refresh that lost to a re-consent.
- **Connector refresh single-flight** (`credential.Source.ResolveConnectionCredential`, `credential.Source.refreshSingleFlight`): A refresh flight may have been started by a caller with a shorter horizon, so every caller judges the shared result against its own horizon and refuses a token that would expire mid-request. refreshSingleFlight refreshes once per Connection grant at a time; concurrent callers share the result and a late waiter re-reads custody instead of refreshing again. Only the grant the callers read is refreshed; custody another consent committed meanwhile is returned untouched, since a failed refresh of it (invalid_grant) would shred a credential no caller of this flight bound. The flight runs detached from caller cancellation with its own 30s bound, while each caller returns as soon as its own context ends.
- **Delegated exchange liveness re-check** (`credential.Source.RequireLiveConnection`): RequireLiveConnection, run after a delegated exchange, applies the frozen-binding check and reads the grant (never the material, never refreshing) from custody, which is authoritative over Connection status because a re-consent commits there first. It also requires the provider to still be accepted, match the consent, and declare the Tool; custody's scopes to cover the mode, since the consent fence omits scopes and a refresh can narrow them before status shows it; and the Connection to still be the frozen, Ready one after custody answers. The provider can change during the exchange before status shows it, so RequireLiveConnection re-validates it as resolution did.
- **Connector refresh horizon covers the tool timeout** (`credential.Source.refreshHorizon`, `credential.Source.refresh`): refreshHorizon is the larger of the refresh skew (DefaultRefreshSkew, 60s) and the executing Tool's curated request timeout, so a provider that rechecks the bearer during a long call never sees it expire mid-request. A refreshed token that already expires within the horizon is sealed but not released; the next call refreshes again.
- **Connector refresh custody fencing** (`credential.Source.refreshSingleFlight`, `credential.Source.refresh`, `credential.Source.recordNarrowedScopes`, `credential.Source.revokeUnstorable`): When the provider rejects the refresh token (invalid_grant), the stale material is shredded without a disconnect tombstone so the person can consent again, unless a newer consent already replaced it, in which case the newer material is returned only if it is not itself about to expire. A refreshed row keeps the GrantSequence and revocation identity of the material it derives from so a later disconnect can still revoke it; only a consent starts a new grant.
- **OAuth scope omission differs from an empty grant** (`credential.Source.refresh`): On refresh, only an omitted scope field inherits the previous grant (RFC 6749 section 5.1); an explicitly empty scope is a grant of nothing and fails the mode check.
- **Tokens are revoked only at their issuing host** (`credential.Source.revokeUnstorable`): revokeUnstorable sends tokens only to the revocation authority sealed with the material (ProviderRevocationDigest); a revocation endpoint moved since consent is never handed them, the same rule disconnect applies.
- **OAuth client secrets are opaque bytes** (`credential.Source.validateProvider`): Provider client secrets are treated as opaque bytes: only emptiness is checked and the value is never trimmed or normalized.
- **Connector refresh status writes are fenced** (`credential.Source.recordRefresh`, `credential.Source.markNotReady`, `credential.Source.verdictStillCurrent`): recordRefresh only logs a failed status write because the refreshed material is already safe in custody. The patch is fenced on the resourceVersion read at flight start so a stale refresh never overwrites a newer consent's scopes or expiry, and other concurrent writers are retried while custody still holds this material so status cannot stay stale indefinitely. recordRefresh fences on the flight-start resourceVersion and retries unrelated conflicts while custody still holds the refreshed material.
- **Person-scoped GitHub credential resolution** (`credential.Source.ResolveGitHubPersonCredential`): ResolveGitHubPersonCredential serves a person's github.com token for operations they run for themselves (not a Task) only from a Ready link they own whose provider is accepted, issues github.com tokens, and is unchanged since consent, valid for at least the horizon. The credential is bound to the Connection UID it was read for, because a Connection deleted and recreated under the same name can reach the same grant sequence, and the Connection is judged again before release in case a disconnect or re-consent landed. The credential must match the Connection UID because a recreated Connection can reach the same grant sequence.

### `internal/contexttoken`

### `internal/events`

- **Execution event vocabulary lives in pkg/storage/v1** (`events.ExecutionEventTruncation`): The execution event types in internal/events are aliases of pkg/storage/v1 because storage providers validate event filters and terminal approval uniqueness against that vocabulary, making it part of the public storage contract. ### `internal/memoryconsolidation`

- **Consolidation input selection** (`memoryconsolidation.CollectInputs`): memoryconsolidation.CollectInputs never reads gateway Sessions, reads Sessions with a running turn because their transcript holds only finished turns and skipping could miss them for good, and drops tool messages so recalled memory cannot return as new evidence. It also reads open memory proposals so the run does not propose again what already awaits review. See [ADR 0051](0051-offline-memory-consolidation.md).
- **A full memory list marks the input truncated** (`memoryconsolidation.CollectInputs`): When memoryconsolidation.CollectInputs lists MaxInputMemories or more memories it marks the input truncated, because the store does not report how many more exist and older memories may have been left out.
- **Transcript budget keeps the newest turns** (`memoryconsolidation.CollectInputs`): memoryconsolidation.CollectInputs cuts each Session's transcript from the oldest end so the budget keeps the newest turns the run is meant to learn from, while the model still reads them in order. A Session's own fields count against the budget once any of its turns is kept. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Stop reading older Sessions after a cut** (`memoryconsolidation.CollectInputs`): Once memoryconsolidation.CollectInputs cuts a newer Session to fit the transcript budget it sets the remaining budget to zero, because older Sessions would only fit in part.
- **Input budgets charge the encoded size** (`memoryconsolidation.encodedSize`): memoryconsolidation.encodedSize counts each item as UserMessage encodes it, plus one for the separating comma, so the budgets pay for JSON escapes, field names, IDs and timestamps and the data never exceeds what CollectInputs counted.
- **Encoding failure consumes the full budget** (`memoryconsolidation.encodedSize`): memoryconsolidation.encodedSize returns MaxInputChars when encoding fails, so an impossible failure fills the budget instead of letting unbounded data through.
- **Closed proposals are read one by one** (`memoryconsolidation.ClosedProposals`): memoryconsolidation.ClosedProposals gets each proposal the run read individually, treating applied, rejected, archived or missing as closed, so the answer does not depend on a bounded list.
- **Open memory proposals are pending or accepted** (`memoryconsolidation.collectProposals`): memoryconsolidation.collectProposals treats pending and accepted-but-unapplied proposals as open, newest first, and lists only memory-change proposal types; other kinds such as skills are never read.
- **List each proposal kind and status separately** (`memoryconsolidation.collectProposals`): memoryconsolidation.collectProposals lists every proposal type and status on its own so proposals of other kinds, such as skills, cannot crowd memory changes out of a bounded list.
- **Full proposal lists mark the input truncated** (`memoryconsolidation.collectProposals`): memoryconsolidation.collectProposals marks the input truncated when any proposal list reaches MaxInputProposals. Applying a proposal sets it to applied, but a provider that keeps applied proposals accepted with an AppliedMemoryID can fill a list with them, which is then treated like any other reached bound.
- **Merge proposal lists newest first and deduplicate** (`memoryconsolidation.collectProposals`): memoryconsolidation.collectProposals sorts the merged lists newest first so the shared limits keep the newest, and deduplicates by ID because a proposal accepted between the pending and accepted reads appears in both.
- **Proposal tags come only from the validated tag line** (`memoryconsolidation.TestProposalsApplyOnlyTheValidatedTags`): Applying a memory proposal takes its tags from the first "Tags:" line of its description, so consolidation writes the validated tags before any model-supplied reason; TestProposalsApplyOnlyTheValidatedTags guards that a model's reason can never name the tags applied.
- **Covered proposal IDs cannot inject tag lines** (`memoryconsolidation.TestProposalsNeverTakeTagsFromACoveredProposalID`): A covered proposal's ID is chosen by whoever created it and is named in the covering proposal's description, so consolidation must render it so it can never add a "Tags:" line; TestProposalsNeverTakeTagsFromACoveredProposalID guards this.
- **Submit tool schema is not the trust boundary** (`memoryconsolidation.SubmitToolParameters`): memoryconsolidation.SubmitToolParameters is the JSON Schema of a Submission shown to the model as guidance only; Validate checks every result again, so the schema is never the trust boundary.
- **Transcript data cannot escape its block** (`memoryconsolidation.UserMessage`): memoryconsolidation.UserMessage encodes input as JSON so transcript text stays inside string values, and escapes the data block tag wherever text spells it in any case, so text can neither close the block nor open another. Other HTML characters are left unescaped so the data is no longer than CollectInputs counted. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Escape only data block tags** (`memoryconsolidation.encodeData`): memoryconsolidation.encodeData disables JSON HTML escaping and replaces only the "<" of data block tags with a \u003c escape, which decodes to the same text, keeping the encoded size equal to what encodedSize charged.
- **Consolidation runs are bounded for one call and one review** (`memoryconsolidation.MaxOperationsLimit`): The memoryconsolidation bounds on operations, sessions, memories and report size keep a run's input, proposals and report small enough for one model call and one human review. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Memory and transcript input budgets are separate** (`memoryconsolidation.MaxMemoryInputChars`): memoryconsolidation.MaxMemoryInputChars and MaxTranscriptInputChars bound memories and transcripts separately so memories never crowd out the transcripts a run learns from. Together they fit a model's context at one token per character; a model that cannot take the input fails the run rather than dropping input, leaving its Sessions to the next run. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Runs read open proposals to avoid repeats** (`memoryconsolidation.MaxInputProposals`): A consolidation run reads up to memoryconsolidation.MaxInputProposals open memory proposals, newest first, so it does not propose again what already awaits review. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Overlong covered IDs are dropped** (`memoryconsolidation.MaxCoveredIDChars`): memoryconsolidation.MaxCoveredIDChars bounds each proposal ID an operation covers; a longer ID is dropped rather than kept, so covers cannot grow a report past its size limit.
- **Window ends a commit grace before now** (`memoryconsolidation.WindowCommitGrace`): memoryconsolidation.WindowCommitGrace is MaxOperationAge plus MaxClockSkew because a Session change is stamped with its write's issue time and a retried write can commit long after; providers refuse writes older than MaxOperationAge, so no change stamped before the window end can commit after the run reads. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Consolidation window boundaries** (`memoryconsolidation.Window`): memoryconsolidation.Window starts at the mode's cursor (the latest completed run's end, or the first run's start) so skipped runs' Sessions are read again, never further back than MaxLookback. It ends on a whole second WindowCommitGrace before now because the store stamps some changes with whole-second times before commit, so later changes fall into the next window rather than between two. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Later proposals block repeats but cannot be covered** (`memoryconsolidation.Input.LaterProposals`): memoryconsolidation.Input.LaterProposals holds open proposals created after the run read its input, reloaded at completion; the model never saw them, so an operation may not cover them, but it also may not repeat them.
- **Closed proposals cannot be covered** (`memoryconsolidation.Input.ClosedProposals`): An operation may not cover a proposal listed in memoryconsolidation.Input.ClosedProposals (applied, rejected, archived or gone at completion), since the fact it proposed may already be in memory.
- **Consolidation output is untrusted and checked per operation** (`memoryconsolidation.Validate`): memoryconsolidation.Validate treats the model's submission as untrusted: each operation is checked against what the run read and dropped with a reason while the others still count. Targets must be read memories at the read generation, still active at that generation when current is given, and not targeted twice; sources must be read Sessions and messages; an operation must not repeat an open proposal unless it covers it with a different change; a merge of k memories costs k-1 of the removal budget, a supersede none and a retire k. See [ADR 0051](0051-offline-memory-consolidation.md).
- **A retire's content is never proposed content** (`memoryconsolidation.newOpenProposals`): memoryconsolidation.newOpenProposals and changeKey ignore a retire proposal's content because a retire creates no memory, so its text must not count as content already proposed.
- **Covered IDs never break a line** (`memoryconsolidation.openProposals.known`): memoryconsolidation.openProposals.known drops covered IDs that are too long or contain whitespace or control characters, because IDs are named in the proposal description and one that could break a line could spell a tag line.
- **Identical changes are always repeats** (`memoryconsolidation.openProposals.check`): memoryconsolidation.openProposals.check rejects a change identical to an open proposal even when it covers it; otherwise an operation may target a memory or propose content an open proposal already does only when it covers that proposal and replaces it with a different change, such as a supersede in place of an add.
- **Repeated citations are trimmed, not rejected** (`memoryconsolidation.distinctSources`): memoryconsolidation.distinctSources drops repeated citations and keeps the first MaxMemoryProposalSources so a model that cites one Session many times does not lose an otherwise valid operation.
- **Consolidation proposal IDs are deterministic** (`memoryconsolidation.ProposalID`): memoryconsolidation.ProposalID derives each proposal ID from the Task UID and operation index so a retried completion cannot create a second copy. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Only validated tags reach the Tags line** (`memoryconsolidation.Proposals`): Applying a memory proposal takes tags from the first "Tags:" line of its description, so memoryconsolidation.Proposals writes the validated tags first and quotes any line in the model's reason or covered proposal IDs that reads as a tag line.
- **Covered proposal IDs are quoted like model text** (`memoryconsolidation.Proposals`): memoryconsolidation.Proposals passes covered proposal IDs through quoteTagLines along with the model's reason, because IDs are chosen by other proposal creators and must never become a tag line.
- **Consolidation reports are redacted** (`memoryconsolidation.Report.Redact`): memoryconsolidation.Report.Redact applies sensitive-text redaction to every free-text field because the report keeps model output and becomes the Task result.
- **Report abridging order** (`memoryconsolidation.Report.Encode`): memoryconsolidation.Report.Encode redacts then, when multibyte or escaped text still exceeds the limit, drops rejected operations, conflicts, the summary, kept operations' text and their covered IDs in that order and marks the report Abridged; nothing a review needs is lost because the proposals keep full text and name what they cover.
- **Task result holds only report structure** (`memoryconsolidation.Report.Structure`): memoryconsolidation.Report.Structure strips all model-written or run-read text and keeps types, targets, sources, covered IDs, Orka-written rejection reasons and counts, because anyone who can read a Task can read its result while the full report requires the permissions the run's inputs need. See [ADR 0051](0051-offline-memory-consolidation.md).

### `internal/outboundaccess`

- **Identity audit falls back to stderr** (`outboundaccess.agentIdentityAuditOutput`): outboundaccess.agentIdentityAuditOutput receives identity use records from resolvers without an AuditLog, such as the AI worker's, which configures no logger, so refused and issued calls are still recorded.
- **Identity audit is never filtered or sampled** (`outboundaccess.defaultAgentIdentityAuditLog`): outboundaccess.defaultAgentIdentityAuditLog writes one JSON line per record with no log-level filter and no sampling, matching the controller's audit sink. See [ADR 0039](0039-agent-identities.md).
- **Identity refusals record a fixed reason only** (`outboundaccess.agentIdentityRefusalPolicy`): Identity use records carry one fixed refusal reason constant (policy, binding, delegation, issuer, canceled) and never the error text, because errors can quote call arguments or issuer responses an audit reader must not see. See [ADR 0039](0039-agent-identities.md).
- **Identity audit is deferred after policy read** (`outboundaccess.KubernetesResolver.auditAgentIdentityUse`): outboundaccess.KubernetesResolver.auditAgentIdentityUse is deferred by Resolve once the policy is read so it records the call's final error, writing one record per identity-backed call and none for other adapters; records never carry tokens, request bodies, full URLs or error text, and Delegated requesters appear only as a keyed pseudonym. See [ADR 0039](0039-agent-identities.md).
- **Audit Task UID falls back to the identity binding** (`outboundaccess.auditTaskUID`): outboundaccess.auditTaskUID names the calling Task from the request or its identity binding, which is safe because both come from the same authenticated Task.
- **Requester pseudonyms are keyed on exact claims** (`outboundaccess.KubernetesResolver.requesterPseudonym`): outboundaccess.KubernetesResolver.requesterPseudonym records nothing without a key, and keys issuer and subject exactly as verified, like connectors.SubjectDigest, so distinct subjects never share a pseudonym while records still join per person. See [ADR 0039](0039-agent-identities.md).
- **Issuer authority is recorded as a digest** (`outboundaccess.auditIssuerInstance`): outboundaccess.auditIssuerInstance replaces the authority URL after "@" in an issuer instance with a stable digest, because audit records carry no full URLs yet must still tell two authorities apart. See [ADR 0039](0039-agent-identities.md).
- **Removing an Agent identity stops calls immediately** (`outboundaccess.KubernetesResolver`, `outboundaccess.KubernetesResolver.requireLiveIdentityAgent`): The resolver refuses identity-backed calls as soon as an Agent's spec.identity is removed, without waiting for the Agent's next reconcile to mark its claim releasing. outboundaccess.KubernetesResolver.requireLiveIdentityAgent requires the bound Agent to exist, hold the claim and still name the identity in its spec, because the claim is marked releasing only on the Agent's next reconcile; a releasing claim stays held so no other Agent can take the identity, but it is no longer used.
- **Tasks from the grant's second are refused** (`outboundaccess.KubernetesResolver`, `outboundaccess.KubernetesResolver.requireLiveIdentityAgent`): Kubernetes times have one-second precision, so the resolver treats a Task created within the same second as an identity claim grant as possibly predating the grant and refuses its identity calls. A regranted identity claim covers only Tasks created strictly after the grant; because both times have one-second precision, outboundaccess.KubernetesResolver.requireLiveIdentityAgent also refuses a Task from the grant's own second.
- **Tasks from before enforcement stay refused** (`outboundaccess.KubernetesResolver`, `outboundaccess.KubernetesResolver.IdentityEnforcementStart`): Until an Agent reconciles and its identity claim is granted again, the resolver refuses identity calls from Tasks created before the current enforcement period, since they may have been created while the check was off. outboundaccess.KubernetesResolver.IdentityEnforcementStart reports when the current Agent use enforcement period began; a Task created before it may have been created while the check was off, so it gets no Agent identity credential even before the claim is granted again. Nil judges a Task by the claim's grant time alone.
- **Connection refusals are safe to relay** (`outboundaccess.ConnectionRequiredError`): outboundaccess.ConnectionRequiredError is returned before anything is sent, and its message is built only from the provider's name, display name, namespace and the link's state, never from a credential or upstream response, so the agent can relay it and the controller can log it.
- **Remediation commands name the Task namespace** (`outboundaccess.ConnectionRequiredError.Error`): outboundaccess.ConnectionRequiredError.Error adds -n <namespace> to the suggested commands when the Task's namespace is known, so the person lists and deletes links there rather than in their CLI default namespace.
- **Tool schemas cannot weaken curated ones** (`outboundaccess.DeclaredConnectorTool`): outboundaccess.DeclaredConnectorTool accepts a Tool only when its parameter schema is semantically equal to the provider's curated schema; an absent, weaker or broken schema cannot replace it.
- **Tool timeouts cannot exceed the curated timeout** (`outboundaccess.DeclaredConnectorTool`): outboundaccess.DeclaredConnectorTool refuses a Tool that would keep a credential-bearing request open longer than the provider's curated timeout; both sides default to 30s. outboundaccess.DeclaredConnectorTool requires a Tool's timeout to equal the provider's curated bound so a credential-bearing request is never held open longer than allowed; an omitted timeout means the 30s default and an explicit nonpositive one is refused because the executor would run it without a deadline.
- **Explicit zero timeouts are refused** (`outboundaccess.DeclaredConnectorTool`): outboundaccess.DeclaredConnectorTool refuses an explicit 0s or negative timeout rather than reading it as the default, because it would run a credential-bearing request without a deadline.
- **Built-in tools need github.com credentials** (`outboundaccess.DeclaredConnectorTool`): outboundaccess.DeclaredConnectorTool never serves a built-in Tool from a provider whose OAuth token URL does not issue github.com credentials, even when its declaration slipped past validation.
- **Connection mode judges arguments before credentials** (`outboundaccess.KubernetesResolver.Resolve`): In connection mode outboundaccess.KubernetesResolver.Resolve rejects arguments the curated schema refuses before the credential source runs, so a refused call can never refresh or shred credential custody.
- **Unbound destinations are refused before credentials** (`outboundaccess.KubernetesResolver.Resolve`): In connection mode outboundaccess.KubernetesResolver.Resolve refuses MCP-backed Tools and templated URLs, whose requests could not be held to the exact curated destination, before the credential source runs.
- **Forwarded writes match only write declarations** (`outboundaccess.DeclaredConnectorTool`): outboundaccess.DeclaredConnectorTool matches a forwarding Tool's write only against a declaration that grants writes, and the call is then judged as a write, so it needs a readWrite link.
- **Own ServiceAccount token is parsed unverified** (`outboundaccess.ServiceAccountFromToken`): outboundaccess.ServiceAccountFromToken reads the ServiceAccount from the token subject without checking its signature, because it is only used on the process's own mounted token.
- **Controller ServiceAccount tokens are never minted** (`outboundaccess.KubernetesResolver.Resolve`): outboundaccess.KubernetesResolver.Resolve refuses a direct policy naming the reserved controller ServiceAccount before any TokenRequest, so the controller's token never reaches a policy's token endpoint.
- **Connection mode resolves only the requester's credential** (`outboundaccess.ResolveRequest.Requester`): outboundaccess.ResolveRequest.Requester is the Task's verified human identity, and connection-mode policies resolve that person's credential and nobody else's.
- **Connection resolution requires the frozen Connection** (`outboundaccess.ResolveRequest.FrozenConnections`): outboundaccess.ResolveRequest.FrozenConnections maps policy name to the Connection identity frozen into the Task's execution snapshot at dispatch; connection-mode resolution requires an entry and fails closed when the live Connection differs.
- **Resolution refuses a policy changed since the caller's check** (`outboundaccess.ResolveRequest.CheckedPolicy`): When outboundaccess.ResolveRequest.CheckedPolicy is set, resolution refuses a policy object whose UID or generation changed after the caller validated it against the dispatched configuration, rather than injecting under a different policy.
- **Person tokens go only to declared Tools** (`outboundaccess.ResolveRequest.Tool`): Connection-mode resolution releases a credential only to a Tool the ConnectorProvider declares with the same URL, method and class, so a policy cannot be attached to an arbitrary endpoint to exfiltrate a person's token.
- **TaskUID only attributes audit records** (`outboundaccess.ResolveRequest.TaskUID`): outboundaccess.ResolveRequest.TaskUID is the caller-authenticated Task UID and is used only to attribute identity use records, including refusals for Tasks with no identity binding; it grants nothing.
- **Agent identity policies act only as the frozen identity** (`outboundaccess.ResolveRequest.AgentIdentity`): agentIdentity-mode policies act only as the identity in outboundaccess.ResolveRequest.AgentIdentity, frozen into the Task's binding; a nil binding fails them closed.
- **Only Tasks created after the claim grant may use the identity** (`outboundaccess.AgentIdentityBinding.TaskCreated`): outboundaccess.AgentIdentityBinding.TaskCreated is compared with the identity claim's grant time because only a Task created after the grant was checked for Agent use while the Agent named the identity.
- **Delegated mode requires managed egress** (`outboundaccess.AgentIdentityBinding.ManagedEgress`): Delegated agentIdentity mode refuses every runtime except built-in RuntimePools, reported by outboundaccess.AgentIdentityBinding.ManagedEgress, because only their Pods reach the network solely through Orka.
- **Definitive issuer refusals stop cached identity tokens** (`outboundaccess.issuerRefusedIdentity`): outboundaccess.issuerRefusedIdentity fails closed once the issuer has definitively refused the Agent's identity, so a cached policy token is not served for new calls; an unreachable issuer or a not-yet-verified identity does not refuse here, and the issuer's own answer decides those calls.
- **Only the controller issues identity credentials** (`outboundaccess.AgentIdentityTokenSource`): outboundaccess.AgentIdentityTokenSource and ConnectionCredentialSource exist only in the controller; worker Pods have no implementation and therefore fail closed on agentIdentity- and connection-mode policies.
- **Forwarding Tools match only same-protocol declarations** (`outboundaccess.ToolBinding.Forward`): A forwarding Tool, marked by outboundaccess.ToolBinding.Forward, matches only a forwarding declaration of the same protocol; its request method comes from the call, so the declared method is not compared.
- **Built-in Tools match only Builtin declarations** (`outboundaccess.ToolBinding.Builtin`): A built-in Tool, marked by outboundaccess.ToolBinding.Builtin, matches only a Builtin declaration of the same name and class and must carry no destination, headers, schema or timeout of its own; custom Tools never match a built-in declaration.
- **Tool static headers must match the declaration exactly** (`outboundaccess.ToolBinding.Headers`): outboundaccess.DeclaredConnectorTool requires a Tool's static headers to equal the provider's declared set by canonical name and exact value, because an undeclared header could change what the credential authorizes.
- **Frozen Connections load by their actual name** (`outboundaccess.FrozenConnection.Name`): outboundaccess.FrozenConnection.Name records the Connection object's name because an adopted link may live under a non-canonical name; the credential source loads by this name, not the canonical one, when it is set.
- **Live Connection must carry the frozen grant** (`outboundaccess.FrozenConnection.GrantSequence`): The live Connection must carry exactly the consent count in outboundaccess.FrozenConnection.GrantSequence, because a re-link of the same object is a new grant the snapshot never bound.
- **Connections are pinned to the policy generation** (`outboundaccess.FrozenConnection.PolicyGeneration`): outboundaccess.FrozenConnection.PolicyUID and PolicyGeneration pin the policy a Connection was frozen under; a policy edited since, for example its credential output header or prefix, needs a re-dispatch.
- **Built-in Connection keys cannot collide with policy names** (`outboundaccess.builtinConnectionKeyPrefix`): outboundaccess.builtinConnectionKeyPrefix is "builtin:" so built-in tool keys share the FrozenConnections map with policy names safely: policy names are DNS labels and never contain a colon.
- **Tool and credential are judged against one provider state** (`outboundaccess.DeclaredConnectorTool`): The connection credential source re-applies outboundaccess.DeclaredConnectorTool to the executing Tool against the same provider state it validates the returned credential with, so the tool and the credential are always judged against one provider state. outboundaccess.DeclaredConnectorTool returns the provider's curated HTTP definition exactly matching the executing Tool and never matches built-in declarations with custom Tools; the credential source re-applies it against the provider state it validates the credential with.
- **Delegated mode re-checks the Connection without touching credential material** (`outboundaccess.ConnectionLivenessChecker`): outboundaccess.ConnectionLivenessChecker verifies, reading only the grant from custody and never the credential material or a refresh, that the requester's Connection is still present, not deleting, Ready and on the frozen UID, generation and grant; Delegated mode requires its ConnectionCredentialSource to implement it.
- **Executor validates arguments before sending credentials** (`outboundaccess.Resolution.Parameters`): outboundaccess.Resolution.Parameters carries the provider-declared schema so the executor validates the call's arguments before the credential leaves the process.
- **Delegated calls require a live Task and Session** (`outboundaccess.KubernetesResolver.DelegationLive`): outboundaccess.KubernetesResolver.DelegationLive checks before every Delegated call that the Task is still running and its Session still open, so cancelling the Task or closing the Session stops the Agent acting for the requester at once; nil fails every Delegated call closed.
- **No policy may mint the controller's ServiceAccount token** (`outboundaccess.KubernetesResolver.ReservedServiceAccount`): outboundaccess.KubernetesResolver.ReservedServiceAccount is the controller's own ServiceAccount; no policy may request a token for it, because the token carries the controller's authority, which the Entra agent identity blueprint trusts, to whatever endpoint the policy names.
- **Authorize credential selectors before reading Secrets** (`outboundaccess.KubernetesResolver.Resolve`): outboundaccess.KubernetesResolver.Resolve runs validatePolicyCredentialAuthority on the policy's exact selectors before ResolveReferences, because reference validation may read Secret data and the policy may have changed between caller checks.
- **A policy leaving connection mode is refused** (`outboundaccess.KubernetesResolver.Resolve`): When a Task was dispatched under a person's Connection for a policy, outboundaccess.KubernetesResolver.Resolve refuses the policy if it has since moved to another adapter, so it never hands out a service credential or route instead.
- **Built-in bindings carry the catalog timeout** (`outboundaccess.declaredBuiltinConnectorTool`): outboundaccess.declaredBuiltinConnectorTool requires the binding to carry exactly the catalog's timeout for the built-in, so the credential is refreshed to cover the whole call and never a caller-chosen bound.
- **Two spellings of one header do not match** (`outboundaccess.sameStaticHeaders`): outboundaccess.sameStaticHeaders rejects a header set with two spellings of one canonical name, because they would collapse into one field on the wire and the set would not be the declared one.
- **Describe a copy of shared refresh errors** (`outboundaccess.KubernetesResolver.resolveRequesterConnection`): A shared credential refresh hands every waiter the same error value, so outboundaccess.KubernetesResolver.resolveRequesterConnection describes a copy it owns instead of mutating the shared ConnectionRequiredError.
- **Unfrozen Connection refusals are explained read-only** (`outboundaccess.KubernetesResolver.unfrozenConnectionRefusal`): outboundaccess.KubernetesResolver.unfrozenConnectionRefusal explains from the requester's current links why a Task carries no Connection (none, several, expired, not Ready, or not bound); it only reads and returns nil when it cannot tell, so the caller keeps its generic refusal.
- **Identity credentials refuse unbound destinations** (`outboundaccess.KubernetesResolver.Resolve`): agentIdentity-mode resolution refuses MCP-backed Tools and Tools whose URL the call's arguments rewrite, because the credential is for one fixed destination and could otherwise reach a host the policy author never chose.
- **Agent identity use is checked before issue and release** (`outboundaccess.KubernetesResolver.requireLiveIdentityAgent`): outboundaccess.KubernetesResolver.requireLiveIdentityAgent runs before a credential is requested and again before it is released, since issuing can take seconds and the Agent can lose its identity or be deleted meanwhile.
- **Deleting Agents stop identity calls at once** (`outboundaccess.KubernetesResolver.requireLiveIdentityAgent`): outboundaccess.KubernetesResolver.requireLiveIdentityAgent refuses as soon as the Agent has a deletion timestamp, even while a finalizer keeps it readable.
- **Delegated liveness is re-checked after issuance** (`outboundaccess.KubernetesResolver.issueAgentIdentityToken`): outboundaccess.KubernetesResolver.issueAgentIdentityToken re-checks delegation liveness once the credential is issued, because refreshing the requester's token and the on-behalf-of exchange can take many seconds and a Task or Session ended meanwhile must not get it.
- **Identity credentials are released only under the current policy** (`outboundaccess.KubernetesResolver.requireUnchangedPolicy`): After issuing an identity credential, outboundaccess.KubernetesResolver.issueAgentIdentityToken re-reads the policy with requireUnchangedPolicy, which refuses unless it is the same object at the same generation, still accepted with resolved references and not deleting, since it may have been revoked or narrowed, including its delegation age.
- **Delegation liveness and age are judged last** (`outboundaccess.KubernetesResolver.issueAgentIdentityToken`): outboundaccess.KubernetesResolver.issueAgentIdentityToken checks delegation liveness and age after the Connection re-check, because that re-check reads custody and Kubernetes and can block, so the delegation must be judged as of release.
- **Unknown delegation start counts as expired** (`outboundaccess.KubernetesResolver.delegationExpired`): outboundaccess.KubernetesResolver.delegationExpired treats a delegation as expired when maxDelegationAge has passed since the root requester's last action, or when that action is unknown.
- **Trusted Service references are exact tuples** (`outboundaccess.TrustedServiceReferences`): outboundaccess.TrustedServiceReferences holds exact namespace/name/port tuples; wildcards are intentionally unsupported so cross-namespace trust is always named explicitly.
- **Platform ServiceAccounts are refused by name too** (`outboundaccess.TrustConfig.PlatformServiceAccounts`): outboundaccess.TrustConfig.PlatformServiceAccounts lists Orka's own ServiceAccounts by namespace/name so they are refused as token sources even without the platform label, for example an externally managed controller account.
- **The AI worker may source its own ServiceAccount** (`outboundaccess.TrustConfig.TokenRequester`): outboundaccess.TrustConfig.TokenRequester names the AI worker ServiceAccount the controller grants TokenRequest to; it may be a token source despite being a platform account, because a token for itself grants it nothing it lacks, while any other platform account is refused.
- **Validation issues never carry credentials** (`outboundaccess.Issue`): outboundaccess.Issue is written to status, so its Message must never contain credentials or a credential-bearing URL.
- **Entra resources must form a valid scope** (`outboundaccess.ValidateSpec`): Orka appends /.default to an agentIdentity entra.resource, so validation rejects a resource with a query or fragment and one without a host or with userinfo, which would produce a scope Entra refuses on every call.
- **Credential prefixes must be valid header values** (`outboundaccess.ValidateSpec`): An output prefix is joined with the credential into one header value, so validation requires it to be a valid HTTP field value with no control bytes other than tab and no DEL.
- **Platform ServiceAccounts are never token sources** (`outboundaccess.ResolveReferences`): outboundaccess.ResolveReferences refuses a ServiceAccount source that is an Orka platform account (by platform label or configured name), because the AI worker would request its token and gain the controller's, other workers', proxies' or publisher's authority; the worker's own account is exempt since its token gives nothing new.
- **Reserved credential output headers** (`outboundaccess.ValidateCredentialHeader`): Outbound access validation refuses credential output headers used for trace propagation, Content-Type and Idempotency-Key: trace propagation would overwrite or leak a credential into telemetry, every Tool request sets its own Content-Type, and brokered consequential calls carry their approval operation key in Idempotency-Key, so such a policy would collide on every call.
- **The platform label, not the chart name, marks platform accounts** (`outboundaccess.ResolveReferences`): outboundaccess.ResolveReferences identifies platform ServiceAccounts by the platform identity label rather than app.kubernetes.io/name, because a Helm nameOverride changes the chart name.

- **Outbound policy resolution is fenced to the checked object** (`worker.ToolExecutor.SetCheckedPolicy`): ToolExecutor.SetCheckedPolicy records the OutboundAccessPolicy object the caller validated before execution, and later resolution of that policy name refuses any other object or generation.
- **Task transaction authority never falls back to process files** (`worker.ToolExecutor.SetTransactionAuthority`): ToolExecutor.SetTransactionAuthority sets task-scoped transaction authority, and calling it with an empty token deliberately disables any fallback to process-global token files so one Task cannot use another's authority.
- **Worker Task UID comes from controller-set environment** (`worker.NewToolExecutor`): NewToolExecutor reads the executing Task UID from the worker Pod environment because the controller sets it and overrides any Task-supplied value, exactly as it does for the Task namespace.
- **Brokered AgentRuntime tools resolve credentials in Orka** (`worker.NewToolExecutorForNamespace`): NewToolExecutorForNamespace builds the controller-side executor for brokered AgentRuntime tool calls so Orka, never the remote runtime backend, resolves tool credentials.
- **Linked-account and Agent identity credentials never follow redirects** (`worker.ToolExecutor.Execute`): Tool requests carrying a linked-account or Agent identity credential are bound to the declared destination, so their HTTP client returns redirects unfollowed; Go forwards custom headers on redirects and would otherwise carry the credential elsewhere.
- **Substrate MCP proxy and router requests never follow redirects** (`worker.ToolExecutor.Execute`): Tool requests sent through the Substrate MCP proxy or router never follow redirects, because a redirect would carry the workload or router credential to another destination.
- **Private-endpoint fixture allowance keeps transport hardening** (`worker.directCredentialHTTPClient`): The private-endpoint fixture allowance relaxes only which addresses a linked-account or Agent identity request may reach; directCredentialHTTPClient still forbids proxies and custom TLS dialers and requires verified TLS 1.2 or newer.
- **Private connection endpoints are a controller dev-only fixture** (`worker.allowPrivateConnectionEndpoints`): allowPrivateConnectionEndpoints lets linked-account and Agent identity requests reach private and cluster-local destinations (still refusing infrastructure addresses) only for local and CI fixtures; the controller sets it once from a dev-only flag, worker Pods never set it, and it must never be enabled in production.
- **Identity credentials travel only to the declared origin** (`worker.toolHTTPClient`): toolHTTPClient returns a redirect unfollowed for linked-account and Agent identity requests because Go forwards custom headers on redirects, and those credentials may travel only to the declared origin.
- **Transaction tokens are single-hop** (`worker.toolHTTPClient`): toolHTTPClient strips the Txn-Token header from any followed redirect, so transaction authority stays single-hop even when an authenticated resource credential may follow a same-origin canonical redirect.
- **Tool error diagnostics include hidden causes and need redaction** (`worker.ToolErrorDiagnostic`): ToolErrorDiagnostic returns the cause a gateway MCP failure deliberately leaves out of its Error text, for operator logs only; callers must still redact and bound it before logging.
- **ToolExecutionError marks only admitted-call failures** (`worker.ToolExecutionError`): ToolExecutionError marks only failures returned by an admitted tool call, never authorization, transport, cancellation or malformed-response errors, and callers must apply their own disclosure policy before exposing its upstream diagnostic as an MCP result.
- **Redirected tool status may follow an applied request** (`worker.ToolHTTPStatusError`): ToolHTTPStatusError.Redirected reports that the non-2xx status answered a followed redirect rather than the original request, which may already have taken effect, so callers must not treat it as a clean failure to retry.
- **Completed API failures are tool results, auth failures are not** (`worker.ToolExecutor.Execute`): A tool endpoint's 4xx or 5xx answer is returned as a ToolExecutionError the model may see as a tool result, except 401, 403 and 407, which, like redirect failures, remain protocol errors.
- **Agent identity credentials stay on the declared destination** (`worker.agentIdentityOriginError`): agentIdentityOriginError refuses any request whose origin differs from the Tool's declared destination, so an Agent identity credential never goes to an origin chosen by call arguments.
- **Connection outbound access is refused on MCP-backed Tools** (`worker.ToolExecutor.prepareConnectionRequest`): A linked-account credential is bound to the provider-declared destination, so connection outbound access policies fail closed on MCP-backed Tools, which send to an actor endpoint rather than spec.http.url, and on any prepared request whose origin differs from the declared URL.
- **Connection credentials attach only to schema-admitted arguments** (`worker.ToolExecutor.prepareConnectionRequest`): The caller, whether a worker or an ACP runtime, is not trusted to have honored the provider's curated schema, so connectors.ValidateToolArguments runs before a person's linked-account credential is attached to a request.
- **Worker token requester mirrors controller resolution** (`worker.toolExecutorTokenRequester`): toolExecutorTokenRequester names the worker's own ServiceAccount as namespace/name so an OutboundAccessPolicy that exchanges the worker's own identity resolves in the worker exactly as it does in the controller.
- **Substrate MCP proxy carries the tool token in a separate header** (`worker.SubstrateMCPToolTxnTokenHeader`): Callers of the Orka MCP proxy send the task-scoped transaction token in SubstrateMCPToolTxnTokenHeader, which the proxy forwards to the actor as Txn-Token; the caller's own Txn-Token header is reserved for Orka API authentication and is never forwarded.
- **Substrate MCP proxy requests are fenced to the validated Tool revision** (`worker.SubstrateMCPToolUIDHeader`): The Orka MCP proxy reloads the Tool, so callers send SubstrateMCPToolUIDHeader, SubstrateMCPToolGenerationHeader and SubstrateMCPToolActorHeader naming the exact Tool lifetime, spec generation and Actor they validated for credential authority and approvals; SubstrateMCPToolBindingMatches refuses any mismatch or missing value rather than running with another credential or Actor.
- **Substrate MCP actor target comes only from Tool status** (`worker.SubstrateMCPActorTarget`): SubstrateMCPActorTarget and SubstrateMCPRouter.NewRequest derive the router target only from the controller-owned Tool status, so caller input can never select which Actor receives a request.
- **Substrate MCP router client must not follow redirects** (`worker.SubstrateMCPRouter.HTTPClient`): Callers of SubstrateMCPRouter.HTTPClient must not follow redirects, because the client carries the manager's router mTLS identity.
- **Tool configuration cannot set Orka-owned Substrate MCP headers** (`worker.SubstrateMCPReservedHeader`): SubstrateMCPReservedHeader lists routing, authority, transport, MCP session, transaction and idempotency headers that Orka owns; a Tool configuration must never set them on a Substrate MCP request.
- **Egress-injected Substrate MCP Secrets need Task credential authority** (`worker.ToolExecutor.validateSubstrateMCPEgressCredentialAuthority`): ToolExecutor.validateSubstrateMCPEgressCredentialAuthority checks that the Task may use every Secret the Substrate egress gateway injects into the actor's outbound requests, on both the router and the proxy route, since a call on either route causes their use.
- **Substrate MCP router calls are always bounded** (`worker.substrateMCPRouterClient`): The manager's shared Substrate router HTTP client has no timeout, so substrateMCPRouterClient copies it with the executor's default timeout and a Tool's own timeout still applies on top; no router call is unbounded.
- **Credential authority is checked before using the Substrate MCP proxy** (`worker.ToolExecutor.prepareSubstrateMCPRequest`): Although the Orka MCP proxy resolves and injects Tool-configured credentials, ToolExecutor.prepareSubstrateMCPRequest still checks the Task's credential authority first, so a Task that may not use the Tool's Secret never asks the proxy to use it.
- **Substrate MCP binding check fails closed on missing values** (`worker.SubstrateMCPToolBindingMatches`): SubstrateMCPToolBindingMatches requires the request's Tool UID, spec generation and Actor to equal the current Tool exactly, and missing values on either side never match.
- **Substrate MCP calls require an Actor verified for the current generation** (`worker.SubstrateMCPToolReadyForCurrentGeneration`): After a Tool spec update, status still names the previous Actor until reconciliation, so SubstrateMCPToolReadyForCurrentGeneration refuses calls until the controller has verified the Actor for the current spec generation; a newly configured credential must never reach the old Actor.
- **Forwarded bodies leave room for the result envelope** (`worker.forwardResultEnvelopeBytes`): forwardResultEnvelopeBytes reserves 64 KiB of the broker's MCP result bound for the status, headers and JSON escaping wrapped around a forwarded response body.
- **Only the ACP broker runs forwarding Tools** (`worker.ToolExecutor.AllowForwarding`): ToolExecutor.AllowForwarding is called only by the ACP broker, where the runtime built the call from a client request and the broker checked it against the prompt's frozen tool policy; native workers and the internal connector endpoint refuse forwarding Tools.
- **Forwarded requests stay on the Tool origin with no caller headers** (`worker.ToolExecutor.prepareForwardRequest`): ToolExecutor.prepareForwardRequest builds a forwarded read, or a write with its JSON body through the Tool's write tool, on the Tool's own origin; no headers come from the call, and the outbound access policy adds the credential as for any Tool.
- **Forwarded writes need the write class and an allowing Tool** (`worker.ToolExecutor.prepareForwardRequest`): A forwarded write runs only when the broker handed the executor the Tool with the write brokered tool class and the Tool sets spec.http.forward.writes; a read sent as the write tool, or a write without both, is refused.
- **Forwarded writes keep their If-Match precondition** (`worker.ToolExecutor.prepareForwardRequest`): prepareForwardRequest copies a forwarded write's If-Match value onto the upstream request, because dropping it would run a guarded write unguarded.
- **Forwarded responses are returned verbatim and redirects unfollowed** (`worker.executeForwardRequest`): executeForwardRequest returns the upstream answer whatever its status so the client sees the service's own errors, and never follows redirects so the credential stays on the Tool's origin while the client handles the redirect.
- **Escaped forwarded body overflow is a tool failure** (`worker.executeForwardRequest`): JSON escaping can grow a forwarded body past harnessv2.MaxMCPResultBytes even when the raw body fits; executeForwardRequest reports that as a ToolExecutionError rather than a broker error.
- **Continuation matching handles JSON-escaped ARM links** (`worker.forwardContinuationRe`): forwardContinuationRe matches Azure Resource Manager $skiptoken parameters, including %24 and JSON \u0024/\u0026 escapes, in nextLink values and URL-valued headers, and stops a value at a backslash so a following escaped separator ends it.
- **Forwarded redaction keeps paging tokens but not credentials** (`worker.redactForwardedText`): redactForwardedText keeps continuation parameters because the generic token= redaction rule would replace a $skiptoken value and the gateway would refuse the next page, but it removes every credential Orka injected first, continuation parameters included.
- **Continuation tokens are kept only when credential-free** (`worker.redactForwardedText`): A continuation token is kept verbatim only when forwardValueHoldsSecret finds no injected credential in it under any encoding a client would undo; otherwise its value is redacted.
- **Percent-encoded credentials are found under any escaping** (`worker.redactPercentEncodedSecrets`): redactPercentEncodedSecrets decodes text while mapping each decoded byte back to its source and replaces only the source of each match, so a credential the upstream percent-encoded in a non-standard way, such as %2D for '-', is removed while the rest of a URL is unchanged.
- **Forwarded JSON bodies stay valid after redaction** (`worker.redactForwardedBody`): redactForwardedBody removes injected credentials from raw bytes first, then redacts a JSON body value by value, never rewriting arrays, objects, numbers or nulls except to redact, so a valid response stays valid JSON and a success status never carries a body the runtime cannot decode; non-JSON bodies are redacted as text.
- **Forwarded JSON strings are redacted after decoding** (`worker.redactForwardedJSON`): redactForwardedJSON judges string literals in decoded form, in keys and values, so a credential the upstream escaped (for example \u002d for '-') is still found, and copies every other byte unchanged.
- **Credential-bearing JSON numbers become redacted strings** (`worker.redactForwardedJSON`): redactForwardedJSON turns a JSON number that contains an injected credential into the string "[REDACTED]"; the literals true, false and null cannot hold one.

### `internal/workspace/daemonprotocol`

- **Substrate router routes only by ate-target-actor** (`workspace/daemonprotocol.TargetActorHeader`): The Substrate router selects the Actor only from the TargetActorHeader (ate-target-actor) header and ignores Host and :authority for routing, so callers must set that header and must not rely on the URL host.
- **Router targets require qualified Actor IDs** (`workspace/daemonprotocol.TargetActor`): daemonprotocol.TargetActor accepts only qualified name.atespace Actor IDs and rejects unqualified ones, so a request can never be routed to an Actor in an implied Atespace.

### `internal/workspace`

- **Resource exhaustion is a retryable capacity wait** (`workspace.ErrorKindResourceExhausted`): workspace.ErrorKindResourceExhausted reports exhausted provider capacity or quota; it is retryable, and callers surface it as waiting for capacity rather than as a failure.
- **Qualified Substrate Actor IDs carry their own scope** (`workspace.SubstrateConfig.Atespace`): SubstrateConfig.Atespace scopes only unqualified Actor names; qualified name.atespace Actor IDs carry their own scope and must never depend on a name-to-namespace cache.
- **Real Substrate control clients always use sealed bootstrap** (`workspace.SubstrateConfig.SealedBootstrap`): SubstrateConfig.SealedBootstrap opts injected control clients into native process-bound credential delivery; real upstream control clients always use the sealed bootstrap protocol regardless of the flag.
- **Substrate router clients never follow Actor redirects** (`workspace.NewSubstrateExecutor`): NewSubstrateExecutor copies a caller-supplied HTTP client, keeping its transport and connections, and installs refuseSubstrateRouterRedirect so no router client follows an Actor's redirect.
- **Executor closes only HTTP clients it built** (`workspace.SubstrateWorkspaceExecutor.Close`): SubstrateWorkspaceExecutor.Close drops idle router connections only when the executor built its HTTP client itself; a caller-supplied client is shared and left alone.
- **Native bootstrap retries reuse the delivered handoff credential** (`workspace.SubstrateWorkspaceExecutor.actorHandoffs`): SubstrateWorkspaceExecutor caches the per-Actor handoff credential in actorHandoffs before a possibly ambiguous bootstrap PUT, so retries use the credential already delivered to that Actor/Pod lifetime; a new executor recovers the installed credential through an authenticated sealed reply instead of minting another.
- **Substrate DeleteActor is snapshot-free and UID-fenced** (`workspace.substrateControlClient.DeleteActor`): substrateControlClient.DeleteActor terminates an Actor in any state without creating a snapshot, and a nonempty actorUID is enforced as a native precondition so a recreated Actor with the same ID is never deleted.
- **Unbooted Substrate Actors are re-verified before readiness** (`workspace.SubstrateWorkspaceExecutor`): Fresh upstream Actors have no current template UID until their first boot, so the executor accepts an unbooted Actor only provisionally and checks its identity again before reporting readiness.
- **Substrate exec results get a bounded collection window** (`workspace.SubstrateWorkspaceExecutor.execResultContext`): The workspace daemon's whole-second command timer can expire before it publishes the final result, so the executor adds substrateExecResultTimeout to collect it without extending the caller's deadline or cancellation and never replays the command.
- **Controller mints per-Actor handoff credentials** (`workspace.SubstrateWorkspaceExecutor.issueActorHandoffCredential`): Upstream Substrate v1 lets only its egress gateway mint actor JWTs, so issueActorHandoffCredential generates a random per-Actor bearer in the controller and delivers it through the sealed bootstrap, bound to the exact Actor UID and worker Pod; injected clients without sealed bootstrap keep the configured static handoff token.
- **Workspace deletion uses native AnyState delete and fails closed** (`workspace.SubstrateWorkspaceExecutor.Delete`): Workspace deletion calls native AnyState DeleteActor rather than suspending first, because suspension creates an unwanted snapshot and cannot delete stateless MCP Actors whose template Data policy has no durable volume; an uncertain delete must not restore credentials or report completion.
- **Substrate worker inventory is matched by worker assignment** (`workspace.substrateWorkerHostsActor`): Native Substrate Workers carry no Actor ID, so substrateWorkerHostsActor correlates inventory with the Actor's immutable worker assignment and also checks the Pod UID when it is known.
- **Sealed handoff recovery never replaces the installed token** (`workspace.SubstrateWorkspaceExecutor.recoverActorHandoff`): During sealed bootstrap recovery, an authenticated empty reply proves the Actor process has not been seeded, and a recovered credential stays only in controller memory and never replaces the token installed in the process.
- **Bootstrap envelopes bind to the observed Pod assignment** (`workspace.SubstrateWorkspaceExecutor.nativeWorkspaceBootstrapRequest`): The provider projects Actor identity but not Pod identity into the process, so nativeWorkspaceBootstrapRequest reads the Actor after the challenge and binds the process key to that observed assignment; a later reroute cannot decrypt the envelope.
- **Substrate Actor keys are routable names, not lifetime fences** (`workspace.SubstrateActorKey`): SubstrateActorKey joins the Actor name and Atespace with a dot, which is unambiguous because both are DNS labels; the key only routes, and resource UIDs, not this name, fence an Actor's lifetime.
- **Substrate lifecycle RPCs get a longer bounded deadline** (`workspace.substrateRPCDeadline`): substrateRPCDeadline gives native lifecycle RPCs that synchronously boot, restore or checkpoint an Actor a longer bounded window for image pulls and snapshot I/O while discovery and metadata calls stay short; caller deadlines and cancellation still win, and no failed mutation is replayed.
- **Substrate router client uses pod-certificate mTLS and never redirects** (`workspace.NewSubstrateRouterHTTPClient`): NewSubstrateRouterHTTPClient requires the pod-certificate client identity because upstream atenet-router v1 serves only mTLS from SPIFFE IDs on its ingress allowlist; it never uses proxies for Actor traffic and never follows redirects, since following an Actor's redirect would send the controller's request, body and credentials wherever the Actor names.
- **Substrate client certificates reload on every handshake** (`workspace.NewSubstrateControlClient`): The Substrate control client reloads its certificate pair at every TLS handshake, including reconnects, because Kubernetes rotates projected Secret files in place; error text never includes certificate contents.
- **Booted template identity is inferred only from an older template** (`workspace.grpcSubstrateControlClient.resolveBootedTemplateUID`): Upstream Substrate v1 records an Actor's template UID only on snapshots and resolves the template by name at boot, so resolveBootedTemplateUID uses the current template's UID only when that template already existed when the Actor was created; a later-created template may be a same-name replacement, and the identity stays unknown then or when either timestamp is missing.
- **A deleted template does not make its Actor NotFound** (`workspace.grpcSubstrateControlClient.resolveBootedTemplateUID`): When an Actor's template has been deleted, which upstream allows, resolveBootedTemplateUID leaves the template identity unknown instead of reporting NotFound, because NotFound would make Delete report a live Actor deleted and Claim try to create it; the unknown identity fails every pinned-template comparison, and UID-fenced Delete can still remove the Actor.
- **Substrate boot requests are honored only without a golden seed** (`workspace.grpcSubstrateControlClient.ResumeActor`): Upstream Substrate v1 removed the per-call boot flag, so grpcSubstrateControlClient.ResumeActor honors a boot request only when the Actor has no snapshot or source Tag and its template has golden snapshots disabled, and fails closed otherwise.
- **Native Actor deletion is UID-fenced and snapshot-free** (`workspace.grpcSubstrateControlClient.DeleteActor`): grpcSubstrateControlClient.DeleteActor terminates an Actor in any state without a snapshot and sends a nonempty actorUID as a native precondition so a different Actor recreated under the same name is never deleted; cleanup callers must prove their own lifetime and ownership fences first.
- **Substrate pagination never returns incomplete inventory** (`workspace.substratePages`): substratePages accepts empty pages with a nonempty continuation token but treats a repeated token as a protocol error, never as a reason to return incomplete inventory.
- **Only VOLUMES snapshots count as data-only** (`workspace.substrateSnapshotScope`): substrateSnapshotScope classifies only VOLUMES snapshot fidelity as data-only; ROOTFS keeps no process memory but is not data-only either, so it stays unclassified and data-only checks fail closed on it (ADR 0049). See [ADR 0049](0049-agent-substrate-v1.md).
- **Substrate diagnostics are read-only and separate compatibility from capability** (`workspace.DiagnoseSubstrate`): DiagnoseSubstrate is read-only and reports configuration and observed native API compatibility separately from the adapter's implemented capabilities; execution and router stream timeouts can only be verified by the bundled conformance suite.
- **gVisor is detected from worker sandbox classes** (`workspace.substrateWorkerRunsGVisor`): Substrate v1 templates no longer carry a sandbox class, so substrateWorkerRunsGVisor detects gVisor from the sandbox runtimes each worker registers.
- **Single-Actor workers are proven from placement booking** (`workspace.substrateWorkerFitsExactlyOne`): Upstream workers accept up to --max-actors Actors, which no WorkerPool field sets, so substrateWorkerFitsExactlyOne proves a worker hosts exactly one Actor when its CPU or memory cannot hold a second template-sized booking (limits plus the runtime's fixed and per-GiB overhead) under every runtime it reports, since Actors cold-boot under the class default and restore under the matching restorable runtime.
- **Capacity comparison avoids overflow** (`workspace.substrateWorkerFitsExactlyOne`): substrateWorkerFitsExactlyOne compares capacity minus one booking against the booking instead of doubling the booking, so a large booking cannot overflow.
- **Memory booking mirrors upstream placement** (`workspace.substrateActorMemoryBooking`): substrateActorMemoryBooking mirrors upstream Substrate placement: memory limit plus the runtime's fixed overhead plus its per-GiB overhead scaled to the limit and rounded down, reporting false for negative inputs or int64 overflow, which placement treats as not fitting.
- **Substrate egress schemes map to passthrough or interception** (`workspace.SubstrateEgressSchemeHTTPS`): Orka's Substrate egress scheme "tls" compiles to an upstream tls_passthrough rule, while "https" is intercepted by the egress gateway, so an Actor using https rules must trust the gateway CA bundle.
- **Actor egress rules are capped below the upstream limit** (`workspace.MaxSubstrateEgressRules`): MaxSubstrateEgressRules caps one Actor egress policy at 64 rules, safely below the upstream limit of 256.
- **Egress rules name Secrets, never carry credential values** (`workspace.SubstrateEgressRule`): SubstrateEgressRule never carries credential values; its optional Credential names a Kubernetes Secret key that the egress gateway resolves and injects at request time.
- **Egress credential injection fails closed without a provider** (`workspace.SubstrateEgressCredential`): SubstrateEgressCredential.Provider names the credential provider class the egress gateway was installed with; an empty Provider means injection is not configured, and a rule that needs a credential fails closed.
- **An empty egress allowlist denies all egress** (`workspace.CompileSubstrateActorEgressPolicy`): CompileSubstrateActorEgressPolicy compiles an empty allowlist into an Actor policy with no rules, which denies all egress and answers external DNS with NXDOMAIN.
- **Egress policy errors block Actor resume** (`workspace.SubstrateNativeClient.EnsureActorEgressPolicy`): SubstrateNativeClient.EnsureActorEgressPolicy installs and then re-reads and verifies an Actor's native egress policy; any error means the stored policy may not match, and callers must not resume the Actor.
- **Stored egress policies take effect only after the gateway cache window** (`workspace.SubstrateEgressPolicyState`): Storing a Substrate egress policy does not make it effective at once: the egress gateway caches each Actor's policy by Actor name for --egress-policy-cache-ttl (10s by default) plus a fetch of up to 4s that may have read earlier rules, and nothing invalidates an entry, so SubstrateEgressPolicyState reports the times callers need to wait out that window.
- **Egress enforcement waits from the latest of three timestamps** (`workspace.SubstrateEgressPolicyState.EnforcedAfter`): SubstrateEgressPolicyState.EnforcedAfter adds the gateway cache window to the latest of UpdateTime (replaced rules may be cached), CreateTime (a deleted and recreated policy restarts at version 1 and cannot be told from a new one) and ActorCreateTime (a new Actor may reuse a deleted Actor's name); all three are compared so no store's stamping is relied on, and only a policy unwritten for a full window is enforced at once.
- **Egress policy writes are verified by re-reading** (`workspace.applySubstrateActorEgressPolicy`): applySubstrateActorEgressPolicy re-reads the policy after every write, to verify its own write or reload after a concurrent one, within substrateEgressApplyAttempts optimistic-concurrency attempts.
- **Egress rules must be unique per host and port** (`workspace.canonicalSubstrateEgressRules`): canonicalSubstrateEgressRules rejects two rules for the same host and port because upstream picks exactly one rule per name and port, treats a tie as an admission error, and two schemes on one origin are ambiguous.
- **Exact egress hosts cannot override a wildcard's scheme** (`workspace.rejectSubstrateEgressOverrides`): rejectSubstrateEgressOverrides refuses an exact host that a same-port wildcard rule also matches with a different scheme, because the gateway prefers the exact rule ("*.example.com" matches exactly one extra label), so the overlap would replace the wildcard's scheme for that host instead of adding access.
- **Egress hosts may not end in a numeric label** (`workspace.canonicalSubstrateEgressHost`): canonicalSubstrateEgressHost refuses any host whose final label is all digits, however long, because the Substrate egress gateway rejects such names.
- **Short Kubernetes Service names are refused for egress** (`workspace.canonicalSubstrateEgressHost`): An Actor's resolver tries search suffixes that its DNS relay refuses and cluster DNS answers only fully qualified Service names, so canonicalSubstrateEgressHost refuses hosts ending in "svc" and names the fully qualified form instead of rewriting the host, since the cluster domain is unknown there.
- **Egress policy equality includes gateway effects** (`workspace.substrateEgressRulesEqual`): substrateEgressRulesEqual compares rule sets independent of order but including each rule's exact gateway effects, so a changed or foreign effect, such as a stale credential injection, makes the policy unequal and Orka replaces it.
- **Data-snapshot fences keep native identities inside the controller** (`workspace.SubstrateDataSnapshotFence`): SubstrateDataSnapshotFence carries the provider identities and versions an atomic data-only resume must compare in the same operation that resumes the Actor; provider-native names stay inside the controller and control process, and only a canonical digest is persisted (ADR 0031, 0049). See [ADR 0031](0031-native-substrate-checkpoints.md).
- **Data checkpoint proofs are provider-persisted for recovery** (`workspace.SubstrateDataCheckpointOperationProof`): SubstrateDataCheckpointOperationProof is the provider-persisted result of one atomically fenced data-only checkpoint, recording the exact source ActorVersion accepted; GetActor must keep returning it so the controller can recover an accepted request without creating another snapshot.
- **Data resume proofs distinguish Orka resumes from out-of-band ones** (`workspace.SubstrateDataResumeOperationProof`): SubstrateDataResumeOperationProof records the controller-supplied OperationID with the exact Actor UID and version a data-only resume accepted; GetActor must keep returning it so a restarted controller can tell its own operation from an out-of-band resume of the same deterministic Actor ID.
- **Worker Pod fences are compared atomically and never persisted** (`workspace.SubstrateWorkerPodFence`): SubstrateWorkerPodFence names the exact worker Pod allowed to receive resumed-runtime credentials; providers must compare every field atomically with delivery and must not log or persist it outside safe status.
- **Credential bootstrap envelopes are never persisted or logged** (`workspace.SubstrateCredentialBootstrapEnvelope`): SubstrateCredentialBootstrapEnvelope carries the exact controller-signed credential request a provider delivers to a resumed Actor; its Body contains credentials and must never be persisted or logged.
- **Credential bootstrap results distinguish conflict, completion and fence failure** (`workspace.SubstrateCredentialBootstrapResult`): SubstrateCredentialBootstrapResult.PayloadConflict means the exact workload was already seeded differently, AlreadyComplete means its one-time bootstrap endpoint already closed, and FenceConflict means the provider rejected the Actor or operation comparison and delivered no part of the credential body.
- **Runtime Actor view is sanitized** (`workspace.SubstrateRuntimeActor`): SubstrateRuntimeActor is the sanitized Actor view used by workspace-backed ACP RuntimePools and must carry no snapshot URIs or provider credentials.
- **LatestDataOperationID makes stale data proofs fail closed** (`workspace.SubstrateRuntimeActor.LatestDataOperationID`): SubstrateRuntimeActor.LatestDataOperationID names the latest data-affecting checkpoint or resume mutation for an Actor lifetime; status-only updates leave it unchanged, and every data-affecting mutation, including one outside Orka, must replace it so stale operation proofs fail closed.
- **Unexpected snapshots force a fail-closed recycle** (`workspace.SubstrateRuntimeActor.SnapshotObserved`): Pools without an operator-permitted data-only suspension policy never request snapshots, so SubstrateRuntimeActor.SnapshotObserved there proves a provider-initiated suspension and forces a fail-closed recycle; data-only pools expect snapshots after a requested suspension but still need an immutable Data-scope proof and an atomic provider-side comparison to resume.
- **DataSnapshot is nil without full snapshot identity** (`workspace.SubstrateRuntimeActor.DataSnapshot`): SubstrateRuntimeActor.DataSnapshot is the immutable provider proof for the latest durable snapshot and stays nil when the configured protocol cannot retrieve ActorSnapshot identity, versions and content scope, so resume cannot proceed on partial proof.
- **Resume fencing support requires a persisted resume proof** (`workspace.SubstrateRuntimeActor.DataResumeOperation`): SubstrateRuntimeActor.DataResumeOperation holds the durable result of the last accepted fenced data-only resume, without credentials or snapshot location; providers that cannot persist and return it must not advertise data-snapshot resume fencing support.
- **Checkpoint fencing support requires an idempotent persisted proof** (`workspace.SubstrateRuntimeActor.DataCheckpointOperation`): SubstrateRuntimeActor.DataCheckpointOperation holds the durable result of the last accepted fenced data-only checkpoint; providers that cannot persist and idempotently return it must not advertise data checkpoint fencing support.
- **Verified snapshot fences persist only a digest** (`workspace.SubstrateRuntimeActor.VerifiedDataSnapshotFence`): SubstrateRuntimeActor.VerifiedDataSnapshotFence validates and canonicalizes the immutable proof for a data-only resume and returns a digest that is safe to persist, while provider-native names and UIDs stay inside the controller process.
- **ActorVersion is a mutable resume fence, not snapshot identity** (`workspace.SubstrateRuntimeActor.VerifiedDataSnapshotFence`): VerifiedDataSnapshotFence sets ActorVersion on the fence for the resume comparison but excludes it from immutable snapshot identity, because status-only Actor updates may advance it after checkpointing without changing snapshot identity or data-operation lineage.
- **Immutable snapshot digest excludes ActorVersion** (`workspace.SubstrateDataSnapshotFence.ImmutableIdentityDigest`): SubstrateDataSnapshotFence.ImmutableIdentityDigest hashes only immutable ActorSnapshot identity and deliberately excludes the mutable ActorVersion, so callers can prove an accepted suspension produced a new snapshot.
- **Memory-holding suspension is prohibited for ACP RuntimePool Actors** (`workspace.SubstrateRuntimeActor.SuspendedOrSuspending`): SubstrateRuntimeActor.SuspendedOrSuspending reports only that the provider Actor is Suspended or Suspending, not what its snapshot holds. A suspension whose snapshot keeps supervisor memory is prohibited for ACP RuntimePool Actors; operator-approved data-only pools may suspend to a VOLUMES (data-only) snapshot, which still needs the proof described under SnapshotObserved, and any other snapshot fails data-only checks closed.
- **Running without a Pod IP is transitional** (`workspace.SubstrateRuntimeActor.RunningStatus`): SubstrateRuntimeActor.RunningStatus reports provider liveness regardless of route readiness, because a just-resumed Actor can be Running before its Pod IP is populated, which is transitional and never a crash.
- **Resuming Actors are not crashed** (`workspace.SubstrateRuntimeActor.Resuming`): SubstrateRuntimeActor.Resuming reports an in-flight cold resume that ResumeActor accepted before the workload reached Running; the checkpoint is being consumed, so it must not be treated as a crash.
- **Crashed Actors are deleted only after proving workload absence** (`workspace.SubstrateRuntimeActor.Crashed`): A crashed Substrate Actor's worker workload is no longer assigned, and Orka may delete it only after durably proving the exact prior workload absent.
- **ACP Actor teardown destroys memory before settling** (`workspace.SubstrateRuntimeActorControl`): gVisor suspension checkpoints supervisor memory, including live pool and provider-proxy credentials, into provider snapshot storage, which the ACP execution-workspace contract forbids; because the provider deletes only suspended Actors, SubstrateRuntimeActorControl teardown first deletes the single-workload worker Pod, then calls SettleActor only to move the memoryless Actor into the deletable suspended state, then DeleteActor.
- **Runtime Actor GetActor reports absence as nil without error** (`workspace.SubstrateRuntimeActorControl.GetActor`): SubstrateRuntimeActorControl.GetActor returns a nil Actor and nil error when the Actor does not exist, so callers distinguish absence from lookup failure.
- **ACP runtime Actors always boot fresh** (`workspace.SubstrateRuntimeActorControl.ResumeActor`): ACP RuntimePool hosting always calls SubstrateRuntimeActorControl.ResumeActor with boot=true so one supervisor lifetime is exactly one fresh boot.
- **SettleActor only after workload memory is destroyed** (`workspace.SubstrateRuntimeActorControl.SettleActor`): SubstrateRuntimeActorControl.SettleActor may be called only after the Actor's workload memory has been destroyed and its absence confirmed, because settling a live supervisor would checkpoint credentials.
- **Runtime Actor deletion is idempotent and state-restricted** (`workspace.SubstrateRuntimeActorControl.DeleteActor`): SubstrateRuntimeActorControl.DeleteActor returns nil when the Actor is already absent, and the provider accepts deletion only of suspended (settled) or crashed Actors.
- **Data checkpoint providers must fence atomically and idempotently** (`workspace.SubstrateRuntimeActorDataCheckpointControl`): SubstrateRuntimeActorDataCheckpointControl.SuspendActorForDataCheckpoint must compare every expected Actor and ActorTemplate fence atomically with the suspension, persist the controller OperationID with the exact source Actor UID and version, expose that proof through GetActor, and return the original result for a repeated OperationID without another snapshot; clients that can only preflight mutable resources must not implement it.
- **Data resume providers must fence resume and credential delivery atomically** (`workspace.SubstrateRuntimeActorDataResumeControl`): SubstrateRuntimeActorDataResumeControl.ResumeActorFromDataCheckpoint must compare every Actor, snapshot and ActorTemplate fence atomically with the resume, persist the OperationID with the accepted Actor UID and version, and return the original result on repeat without replaying the snapshot; BootstrapActorCredentialsForDataResume must atomically compare that proof, LatestDataOperationID and the exact worker Pod fence on every call, including AlreadyComplete, and fail before delivering credentials if any changed. Clients limited to preflight checks or unfenced routes must not implement it.
- **Ambiguous Actor creation needs a provider attestation before retry** (`workspace.SubstrateRuntimeActorCreateRecoveryControl`): Retrying an ambiguous CreateActor requires SubstrateRuntimeActorCreateRecoveryControl's provider attestation, because a GetActor miss alone is insufficient: the original call may still materialize the deterministic Actor later.
- **Only W3C trace context crosses to Substrate** (`workspace.substrateTracePropagator`): substrateTracePropagator and substrateTracingTransport send only W3C trace context to Substrate and strip Baggage, because baggage can carry caller-supplied values and must never cross that trust boundary.
- **Substrate gRPC telemetry is parent-only and content-free** (`workspace.substrateGRPCTelemetryOptions`): substrateGRPCTelemetryOptions adds nothing when telemetry is disabled, records spans only inside an existing trace so background reconciles never start a root trace per Substrate call, and uses a handler that records no message events and never reads request metadata, keeping bearer credentials out of spans.
- **Router tracing records no request details and preserves httptrace** (`workspace.substrateTracingTransport`): substrateTracingTransport records only the method, router authority and response status for requests inside an existing trace, never request paths, queries or headers (which name the target Actor and carry handoff and bootstrap credentials), and passes the request context unchanged to the base transport because harness v2 relies on httptrace hooks for written/unwritten request evidence.
- **Router span errors record only a coarse class** (`workspace.substrateTracingTransport.RoundTrip`): substrateTracingTransport records transport failures only as error.type=transport, because transport errors can embed URLs that name Actors or carry sensitive query data.
- **Router spans end at response headers** (`workspace.substrateTracingTransport.RoundTrip`): substrateTracingTransport ends each router span when response headers arrive, because long-lived router streams would otherwise keep the span open for an entire ACP prompt.
- **Workspace execution boundary is backend-neutral** (`workspace`): Package workspace models only the operations Orka needs from a durable-workspace backend and must not import backend client or CRD types such as agent-sandbox's; concrete backends live behind adapters that implement WorkspaceExecutor.

### `workers/ai`

- **Connector approval targets treat empty arguments as {}** (`ai.approvalTargetArguments`): approvalTargetArguments replaces empty arguments of a connector-backed Tool with the empty JSON object, because the controller executes and digests such a call as {}; a worker target built from the raw empty bytes would never match the controller's approval digest.
- **Connector approval digest binds the frozen Connection** (`ai.approvalTargetSpecDigest`): approvalTargetSpecDigest digests a connector-backed Tool with its policy and the Connection binding frozen with the Job, because the controller recomputes the same digest from the live Tool and frozen Connection and refuses the claim when either changed; a Job re-created against a re-linked account needs a fresh approval. See [ADR 0063](0063-code-comment-decisions-round-1.md).
- **Approval targets bind the Substrate actor ID** (`ai.approvalTargetSpecDigest`): approvalTargetSpecDigest includes the Atespace-qualified Tool.Status.Actor.ActorID for Substrate-actor MCP tools, because that ID selects the router target behind the Orka MCP proxy; an approval must bind to the exact actor it was granted for.
- **Remote MCP credentials never come from mounted files** (`ai.validateApprovalCustomToolCompatibility`): The approval compatibility check rejects mounted credential sources for approval-gated tools but exempts remote MCP tools, because remote MCP credentials are always read through the exact API Secret selector and never from mounted files, so their approval identity stays bindable.
- **Approval matching validates the original argument bytes** (`ai.handleExplicitRequestApprovalBatch`): The approval gate validates a call's original argument bytes, including duplicate keys and Unicode, before normalizing them for matching, and execution still receives the original call; normalizing first would hide ambiguous payloads from validation.
- **Missing targetArguments never default to the empty object** (`ai.handleExplicitRequestApprovalBatch`): When matching a resolved decision for an explicit request_approval call, the gate only uses the decision if targetArguments is present as an object; normalization drops a declared null, and letting a missing value inherit the empty-object default would match an approval the model never targeted.
- **Explicit approval targets validate severity like the tool** (`ai.explicitApprovalTargetForCall`): explicitApprovalTargetForCall rejects any severity other than empty, warning, or critical, matching RequestApprovalTool.Execute, because a resolved decision can short-circuit the tool and would otherwise let an invalid request bypass its validation.
- **Azure routing test exercises the real run providers** (`ai.TestAzureDeploymentWorkerRouting`): TestAzureDeploymentWorkerRouting builds its providers through run rather than a second copy of the environment-to-config mapping, so the regression covers the mapping the worker actually uses; Kubernetes startup is deliberately outside its scope.
- **Connector response limit covers worst-case escaping** (`ai.connectorToolResponseLimit`): connectorToolResponseLimit is 64 MiB because the controller caps a tool body at 10 MiB and JSON escaping can expand control characters sixfold, plus room for the envelope. postConnectorToolRequest reports a body past the bound as an error instead of truncating it, since a truncated document would later fail to decode as an attempted call.
- **Connector calls retry 503 a few times** (`ai.connectorToolUnavailableRetries`): executeConnectorToolViaController retries a controller 503 up to connectorToolUnavailableRetries times with doubling backoff, because a fresh worker Pod can reach the endpoint before the Task's Job identity is published; nothing was executed, and the window closes within seconds.
- **Unreadable connection bindings fail closed** (`ai.parseConnectionBindings`): parseConnectionBindings returns no bindings for an unreadable value instead of failing, which is safe because every connector approval digest then carries an empty Connection identity that the controller never matches. The bindings carry no token material.
- **Connector proxy timeout clamps before adding margin** (`ai.connectorToolProxyTimeout`): connectorToolProxyTimeout clamps the Tool's declared timeout to connectors.MaxHTTPToolTimeout before adding connectorToolSettlementMargin, so a huge declared duration cannot overflow, and the proxy deadline always exceeds the controller's own tool timeout so a slow but legitimate call is never cut off by the proxy first.
- **Connector settlement margin** (`ai.connectorToolSettlementMargin`): connectorToolSettlementMargin adds 30s to the worker's proxy deadline to cover the controller's own work around the provider call: approval claims, effect-ledger writes, and response encoding.
- **Connector-backed tools never execute in the worker** (`ai.connectorBackedTools`): connectorBackedTools routes Tools behind a connection-mode OutboundAccessPolicy to the controller because the person's token lives only there. A policy that cannot be read is retried briefly and then fails startup, since a connector-backed tool without its policy spec would compute an approval target the controller never matches.
- **Frozen connector digests bound routing** (`ai.connectorBackedTools`): connectorBackedTools always routes a tool whose digest the controller froze into the Job to the controller, which refuses it if its policy or definition drifted; live state can only add connector-backed tools and never route a frozen one back into the worker Pod.
- **Missing connector policy routes to the controller** (`ai.connectorBackedTools`): connectorBackedTools treats a Tool whose OutboundAccessPolicy is missing as connector-backed, so the worker Pod never tries to resolve a credential it may not hold.
- **Connector marker comes only from routing** (`ai.markConnectorBackedTools`): markConnectorBackedTools clears any connector-backed annotation that arrived on the Tool object before setting it from the routing classification, so a Tool cannot opt out of the worker's full approval digest by carrying the annotation itself.
- **Controller client ignores proxies and redirects** (`ai.controllerHTTPClient`): controllerHTTPClient disables inherited proxy settings and refuses redirects so the worker's projected ServiceAccount token is only ever sent to the controller URL itself.
- **Connector errors after send count as attempted** (`ai.executeConnectorToolViaController`): executeConnectorToolViaController marks errors after the controller answered as attempted so the approval gate does not re-fire a consequential action. A pure transport failure is not attempted and does not consume the local approval, because the controller's claim and effect ledger make an exact retry safe.
- **Connector approval ID equals the idempotency key** (`ai.executeConnectorToolViaController`): executeConnectorToolViaController sends the gate's idempotency key as the ApprovalID too, because in the worker's approval gate the approval key doubles as the idempotency key and the controller verifies it before executing.
- **Ambiguous connector transport failures are retry-safe** (`ai.executeConnectorToolViaController`): A transport failure to the controller is ambiguous but is returned without the attempted marker, so it never consumes the local approval; the controller's claim and effect ledger make an exact retry safe by replaying a committed result or refusing a call still executing. A response that arrived but could not be read is attempted.
- **Connector 502 counts as an attempted call** (`ai.decodeConnectorToolResponse`): decodeConnectorToolResponse marks an HTTP 502 from the controller as an attempted tool execution, because 502 means the controller reached the provider and the action may have happened.
- **Gateway reply omission is local-only** (`ai.newNativeGatewayReplySender`): When newNativeGatewayReplySender omits reply_in_conversation it writes only a fixed local reason code to stderr; neither upstream diagnostics nor a remote event request may turn this optional dependency into a leak or a startup dependency.
- **Gateway reply bootstrap failure only omits the tool** (`ai.newNativeGatewayReplySender`): newNativeGatewayReplySender omits reply_in_conversation when it cannot read the Task for bootstrap context: an unreadable Task is not an identity grant, and it is not a reason to fail otherwise valid model work.
- **Gateway reply authenticates durable origin** (`ai.newNativeGatewayReplySender`): newNativeGatewayReplySender authenticates the Task's durable gateway origin rather than current message admission, so later readiness or capability withdrawal cannot hide the tool permanently. Optional service failures omit only this tool, an explicit identity rejection still fails startup, and identity is never inferred from a budget, capability, or 503 error.
- **Gateway reply Task reader uses a static REST mapper** (`ai.newNativeGatewayReplyTaskReader`): newNativeGatewayReplyTaskReader builds a static REST mapper for the Task kind because the shared client's lazy discovery uses context.TODO() rather than the caller's context and could stall bootstrap; a private mapper avoids changing timeouts or mappings for every other worker tool.
- **AI worker tests install a controller-runtime logger** (`ai.TestMain`): The AI worker TestMain installs a controller-runtime logger that writes to the current stderr, as a real application must, so the missing-logger warning never appears while real diagnostics still reach captureNativeReplyStderr's exact warning assertions.
- **Gateway reply tests use uncached tokens** (`ai.TestNativeGatewayReplyTokenReviewBackendUnavailable`): The gateway reply retry tests write a unique, never-authenticated token per case so every attempt goes through a real TokenReview; a shared token would hit the cache and stop exercising the retry path.
- **Idempotency injection tests compare exact number spellings** (`ai.TestInjectIdempotencyKeyPreservesArguments`): The idempotency injection tests compare argument bytes, not only digests, across extreme and unusual JSON number spellings, because injection must preserve the model's exact number spelling and a digest comparison alone would miss a respelling.
- **Injection test tool declares real parameter types** (`ai.injectionRegistryTool`): injectionRegistryTool declares typed parameters so the idempotency injection tests exercise both injection and the real Registry.Execute type validation, not only a permissive test tool.
- **Corrected tool arguments need their own approval** (`ai.handleExplicitRequestApprovalBatch`): Approvals bind exact tool arguments, so a call retried with corrected arguments has a distinct approval identity and needs its own approval; exact argument binding must not be loosened just to permit a retry.
- **Gateway Tasks read the user turn only from the transcript** (`ai.prepareAIWorkerInput`): Gateway Tasks carry their current user turn only in the canonical session transcript, so prepareAIWorkerInput fails when that required input is missing rather than substituting a direct prompt.
- **AI worker settles before telemetry shutdown** (`ai.run`): run defers finishAIWorkerRun after the span and telemetry deferrals so it executes first, settling the Task result before span completion and telemetry shutdown can observe cancellation.
- **GenAI tracing wraps the composed provider** (`ai.run`): run wraps the provider with llm.NewTracingProvider after retry and fallback composition so spans report the concrete serving provider while still covering the whole logical model call.
- **Memory consolidation worker runs are tool-free** (`ai.run`): In memory consolidation mode run calls runMemoryConsolidation before registering any tools or loading memory or skills, because the controller supplies the consolidation inputs and validates the result. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Memory tool registration does not enable tools** (`ai.registerMemoryTools`): run registers the memory tools in the default registry unconditionally; registration only makes them resolvable and does not enable any tool the controller omitted from the Task's enabled tool list.
- **Durable memory never blocks the AI worker** (`ai.run`): run treats durable memory context and reflection guidance as optional: loadDurableMemoryContext failures yield no section, because memory infrastructure must never prevent the worker from running the Task.
- **Child Tasks inherit connector authority only through a controller seal** (`ai.sealChildTaskViaController`): Child Tasks a worker creates inherit the requester's connector authority only when the controller seals them on the worker's authenticated request through sealChildTaskViaController; the worker never stamps that authority itself.
- **Gateway tools need an authorized sender to be advertised** (`ai.buildLLMTools`): buildLLMTools receives the base ToolContext so it advertises gateway tools such as reply_in_conversation only when a bound, controller-authorized GatewayReplySender is present.
- **Memory consolidation does not require a prompt** (`ai.prepareAIWorkerInput`): prepareAIWorkerInput does not require a prompt in memory consolidation mode, because a consolidation run has its own fixed instruction and the prompt is only an optional focus.
- **Frozen connector tools fail startup instead of being dropped** (`ai.loadCustomTools`): loadCustomTools never silently drops a Tool the controller dispatched as connector-backed: a read that keeps failing fails startup so the Pod restarts with the tool set it was dispatched with instead of running with a permanently reduced one.
- **Deleted connector tools fail the Job for re-dispatch** (`ai.loadCustomTools`): loadCustomTools fails startup when a dispatched connector-backed Tool no longer exists; the Job is never retried at the Job level, so the controller's retry re-dispatches with a fresh freeze rather than the worker running a tool set nobody dispatched.
- **Remote MCP binding is mandatory** (`ai.loadCustomTools`): loadCustomTools treats remote MCP binding and discovery as mandatory and Task-authorized, failing instead of silently omitting a selected capability.
- **Approval binds the validated policy snapshot** (`ai.bindApprovalResolvedOutboundPolicyVersion`): bindApprovalResolvedOutboundPolicyVersion binds the exact OutboundAccessPolicy snapshot the caller already validated, so a second policy read cannot introduce different selectors between validation and approval binding.
- **Forwarding Tools are never model functions** (`ai.buildLLMTools`): buildLLMTools skips Tools with spec.http.forward because a forwarding Tool serves a command-line client inside an ACP runtime and is never advertised to the model as a function.
- **Transcript parsing keeps a blank final row visible** (`ai.loadSessionContext`): loadSessionContext strips only one trailing newline, the JSONL terminator, before splitting, so an actual blank final row is still detected when the transcript input is required.
- **Transcript errors report only the line number** (`ai.loadSessionContext`): loadSessionContext reports an invalid transcript message only by line number, because JSON decoder errors can include transcript contents.
- **Required transcript must end in a user turn** (`ai.loadSessionContext`): When the transcript is required, loadSessionContext validates that the actual final row is a non-empty user message before filtering roles or adding provenance, so filtering cannot make a different row look like the final turn.
- **Plan fetch waits for Job identity publication** (`ai.loadPlanContext`): loadPlanContext retries for up to five minutes because a worker Pod can start before the controller persists its Job name and UID; this matches the required session transcript startup window while honoring cancellation and keeping authorization fail-closed.
- **Gateway reply execution identity is per turn** (`ai.executeAgentLoopWithEvents`): executeAgentLoopWithEvents draws a fresh reply execution ID for each execution, because a new model turn is a new logical operation rather than a semantic duplicate; the ID stays fixed across transport retries of the same tool execution.
- **Schema preflight does not consume approval** (`ai.executeAgentLoopWithEvents`): executeAgentLoopWithEvents validates arguments against the tool schema before execution without consuming the approval, because a rejected preflight cannot execute the tool; once execution starts the fired key is retained even if the tool returns an argument-shaped error.
- **AI worker outcome is settled before publishing** (`ai.finishAIWorkerRun`): finishAIWorkerRun decides the run outcome before recording completion events, so a lost event response cannot change the Task's outcome.
- **Child seal failure is not a tool error** (`ai.sealChildTaskViaController`): sealChildTaskViaController lets the controller authenticate the Pod as the parent Task's worker and check the child's ownership and requester before sealing; a failed seal leaves the child unverified for connector use and is not an error for the tool that created it.
- **Child seals retry transient failures** (`ai.sealChildTaskViaController`): Nothing repairs a child Task seal later, so sealChildTaskViaController retries briefly on 409 (the child changed between the controller's read and its fenced seal), 429, 5xx, and transport errors; any other response is final.
- **Seal client ignores proxies and redirects** (`ai.sealHTTPClient`): sealHTTPClient carries the worker's ServiceAccount token, so it neither honors proxy environment variables nor follows redirects; the token reaches the controller and nothing else.
- **Agent loop never re-reads process model settings** (`ai.TestExecuteAgentLoop_PreservesModelSettings`): The agent loop must use the model settings passed to it rather than re-reading temperature or max-token environment variables; TestExecuteAgentLoop_PreservesModelSettings sets invalid environment values to prove it.
- **Model request events carry provider and model keys** (`ai.TestAIWorkerEventCompletenessSmoke`): Model request completed events must carry the "provider" and "model" content keys because the Task trace view reads them; TestAIWorkerEventCompletenessSmoke guards that contract.
- **Memory consolidation retries 503 until the Job is published** (`ai.memoryConsolidationUnavailableAttempts`): memoryConsolidationClient.post retries a controller 503 up to memoryConsolidationUnavailableAttempts times, spaced by memoryConsolidationRetryDelay, because the controller answers 503 until it has published the worker's Job; the run waits instead of failing.
- **Memory consolidation runs submit one structured result** (`ai.runMemoryConsolidation`): runMemoryConsolidation takes its inputs from the controller and offers the model only the submission tool; the controller validates the structured result and records the report that becomes the Task result. No other tool runs and no memory is injected. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Retried consolidation Pods return the recorded report** (`ai.runMemoryConsolidation`): runMemoryConsolidation returns the controller's existing report when the begin call already carries one, which covers a skipped run and a retried Pod of a finished run, so a retry never asks the model again.
- **Consolidation submits only completed model responses** (`ai.requestConsolidation`): requestConsolidation rejects any response whose normalized outcome is not completed or tool calls, because an unfinished, refused, or failed response may still carry a valid tool call and submitting it would propose from a result the model never finished.
- **Consolidation distinguishes empty from missing results** (`ai.requestConsolidation`): requestConsolidation treats a missing result list as no answer and asks again, while an empty list means nothing changes; a missing list must never finish the run as a no-op.
- **Consolidation reminder answers every tool call** (`ai.consolidationReminder`): consolidationReminder replays the model's turn and, when it called tools, carries the reminder in a result for each call, because providers reject an assistant turn with no text and no calls and require a result for every call.
- **Deprecated memory tool warnings log only the name** (`ai.warnDeprecatedMemoryTool`): warnDeprecatedMemoryTool logs only the known tool name and never the model's arguments or memory or transcript content.
- **Model setting errors omit the raw value** (`ai.parseModelSettings`): parseModelSettings returns fixed error messages instead of strconv errors, because parsing errors include the raw input, which must not enter worker logs or events.
- **Non-positive output caps keep the default** (`ai.parseModelSettings`): parseModelSettings keeps the 4096-token default when the Agent's output cap is omitted or non-positive, preserving the historical behavior for existing Agents.
- **Native remote MCP preparation fails closed** (`ai.prepareNativeRemoteTools`): prepareNativeRemoteTools is a fail-closed phase that runs before any tool is exposed to the model, and it uses a separate executor so the legacy backend's authority and defaults stay untouched.
- **Only known remote Tools require a live reread** (`ai.prepareNativeRemoteTools`): prepareNativeRemoteTools fails when it cannot reread an enabled Tool already known to be remote MCP, but skips unreadable non-remote selections, whose built-in collision checks and unresolved selections are handled elsewhere.
- **Remote MCP binding is rechecked before discovery sends** (`ai.prepareNativeRemoteTools`): prepareNativeRemoteTools installs a preparation fence that revalidates each Tool after resolution while the actual transport is frozen, because Kubernetes UIDs and resource versions never revert to a bound version after mutation, so discovery cannot send credentials through a newly resolved binding.
- **Remote MCP definitions are rechecked after discovery** (`ai.prepareNativeRemoteTools`): prepareNativeRemoteTools revalidates every remote Tool after network discovery so a concurrent edit cannot become the meaning of the already prepared model definition.
- **Frozen connectors never become remote MCP** (`ai.validateNativeRemoteConnectorOverlap`): validateNativeRemoteConnectorOverlap rejects the whole tool selection before any discovery request when a frozen connector-backed Tool now looks like remote MCP, so a connector cannot escape controller custody by drifting to remote.
- **Remote MCP validation carries its own deadline** (`ai.validateNativeRemoteTool`): validateNativeRemoteTool applies worker.RemoteMCPTimeout itself because approval refresh calls it directly without an execution deadline.
- **Remote MCP namespace test models worker RBAC** (`ai.TestNativeRemoteMCPAgentNamespaceBoundary`): TestNativeRemoteMCPAgentNamespaceBoundary wraps the fake client to refuse foreign-namespace Agent reads, because the underlying fake permits them while the worker's real RBAC does not.
- **Remote MCP route tests keep the real resolver** (`ai.remotePreparationReader`): remotePreparationReader keeps the real resolver and its side effects and injects changes only at the Kubernetes read boundary, after native binding but during request preparation, so the tests exercise the production fencing path.
- **Usage workflow E2E uses production components** (`ai.TestUsageIssueToMergedPRWorkflowE2E`): TestUsageIssueToMergedPRWorkflowE2E runs the production monitor, AI model loop, ACP journal, authenticated HTTP routes, Task finalizer, and on-disk SQLite store; only Kubernetes, provider responses, GitHub, and verified publisher delivery are fixtures, and no usage observations or PR outcomes are inserted directly into the store.
- **Usage workflow fixture disables keep-alives** (`ai.newUsageWorkflowFixture`): newUsageWorkflowFixture uses its own transport with keep-alives disabled, because the fixture tests persisted workflow state rather than connection reuse and idle keep-alives would delay API server replacement.
- **Usage workflow fixture retries port collisions** (`ai.usageWorkflowFixture.start`): usageWorkflowFixture.start retries a few times on bind collisions because the API Start accepts a port rather than a listener, and it accepts only readiness observed by its own store so another local server cannot satisfy it.

## Consequences

- These decisions are still in force. A change that breaks one must supersede that
  entry in a new ADR.
- Symbols get renamed. When an entry's symbol no longer exists, search for the behavior it
  describes.
- Entries recovered from test comments record why a test is shaped the way it is, so the test
  stays honest. A later ADR may supersede them once the tests explain themselves.
