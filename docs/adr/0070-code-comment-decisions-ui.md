# 70. Decisions recovered from code comments: the UI

Date: 2026-11-22

## Status

Accepted. This record is a catalog produced by the comment ban in
[ADR 0062](0062-code-carries-no-comments.md). Each entry was a code comment that recorded a
non-obvious decision in `ui/`. The comment was deleted, and the decision now lives here.

## Context

Round 2 of the comment cleanup classified every comment left after
[ADR 0063](0063-code-comment-decisions-round-1.md). In `ui/` it found 246 distinct decisions
that a reader of the code alone could get wrong. Comments that stated the same rule in several
places are merged into one entry. Where an earlier ADR already records a decision, the entry
links it.

## Decision

Each entry names the symbols it governs, so `rg '<symbol>'` finds the code. Entries are
grouped by package and ordered by source position as of round 2.

### `ui/src`

- **Token change clears query cache and chat store** (`app.useAuthStore.subscribe`): app.tsx subscribes to the auth store and, whenever the token changes (logout or a different sign-in), clears the React Query cache and resets the chat store, including transcript, session, persisted provider/model selections, and the turn epoch that aborts any in-flight turn. Cached state belongs to the token that fetched it, so a new session must never read or reuse the previous token's data.
- **Namespace changes reset chat at app level** (`app.useUIStore.subscribe`): app.tsx keeps the chat store synchronized with the global namespace through a module-level useUIStore subscription, because the namespace can change from the header while the Chat page is not mounted. Switching namespaces must always reset the old transcript and abort its in-flight turn.
- **Hash token capture runs before the router** (`app.captureHashToken`): app.tsx calls captureHashToken before createRouter so the sign-in token in the URL fragment is captured before the router reads and rewrites the location.
- **Demo build keeps routes in the URL fragment** (`app.createRouter`): The router renders unknown addresses inside the root layout's Outlet via defaultNotFoundComponent. The demo is served from a static host that cannot fall back to index.html for deep links, so the demo build keeps the route in the URL fragment (hash history).
- **index.html pre-paint script mirrors the UI store theme migration** (`ui/index.html pre-paint theme script`): The inline script in ui/index.html applies the persisted theme before React loads so a dark page never flashes light, and therefore repeats the UI store's persisted-theme migration (a stored light from before version 1 is the old default). An entry with no version is not migrated, matching zustand, which always writes a version and skips migrating unversioned entries; index-html.test.ts runs the script to keep the two in step.
- **Fonts are bundled, never fetched from a CDN** (`ui/src/main.tsx`): The dashboard imports its fonts from @fontsource packages so Vite bundles them and the UI works offline and in air-gapped clusters without a runtime CDN fetch.
- **Demo code is excluded by a static mode check** (`ui/src/main.tsx`): The demo build answers API calls in the browser from sample data; the `import.meta.env.MODE === 'demo'` check around the dynamic import must stay static so other builds drop the demo code entirely.

### `ui/src/components/agents`

- **Agent mode switch resets mode-specific fields** (`AgentCreateForm.handleModeChange`): AgentCreateForm.handleModeChange clears model, token, and runtime fields on a mode switch because they mean different things per mode (the native max-tokens field and OpenCode's output limit share state); carrying them over would submit a value meant for the other mode. The role and soul apply to both modes and carry over.
- **Agent form rejects an unlisted Provider pick** (`AgentCreateForm.handleSubmit`): AgentCreateForm refuses to submit when the selected Provider is no longer in the current namespace's list, because a namespace switch can leave a stale provider name in state.
- **Authorization failures replace cached query data** (`AgentDetail`): React Query keeps the last successful data when a refetch fails, so Orka UI pages treat a 403 (and a 404 or 501 where that is terminal) as replacing cached data rather than rendering it, and other failures replace the page only when nothing was loaded. Otherwise a token that lost access would keep seeing resource names and stale decision controls.
- **Controls keep keyboard focus off body** (`AgentDetail delete button`): Pending action buttons use aria-disabled instead of disabled, and actions that remove, swap, or disable their own button move focus to a stable element such as the chat composer. Disabling or unmounting the focused element would drop keyboard focus to <body>.

### `ui/src/components/attention`

### `ui/src/components/chat`

- **Chat send reads streaming state from the store** (`ChatInput.handleSend`): ChatInput checks useChatStore.getState().isStreaming rather than the render snapshot, because a second Enter in the same tick must see the turn the first one just started.
- **Controls keep keyboard focus off body** (`ChatInput.handleStop`, `ChatPage.handleNewChat`): Pending action buttons use aria-disabled instead of disabled, and actions that remove, swap, or disable their own button move focus to a stable element such as the chat composer. Disabling or unmounting the focused element would drop keyboard focus to <body>.
- **Chat composer stays enabled while a reply streams** (`ChatInput textarea`): The chat textarea is never disabled during streaming so it keeps focus and the next message can be drafted; only sending is blocked.
- **Transcript auto-follow tracks the reader's last scroll** (`ChatMessageList.followingRef`, `ChatMessageList scroll effect`): ChatMessageList records whether the reader was near the bottom from scroll events only, because content growth alone must not change it. A reader who scrolled up keeps their place while a reply grows, and the reader's own message always returns the transcript to the bottom.
- **Scroll areas force Radix content wrapper to block** (`ChatMessageList ScrollArea`): Radix ScrollArea wraps viewport content in a display: table box that grows to the widest unbreakable line, so ChatMessageList passes viewportClassName [&>div]:block! to keep long tool arguments from widening and clipping the transcript.
- **Authorization failures replace cached query data** (`ChatPage providers`): React Query keeps the last successful data when a refetch fails, so Orka UI pages treat a 403 (and a 404 or 501 where that is terminal) as replacing cached data rather than rendering it, and other failures replace the page only when nothing was loaded. Otherwise a token that lost access would keep seeing resource names and stale decision controls.
- **Stale chat Provider picks fall back only in the rendered namespace** (`ChatPage providerGone`): ChatPage clears a persisted provider pick that the loaded list no longer contains, since sending it would fail provider resolution on every turn. The check is gated on the store's active namespace matching the rendered one, because mid-switch the render holds the old pick against the new list and clearing then would erase the new namespace's restored selection.
- **Sole ready Provider is preselected** (`ChatPage soleReadyProvider`): Without a server default provider an empty pick cannot send, so ChatPage preselects the Provider when the namespace lists exactly one ready one; any other shape leaves the picker empty and disables sending with a hint.
- **Chat model override requires a provider** (`ChatPage modelNeedsProvider`): The server accepts a model override only alongside a provider, so ChatPage disables the model input when there is neither a Provider pick nor a server default provider to pin it to.
- **New Chat during a reply asks before deleting** (`ChatPage.handleNewChat`): New Chat while a reply streams orphans the turn, which sends DELETE /chat/{sessionId} and deletes the chat and its history like Stop does, so ChatPage.handleNewChat asks for confirmation first; an idle chat resets at once.

### `ui/src/components/common`

- **Error-phase problems come from the Ready condition** (`statusProblem`): statusProblem reports a problem only for the Error phase and reads its reason and message from the Ready=False condition, because the RepositoryScan and RepositoryMonitor controllers record the cause (InvalidRepository, InvalidSchedule, ScanFailed) only there. Other not-ready phases already describe themselves.

### `ui/src/components/connectors`

- **Connector messages never name the default scope** (`ConnectorsPage scope messages`): The connector read and manage scopes are operator-configurable, so ConnectorsPage error messages describe the scope your controller requires instead of naming a default scope such as orka:connectors.
- **Spent connector callbacks are never replayed** (`ConnectorsPage.callbackSpent`): A consent completed in another namespace remounts the namespace-keyed connector content before the router clears the callback search, so ConnectorsPage remembers the spent callback outside that content and the new content never replays it or reports a consent without a completion token.
- **Connector changes poll until the list reflects them** (`ConnectorsPage.expectations`, `ConnectorsPage.settleExpectations`, `ConnectorsPage refetchInterval`): The connections list is served through an eventually consistent cache, so after a mode change or disconnect ConnectorsPage records an expectation and keeps polling until the list shows the requested mode or no longer shows the link. Only data the server returned settles an expectation; optimistic cache writes never do, or a stale refetch could end polling early. Polling also continues while a link is Pending or deleting so a finalizer revoking tokens resolves on screen.
- **Connector completions run in the sealed namespace** (`ConnectorsPage completion`, `ConnectorsPage completion success`): ConnectorsPage keeps the completion token in the URL fragment until the server accepts it, so a failed attempt can be retried in the page or by reloading. The completion is spent in the namespace the consent was sealed in, never the page's current pick, and on success the page switches to that namespace so the new link is not hidden behind a success notice.
- **Address-bar namespaces are validated before use** (`ConnectorsPage callbackNamespace`): The connector callback namespace arrives in the address bar, so ConnectorsPage ignores any value that is not a valid Kubernetes namespace rather than using or persisting it.
- **Failed consent namespaces are offered, not persisted** (`ConnectorsPage failedElsewhere`): The connector error redirect is not authenticated, so when a failed consent was sealed in another namespace ConnectorsPage offers a switch to it rather than writing it into the persisted namespace selection; the content remounts with the same callback search so the notice is kept.
- **Only non-retryable conflicts spend a connector completion** (`ConnectorsPage completion error`): A 409 that asks for a retry (controller has not adopted the Connection, provider not accepted yet, or a committed completion awaiting its status pass) keeps the completion token; any other conflict means the consent expired or was superseded, so ConnectorsPage clears the callback.
- **Foreign Connections read as not found** (`ConnectorsPage completion hint`): The connections API answers 404 for another person's Connection rather than revealing it, so ConnectorsPage gives a 404 the same sign-in-as-yourself and CLI fallback hint as a 401 or 403.
- **Consent opens only after disclosure** (`ConnectorsPage.openConsent`): ConnectorsPage.openConsent opens the provider consent only after the page has shown what it grants; if the provider began serving agent hosts after the page loaded, that is shown first instead of opening consent.
- **Duplicate connector links make every link unusable** (`ConnectorsPage byProvider`, `ConnectorsPage duplicated`): Connector resolution refuses every link to a provider while the person holds more than one, so ConnectorsPage shows extra links on their own, disconnectable, and marks the provider card's own link unusable too.
- **Connections outlive their provider** (`ConnectorsPage retained`): A Connection deliberately outlives its ConnectorProvider because it still holds the person's tokens, so ConnectorsPage shows it, disconnectable, even when no provider card claims it.
- **Connector link badges trust current provider readiness** (`ConnectionBadge`): A link is usable only while its ConnectorProvider is accepted, and the Connection's own conditions can lag a provider change; the API also folds the current provider's consent and scope checks into ready. ConnectorsPage therefore shows provider unavailable when the provider is not ready, and a stale Ready state without ready as needing a reconnect.

### `ui/src/components/events`

- **Event payloads come only from the redacted API content** (`EventRow.stringifyContent`, `EventTimeline copy`): EventRow and EventTimeline pretty-print and copy the execution event exactly as the API serves it; the backend sanitizes and truncates content before serving, and the UI must never fetch or expose hidden raw payload data.
- **Trace arrays default to empty** (`TaskTraceView`): The Go API marshals empty trace groups as JSON null (nil slices) and the client casts the response without parsing, so TaskTraceView defaults every trace array with ?? [] before using array methods; otherwise a task with no events would crash the Trace tab.
- **Trace view never hides recorded events** (`TaskTraceView.hasStructured`, `TaskTraceView raw timeline`): TaskTraceView shows the empty state only when there are no structured groups and no timeline; when events exist but no structured groups were derived it renders the raw timeline so nothing is hidden. Errors and warnings render their own sections, so an error- or warning-only trace counts as structured.

### `ui/src/components/layout`

- **Connectors nav entry follows server availability** (`Sidebar connectorsProbe`): Connectors exist only when the controller runs with --connectors-enabled. The mobile overlay state is separate from and never written to the persisted sidebarCollapsed preference, so leaving the breakpoint restores the desktop layout.

- **Unavailable session page keeps its heading and a way back** (`SessionUnavailable`): SessionUnavailable renders the page heading (and so the browser tab title) and a link back to the session list even when the session is missing or unreadable, so users are never stranded on a blank page.

### `ui/src/components/tasks`

- **Diff parser trusts hunk counters over header-looking lines** (`parseDiff (diff-viewer)`): The diff viewer's parser treats a line as a file header only when the current hunk has no old or new lines remaining, because source lines inside a hunk can look like 'diff ' or '--- ' headers. Metadata rows such as 'index ...' and '\ No newline at end of file' stay visible but never get line numbers or advance the counters, and the empty item from a trailing patch newline is dropped.
- **Failed child results come from the child's status message** (`ExecutionGraph/buildGraph`): status.childTasks carries no result for a child that failed before reporting one, so ExecutionGraph fetches the children list only when such a child exists and uses its status.message as the result. The result chip is toned by phase so a failed child's output never reads as success.
- **Unknown phases display literally and style as Pending** (`ExecutionGraph node phaseLabel`): ExecutionGraph nodes show the literal phase string to sighted and assistive-technology users, matching StatusDot's contract; only the styling falls back to Pending for unknown phases, so an unexpected phase like Terminating is never mislabeled.
- **Fork dialog ignores submissions that resolve after a reset** (`ForkDialog.submissionRef`): ForkDialog bumps submissionRef on every reset and ignores any in-flight fork result whose submission number no longer matches, so a request that resolves after the dialog was closed (Escape, overlay, X while pending) cannot repopulate the still-mounted component with a stale success screen.
- **Fork idempotency keys are bound to the request and cleared only on confirmed success** (`ForkDialog idempotency key`): ForkDialog binds its idempotency key to a signature of the trimmed request (checkpoint afterSeq, name, agent, prompt) and mints a fresh key whenever the signature changes, because the backend derives the deterministic fork auto-name from the key alone and a reused key would resolve to the wrong fork. The key is kept across retries and across pending or error closes, because the POST cannot be aborted and an error is ambiguous (the fork may already exist); it is cleared only after a confirmed success.
- **Every fork dialog dismissal resets its state** (`ForkDialog.handleOpenChange`): ForkDialog routes every dismissal (Escape, overlay, X, footer Close/Cancel) through one handler that resets form and result state, because the dialog stays mounted under TaskEventTimeline and would otherwise reopen on a stale success screen or leftover input.
- **Status chips sit on the card surface for AA contrast** (`KanbanBoard column count chip`): KanbanBoard's column count chip uses the card surface (bg-card) with the status text color rather than the column's own status tint, because tint-on-tint fails WCAG AA contrast.
- **Kanban board walks every task page at the Live cadence** (`KanbanBoard`): KanbanBoard walks every task list page up to the shared summary cap, like the Dashboard, so column counts cover the namespace rather than the first 100 names; because the walk is heavier than one page, it polls at the Live view's 10s cadence.
- **List views keep their last data on refresh failure except 403** (`ui list views (KanbanBoard, task/session lists)`): List views show an error in place of data only for a 403, which always replaces the view, or when nothing has loaded yet; any other failed background refresh keeps the last loaded list so a transient error does not blank the page.
- **Attention board lanes wait for the attention ranking** (`AttentionBoard`): AttentionBoard puts Tasks in Agent working or Done only after the server's attention ranking has loaded and while it is fresh. If the ranking is loading, failed, or stale, those lanes stay unclassified, because sorting Tasks without a current ranking would put a Task that needs the user into Done. A 403 replaces the cached ranking; other refresh failures keep the last Needs you items with a note.
- **Run timeline pins the terminal marker last** (`RunTimeline buildEvents`): RunTimeline's buildEvents sorts events by bucket, then timestamp, with a stable index tiebreak for undated events. Everything shares bucket 0 except the terminal marker, which is pinned to bucket 1 so it renders last even when an earlier event is undated or its completion time precedes the synthetic Iteration N event; that iteration event is anchored to the newest condition time (else startTime) so it follows the work that led to it.
- **Cancelled runs render neutrally** (`RunTimeline terminal marker`): RunTimeline treats Cancelled as terminal (a user-stopped run) and styles it neutrally rather than as a failure or success.
- **Log viewer freezes lines while the reader is scrolled up** (`StructuredLogViewer frozen`): StructuredLogViewer holds the displayed lines while the reader is scrolled up, because a running task refetches a sliding tail window every poll, which would shift rows and restart their numbers under the reader; pinning to bottom resumes live updates.
- **Log viewer scrolls its own container** (`StructuredLogViewer.scrollToBottom`): StructuredLogViewer scrolls its log container by setting scrollTop instead of calling scrollIntoView on a bottom marker, because scrollIntoView also scrolls every ancestor and moved the whole page when the tab opened.
- **Missing logs before a pod exists are not an error** (`StructuredLogViewer unavailable state`): StructuredLogViewer treats 'no Job or pod yet' (pending tasks, scheduled parents, runtime-pool agents) as expected: it shows the server's reason instead of an error with Retry, and running tasks keep polling so logs replace the notice.
- **Approvals on terminal tasks are read-only except the parked sign-off** (`ApprovalCard closed/actionable`): The backend rejects approval decisions on terminal Tasks with 409, so ApprovalCard shows a pending approval on a terminal Task read-only, unless it is the approval an active parked wait (ADR 0041) is waiting on, which stays decidable after the parked turn has ended. See [ADR 0041](0041-data-only-parked-turns.md).
- **Decided approval cards keep keyboard focus** (`ApprovalCard heading focus`): After a decision succeeds or a 409 refetch settles the card, ApprovalCard moves focus to its heading, because the decided card drops its Approve/Decline buttons and focus would otherwise fall back to the page.
- **Approval 409s refetch immediately** (`ApprovalCard.submit`): When an approval decision returns 409 (decided elsewhere, expired, or cancelled), ApprovalCard shows the conflict and calls onConflict to refetch right away instead of waiting for the next poll, because useDecideApproval only invalidates its query on success.
- **Approval risk summary shows only while pending** (`ApprovalCard riskSummary`): ApprovalCard shows the request's riskSummary only while the approval is pending, because it can describe a tool that has not executed; after a decision the execution outcome describes the current state.
- **Pending action buttons use aria-disabled, not disabled** (`ui pending action buttons (aria-disabled)`): Buttons whose mutation is in flight are marked aria-disabled and guarded in their handlers instead of using the disabled attribute. Disabling the focused button drops keyboard focus to <body>, so a failed action would lose the user's place.
- **Approval panel keeps polling past termination and for parked sign-offs** (`TaskApprovalPanel polling`): TaskApprovalPanel polls while the Task is running and while execution after termination is unresolved, since recovery can still update approvals on terminal Tasks. A parked sign-off keeps polling until decided, including across an empty first response or failed read, which carry no pending approval.
- **Artifact 501 means store disabled, other errors are failures** (`TaskArtifactsPanel`): TaskArtifactsPanel treats a 501 from the artifacts endpoint as the artifact store being disabled and shows a normal empty state; any other error is a real failure and must not be shown as 'No artifacts'.
- **Task cancel is fenced by UID** (`TaskCancelDialog.taskUID`): TaskCancelDialog sends the UID of the Task the user is confirming, so a Task deleted and recreated under the same name is never cancelled in its place.
- **Task create form never submits a stale or hidden Agent** (`TaskCreateForm aiAgentRef`): TaskCreateForm drops cached Agent data whenever the Agent list request errors (for example a 403 from a token that cannot list Agents), so names from an earlier identity never populate the selector. The chosen Agent counts only while it names a native Agent in the current namespace's latest list; a selection is remembered with its namespace, and a namespace change, deletion, runtime conversion, or errored list drops it so an unqualified or stale agentRef is never submitted while the selector renders empty.
- **Task create form guards double submit with a ref** (`TaskCreateForm.submittingRef`): TaskCreateForm uses submittingRef because the mutation's isPending updates a render after the click, so a fast double click would POST twice (a 201 then a 409 toast). A created Task keeps the guard set while the page navigates away.
- **Agent-backed AI tasks send only explicit overrides** (`TaskCreateForm agentProviderLocked`): When an Agent is chosen, TaskCreateForm sends only provider/model values the user re-entered after opening the overrides disclosure, so the controller merges the rest from the Agent; inline values typed before choosing an Agent are cleared rather than sent as hidden overrides. For a providerRef Agent the controller makes the Provider CRD type authoritative, so ai.provider is never submitted.

- **Cancellation requested=false is an idempotent no-op** (`ui/src/hooks/use-tasks.ts TaskCancellation.requested`): TaskCancellation.requested is true only when this request recorded the cancellation; it is false when the Task already had a cancellation or was already Cancelled, which is a successful no-op rather than an error.
- **Cancel requests are pinned to the confirmed Task UID** (`ui/src/hooks/use-tasks.ts useCancelTask`): useCancelTask sends the UID of the Task the person confirmed, so the server refuses (409) a cancel aimed at a different Task recreated under the same name since the confirmation.
- **Task event polling stops on 501, 403, and post-load 404** (`ui/src/hooks/use-tasks.ts useTaskEvents`): useTaskEvents does not retry 501 (feature off), 403 (forbidden for this token) or 404, and its refetchInterval stops polling on 501 and 403 and on 404 after events were seen, because consumers without an enabled-guard (such as the runtime canvas spotlight) would otherwise poll forever. A 404 before any events were seen keeps polling because a fresh Task can transiently 404 while caches catch up.

### `ui/src/lib`

- **apiErrorMessage accepts every server error body shape** (`ui/src/lib/api-client.ts apiErrorMessage`): apiErrorMessage extracts a readable message from {"error":{"message"}}, {"error":"..."} and {"message":"..."} bodies because different server paths use each shape; any other body is returned as text so callers never render raw JSON.
- **A 401 clears only the token the request carried** (`ui/src/lib/api-client.ts request`): The API client clears the stored token on 401 only when the request carried a token and that token is still the current one; a late 401 for a tokenless request or for a token replaced by a new sign-in must not sign the new session out.
- **Requested waits count as working only after a Succeeded turn** (`ui/src/lib/attention-lanes.ts isAgentWorking`): isAgentWorking treats a Requested wait as working only when the Task's turn Succeeded, because a park wait arms only after its turn settles Succeeded; after a Failed or Cancelled turn the requested wait is abandoned and the agent is no longer working. See [ADR 0041](0041-data-only-parked-turns.md).
- **Task-derived Needs you cards back up the server's approval ranking** (`ui/src/lib/attention-lanes.ts groupByAttention`): groupByAttention lets the server's attention items drive Needs you and removes their Tasks from the other lanes, but a Task whose own state shows an approval wait (isTaskAwaitingApproval, which must match the server's Task-only selection) and has no approval item is never put in Agent working or Done; it gets a Task-derived card with the server's approval rank (1). Only approval items suppress that card, and the card carries no approval because the caller may not be able to read the Task's approvals.
- **Unread attention sources fail closed** (`ui/src/lib/attention-lanes.ts attentionSourceNotes`): attentionSourceNotes and mergeApprovalsSource treat approvals as unread for every state except included, including a missing or unknown state, and across pages unavailable or unknown wins over partial, which wins over included; an empty Needs you list is never shown as nothing-needs-you while approvals were not read. Skipped sources are kept apart from `incomplete` scan limits.
- **Connector consent completes in its sealed namespace** (`ui/src/lib/connectors.ts ConnectorCallbackSearch.namespace`): The OAuth callback returns the namespace the consent was sealed in, and the completion request must target that namespace rather than the currently selected one.
- **Connector completion token travels in the URL fragment** (`ui/src/lib/connectors.ts readCompletionToken`): The one-time connector completion token is carried in the URL fragment so it never reaches a server log or Referer header. It stays in the address bar until completion succeeds so a failed attempt can be retried with a reload; leaving it there is safe because the server accepts it exactly once.
- **Connector completion CLI command requires Kubernetes names** (`ui/src/lib/connectors.ts completionCommand`): completionCommand returns null unless the callback's connection and namespace values are valid Kubernetes names, because they come from the address bar and a crafted link must not become a shell command the person is told to paste.
- **UI lookup tables live in plain .ts modules** (`ui/src/lib/event-severity.ts SEVERITY_META`): Non-component exports such as SEVERITY_META and the task-status metadata live in plain .ts modules without JSX, because exporting them from a component module trips react-refresh. Severity reuses the status palette (info as running, warning as pending, error as failed) so the UI keeps one color language.
- **Execution event schema declares top-level model telemetry** (`ui/src/schemas/execution-event.ts`): The execution event schema must declare the provider, model, stopReason, inputTokens and outputTokens fields the backend emits at the top level of model events, because Zod strips undeclared keys and a streamed event would otherwise overwrite the full-telemetry row from the initial page in mergeEventsBySeq.
- **Event categories are functional; errors are shown by severity** (`ui/src/lib/execution-events.ts ExecutionEventCategory`): ExecutionEventCategory groups execution events by functional area following the taxonomy in internal/events/execution_event.go. Error highlighting is driven by severity, not by category, so failures stay grouped with their functional area instead of a separate error category.
- **Later event sources win on seq collisions** (`ui/src/lib/execution-events.ts mergeEventsBySeq`): mergeEventsBySeq dedupes by seq and lets later sources win on a collision, so callers must pass live stream events after the initial replay page for them to supersede it.
- **Model usage aggregation per prompt** (`ui/src/lib/execution-events.ts latestModelUsageEvents`): Harness v2 ModelUsageUpdated events are cumulative snapshots within one prompt, so latestModelUsageEvents keeps the newest event per prompt, carries forward counters omitted by partial updates, and sums prompts at the Task level. The native AI worker's unscoped usage updates (counters nested in content, no model or token fields) are skipped because its ModelRequestCompleted events already report them and they would only add an empty unknown-model entry.
- **Malformed SSE frames do not advance the stream cursor** (`ui/src/lib/execution-events.ts parseExecutionEventFrame`): parseExecutionEventFrame classifies invalid JSON and schema-mismatched payloads as 'unknown' so the stream loop skips them without advancing its resume cursor.
- **Full-list walks are capped at maxListWalkPages** (`ui/src/lib/list-api.ts maxListWalkPages`): walkAllPages is unbounded by default so selectors and inventories stay exhaustive, but summary views pass maxListWalkPages (20): terminal objects accumulate without limit and an unbounded walk on a polling interval grows into an ever-larger request burst against the API server and browser memory. Beyond the cap a view gets a partial resource-key-ordered sample and must surface `truncated`.
- **403 responses are never retried or polled** (`ui/src/lib/list-api.ts retryUnlessForbidden`): retryUnlessForbidden and pollUnlessForbidden stop retrying and polling on 403, because a 403 is permanent for the current identity and repeating it only generates denied requests and audit-log noise; other failures get three tries.
- **Views replace data on 403 but keep it on other refresh failures** (`ui/src/lib/load-problem.ts loadProblem`): loadProblem reports a 403 even when data has loaded, because the token can no longer see that data, but reports any other failure only while nothing has loaded, so a failed background refresh keeps the data already shown.
- **Login return never persists the URL fragment** (`ui/src/lib/login-return.ts rememberLoginReturn`): rememberLoginReturn stores only the path and query in sessionStorage; the fragment stays in the address bar because a connector consent callback carries its one-time completion token there and it must never be persisted.
- **Login return uses the router's fragment** (`ui/src/lib/login-return.ts takeLoginReturn`): takeLoginReturn re-attaches the fragment from the router's location.hash rather than window.location.hash, because under hash routing window.location.hash holds the route itself.
- **Sign-in hash tokens are captured before the router starts** (`ui/src/lib/login-return.ts captureHashToken`): captureHashToken removes a #token= sign-in fragment from the address bar and holds it in memory once at app start, before the router reads the URL, so the root redirect and the login page never race over it and the token never lands in browser history.
- **Parked approvals are decidable only while the wait is active** (`ui/src/lib/parked-approval.ts activeParkedApprovalId`): activeParkedApprovalId returns the parked sign-off approval while its wait is active even though the Task phase is terminal, because the backend accepts a decision on exactly that approval then. A Requested wait counts only after a Succeeded turn (it is abandoned after Failed or Cancelled), and a wait past its deadline is no longer shown as waiting even before the controller records expiry, matching the attention and approvals views. See [ADR 0041](0041-data-only-parked-turns.md).
- **UI cron validation mirrors the controller's robfig/cron parser** (`ui/src/lib/repository-form-validation.ts isCronSchedule`): isCronSchedule and everyScheduleError accept exactly what the controller's robfig/cron ParseStandard accepts (field bounds with weekday 0-6 only, names, steps, lists, @-descriptors, CRON_TZ=/TZ= prefixes), plus two stricter rules: empty list items are refused as typos and @every needs a Go duration of at least one minute so scans do not run almost continuously. robfig/cron reads everything after exactly "@every " as a Go duration, and time.ParseDuration refuses values beyond int64 nanoseconds, so the UI does too.
- **Runtime health checks never report a false pass** (`ui/src/lib/runtime-validation.ts deriveRuntimeChecks`): deriveRuntimeChecks degrades each check to 'unknown' when its data is absent rather than passing, and the authoritative Task phase drives the outcome so a Failed or Cancelled Task fails or warns regardless of an empty or stale trace. Reaching a terminal state is its own passing check; an in-progress Task or one without artifacts is 'info', which never moves rollupStatus (fail > warn > unknown > pass), unless its Pod is stuck waiting and needs a person.
- **Trace arrays may be null** (`ui/src/lib/runtime-validation.ts deriveRuntimeChecks`): Go marshals empty trace slices as null, so every trace array is guarded with `?? []` before use in deriveRuntimeChecks, as in TaskTraceView.
- **Label and annotation values are hidden when they may carry secrets** (`ui/src/lib/secret-like.ts looksSecret`): looksSecret hides a label or annotation value whose key looks credential-bearing, whose value looks like a credential, or whose value exceeds MAX_VALUE_CHARS (80) because long values can carry an embedded blob or token; UNSAFE_KEY_PATTERN also covers annotations such as kubectl last-applied-configuration that embed a whole spec, including env.
- **Free text with a credential sign is hidden whole** (`ui/src/lib/secret-like.ts containsCredential`): containsCredential triggers hiding the whole text rather than redacting a span, because finding where a secret ends inside prose is unreliable and a partial cut leaves pieces. Its patterns avoid leading wildcards and bound the URL scheme so matching stays linear, check query parameter names segment by segment in two linear steps, and require enough token length or a separator so prose such as 'Bearer tokens expire', 'design' or `max_tokens: 100` does not count.
- **Displayed container commands round-trip through splitShellWords** (`ui/src/lib/task-command.ts formatShellCommand`): formatShellCommand single-quotes any word that is empty or holds spaces, quotes or shell metacharacters (escaping inner single quotes as '\''), so the displayed command line splits back into the same argv under a POSIX shell and under splitShellWords, which the create form uses.
- **UI Task phase sets mirror the controller** (`ui/src/lib/task-phase.ts`): TERMINAL_TASK_PHASES matches Go TaskPhase.IsTerminal() (Succeeded, Failed, Cancelled) and isTaskInFlight matches the controller's concurrency accounting (Pending, Running, Finalizing; Finalizing is included because publication happens there). Scheduled is a recurring parent that never completes, and unknown or missing phases are neither terminal nor in flight.
- **URLs in the Task resource view keep all but their credentials** (`ui/src/lib/task-resource.ts withoutCredentials`): scrubbedText keeps a value that is a single URL but strips its userinfo, query and fragment, and hides the path when it is a webhook secret or holds a token, checked after percent-decoding as the server reads it and without userinfo; a URL or path that will not parse or decode is hidden whole because nothing says where its credentials end. Such URLs are kept rather than hidden because legacy harness-v1 repository URLs were stored without the current credential rules.
- **Webhook URLs show only scheme and host** (`ui/src/lib/task-resource.ts shownWebhookURL`): shownWebhookURL shows only the origin of a webhook URL because the secret can be in the path (Slack), the query (signed URLs) or userinfo.
- **The Task resource view omits secret-bearing content** (`ui/src/lib/task-resource.ts displayedTaskResource`): displayedTaskResource shows the Task as kubectl would but never displays environment values, the webhook URL past its host, credentials in URLs, other text that looks like a credential, secret-looking labels and annotations, or kubectl annotations (last-applied embeds the whole spec, env included). The API's `plan` is not part of the resource and is omitted.
- **Status and type styles are complete Tailwind literals in a plain .ts module** (`ui/src/lib/task-status.ts`): task-status.ts is the single source of status and type color, drawn from the status-* and type-* design tokens. Class strings are written as complete literals because Tailwind's content scanner cannot see dynamically composed names such as `bg-status-${phase}`, and the module has no JSX so its constant exports do not trip react-refresh/only-export-components.
- **UI workspace repository validation mirrors the controller and is never stricter** (`ui/src/lib/workspace-repository.ts validateWorkspaceRepositoryUrl`): validateWorkspaceRepositoryUrl, workspaceRepositoryIdentity, sameWorkspaceRepositoryIdentity, isForbiddenRepositoryIpLiteral and workspaceSubPathError mirror the controller's canonicalization (security.CanonicalRepositoryCloneURL, canonicalWorkspaceRepositoryURL), IP-literal rule, identity comparison and the harness-v2 relative-root check. The controller preflight stays authoritative; the UI only rejects obviously doomed input before a Task is created, so it must never be stricter than the controller.
- **Well-formed text check uses a regex, not String.isWellFormed** (`ui/src/lib/workspace-repository.ts isWellFormedText`): isWellFormedText rejects lone UTF-16 surrogates (the equivalent of Go's utf8.ValidString) with a regex so the UI does not require the ES2024 String.isWellFormed lib.
- **Repository paths must be canonical as written** (`ui/src/lib/workspace-repository.ts validateWorkspaceRepositoryUrl`): validateWorkspaceRepositoryUrl requires the path as written to equal the browser-parsed pathname, because the parser resolves dot segments but the original string is what gets submitted and the controller rejects unclean paths. It also requires the path to round-trip through decode and canonical re-encoding, as the controller does, so escapes such as %2F that hide extra path structure are rejected.
- **UI source-ref and branch validation mirrors the controller** (`ui/src/lib/workspace-source-ref.ts workspaceSourceRefError`): workspaceSourceRefError and workspacePublicationBranchError mirror publisherservice.CanonicalWorkspaceSourceRef and store.ValidateFullBranchRef: a source selector is a full lower-case commit SHA, a refs/heads/ branch, a refs/tags/ tag, or a short ref name. The controller stays authoritative, so these checks must never be stricter than its rules.

### `ui/src/routes`

- **A captured sign-in token always goes to the login page** (`ui/src/routes/__root.tsx`): The root layout sends a #token= fragment captured at app start to the login page even when a token is already stored, because it is an explicit sign-in request.
- **Login return never persists the URL fragment** (`ui/src/lib/login-return.ts rememberLoginReturn`): rememberLoginReturn stores only the path and query in sessionStorage; the fragment stays in the address bar because a connector consent callback carries its one-time completion token there and it must never be persisted.
- **Login returns only from /login and never continues after a rejected sign-in** (`ui/src/routes/login.tsx LoginPage`): LoginPage navigates to the remembered return only while the address is still /login, because the new token swaps the root layout before the route match changes and the page mounts again briefly at the destination after the return was taken. A rejected sign-in stays on the login page with its error even when an earlier token is still stored, instead of silently continuing as the old identity.

### `ui/src/routes/security/findings`

- **Bare /security/findings redirects to /security** (`ui/src/routes/security/findings/index.tsx`): Findings are listed per repository, so the bare /security/findings address redirects to the Security page instead of matching /security/$repoId as a repository named "findings".

### `ui/src/schemas`

- **Agent schema keeps the identity binding** (`ui/src/schemas/agent.ts`): The Agent spec schema declares spec.identity even though the UI does not edit it, because Zod strips undeclared keys and editing an Agent would otherwise drop its identity binding.
- **canApprove and canDecline are hints only** (`ui/src/schemas/attention.ts canApprove`): Attention items' canApprove and canDecline are UI hints (null when unknown); the approval decision POST enforces authorization.
- **Execution event schema declares top-level model telemetry** (`ui/src/schemas/execution-event.ts`): The execution event schema must declare the provider, model, stopReason, inputTokens and outputTokens fields the backend emits at the top level of model events, because Zod strips undeclared keys and a streamed event would otherwise overwrite the full-telemetry row from the initial page in mergeEventsBySeq.
- **Provider list accepts CRD and flat projections** (`ui/src/schemas/provider.ts providerListItemSchema`): GET /api/v1/providers returns full Provider objects for ServiceAccount/OIDC callers and a flat {name, namespace, type, defaultModel, ready} projection for transaction-token callers, so providerListItemSchema normalizes both. A CRD-shaped item without status.ready means false because the CRD serializes it with omitempty; only the flat projection may leave readiness unknown.
- **AgentRuntime mcpPolicy is optional on read** (`ui/src/schemas/runtime.ts`): Stored v2 AgentRuntime registrations created before MCP policy materialization may omit mcpPolicy, so read and list schemas keep it optional and preserve those records; dispatch validates the policy before using the registration.
- **UI parses only the safe execution workspace status** (`ui/src/schemas/task.ts executionWorkspace status`): The execution workspace status schema parses only provider-neutral lifecycle, placement and density metadata from ExecutionWorkspaceStatus; provider credentials and unsafe provider-native identifiers are deliberately excluded. See [ADR 0024](0024-acp-execution-workspace-runtime-pools.md).
- **Execution bindings expose metadata and digests only** (`ui/src/schemas/task.ts agentExecutionBindingSchema`): agentExecutionBindingSchema describes the authoritative execution route with snapshot metadata and abbreviated digests only; snapshot bodies are never exposed through ordinary API surfaces.

### `ui/src/stores`

- **Chat state is scoped to namespace and identity** (`ui/src/stores/chat.ts`): Providers and chat sessions are namespace-scoped, so the chat store keys the persisted provider/model choice by namespace (selections, swapped in by selectNamespace), and switching between two namespaces drops the transcript and session ID instead of replaying them elsewhere; the initial activation keeps what is there. resetForIdentityChange drops the transcript, session, choices and persisted selections on a token change. Only per-namespace picker choices are persisted; version 0's single global choice is dropped on upgrade because it cannot be attributed to a namespace.
- **Chat turns are fenced by turnEpoch** (`ui/src/stores/chat.ts turnEpoch`): turnEpoch is incremented whenever the transcript is reset (namespace switch, new session, identity change) so an in-flight turn can tell it no longer owns the transcript and aborts its request via its epoch subscription.
- **Chat picker falls back to in-memory storage** (`ui/src/stores/chat.ts rawStorage`): rawStorage uses browser localStorage when it is usable and otherwise an in-memory map, because access can throw (opaque origin, blocked site data), Node exposes an unusable bare localStorage, and some jsdom setups have none; the fallback keeps the picker working for the page lifetime without persistence.
- **Mobile sidebar state is never persisted** (`ui/src/stores/ui.ts persistedUIState`): persistedUIState persists only durable preferences; the mobile sidebar overlay below the md breakpoint is session-local so a narrow viewport cannot overwrite the desktop sidebarCollapsed preference.
- **index.html pre-paint script mirrors the UI store theme migration** (`ui/index.html pre-paint theme script`): The inline script in ui/index.html applies the persisted theme before React loads so a dark page never flashes light, and therefore repeats the UI store's persisted-theme migration (a stored light from before version 1 is the old default). An entry with no version is not migrated, matching zustand, which always writes a version and skips migrating unversioned entries; index-html.test.ts runs the script to keep the two in step.

### `ui`

- **Only thin route wrappers are excluded from coverage** (`ui/vite.config.ts coverage.exclude`): The coverage exclude list in ui/vite.config.ts names only thin route wrapper files; route logic and new routes must stay in coverage.

## Consequences

- The UI's ESLint config allows empty `catch` blocks (`no-empty` with `allowEmptyCatch`). An
  intentionally ignored exception can no longer carry a comment, and the entries above record
  why each one is ignored.
- These decisions are still in force. A change that breaks one must supersede that
  entry in a new ADR.
- Symbols get renamed. When an entry's symbol no longer exists, search for the behavior it
  describes.
- Entries recovered from test comments record why a test is shaped the way it is, so the test
  stays honest. A later ADR may supersede them once the tests explain themselves.
