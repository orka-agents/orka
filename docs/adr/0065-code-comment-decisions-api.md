# 65. Decisions recovered from code comments: the API server

Date: 2026-11-22

## Status

Accepted. This record is a catalog produced by the comment ban in
[ADR 0062](0062-code-carries-no-comments.md). Each entry was a code comment that recorded a
non-obvious decision in `internal/api`. The comment was deleted, and the decision now lives here.

## Context

Round 2 of the comment cleanup classified every comment left after
[ADR 0063](0063-code-comment-decisions-round-1.md). In `internal/api` it found 1044 distinct decisions
that a reader of the code alone could get wrong. Comments that stated the same rule in several
places are merged into one entry. Where an earlier ADR already records a decision, the entry
links it.

## Decision

Each entry names the symbols it governs, so `rg '<symbol>'` finds the code. Entries are
grouped by package and ordered by source position as of round 2.

### `internal/api`

- **ACP artifact authorization authenticates from headers before reading the body** (`api.Server.issueACPArtifactAuthorization`): The artifact authorization endpoint resolves the provider bearer from the non-secret pool namespace/UID headers and rejects bad bearers before consuming the request body. Runtimes can reach this endpoint, so an unauthenticated peer must not be able to stream or drip-feed a body and tie up controller handlers.
- **Artifact request body pool identity must match the preauthenticated headers** (`api.Server.issueACPArtifactAuthorization`): After preauthentication, the body's namespace and RuntimePool UID must equal the header identity used to authenticate the bearer, so a valid bearer for one pool cannot authorize an artifact for another pool.
- **Operation capabilities are verified with a fresh timestamp after provider resolution** (`api.Server.issueACPArtifactAuthorization`): VerifyOperationCapability is called with time.Now() taken after provider resolution, because that resolution performs Kubernetes I/O and a capability that expired meanwhile must not be accepted against the earlier clock.
- **External artifact authorization re-resolves the provider after reading the body** (`api.Server.authorizeExternalACPArtifactRequest`): After consuming the body, the external artifact path re-resolves the runtime provider by identity. This closes races where the registration, its conformed Secret versions, or a colliding provider appeared after header preauthentication.
- **External artifact capability is verified last against the freshly resolved Secret** (`api.Server.authorizeExternalACPArtifactRequest`): The external artifact capability check runs last, against the freshly resolved frozen capability Secret and the current time, so any expiry or Secret rotation during the preceding reads fails closed.
- **Artifact RuntimePool resolution works from non-secret header identity** (`api.Server.resolveArtifactRuntimePoolByIdentity`): resolveArtifactRuntimePoolByIdentity resolves the RuntimePool and its exact active-instance controller-auth Secret from a non-secret pool namespace and UID taken from headers, so the caller's bearer can be authenticated before the request body is read.
- **Controller-auth Secret is selected by the pool's active instance epoch** (`api.Server.resolveArtifactRuntimePoolByIdentity`): During graceful epoch replacement both the draining instance's and the next epoch's controller-auth Secrets exist, so the resolver selects the Secret mounted by the pool's exact active instance rather than requiring a single Secret to exist.
- **Publisher broker endpoints authenticate from headers before reading the body** (`api.Server.issuePublisherArtifactAuthorization`, `api.Server.issuePublisherCredential`): Publisher artifact authorization and the credential broker check the shared publisher bearer before consuming the request body, because runtime Pods can reach these endpoints and unauthenticated peers must not be allowed to stream request bodies. The ACP credential broker checks the shared publisher bearer before consuming the request body, because runtime Pods can reach it and unauthenticated peers must not be allowed to stream request bodies.
- **Workspace upload authorization tolerates the Submitting handoff only** (`api.Server.authorizePublisherWorkspaceUpload`): Task status and the external-effect lease are separate Kubernetes objects, so the Task can advance once to Submitting while the workspace preparation effect still reads InFlight. authorizePublisherWorkspaceUpload tolerates that single handoff state but rejects every later and terminal state; authorizePublisherParentEffect separately enforces the live current-epoch lease.
- **Publisher broker leases are fenced by the current controller epoch** (`api.externalEffectLeaseActive`): externalEffectLeaseActive requires an in-flight effect's lease to belong to the controller's current durable epoch fence. Publisher broker paths authenticate with a shared bearer and no per-request epoch capability, so a lease from a superseded controller epoch must stop authorizing immediately even before its wall-clock expiry.
- **Preauth test uses an invalid body to prove ordering** (`api.TestACPArtifactAuthorizationBrokerAuthenticatesBeforeBody`): The wrong-bearer preauth test case sends invalid JSON so that a 403 instead of a 400 proves bearer authentication happens before the body is parsed.
- **Content-Length requirement exempts routes with their own bounded readers** (`api.acpArtifactStreamingGuard`): The Content-Length requirement skips gateway adapter ingress, the native session import POST, and the MCP endpoint POST. Gateway ingress legitimately arrives chunked or as HTTP/2 without a length and enforces its own per-route limit; native import and the MCP endpoint read bounded streams (MCP reads at most one byte past its limit under a read timeout), so chunked requests are safe there.
- **Artifact handler tests allow 30s for durable fsync writes** (`api.performArtifactRequest`): Artifact handler tests use a 30s app.Test timeout with FailOnTimeout because each artifact operation fsyncs files and directories several times and can exceed 5s on a saturated host, while a hung handler still fails with a deadline error.
- **Operator-tainted sessions never receive forge write credentials** (`api.Server.authorizePublicationCredential`): The credential broker backstops the controller's pre-publishing gate: a session tainted by operator access never receives publication credentials. The taint may be on the Task, its linked workspace incarnation, or another Task that shared that incarnation, so all three are checked and an unreadable taint fails closed.
- **MCP broker handler owns its context instead of fasthttp's RequestCtx** (`api.acpMCPBrokerHTTPHandler`): fasthttpadaptor passes the pooled *fasthttp.RequestCtx as r.Context(), which must not be used after the handler returns and is neither a WithCancel context nor an AfterFunc implementer, so any derived cancelable context spawns a goroutine that may call Done after reuse or shutdown. acpMCPBrokerHTTPHandler therefore gives the broker a fresh background context carrying only the API server span, and forwards shutdown through a watcher that holds just the Done channel and is joined before the handler returns.
- **MCP broker context copies only the server span** (`api.acpMCPBrokerHTTPHandler`): acpMCPBrokerHTTPHandler copies only the server span context from Fiber's local context so broker and tool spans keep their parent without inheriting the pooled request context.
- **Agent host API responses never carry token material** (`api.AgentHostResponse`): AgentHostResponse describes the signed-in person's own agent host and must never include access or refresh token material; only names, phase, readiness and connection state are returned. See [ADR 0036](0036-agent-hosts-from-connections.md).
- **Agent host Environment is the Copilot app's listed name** (`api.AgentHostResponse.Environment`): AgentHostResponse.Environment carries the environment name the Copilot app lists, which is the name the chart's template assigns, so it must stay derived from that template rather than the AgentHost object name.
- **Self-service wake never lifts an operator suspension** (`api.Handlers.WakeOwnAgentHost`): WakeOwnAgentHost only wakes a host that was suspended for idleness; a host an operator suspended stays suspended and the request is refused, because lifting it is the operator's decision. See [ADR 0036](0036-agent-hosts-from-connections.md).
- **Wake requests are dated strictly after the idle suspension** (`api.Handlers.WakeOwnAgentHost`): The controller wakes a host only for a wake request dated after its suspension, and both timestamps are stored to the second, so WakeOwnAgentHost truncates to seconds and bumps the wake time to one second past the suspension when they would otherwise be equal.
- **Agent host self-service writes are fenced to the checked object** (`api.Handlers.WakeOwnAgentHost`, `api.Handlers.DeleteOwnAgentHost`): WakeOwnAgentHost patches with an optimistic lock and DeleteOwnAgentHost deletes with UID and resourceVersion preconditions, so a host replaced under the same name after the ownership check, possibly another person's, is refused rather than woken or deleted. DeleteOwnAgentHost deletes with UID and resourceVersion preconditions taken from the ownership check, so a host replaced under the same name since, which may be another person's, is never deleted.
- **Deleting one's own agent host deletes its volume and a fresh host follows** (`api.Handlers.DeleteOwnAgentHost`): DeleteOwnAgentHost deletes the host and its volume; while the person stays linked to a provider serving hosts, the controller creates a fresh host afterwards. See [ADR 0036](0036-agent-hosts-from-connections.md).
- **Own agent host lookup is keyed by the caller's verified identity** (`api.Handlers.ownAgentHost`): ownAgentHost finds only the host fed by the caller's own provider link. Only the controller creates such hosts and the link name derives from the caller's verified issuer and subject, so no request can reach another person's host.
- **Retained agent hosts stay visible after their provider stops serving hosts** (`api.Handlers.ownAgentHost`): ownAgentHost considers links to every provider, not only providers currently serving hosts, so a host kept after its provider stopped serving hosts remains its person's to see and delete; a host from a currently serving provider is preferred.
- **Hosts outliving their provider are matched by link name** (`api.Handlers.ownAgentHost`): A host kept after its person disconnected can outlive its provider, which nothing holds once the link is gone; ownAgentHost then falls back to linksTo, because the link's name still identifies whose host it is.
- **Recorded provider names cannot make another person's link match** (`api.linksTo`): linksTo matches a host to the caller's link to the provider the host records, or for hosts recording none, to the provider prefix of its link name. Because a link name ends in a digest of the provider and the person's verified identity, a recorded name only says where to look and can never make another person's link match.
- **Agent host readiness is checked against an uncached Connection** (`api.Handlers.currentAgentHostResponse`): currentAgentHostResponse refuses a Ready condition observed for an older link or consent, reading the Connection without the informer cache because the cache may still describe the preceding grant right after the caller finishes a new consent.
- **Binding an Agent identity requires bind only when newly added** (`api.authorizeAgentIdentityBind`): authorizeAgentIdentityBind requires the bind verb on agentidentities/<issuer> only when a write sets an Agent identity the previous version did not hold; removing an identity needs no grant, so unrelated edits are not blocked.
- **Agent identity bind reviews the same subject as Agent use** (`api.authorizeAgentIdentityBind`): authorizeAgentIdentityBind builds its SubjectAccessReview with agentUseReviewSubject so that bind and use grants on Agents name one and the same subject form.
- **Only the requester approves calls under a Delegated agent identity** (`api.requireRequesterApprovesDelegatedWrite`): When a Task's binding froze a Delegated agentIdentity policy, requireRequesterApprovesDelegatedWrite lets only the Task's requester approve a call, because the call can act as that person. The decision rests on the write-once execution binding, never the live Tool or policy that an editor could change and restore around an approval; anyone authorized to decide approvals may still decline.
- **Agent REST writes reject what the reconciler rejects** (`api.TestHandlers_AgentWritesRejectInvalidSoulAndCopilotInstructions`): Agent REST writes validate soul and Copilot instructions the same way the Agent reconciler does, so the API never persists an Agent that can never become ready.
- **Conditional Agent spec update never adopts concurrent edits** (`api.Handlers.UpdateAgentSpec`): UpdateAgentSpec replaces an Agent's spec only on the UID and generation the caller observed, and a patch retry after a resourceVersion conflict never advances those expectations, so it cannot adopt a concurrent spec edit or a same-named replacement.
- **Agent update handlers authorize before parsing the body** (`api.Handlers.UpdateAgentSpec`): UpdateAgent and UpdateAgentSpec resolve namespace isolation and context-token authorization before binding the JSON body, so unauthorized namespace probes cannot learn whether a payload is syntactically valid.
- **Agent use authorization is a process-wide setting** (`api.agentUseAuthorization`): agentUseAuthorization is set once from ServerConfig at startup and is process-wide so every API path that creates a Task or another object naming an Agent enforces it without threading a setting through each caller.
- **OIDC and TxToken callers are reviewed as issuer-prefixed subjects** (`api.agentUseReviewSubject`): agentUseReviewSubject reviews Kubernetes-authenticated callers exactly as the API server authenticated them, and OIDC or transaction-token callers as "<issuer>#<sub>" with groups carrying the same prefix, matching kube-apiserver's default OIDC form. Token display claims are neither unique nor stable, and an unprefixed name or group could match a Kubernetes user, ServiceAccount or system: group; any other caller has no reviewable identity.
- **Agent use is checked only for newly named Agents** (`api.authorizeAgentRefsUse`): authorizeAgentRefsUse checks only Agents an object newly names; Agents the previous version already named were authorized when added, so an unrelated edit by someone without use on them still succeeds.
- **Agent references are compared exactly when deciding what is new** (`api.authorizeAgentRefsUse`): authorizeAgentRefsUse compares stored Agent references exactly, as admission does: a reference the controller cannot resolve, such as one with stray whitespace, is not the Agent its corrected name runs, so correcting it requires a new use check.
- **AHP project checkouts are not the turn's source** (`api.ahpProjectRoot`): ahpProjectRoot is where projects appear in the user's workspace when workspaces are enabled; each turn's Task still clones the repository itself, so the workspace checkout is never the source a turn runs on. See [ADR 0034](0034-agent-host-protocol-api.md).
- **The single AHP agent is advertised with id copilot** (`api.ahpAgentProvider`): ahpAgentProvider is the one agent the AHP backend offers, covering every model the user may run on whichever runtime serves it. Its id is copilot because some clients only send to an agent with that id.
- **Built-in runtime order decides which runtime serves a shared model** (`api.ahpBuiltInRuntimes`): ahpBuiltInRuntimes is ordered: a model several runtimes serve is offered once, on the first runtime in this list, and ahpChooseModel runs it there.
- **AHP sessions without a credential Secret clone public repositories read-only** (`api.AHPBackendConfig.GitCredentialSecret`): AHPBackendConfig.GitCredentialSecret names a Secret in each user's namespace whose token key clones and publishes their repositories; when that Secret is absent, sessions clone public repositories read-only.
- **AHP without a workspace class publishes every write turn** (`api.AHPBackendConfig.WorkspaceClass`): AHPBackendConfig.WorkspaceClass selects an ExecutionWorkspaceClass so a session's files stay warm between turns; when empty, every write turn publishes and the next turn starts from that publication.
- **AHP workspace image must be digest-pinned and provide sh and git** (`api.AHPBackendConfig.WorkspaceImage`): AHPBackendConfig.WorkspaceNamespace and WorkspaceImage enable per-user workspaces holding git checkouts and terminals; the image must be digest-pinned and provide sh and git.
- **AHP workspace idle timeout semantics** (`api.AHPBackendConfig.WorkspaceIdleTimeout`): AHPBackendConfig.WorkspaceIdleTimeout is how long a workspace with no shells, no running turn and nothing unpushed stays after its last use; zero keeps workspaces until their user's last session ends.
- **AHP workspace git reads use the person's own token** (`api.AHPBackendConfig.RepositoryCredential`): AHPBackendConfig.RepositoryCredential returns the person's own github.com token from their linked account, valid for at least AHPWorkspaceTokenHorizon, for workspace git reads; when nil, workspaces are limited to public repositories.
- **Queued AHP messages recheck their sender's token before running** (`api.ahpBackend.recheckToken`): ahpBackend.recheckToken verifies that a principal's connection token is still valid before a message it sent earlier runs, so a revoked connection cannot run queued work.
- **Queued AHP messages run with their sender's authority only** (`api.ahpBackend.pendingAuth`): ahpBackend.pendingAuth records who sent each waiting message, keyed by user, session and message id, and a message runs with its sender's authority only.
- **Terminal URIs are never reused** (`api.ahpBackend.retired`): ahpBackend.retired holds terminal URIs already used so input queued for an ended terminal can never reach a new terminal on the same URI.
- **A session's turn slot is reserved from admission to start** (`api.ahpBackend.reserved`): ahpBackend.reserved holds a session's turn slot from the moment a message is admitted until its turn starts, so a second message cannot slip in and start a concurrent turn.
- **Per-user lifecycle lock serializes workspace ownership decisions** (`api.ahpBackend.lifecycle`): ahpBackend.lifecycle serializes, per user, everything that decides who owns workspace state: session branch claims, session disposal and terminal creation.
- **AHP per-user locks are never taken while mu is held** (`api.ahpBackend.lockUser`, `api.ahpBackend.lockChanges`): ahpBackend.lockUser and lockChanges take per-user locks that must never be acquired while b.mu is held, to keep a fixed lock order and avoid deadlock. ahpBackend.lockChanges takes the per-user changeset lock, which must never be acquired while b.mu is held.
- **Turn reservations expire after 30 seconds** (`api.ahpReservationTTL`): ahpReservationTTL frees a reserved turn slot whose message the host never applied, so a lost admission cannot block a session forever.
- **Manual AHP approval holds only policy-allowed requests** (`api.ahpApplyApprovalMode`): ahpApplyApprovalMode makes a manual-approval turn hold every permission request Orka's policy would allow for the person to decide; allow-all leaves the decision to policy, so neither mode can grant what policy denies.
- **Active AHP turn is persisted across controller restarts** (`api.ahpSession.ActiveTurn`): ahpSession.ActiveTurn and ActiveTask are stored so a running turn survives a controller restart and can still be settled from its Task.
- **AHP turns are fenced to their Task UID** (`api.ahpSession.ActiveTaskUID`): ahpSession.ActiveTaskUID is the UID of the Task created under ActiveTask; a Task created later under the same name is not the turn's, and its events, approvals and result are never taken for the turn.
- **AHP messages sent mid-turn are queued** (`api.ahpPending`): Orka's runtimes take no input mid-turn, so every message sent while an AHP turn runs is queued as an ahpPending, with steering messages queued first. See [ADR 0034](0034-agent-host-protocol-api.md).
- **Pending message versions pair each sender with one version** (`api.ahpPending.Version`): ahpPending.Version names one version of a waiting message; a replaced message gets a new version so its sender can never be paired with another version's content.
- **AHP principals are always OIDC users** (`api.ahpPrincipalUserInfo`): ahpPrincipalUserInfo builds an OIDC UserInfo because AHP tokens are minted only for a person's own OIDC sign-in.
- **Recreated AHP session URIs never reach earlier Orka Sessions** (`api.ahpOrkaSessionName`): ahpOrkaSessionName hashes the user key, session URI and a chat id that is new on every creation, so a session URI created again after disposal never reaches the Orka Session and Tasks its earlier use kept.
- **AHP model listing is not the authorization boundary** (`api.ahpBackend.agentChoices`): ahpBackend.agentChoices lists built-in-runtime Agents the person may use, one per runtime and model, but each turn's Task is authorized again when it is created.
- **AHP hides models of Agents marked not Ready** (`api.ahpBackend.agentChoices`): ahpBackend.agentChoices skips Agents whose Ready condition is False, such as an OpenCode Agent without model limits, because they would fail every turn; Agents not yet checked are still offered.
- **AHP offers models only through Agents the person may use** (`api.ahpBackend.agentChoices`): ahpBackend.agentChoices runs authorizeAgentUse per Agent so a model the person cannot start a turn with is never shown as enabled.
- **AHP recovers a user's turns on connection** (`api.ahpBackend.PrepareConnection`): ahpBackend implements ahphost.ConnectionPreparer so the host recovers a user's turns when they connect, not only once a client lists agents. PrepareConnection settles, once per user, the turns a previous leader left running, so a client that subscribes only to a session or chat sees those turns and their held approvals live; recovering only on agent listing was insufficient.
- **Agent listing only retries failed recovery** (`api.ahpBackend.Agents`): The AHP host lists agents with its lock held, which recovery must not wait under; connections recover first and ahpBackend.Agents only retries a recovery that failed.
- **Workspaces are warmed only when something will remove them** (`api.ahpBackend.Agents`): ahpBackend.Agents warms the user's workspace only when an idle timeout is set or the person has a session, because without an idle timeout only a session's or shell's end removes it, and a person who only lists agents would otherwise keep a workspace and its credentials forever.
- **Listed AHP models are marked enabled** (`api.ahpBackend.Agents`): Every model ahpBackend.Agents lists already passed the user's Agent authorization and is marked enabled, because clients may refuse to send to a model the host does not mark enabled.
- **Default-branch backfill never resurrects removed projects** (`api.ahpBackend.HandleExtension`): Default-branch lookups run without the user lock, but backfillDefaultBranch writes under the lock project removal holds and only updates a project still stored, so a project removed meanwhile stays removed.
- **Removing an AHP project keeps its checkout** (`api.ahpBackend.removeProjectCommand`): removeProjectCommand takes a project off the user's list but leaves its checkout in place.
- **Projects in use by a session cannot be removed** (`api.ahpBackend.removeProject`): ahpBackend.removeProject refuses to remove a project a session still uses, because its turns and worktree need it; sessions are created under the same per-user lock so the check cannot race.
- **Adding an AHP project never clones it** (`api.ahpBackend.addProject`): ahpBackend.addProject only records a repository; Orka never clones it there, and each turn's Task clones it in its own workspace with Orka's credentials.
- **AHP projects are unique by path** (`api.ahpBackend.addProject`): Sessions, worktrees and checkouts find a project by its path, which omits the host, so ahpBackend.addProject refuses a second repository on the same path, under the lock project removal and session creation hold.
- **AHP repository URLs are canonical https without credentials** (`api.ahpCanonicalRepository`): ahpCanonicalRepository accepts only https repository URLs without userinfo, query or fragment, and returns them without a trailing .git.
- **Escaped query and fragment characters are rejected in repository paths** (`api.ahpCanonicalRepository`): ahpCanonicalRepository rejects path segments containing backslash, space, ? or #, because an escaped ? or # decodes into the path and, written back, git would read it as a query or fragment.
- **AHP directory URIs are escaped** (`api.ahpDirectoryURI`): ahpDirectoryURI builds file URIs through url.URL so directory names containing #, ? or % survive a client's URI parser.
- **Autopilot-style approval modes map to manual** (`api.ahpApprovalModeFrom`): Orka has no model-reviewed approvals, so ahpApprovalModeFrom maps that client mode to manual and asks the person instead. See [ADR 0034](0034-agent-host-protocol-api.md).
- **AHP session creation runs nothing** (`api.ahpBackend.CreateSession`): ahpBackend.CreateSession only records a session in one of the user's projects; nothing runs until the first message, whose turn Task creates the Orka Session.
- **AHP session URIs cannot use reserved channel schemes** (`api.ahpBackend.CreateSession`): ahpBackend.CreateSession rejects session URIs starting with ahp-chat:, ahp-changeset:, the content scheme or the terminal scheme, because the backend routes those schemes to a session's chat, changeset, file contents and terminals.
- **One project branch belongs to one AHP session** (`api.ahpBackend.CreateSession`): A project's branch belongs to exactly one AHP session, whose worktree and publications it holds; ahpBackend.CreateSession performs the project lookup, branch claim and record write under the user's lifecycle lock, which project removal also holds.
- **Session branches that clash by prefix are replaced** (`api.ahpBackend.CreateSession`): Git cannot hold a branch alongside one it is a prefix of, so ahpBackend.CreateSession replaces a requested branch that clashes with the base branch or, with workspaces enabled, with the clone's default branch, by a random orka/session- branch.
- **AHP session record is written last** (`api.ahpBackend.CreateSession`): ahpBackend.CreateSession writes the session record, which claims the branch and holds the project, after the chat record, so a failure leaves at most the chat's random-keyed record.
- **AHP session creation prepares the worktree eagerly** (`api.ahpBackend.CreateSession`): Clients run git in a new session's working directory right away, so ahpBackend.CreateSession ensures the workspace worktree with a bounded wait; a worktree that takes longer is finished before a terminal opens in it.
- **Disposing an AHP session keeps the Orka Session history** (`api.ahpBackend.DisposeSession`): ahpBackend.DisposeSession cancels a running turn and forgets the AHP session, while the Orka Session and its Tasks keep their history.
- **AHP disposal is serialized with branch claims** (`api.ahpBackend.DisposeSession`): ahpBackend.DisposeSession holds the user's lifecycle lock so nothing can claim the branch or start using the workspace until the worktree, workspace decision and records are settled; a session already disposed by another request is left alone.
- **Disposal fails while the session's Task may still run** (`api.ahpBackend.DisposeSession`): If cancelling the session's active Task fails, ahpBackend.DisposeSession fails and can be retried rather than forgetting a Task nothing could then cancel or follow.
- **Worktree removal precedes branch release** (`api.ahpBackend.DisposeSession`): ahpBackend.DisposeSession removes the worktree while the session still holds its branch, so a new session cannot claim the branch and lose its files. Nothing holding work found nowhere else is removed; terminals outlive sessions, so while one runs the worktree stays, and the workspace goes only with the last session.
- **Session state deletion is fenced by mu** (`api.ahpBackend.DisposeSession`): Every AHP session update holds b.mu from read to write, so the disposal deletes under b.mu and an update that read the record earlier cannot write it back afterwards.
- **AHP Task cancellation is UID-fenced and reads uncached** (`api.ahpBackend.cancelTask`): ahpBackend.cancelTask treats a Task that is gone, being deleted or finished as done and returns any other failure because the Task may still run. With a UID it stops only the Task created under it, and it reads from the API server because a cache that has not seen a just-created Task would report it gone.
- **Only the turn's requester cancels its Task via AHP** (`api.ahpBackend.cancelTask`): ahpBackend.cancelTask refuses to cancel a Task that ahpOwns does not attribute to the calling person.
- **Model switches move an AHP session to a new Orka Session** (`api.ahpBackend.resolveModel`): An Orka Session is bound to one runtime profile, so ahpBackend.resolveModel keeps a session's Agent until the person picks another model, and switching moves the session to a new Orka Session. When the session's Agent is no longer offered, another Agent offering the same model takes over the same way, so choosing the listed model never leads back to the Agent that is gone. See [ADR 0034](0034-agent-host-protocol-api.md).
- **AHP client actions are allowlisted** (`api.ahpBackend.AuthorizeClientAction`): ahpBackend.AuthorizeClientAction admits only the client actions the backend acts on and harmless view actions; anything else is rejected.
- **Client-provided tools are never offered to agents** (`api.ahpBackend.AuthorizeClientAction`): AHP view-state actions about an active client's tools are admitted only as view state; client-provided tools are never offered to Orka agents.
- **Unqueue never clobbers a newer sender** (`api.ahpBackend.unqueue`): ahpBackend.unqueue takes back a message the store would not queue: a message it would have replaced stays queued with its prior sender and is shown again, otherwise the client removes it; a sender set since by another message is left alone.
- **AHP cancel affects only the turn it named** (`api.ahpBackend.cancelTurn`): ahpBackend.cancelTurn runs after admission, when the named turn may have ended and another started, so it acts only if the session's active turn still matches the cancelled turn id.
- **Turn cancellation retries in the background** (`api.ahpBackend.keepCancelling`): ahpBackend.keepCancelling retries stopping a cancelled turn's Task through transient failures off the action queue, because the client already shows the turn as cancelled.
- **Tool confirmations apply only to their own turn** (`api.ahpBackend.HandleClientAction`): ahpBackend.HandleClientAction applies a tool-call confirmation only when the session's active turn matches the action's turn id, as for cancels.
- **Steering messages are queued first** (`api.ahpBackend.HandleClientAction`): Orka's runtimes take no input mid-turn, so ahpBackend.HandleClientAction queues a steering message first and shows it so, making it appear once when its turn starts rather than also as input to the running turn.
- **Pending queue bound is enforced at write time** (`api.ahpBackend.HandleClientAction`): ahpBackend.HandleClientAction rechecks ahpPendingMax inside the session update, because messages from two connections can both be admitted below the bound.
- **Approval mode display never diverges from stored mode** (`api.ahpBackend.HandleClientAction`): When a client changes the approval mode, ahpBackend.HandleClientAction retries storing it through transient failures; if it still cannot be stored, it shows the mode the session's turns actually run under so no client shows a mode they do not.
- **updateSession errors mean the change did not happen** (`api.ahpBackend.updateSession`): Callers of ahpBackend.updateSession whose next step depends on the change must check the error, because the change happened only if it is nil.
- **Some AHP session updates retry until they land** (`api.ahpBackend.updateSessionUntilDone`): ahpBackend.updateSessionUntilDone applies a session update that must not be lost, retrying in the background while the store refuses it until it lands or the session is gone; the returned channel closes once it has.
- **AHP resource reads never touch the server's disk** (`api.ahpBackend.ReadResource`): ahpBackend.ReadResource serves changeset before/after contents as the agent reported them. On the root channel a file is read from the user's running workspace so later terminal or branch changes show; otherwise the session is found from the content URI or the user's session that last changed the file. Nothing is read from the API server's own disk.
- **Newer deletions supersede older session contents** (`api.ahpBackend.ReadResource`): ahpBackend.ReadResource treats a file deletion as a change, so an older session's contents of a file a newer session deleted are not served as the file.
- **AHP reads Secrets without the manager cache** (`api.ahpBackend.gitSecretToken`): ahpBackend.gitSecretToken reads Secrets through the uncached API reader so the manager's cache never starts watching Secrets for this lookup.
- **AHP default-branch lookup only contacts github.com** (`api.ahpDefaultBranchHost`): ahpDefaultBranchHost is the only host Orka asks for a repository's default branch; the namespace's repository credential is never sent anywhere else and no other address is reached on a user's behalf.
- **Default-branch requests use a fixed github.com base** (`api.ahpBackend.defaultBranch`): ahpBackend.defaultBranch builds its request from the fixed github.com base and takes only the escaped repository path from the project URL, so a project cannot redirect the request or the credential to another host.

- **A lagging AHP subscription ends the turn from stored state** (`api.ahpTurn.run`): When the live subscription falls behind and drops events, ahpTurn.run marks the turn lagged so it ends from the Task's stored result, opens a new subscription for what comes next, and reads held permission requests back from their records so none waits unseen until it expires.
- **AHP turns without a known Task UID adopt the first one found** (`api.ahpTurn.ownsTask`): A recovered AHP turn whose Task UID is unknown takes the UID of the Task it first finds under its name and keeps it in the session record, so ahpTurn.ownsTask rejects any Task created later under that name.
- **AHP records a sentinel UID for a Task already gone** (`api.ahpTaskGoneUID`): ahpTaskGoneUID is a UID no Task can have; it is recorded for a turn whose Task was already gone at recovery, so no Task created later under that name is taken for the turn's, and later recoveries also know the Task was gone.
- **AHP turn take-back retries until it lands** (`api.ahpBackend.takeBackOnceStopped`): A session still recording a turn refuses every later message, so ahpBackend.takeBackUncreatedTurn retries until the take-back lands, and queued messages run only after it. takeBackOnceStopped keeps asking a Task whose creation reported failure to stop; a Task that cannot be stopped keeps the session busy, and recovery follows or settles it, rather than letting a next turn run beside it.
- **AHP turn Task UIDs are persisted with retries** (`api.ahpTurn.recordTaskUID`): ahpTurn.recordTaskUID retries a write the store refuses, because without the UID in the session record a later recovery would adopt whatever Task then holds the name.
- **AHP renames typed tool calls clients cannot fill** (`api.ahpTypedToolFields`): Clients draw some tool names as typed calls from specific input fields: the Copilot app draws "read" or "view" as a file view of the input's path and shows "View unknown" without one, while the Copilot runtime names calls by ACP kind (read, search, edit) and sends no input. ahpTypedToolFields lists those names and fields, and ahpToolName renames a call whose input lacks every field so clients show its title instead.

- **AHP live usage reports only prompt-scoped counts** (`api.ahpTurn.usage`): ahpTurn.usage ignores session-scoped usage updates; session-wide totals come from the completed result, so live updates report only the current prompt's token counts.
- **AHP confirmations are answered as the confirming connection** (`api.ahpTurn.confirm`): ahpTurn.confirm answers a held permission request with the identity of the connection that confirmed it. A refused approval reopens the confirmation; a refused denial needs no action, because the request then expires and is rejected, so the tool does not run either way.
- **AHP changeset line counts are multiset estimates** (`api.ahpLineChanges`): ahpLineChanges counts added and removed lines by matching lines as a multiset; it is a cheap summary count for the changeset, not a diff, and moved lines count as unchanged.
- **AHP stored answers get the same redaction as live answers** (`api.ahpTurn.showStoredAnswer`): When a turn did not see its whole answer live, ahpTurn.showStoredAnswer shows the Task's stored result, and that result receives the same pattern redaction as a live final answer before anyone sees it. After live updates fell behind, it is shown in its own part beside the streamed text and becomes the reply the conversation keeps.

- **AHP shows deadline-stopped turns as failed** (`api.ahpTurn.settle`): A turn stopped by its deadline (controller.ACPTaskTimeoutReason) is shown as failed with a time-limit message, not as cancelled, because a cancelled turn reads as though the person cancelled it.

- **AHP uses reply text as a failed turn's reason** (`api.ahpTurn.failureMessage`): A runtime that reports a failure as reply text leaves the Task only the generic prompt failure message, so ahpTurn.failureMessage appends the runtime's own text as the reason the person needs.

The turn's published flag lands with its end, because a later model switch must see that the branch was pushed or it would continue on it. The caller holds t.mu, so the retry uses the values captured then.

- **Connector provider reads are uncached** (`api.Handlers.providerReader`): Connector handlers read ConnectorProviders through the uncached reader, as credential resolution does, so informer lag never advertises a link resolution already refuses and the reads before a code exchange or custody commit see the provider as it is.
- **Duplicate links to one provider are never ready** (`api.markDuplicateLink`): markDuplicateLink marks every link unusable when a person holds more than one link to the same provider, because credential resolution refuses all of them as ambiguous.
- **Connection subject comes only from the verified identity** (`api.Handlers.CreateConnection`): CreateConnection takes the Connection's subject only from the verified identity and rejects request bodies carrying any other field.
- **Custody finalizer is installed at creation** (`api.Handlers.CreateConnection`): CreateConnection installs ConnectionCustodyFinalizer when the Connection is created so no token can be exchanged or parked for a Connection the controller cannot finalize.
- **Concurrent Connection creation reuses the winner** (`api.Handlers.CreateConnection`): When a concurrent request for the same identity and provider created the Connection first, CreateConnection reuses it under the same ownership checks and reads it uncached because the informer may not have seen the winner yet.
- **Connections cannot be rebound to another provider** (`api.Handlers.CreateConnection`): A Connection's provider reference is immutable; CreateConnection refuses to reuse an object bound to another provider because it cannot be relabeled and a consent started for it could never link.
- **Reused Connections get their ownership labels restored** (`api.Handlers.CreateConnection`): A reused Connection may lack the ownership labels the list route selects by, so CreateConnection restores them from the authoritative spec before starting consent.
- **Links are pending while consent for their mode is outstanding** (`api.markConsentPending`): When a link's grant does not cover the requested mode, or consent is restarted, the handlers project it as Pending via markConsentPending regardless of stale controller conditions.
- **Narrowing a link to a covered mode is usable at once** (`api.Handlers.UpdateConnection`): Narrowing a link to a mode its existing grant covers keeps it Ready immediately even though the spec write bumped the generation the controller's conditions observe; the controller catches up on its next pass.
- **Connection updates must name the mode** (`api.Handlers.UpdateConnection`): UpdateConnection requires an explicit mode; the empty default belongs to creation only so a client cannot narrow a link by omission.
- **Consent restarts whenever the grant does not fit** (`api.Handlers.UpdateConnection`): UpdateConnection starts consent whenever the granted scopes do not cover the mode or the provider's OAuth client changed, not only on the request that changed the mode, so a retry after a failed consent start still returns an authorize URL.
- **Disconnect runs in the custody finalizer** (`api.Handlers.DeleteConnection`): DeleteConnection only deletes the Connection; custody removal and best-effort provider revocation happen in the controller's finalizer so API and kubectl deletes behave identically. See [ADR 0033](0033-user-connectors.md).
- **Foreign Connections are reported as not found** (`api.Handlers.loadOwnedConnection`): loadOwnedConnection reports another person's Connection as not found so Connection names cannot be enumerated.
- **Retryable connector conflicts say retry** (`api.Handlers.CompleteConnection`): Connector completion keeps the parked row while the provider's conditions catch up, and every retryable conflict message says "retry" so a client can tell it from a consent that can never be finished.
- **OAuth client secret is read uncached** (`api.Handlers.providerOAuthConfig`): providerOAuthConfig reads the provider's OAuth client secret through the uncached reader so it never enters the informer cache.
- **OAuth client secret is never trimmed** (`api.Handlers.providerOAuthConfig`): providerOAuthConfig treats the client secret as opaque bytes: only emptiness is checked, and the value is never trimmed.
- **Revocation identity is bound at consent start** (`api.Handlers.startConnectorConsent`): startConnectorConsent seals the provider revocation digest with the consent and carries it through the callback, so an endpoint moved during the consent window is never handed the tokens at disconnect. Connector tokens are sealed with the revocation endpoint identity that consent started under, so moving the provider's revocation endpoint while the person is at the provider never makes disconnect hand the tokens to the new endpoint.
- **Authorization codes are bound to one client and scope set** (`api.Handlers.startConnectorConsent`): startConnectorConsent seals the provider authority digest and requested scopes so the code may only ever be exchanged with that OAuth client for those scopes; a token that reports no scope is credited with exactly them.
- **Connector callback is unauthenticated by design** (`api.Handlers.ConnectionCallback`): ConnectionCallback is unauthenticated because the browser returns from the provider without an Orka bearer token; the signed single-use state plus the sealed PKCE verifier are the credential. It never echoes provider parameters and never places token material anywhere but the sealed custody row.
- **Mode change during consent aborts the code exchange** (`api.Handlers.ConnectionCallback`): ConnectionCallback exchanges no code when the Connection's mode changed while the person was at the provider, because completion would refuse the result and no token should be issued.
- **Provider change during consent aborts the code exchange** (`api.Handlers.ConnectionCallback`): ConnectionCallback refuses to exchange a code when the provider was replaced or its OAuth client changed during consent, because the code belongs to the old client and must not be sent to the new endpoints.
- **Partial scope grants are refused** (`api.Handlers.ConnectionCallback`): ConnectionCallback refuses a token granted fewer scopes than the sealed consent requested, so a readWrite link never advertises tools its token cannot use. The requested set is the one sealed with the consent, never the provider's current configuration, and only an omitted scope field means "as requested"; an explicitly empty one is a grant of nothing.
- **Uncommitted connector tokens are dropped, never revoked** (`api.Handlers.discardCompletion`): Token material nobody committed is dropped and left to expire rather than revoked, because Orka cannot prove whose grant it is: a forwarded consent link or a provider that re-issues long-lived tokens could make it another person's live credential.
- **Consent tokens are parked until the owner commits** (`api.Handlers.ConnectionCallback`): ConnectionCallback parks issued tokens and hands the completing browser a one-time completion token that only the Connection's owner may spend, which stops a forwarded consent link from binding a victim's account to an attacker's Connection.
- **Tokens are sealed with their issuer digest** (`api.Handlers.ConnectionCallback`): Parked credentials carry the provider issuer digest so any later refresh or revocation knows which client issued them, independent of tool-destination changes.
- **Consented authority is re-verified at completion** (`api.Handlers.ConnectionCallback`): The parked completion records the full consented authority digest (client identity plus tool destinations) so CompleteConnection verifies it again before committing.
- **Ownership is checked before the completion token** (`api.Handlers.CompleteConnection`): CompleteConnection checks Connection ownership before examining the completion token so a non-owner learns nothing about the token, not even whether it is well-formed.
- **Completion rows are peeked, not consumed** (`api.Handlers.CompleteConnection`): CompleteConnection peeks the parked completion and removes it only after both the credential and the linked status commit, so a transient failure in between can be retried with the same token.
- **Completions are fenced to their Connection and authority** (`api.completionFenceError`): A parked completion must belong to the presenting Connection and to the provider authority the person consented under, or it is discarded so it cannot be retried across Connections. A committed completion is exempt only from the mode check, because custody already holds its material and it is the only record that repairs a lost status write.
- **Expired tokens without refresh are not committed** (`api.Handlers.CompleteConnection`): CompleteConnection discards a completion whose short-lived token has no refresh token and expired while the browser held it, since committing it would advertise a Ready link nothing can use.
- **Committed completion resumes only against unchanged custody** (`api.Handlers.CompleteConnection`): A retry after a failed status write resumes a committed completion only if custody still holds exactly its material and grant sequence; any other grant, even one re-issuing the same token strings, means a newer completion replaced it and wins.
- **Linked status is re-judged after custody replacement** (`api.Handlers.markConnectionLinked`): markConnectionLinked runs after custody was replaced, so when the Connection changed meanwhile (a mode PUT or reconciler status pass) it re-reads and judges it again against the committed material instead of leaving it describing a grant custody no longer holds.
- **Older consents never roll linked status back** (`api.Handlers.markConnectionLinked`): markConnectionLinked stops when a later consent already recorded its grant, so an older completion cannot roll the Connection status back behind custody.
- **Completion token travels only in the URL fragment** (`api.Handlers.connectorCallbackRedirect`): connectorCallbackRedirect puts only a fixed reason code and the Connection name in the query string; the one-time completion token goes in the URL fragment, which browsers keep out of requests, referrers, and server logs.
- **Callback redirect carries the consent namespace** (`api.Handlers.connectorCallbackRedirectTo`): connectorCallbackRedirectTo includes the namespace the consent was sealed in so the page completes the link where it was started rather than in whatever namespace it currently shows.
- **Connection completion needs both owner and one-time token** (`api.Handlers.CompleteConnection`): The OAuth callback only parks tokens and returns a one-time completion token in the redirect fragment; CompleteConnection commits only when the authenticated Connection owner presents that token. This defeats the forwarded-link attack, where an attacker sends their authorize URL to a victim: the victim holds the token but is not the owner, and the attacker owns the Connection but never sees the token. The token cannot commit into a different Connection: an attempt that fails the completion fence (wrong Connection, changed authority, expiry) discards the parked completion and so consumes the token, while a completion whose custody commit succeeded but whose status write failed keeps the token valid for retry.
- **Connector consent requires the custody finalizer** (`api.connectionCustodyProtected`): A Connection without the custody finalizer, such as one created outside the API, cannot start consent, and one that loses it after consent started is refused at the callback before any code exchange and again at completion. Without the finalizer, disconnect could delete the object without the controller revoking and removing sealed tokens.
- **Discarded connector completions are never revoked** (`api.Handlers.discardCompletion`): When a parked completion is discarded (stale mode, rotated client, partial grant, expiry), its tokens are left to expire and are never revoked. Providers such as GitHub can re-issue the exact committed long-lived token during a widening consent, so revoking discarded material could kill the live committed credential.
- **Omitted token scope means as-requested; empty scope grants nothing** (`api.Handlers.ConnectionCallback`): Following RFC 6749, a token response that omits the scope field granted exactly what the consent requested, while an explicitly empty scope is a grant of nothing. The connection callback must not treat an empty scope as as-requested.
- **A rotated OAuth client invalidates in-flight consent** (`api.completionFenceError`): If a ConnectorProvider's OAuth client is rotated while the person is at the provider, the authorization code must not be exchanged with the new client, and parked tokens from the old client are discarded rather than sent to the new client for revocation. A rotated client also forces fresh consent on the next mode change even when the granted scopes cover it.
- **Sealed connector credentials record their issuing client** (`store.ConnectorCredential`): Each sealed connector credential records the digest of the OAuth client that issued it, independent of Connection status, because refresh and revocation must authenticate with that same client rather than whatever the provider currently configures.
- **Completion retries are fenced by grant sequence** (`api.Handlers.CompleteConnection`): A completion that wrote custody but failed its status write stays retryable, but a retry after a newer completion committed different tokens must return 409 and not overwrite the newer commit. Each commit takes a new grant sequence in custody and the Connection status mirrors it.
- **Reauthorization retires, not drops, the previous credential** (`api.Handlers.CompleteConnection`): Linking a Connection again retains the previous credential sealed and retired instead of deleting it, so disconnect can still revoke it at the provider.
- **Omitted scope binds to what consent asked for** (`api.Handlers.ConnectionCallback`): When the token response omits scope, the grant is the scope set the consent originally requested, not the provider's current configured scopes; if the provider's scopes grew meanwhile, the link stays Pending until the person consents again.
- **Consent covers tool destinations, not only the OAuth client** (`api.completionFenceError`): The consented authority of a Connection includes the provider's credential-receiving tool destinations as well as its OAuth client. Adding or retargeting a tool between callback and completion, or before a committed retry, refuses recording the link, so tokens are never marked consented for a destination the person never saw; nothing is revoked.
- **Connection views revalidate against the current provider** (`api.revalidateConnectionView`): Connection API views re-run the checks credential resolution applies (current OAuth client, scope coverage, provider acceptance and existence, duplicate links) instead of trusting the Connection's Ready condition, so the dashboard and CLI never advertise a link resolution would refuse.
- **Connection views read providers uncached** (`api.Handlers.providerReader`): Connection views read ConnectorProviders through the uncached reader, as credential resolution does, so informer lag after a provider change cannot make a view report a link Ready that resolution would refuse.
- **Memory consolidation Tasks need read scopes for everything they read** (`api.contextTokenMemoryConsolidationFailures`): A context-token caller creating a Task that runs memory consolidation must hold the session-read and memory-read scopes, because the run reads every Session and memory in its namespace, and the memory-write scope in Propose mode, because it creates memory proposals. Kubernetes permissions are checked separately.
- **OpenCode provider authorization uses the Agent model identity** (`api.contextTokenTaskCreateEffectiveProviderModel`): contextTokenTaskCreateEffectiveProviderModel treats the Provider CRD type as authoritative for provider-backed execution, but built-in OpenCode executes the immutable Agent model identity and derives its provider from the qualified model ID. For OpenCode Tasks, Task AI provider/model fields and the Provider CRD type must not drive context-token provider authorization, or a token could be authorized for a different provider than the one that executes.
- **Substrate egress-injected Secrets count as credential use** (`api.collectSubstrateMCPEgressCredentialSecrets`): Secrets that the Substrate egress gateway injects into a Tool actor's requests are used whenever the Tool is invoked, so a context-token caller using such a Tool must hold the secrets credential-read scope for each of them.
- **Branch-constrained tokens refuse an unconstrained workspace ref** (`api.contextTokenWorkspaceFailures`): Execution gives Task workspace.ref precedence over branch, so when a context token constrains only the branch, a request that pairs the allowed branch with any ref selector is refused; otherwise the ref would bypass the branch constraint.
- **Brokered built-in tools have no Tool credential policy** (`api.contextTokenNativeRuntimeToolName`): The ACP broker serves its built-in tools ahead of any Tool resource with the same name, so contextTokenNativeRuntimeToolName treats those names, and runtime-native built-ins, as needing no Tool resource or Tool credential policy in an explicit allowlist. That classification grants nothing else: names the broker does not serve must still resolve, and a token's allowedTools context still bounds the allowlist.
- **list_connections follows the connector-read scope** (`api.connectorReadToolAuthorizer`): The list_connections tool exposes the same data the connector routes guard with the connector-read scope, so a delegated context token without that scope never sees the tool in the completion tool list, and connectorReadToolAuthorizer refuses the call at execution time (audit mode records and allows, matching the routes). It is also refused when connectors are disabled on the controller.
- **Linked-account tools follow the connector-read boundary** (`api.scopedLinkedAccounts`): The linked GitHub built-in tools of chat and the OpenAI/Anthropic compatibility proxies resolve a person's linked account only when a delegated context token carries the connector-read scope; under enforcement a narrowed token uses no linked account and never reaches the resolver, while audit mode resolves the link and records the missing scope.
- **Session event seq is the session cursor; taskSeq is the source** (`api.SessionExecutionEventResponse`): In SessionExecutionEventResponse, seq is the session-level cursor clients page with, while taskSeq is the sequence of the event in its source Task stream; clients must not use taskSeq as the session cursor.
- **Execution event API omits store-only fields** (`api.NewExecutionEventResponse`): NewExecutionEventResponse deliberately omits store-only fields such as ExecutionEvent.Usage from the public execution event representation; adding them to the DTO is an API exposure decision, not a mechanical mapping.
- **Event JSON integers parse without arbitrary precision** (`api.boundedJSONNumberInt`): boundedJSONNumberInt parses integral JSON decimal and exponent encodings without constructing arbitrary-precision values, so untrusted payloads cannot force huge allocations; out-of-range values clamp to the platform int range and negative or fractional values read as zero.
- **Reopened redaction journals mask later runtime text** (`execution event redaction journal (State reopen)`): The execution-event redaction journal does not persist logical field boundaries across turns, so after session recovery (a reopened journal) or when a value has two public copies it masks all later runtime text with the redacted value instead of risking reconstruction of a protected value across fields.
- **Task event streams are fenced to the authorized UID** (`api.Handlers.StreamTaskEvents`): Live execution events are published by Task name, so StreamTaskEvents filters them to the UID of the Task it authorized and never streams events of a Task re-created under the same name meanwhile.
- **SSE writers clone request strings and own their context** (`api.Handlers.StreamTaskEvents / StreamSessionEvents`): SendStreamWriter callbacks outlive the Fiber handler and Fiber recycles request buffers and contexts after the handler returns, so the stream handlers clone every string derived from fiber.Ctx, use a stream-owned context, and detect client disconnects through write and heartbeat failures.
- **Live events are a lossy tap; durable events are authoritative** (`api.Handlers.StreamTaskEvents`): StreamTaskEvents subscribes to live events before writing the durable replay so none is missed in between; live delivery is lossy, so a dropped subscriber gets one live_lagged frame and the durable event stream continues as the authoritative record.
- **Chat-session label attributes events only to chat Sessions** (`api.executionEventSessionName`): executionEventSessionName attributes a Task's execution events to spec.sessionRef, or for chat-API Tasks to the Session named by the orka.ai/chat-session label, which clients cannot set through the API. The label counts only when it names a chat-type Session, and without a session store it is not trusted at all.
- **Event streams stay open for terminating Tasks** (`api.Handlers.taskDeletedForEventStream`): A Task that is terminating but still readable can still emit cancellation, failure, or cleanup events, so taskDeletedForEventStream keeps the event stream open until the object is actually gone.
- **Losing settlement writers keep the already-public prefix** (`execution event redaction journal (settlement)`): The execution-event journal permits transcript publication after settlement, so a writer that loses the settlement race must still account for the prefix the winner already made public; otherwise later redaction could let joined copies reconstruct a protected value.
- **External route permissions mirror Kubernetes authorization requests** (`api.apiResourcePermission`): apiResourcePermission names a Kubernetes resource or documented virtual resource, with a slash separating resource and subresource. Create on a collection carries no name, exactly like the API server's own authorization request, and named actions on virtual subresources are checked against the parent object's name.
- **External API inventory preflights compound writes** (`api.externalAPIPolicies`): externalAPIPolicies is the complete external API inventory, checked against independent HTTP cases and the operator reference by tests. Handler checks still enforce loaded-object, gateway, and workspace permissions, but compound operations preflight all their write permissions in the inventory, before a handler can persist a record, enqueue work, or contact a provider.
- **Attention views authorize per item** (`api.externalAPIPolicies (GET /api/v1/attention)`): The attention and approvals views are authorized as Task list at the route, but each Task still passes the ListTasks filters and monitor items need their own list grants checked in the handler.
- **Consolidation reports need the permissions of their inputs** (`api.externalAPIPolicies (memory-consolidation-report)`): A memory consolidation run's full report holds text drawn from every Session, memory, and open proposal it read, so reading the report requires the list/get permissions needed to read those inputs, not only Task get.
- **Operator workspace access needs dedicated subresources** (`api.externalAPIPolicies (operator workspace access)`): Operator workspace access routes are authorized against dedicated virtual subresources of tasks that no built-in aggregate role grants, plus Task get; Task get alone never authorizes exec or file access. See [ADR 0044](0044-operator-workspace-access.md).
- **Tool MCP proxy is authorized by Tool get** (`api.externalAPIPolicies (POST /api/v1/tools/:name/mcp)`): The Tool MCP proxy invokes the Tool's actor under the caller's Tool get permission, matching the authority workers used when they read the Tool and called it directly.
- **Security finding actions grant only their fixed transitions** (`api.externalAPIPolicies (security findings)`): Named security-finding actions such as validate and patch are authorized by their own subresource create grants, which include only their fixed finding-state transitions; general edits, including dismissal and reopening, require update on securityfindings.
- **Connector and AHP token routes are identity-only** (`api.externalAPIPolicies (connector and AHP token routes)`): Connector and AHP token routes are identity-only at the policy layer; their handlers require a verified OIDC or context-token identity and ownership of the Connection or token, and refuse TokenReview and ServiceAccount callers so they never reach the store.
- **Control-plane MCP entry only authenticates** (`api.externalAPIPolicies (POST /mcp)`): The POST /mcp entry is identity-only: each tool call replays its REST route in process with the caller's credentials and is authorized by that route's policy and handler checks, never by the /mcp entry itself. See [ADR 0043](0043-control-plane-mcp-server.md).
- **External routes authorize per endpoint and fail closed** (`api.externalAPIRouter`): externalAPIRouter installs authorization on each endpoint rather than as group middleware, because only the endpoint sees Fiber's resolved path parameters. An endpoint without an inventory policy fails closed, and the inventory test requires an independent authorization case before it ships.
- **GitHub sign-in sessions reach only opted-in routes** (`api.githubSessionRoutes`): A GitHub sign-in session may reach only identity-only routes listed in githubSessionRoutes, which act on the caller's own sign-in, links, agent host, and AHP tokens. Being identity-only is not enough: a route must opt in, so routes added later stay closed to sessions. The control-plane MCP endpoint is identity-only but not a session route. See [ADR 0037](0037-github-sign-in.md).
- **Only TokenReview identities get SubjectAccessReview checks** (`api.Handlers.checkExternalRoute`): checkExternalRoute applies Kubernetes namespace and SubjectAccessReview checks only to TokenReview identities; direct OIDC validation and transaction tokens have their own authorization contracts and must not be reinterpreted as Kubernetes TokenReview identities.
- **Usage authorization and selection share one namespace set** (`api.Handlers.usageTeamNamespaces`): usageTeamNamespaces computes the namespace set used both to authorize a usage request and to select its report, so the two cannot diverge; explicit teams replace the namespace query and default.
- **Noncanonical namespaces are refused before authorization** (`api.Handlers.externalRequestNamespace`): Proposal actions trim the namespace in the store, so externalRequestNamespace rejects namespace input with surrounding whitespace before namespace isolation and SubjectAccessReview; otherwise authorization could cover a different namespace than the eventual write.
- **Authorization binds namespace exactly as the handler does** (`api.bindExternalNamespace`): bindExternalNamespace decodes the request namespace with the same typed JSON binding the handler uses, including duplicate-key and case-insensitive field behavior, and ignores fields the handler ignores, so authorization checks the namespace the handler will actually write to.
- **CRUD routes require only the action's exact grant** (`api.externalAPIPolicies (CRUD routes)`): External CRUD routes are authorized with only the exact verb of the action; an update or delete must not additionally require get or list for the handler's internal read of the object. Repository monitor validation additionally requires access to the referenced reviewer Agent.
- **Only applying a proposal links a memory to it** (`api.Handlers.CreateMemory`, `api createNamespaceMemory`): Memory create refuses a caller-supplied source proposal ID; only applying a proposal records that link, because a memory created with a proposal's ID would otherwise block that consolidation proposal from ever applying. Memory creation refuses a client-set sourceProposalId, because only applying a proposal links a memory to it. A memory created with a proposal's ID would be returned as that proposal's application or, for a consolidation proposal, would block it from ever applying.
- **Authorization inventory fixture stays independent of the policy map** (`api.externalAuthorizationInventory`): externalAuthorizationInventory is written by hand, independent of externalAPIPolicies: each row is an actual HTTP request with its expected resource authorizations, including every write of compound operations, and an omitted route fails the inventory check. Generating it from the production map would make the test unable to catch a wrong policy.
- **Oversized usage report test uses a 60s deadline** (`api oversized usage report test`): The oversized usage report test scans 20,000 SQLite rows, about 0.4s normally but 11-12s under -race, so it uses a 60s Fiber test timeout with FailOnTimeout; a hung handler still fails with a deadline error rather than an empty response.
- **Pre-credential routes are authenticated by their own contracts** (`api route inventory exemptions`): A few external routes have no externalAPIPolicies entry because they run before any Orka credential exists: bound-secret ingress has its own tested contract, the OAuth connector callback is authenticated by signed single-use state, and GitHub sign-in endpoints check the GitHub token. Every other registered route must have an explicit policy.
- **Live authorization test needs an explicit disposable cluster** (`api.TestExternalAPILiveTokenReviewAuthorization`): TestExternalAPILiveTokenReviewAuthorization runs only when ORKA_AUTHORIZATION_E2E_KUBECONFIG names a disposable cluster with the Task, Tool, and Skill CRDs, so ordinary unit tests never use the current Kubernetes context; all records live in a namespace removed on cleanup.
- **Authorization tests never print credentials** (`api authorization tests (credential handling)`): Authorization tests keep issued ServiceAccount tokens and other credential values in memory only and never include requests or credential values in assertion messages, fixture files, or logs.
- **Legacy monitor gitSecretRef applies only without readCredentialRef** (`RepositoryMonitor read credential (gitSecretRef)`): A RepositoryMonitor's legacy gitSecretRef is the effective read credential only when readCredentialRef is absent, and write workflows (issues, repair) require the explicit readCredentialRef field; authorization must check whichever credential reference is effective.
- **API tool calls run on the caller's permissions** (`api.authorizeExternalToolContext`): authorizeExternalToolContext swaps the tool context's clients for ones that authorize each operation against the API caller's resource permissions; controller and worker tool clients are never changed.
- **Caller-supplied Agent/Provider references need caller get** (`api.externalToolReferenceReader`): externalToolReferenceReader keeps direct uncached policy reads for freshness, but Agent and Provider references supplied by an API caller are still checked against the caller's get permission so the direct reader cannot be used to bypass it.
- **Proxy GitHub tools are bound per request** (`api.registryForExternalToolCall`): The compatibility proxy's GitHub tools keep the client they were constructed with, so registryForExternalToolCall binds those instances to the current request in a per-call registry instead of mutating the shared default registry.
- **External tool client authorizes the final operation** (`api.externalToolClient`): externalToolClient authorizes each concrete client operation after the tool has resolved its arguments and defaults, so the check covers what is actually sent; it deliberately does not expose Watch.
- **Tool discovery degrades; execution stays strict** (`api.externalToolDiscoveryClient`): externalToolDiscoveryClient omits metadata the caller cannot read so ordinary chat stays usable, while executable tools receive the strict authorizing client and still return authorization errors.
- **External tool resource access is an explicit allowlist** (`api.externalToolResource`): externalToolResource maps only the concrete resources used by management tools and code_exec to permissions; any new resource access must be assigned an explicit permission here, and unmapped objects are refused.
- **Chat tools cannot see Gateway or others' AHP Tasks** (`api.externalToolClient.authorizeTask`): Gateway-owned Tasks require the dedicated Gateway read/operate API checks and another person's AHP turns are visible only to their requester, so externalToolClient.authorizeTask reports both as NotFound to generic chat tools, which cannot act on them or reveal their transcripts.
- **Tool-created Tasks cannot continue AHP sessions** (`api.externalToolClient.Create`): A Task created by an external tool is not private, so continuing an AHP session with it would read the conversation into a non-private Task: another person's AHP session is reported not found, and even the owner's own (or a ServiceAccount's) is refused.
- **Tool Task deletes are fenced to the authorized object** (`api.externalToolClient.Delete`): externalToolClient.Delete loads the Task, authorizes ownership, and deletes with UID and resourceVersion preconditions so the authorization decision cannot apply to a replaced or mutated object.
- **External tool client closes unused write entry points** (`api.externalToolClient.Apply`): No external tool needs server-side apply, collection deletion, or subresource mutation, so externalToolClient refuses those entry points instead of inheriting them from the controller client.
- **Fork workspace data and transcript context are selected separately** (`api.ForkTaskRequest.ExecutionCheckpoint`): In a fork request, executionCheckpoint is the only selector of workspace data; afterSeq selects transcript context independently and is never treated as a filesystem checkpoint.
- **Fork idempotency requires an explicit Idempotency-Key** (`api.Handlers.ForkTask`): ForkTask mints a unique random name by default because forking one checkpoint into several divergent branches (different prompt, agentRef, or workspace) is the primary use case; (source, afterSeq, requester) does not identify a logical fork. For a Session-only reuse class it creates a new Session named after the fork so later turns continue the fork's data; other class-backed workspaces are deleted on detach.
- **Forks cannot continue another person's AHP session** (`api.Handlers.forkSessionHidden`): forkSessionHidden refuses a fork that would continue another person's AHP session. The one exception is the fork's own new session: a fork of an AHP turn with per-session workspace reuse starts a session named after itself, which it owns while no Task continues it and no Session by that name exists.
- **Only caller-object rejections map to 400** (`api.invalidObjectError`): invalidObjectError maps a Kubernetes Invalid rejection or an admission webhook denial of a caller-supplied object to 400, and returns nil for anything else, so an authorization failure of the API server's own identity stays a server error rather than looking like the caller's mistake.
- **Gateway ingress rate-limits before auth and dedup** (`api.Handlers.HandleGatewayEvent`): HandleGatewayEvent applies the ingress rate limiter before body parsing, adapter authentication, and duplicate lookup. Letting retries or duplicates bypass it would give unauthenticated sources a datastore-backed oracle and reopen the pre-auth resource-exhaustion path; a throttled duplicate can safely retry later.
- **Unknown gateway admission outcomes are retryable** (`api.Handlers.HandleGatewayEvent`): Gateway admission deduplicates by Gateway UID and externalEventId, so when the outcome of an admission write is unknown HandleGatewayEvent returns 503 asking the adapter to retry the same event, which is safe even if the first write committed.
- **Cached gateway lists never pose as complete pages** (`api.Handlers.listGatewayPage`): listGatewayPage prefers the uncached API reader, which pages natively and whose expired or malformed continue tokens are reported as the caller's 410/400. When only the cached client exists, a limited request is served as one unlimited cached list and continue tokens are rejected, because the cache truncates at Limit and stamps an unusable continue sentinel; the sentinel is also normalized away so it never reaches a client.
- **GitHub sign-in limits are sized to the App rate limit** (`api.githubSignInGlobalRate`): GitHub sign-in, session renewal, and invites share the GitHub App's rate limit (typically 5,000 requests an hour). One sign-in makes at most four App-authenticated calls, so the global sign-in limit (0.25/s, burst 30) allows at most 900 sign-ins, 3,600 calls, an hour regardless of client count. The per-client limit (keyed by address, which behind an Ingress is the proxy's) lets a team of about 20 sign in together and 12 a minute after while stopping one source from using the whole global rate; renewals share it, keyed by person.
- **Per-client limits are checked before the shared limit** (`api.gatewayIngressLimiter.AllowClientFirst`): AllowClientFirst spends shared global capacity only on a request its client's own limit admits, so a client over its limit cannot drain what every other client shares; a request the global limit then refuses returns its client's token.
- **Invite completion has its own timeout** (`api.inviteCompletionTimeout`): The device code's expiry ends only the wait for the invited person's approval; checking and linking an approved invite is bounded separately by inviteCompletionTimeout (2 minutes), so an approval near expiry can still complete.
- **Invite responses never carry tokens** (`api.InviteResponse`): InviteResponse reports an invite and how it ended but never carries GitHub tokens, so polling an invite through the API cannot leak the invited person's credentials to the operator.
- **Invites disclose that accepting starts an agent host** (`api.InviteResponse.AgentHost`): InviteResponse.AgentHost tells the operator to disclose before approval that accepting starts an agent host whose code can read the person's GitHub token; the person must be told this before approving the device code. See [ADR 0036](0036-agent-hosts-from-connections.md).
- **Invites require host creation** (`api.Handlers.CreateInvite`): An invite exists to give someone who cannot reach Orka a Copilot environment, so CreateInvite returns 501 when the controller does not create agent hosts for sign-ins; a link alone would leave the invited person nothing to use.
- **Invite app credentials are read before any device flow** (`api.Handlers.CreateInvite`): CreateInvite reads the GitHub App's credentials before GitHub issues anything, so every later refusal can revoke the tokens it was issued.
- **Invite slots are reserved before starting a device flow** (`api.Handlers.CreateInvite`): CreateInvite reserves a slot in the bounded pending-invite table (maxPendingInvites) before asking GitHub for a device code, so a full table refuses with 429 and never starts device flows it cannot track.
- **Invite revocation tries current then creation-time app credentials** (`api.Handlers.inviteRevocationConfig`): After approval, completeInvite re-reads the app's credentials as a rotated Secret would be; if they cannot be read, or revocation with them fails, the credentials read at invite creation are used. inviteRevocationConfig follows a rotated Secret reference only for cleanup: the provider need not be ready but must still identify the issuing app, and the rotated candidate never authorizes the changed invite.
- **Invites revoke every token they will not keep** (`api.Handlers.completeInvite`): Tokens obtained for someone other than the invited login, from a person who may not sign in, left unused because an existing link was kept, or not stored because linking failed, are revoked with the issuing app's credentials; the invite outcome reports whether GitHub confirmed the revocation and never reports an unconfirmed one as done.
- **An invite links only to the provider it disclosed** (`api.Handlers.completeInvite`): The person approved what the invite disclosed, so if the GitHub provider was replaced or changed while the code was pending (UID, generation, authority digest, agent host, or scopes), completeInvite refuses the invite and revokes the token with the issuing app; a new invite is needed.
- **Invited hosts require expiring, refreshable tokens** (`api.Handlers.completeInvite`): An invite provisions an agent host, and a host accepts only a user token that expires and has a refresh token beside it, so completeInvite refuses and revokes a token GitHub issued without expiry or refresh token, telling the operator to enable user-token expiration in the GitHub App.
- **Invite identity checks redeem the refresh token once** (`api.Handlers.inviteIdentity`): inviteIdentity checks that the approved token belongs to the invited login and, given a refresh token, redeems it once so custody holds what GitHub issued from it. It rechecks the login on the refreshed token: an account renamed between the checks is no longer the invited login, and membership is read for the login GitHub reports now. See [ADR 0037](0037-github-sign-in.md).
- **Invites accept links committed but not yet recorded** (`api.Handlers.completeInvite`): When custody committed an invite's grant but the Connection status write failed, the invite is Accepted and the Connection reconciler records the link from the committed completion. A host decline the person's existing link carried is lifted in the same commit, because nothing repairs it later.
- **Unlabel events of include labels are accepted** (`api.repositoryMonitorAcceptsPullRequestEvent`): repositoryMonitorAcceptsPullRequestEvent accepts an unlabeled event whose removed label was an include label, even though the pull request no longer matches, so the monitor run can retire that pull request.
- **Label commands are filtered before the label is consumed** (`api.repositoryMonitorAcceptsLabelCommand`): repositoryMonitorAcceptsLabelCommand rejects a pull request outside the monitor's include labels before the one-shot command label is consumed, so an out-of-scope command leaves the label in place; the controller re-checks inclusion independently and remains authoritative.
- **Read-only monitor commands use a triage threshold** (`api.repositoryMonitorPermissionAllowedForIntent`): RepositoryMonitor AllowedRepositoryPermissions is deliberately an allowlist for write commands only (the CRD permits write, maintain, and admin); read-only commands instead require GitHub triage permission or better, not that write-only policy.
- **Issue snapshot digests hash only agent-visible content** (`api.githubIssueSnapshotDigest`): githubIssueSnapshotDigest hashes exactly the issue content supplied to agent workflows and deliberately excludes GitHub's updated_at, which also changes when one-shot command labels are consumed or re-added; including it would defeat active-action coalescing for identical input.
- **Finished monitor work actions are never reopened** (`api.Handlers.markRepositoryMonitorCommandWorkActionRetryPending`): Marking a monitor work action retry-pending is done by the store in one step that checks status and writes together: a finished action is final, and reopening one, even one the controller completes concurrently, would run its work again.
- **Pause intake ignores suspension and command settings** (`api.repositoryMonitorAcceptsPauseEvent`): repositoryMonitorAcceptsPauseEvent accepts pause labels even for a suspended monitor, because suspension only pauses scheduling and completed Task handoffs still need to see a pause; pause is policy intake, independent of command enablement and issue filters, requiring only that issue targets are enabled.
- **Pause permission lookup may use the read credential** (`api.Handlers.repositoryMonitorPauseActorPermission`): The pause actor's permission lookup is a read-only GET, so repositoryMonitorPauseActorPermission may run it with the monitor's read credential through the existing token validation, without relaxing the forge-credential requirement for any mutation command.
- **Pause guards persist before runs and clear only via inventory** (`api.Handlers.handleRepositoryMonitorPauseEvent`): Reconciliation ingests completed Tasks before queued inventory runs, so handleRepositoryMonitorPauseEvent persists the durable pause guard before exposing a run, letting its handoff see the pause. Removal deliveries can arrive before or after a newer label addition, so only fresh inventory may clear the guard, never an unlabeled delivery.
- **Pause rejections keep one receipt per delivery** (`api.Handlers.recordRepositoryMonitorPauseRejection`): recordRepositoryMonitorPauseRejection records at most one rejection receipt per webhook delivery, like accepted intake, so GitHub delivery retries do not duplicate rejection events.
- **Session tokens carry a distinguishing prefix** (`api.sessionTokenPrefix`): Orka session tokens start with sessionTokenPrefix (orka_s_) so the API authenticator routes them only to the session store and never offers them to OIDC or ServiceAccount token review.
- **GitHub token expiry is capped at eight hours** (`api.maxGitHubAccessTokenLife`): maxGitHubAccessTokenLife caps the expiry a sign-in claims for its GitHub token and is the assumed expiry of a token that reports none, because GitHub App user tokens last eight hours. A link that cannot refresh then ends, and every refresh rechecks org/team membership. See [ADR 0037](0037-github-sign-in.md).
- **Sign-in uses the agent-host provider's GitHub App** (`api.GitHubSignInConfig`): GitHubSignInConfig signs people in through the GitHub App of the agent-host ConnectorProvider: that app's OAuth client verifies submitted tokens, and a sign-in links the person's account through the same provider. See [ADR 0037](0037-github-sign-in.md).
- **CreateHosts false records a host decline** (`api.GitHubSignInConfig.CreateHosts`): When GitHubSignInConfig.CreateHosts is false, every sign-in is recorded as declining an agent host rather than simply skipping host creation, so no controller later provisions a host from that link.
- **GitHub sessions reach only self-service routes** (`api.GitHubSignInConfig.authenticateSession`): authenticateSession resolves a session token to a verified person, but identities of type githubSession may only reach routes that act on the caller's own links, agent host, and AHP tokens. See [ADR 0037](0037-github-sign-in.md).
- **Session store outages are not token rejections** (`api.GitHubSignInConfig.authenticateSession`): When the session store is unavailable, authenticateSession returns errSessionStoreUnavailable instead of an unauthorized error, because a client treating 401 as a verdict would discard a session that is still live.
- **Auth config response carries no secrets** (`api.AuthConfigResponse`): AuthConfigResponse is served without authentication by GetAuthConfig, so it must only ever contain public sign-in options and never secret material.
- **Sign-in provider must serve agent hosts** (`api.Handlers.signInProvider`): signInProvider only returns a ready ConnectorProvider that serves agent hosts, because sessions renew from the host link and sign-in starts a host unless the person declines one.
- **Sign-in refuses ambiguous agent-host providers** (`api.Handlers.signInProvider`): signInProvider fails when two ConnectorProviders in a namespace serve agent hosts, because the controller provisions no host in that case and sign-in would promise a host that never arrives.
- **People are identified by numeric GitHub ID** (`api.SessionResponse.Subject`): Session subjects use the numeric GitHub user ID rather than the login, because logins can be renamed and reused by a different person.
- **Sign-in verifies token app and membership** (`api.Handlers.SignInWithGitHub`): SignInWithGitHub is unauthenticated because the submitted GitHub token is the credential; it must verify the token was issued to Orka's own GitHub App and that its person is in an allowed org or team before linking the account and issuing a session. See [ADR 0037](0037-github-sign-in.md).
- **Sign-in is rate limited before reading the body** (`api.Handlers.SignInWithGitHub`): SignInWithGitHub applies signInLimiter before reading the body or authenticating anyone, because each attempt checks its token with GitHub as the App; without a limit any caller could exhaust the App's GitHub rate limit, shared with renewal and invites, and lock everyone out.
- **Only tokens a sign-in minted are revoked** (`api.Handlers.SignInWithGitHub`): SignInWithGitHub revokes a token it does not store only if the sign-in minted it; a client-submitted token is never revoked because the client keeps it and custody may hold that same token for the person's working link.
- **Only GitHub-confirmed expiries admit a host** (`api.Handlers.SignInWithGitHub`): An agent host only takes a token that expires, and SignInWithGitHub treats an expiry as confirmed only for tokens it minted via the refresh token GitHub issues alongside expiring tokens; a submitted expiresIn is the client's unverified claim.
- **Submitted refresh tokens are proven by refreshing** (`api.Handlers.SignInWithGitHub`): A submitted refresh token arrives unchecked, so SignInWithGitHub refreshes it once to prove it belongs to the same person, and custody then stores only tokens GitHub issued from that refresh.
- **Membership refusals only on GitHub's verdict** (`api.Handlers.SignInWithGitHub`): SignInWithGitHub refuses a person only when GitHub answers that they are not an allowed member; when GitHub cannot answer the request is retryable. In both cases the token the sign-in obtained is not used.
- **Non-refreshable links bound the session** (`api.Handlers.SignInWithGitHub`): When the linked GitHub token cannot refresh, the issued session's deadline is that token's expiry, since the session could not be renewed past it.
- **Renewals share the sign-in rate limit** (`api.Handlers.RenewSession`): RenewSession spends the App's GitHub rate limit and returns a renewable session, so renewals, concurrent or chained, are charged to the sign-in limiter under a per-person key and the overall limit.
- **Non-refreshable links do not renew** (`api.Handlers.RenewSession`): RenewSession refuses to renew when custody's token is not refreshable: such a token is held only until the deadline Orka chose, which the session already ends at, so the person must sign in again and have membership rechecked.
- **Renewal requires the subject's own grant** (`api.Handlers.RenewSession`): RenewSession requires the link to still hold the session subject's own grant; it renews for the session's subject, never for whoever the refreshed token happens to belong to.
- **Token lifetime is capped before Duration conversion** (`api.gitHubTokenExpiry`): gitHubTokenExpiry caps expiresIn at maxGitHubAccessTokenLife in seconds before converting to a time.Duration, because a large client-submitted expiresIn would overflow and yield an expiry in the past; a missing expiry uses the same cap.
- **Unrecorded sign-in links are repaired by reconciler** (`api.errSignInLinkUnrecorded`): errSignInLinkUnrecorded covers a sign-in whose custody commit succeeded but whose Connection status write failed; the Connection reconciler records the link from the committed completion, so the handler need not roll back custody.
- **Sign-in links through the consent pipeline** (`api.Handlers.linkGitHubSignIn`): linkGitHubSignIn records sign-in tokens through the same consent, completion, and commit steps as a browser consent so custody's fences apply equally. Its held result is false when nothing stored the tokens, and the caller then revokes them if it minted them.
- **Sign-ins for one Connection are serialized** (`api.Handlers.linkGitHubSignIn`): linkGitHubSignIn holds a completion lock keyed by Connection UID so each sign-in judges the link as the previous one left it; a waiting sign-in reuses what was just linked rather than commit a second grant.
- **Host declines are ordered around link changes** (`api.Handlers.linkGitHubSignIn`): linkGitHubSignIn records an agent-host decline under the completion lock before the link changes, so no host takes the new grant, and lifts it only after custody holds a grant a host may take; overlapping sign-ins therefore never undo each other's decline.
- **Repeat sign-ins keep a working link** (`api.Handlers.linkGitHubSignIn`): linkGitHubSignIn keeps an existing link that still holds the person's account, because every commit retains the grant it replaces until disconnect and relinking on each sign-in would soon refuse new ones; the unused token is revoked unless custody holds it.
- **Uncertain links are not replaced** (`api.Handlers.linkGitHubSignIn`): When linkGitHubSignIn cannot tell whether the existing link still works, it fails retryably instead of replacing it, because a replacement would spend one of the grants custody retains.
- **Kept link's token bounds the session** (`api.Handlers.linkGitHubSignIn`): When linkGitHubSignIn keeps an existing non-refreshable link, the session deadline comes from that kept token's expiry, not from the token just submitted.
- **Unknown completion outcome counts as held** (`api.Handlers.linkGitHubSignIn`): When storing the completion fails ambiguously, linkGitHubSignIn reports the tokens as held so the caller does not revoke a token custody may have stored.
- **Decline is lifted before the status write** (`api.Handlers.linkGitHubSignIn`): linkGitHubSignIn lifts the host decline before writing Connection status, because the Connection reconciler repairs a failed status write from the completion while nothing would repair a decline left in place.
- **Decline writes are fenced to the locked Connection** (`api.Handlers.recordAgentHostDecline`): recordAgentHostDecline runs under the UID-keyed completion lock and writes only to the Connection read under it: conflicting writes are reread and retried, and a Connection recreated under the same name is never written.
- **Which existing sign-in links are kept** (`api.Handlers.signInLinkHolds`): signInLinkHolds never keeps a non-expiring token, because membership is rechecked only at refreshes, and for host-starting sign-ins never keeps a non-refreshable one, whose Orka-chosen expiry a host does not take. It errors when custody or GitHub cannot answer, so only a link shown not to work is replaced, and on error still returns custody's token when known so the caller never revokes it.
- **Concurrent Connection creates are reread uncached** (`api.Handlers.ensureSignInConnection`): When ensureSignInConnection loses a create race to a concurrent sign-in, it rereads the Connection with an uncached reader because the informer may not have observed it yet, then applies the same checks.
- **Sign-in rejects Connections for another provider** (`api.Handlers.ensureSignInConnection`): ensureSignInConnection rejects an existing Connection whose providerRef differs, matching CreateConnection's immutable providerRef, so a Connection created outside the API under the canonical name never receives this provider's grant.
- **Custody requires the protecting finalizer** (`api.Handlers.ensureSignInConnection`): ensureSignInConnection only writes custody for a Connection carrying the finalizer that tombstones and revokes custody on delete; a Connection created elsewhere gets the finalizer when first reconciled.
- **GitHub sessions cannot reach the MCP endpoint** (`api.Handlers.authorizeExternalRoute`): The /mcp endpoint is identity-only, yet a githubSession identity is still refused there: sessions may reach only routes acting on the person's own links, agent host, and AHP tokens.

With namespace isolation enforced, authenticated callers must carry a namespace and may access only that namespace.

- **Connector tool execution preconditions** (`api.InternalHandlers.ExecuteConnectorTool`): ExecuteConnectorTool requires the caller to be the Task's current worker Pod (via its ServiceAccount token), the Tool to sit behind a connection-mode OutboundAccessPolicy and be enabled for the Task after readOnly filtering, and resolves the credential from the Connection frozen in Task status. The response carries only the tool result, and the executor redacts credential material from errors.
- **Connector arguments are validated server-side** (`api.InternalHandlers.ExecuteConnectorTool`): ExecuteConnectorTool validates arguments against the Tool's schema because the worker is not trusted to have honored it; the person's credential is attached only to arguments the schema admits.
- **Dispatched tool list bounds connector calls** (`api.InternalHandlers.ExecuteConnectorTool`): ExecuteConnectorTool refuses any tool absent from the Job's immutable frozen tool list, so a Task or Agent edited after dispatch cannot add a capability the worker was not started with.
- **Only the dispatched Tool definition executes** (`api.InternalHandlers.ExecuteConnectorTool`): ExecuteConnectorTool compares ConnectorToolDispatchDigest with the digest frozen at dispatch and refuses a Tool retargeted after dispatch (URL, method, headers, schema), a policy whose credential output changed, or either object deleted and recreated even with the same spec, whether or not the call needs approval.
- **Claims are released only before a provider request** (`api.InternalHandlers.runConnectorTool`): runConnectorTool hands a claimed approval back on every failure before a provider request, so an exact retry or a fresh human decision can claim it again; once a request reached the provider the claim stays spent.
- **Reserved effects settle before claims are released** (`api.InternalHandlers.runConnectorTool`): On a pre-request failure runConnectorTool first settles the reserved effect as Failed so the ledger never keeps an orphaned Pending record, and releases the claim only once that transition is durable; otherwise the worker is asked to retry with the claim still held.
- **Concurrent holders own the effect record** (`api.InternalHandlers.runConnectorTool`): When another execution holds the effect record, runConnectorTool returns 409 and leaves the claim spent until that execution settles it.
- **Credential injection is pinned to the checked policy** (`api.InternalHandlers.runConnectorTool`): runConnectorTool pins the executor to the policy name, UID, and generation whose dispatch digest was checked, so a policy replaced or edited in between is refused rather than executed under an unchecked configuration.
- **Connector calls are re-judged at send time** (`api.connectorSendGate`): Because policy reads and credential resolution (possibly a token refresh) run inside Execute, connectorSendGate rechecks the caller's authority, the Tool, its policy, and the frozen Connection immediately before the request leaves, so a cancelled Task, replaced Job, edited or withdrawn Tool or policy, or disconnected link never reaches the provider.
- **Provider idempotency key is the approval claim** (`api.InternalHandlers.runConnectorTool`): The downstream idempotency key for a consequential connector call is the claimed approval key rather than a worker-chosen value, so the provider sees one request per approval.
- **Caller authority is rechecked before the effect** (`api.InternalHandlers.runConnectorTool`): runConnectorTool reruns verifyTaskCaller right before the external effect so a Task cancelled or a Job replaced during its lookups cannot still reach the provider.
- **Read connector calls share the timeout clamp** (`api.InternalHandlers.runConnectorTool`): Unclaimed read connector calls are bounded like claimed ones: the Tool's own timeout is clamped to connectorToolMaxTimeout.
- **Credential resolution failures are 424** (`api.InternalHandlers.runConnectorTool`): When credential resolution fails before any request is sent (no connection, revoked, or changed since dispatch), runConnectorTool reports 424 Failed Dependency and hands the approval back.
- **Durability failures surface to the worker** (`api.InternalHandlers.runConnectorTool`): If settling or releasing a claim could not be made durable, runConnectorTool returns that error instead of the plain 424, so the worker retries appropriately rather than treating the call as settled.
- **Unattempted call refusals respect record ownership** (`api.unattemptedConnectorCallRefusal`): unattemptedConnectorCallRefusal refuses a caller that lost authority at the send gate and hands its claim back, but reports a claim whose effect record another request moved without settling or releasing anything, since that request owns the record.
- **Consequential connector calls are ledgered** (`api.InternalHandlers.runConnectorToolEffect`): runConnectorToolEffect records each approval-claimed call under its claim key with the frozen Connection digest and the approval's argument and configuration digests, so outcomes survive controller restarts and are auditable. A call failing before any request settles Failed; one the provider may have applied settles OutcomeUnknown.
- **Lost results do not reopen succeeded effects** (`api.InternalHandlers.runConnectorToolEffect`): When a call succeeded and its record is terminal but the result could not be retained, the claim stays spent and nothing is settled or released again.
- **Unsettled effects ask the worker to retry** (`api.InternalHandlers.runConnectorToolEffect`): If the effect record could not be settled and the ledger still shows the call in flight, the worker gets a retryable 503 rather than a settled 502, so it does not spend its approval on a record nothing will reconcile.
- **Connector calls are capped at ten minutes** (`api.connectorToolMaxTimeout`): connectorToolMaxTimeout caps a connector-backed call and its effect lease at the same bound the ConnectorProvider declaration enforces on curated tools.
- **Connector timeout matches executor deadline** (`api.connectorToolTimeout`): connectorToolTimeout uses the Tool's declared request timeout, the same deadline the executor applies, so the effect lease covers the whole call; because a Tool CR has no upper bound it is clamped to connectorToolMaxTimeout.
- **Reserved effects settle only from Pending** (`api.InternalHandlers.settleReservedConnectorEffect`): settleReservedConnectorEffect moves a reserved record to a terminal state only while it is exactly Pending; a record another execution holds in flight or that is already settled is reported with ErrExternalEffectNotPending and left alone.
- **Frozen Connection is rechecked before send** (`api.connectorConnectionUnchanged`): connectorConnectionUnchanged rereads the frozen Connection right before the request is sent so a disconnect or re-link after credential resolution never reaches the provider with the released token.
- **Effect request records are non-secret** (`api.connectorToolEffectRequest`): connectorToolEffectRequest records only non-secret data: what was approved and which person's link, by frozen identity digest, the call acted under.
- **Binding digests distinguish consents** (`api.connectorBindingDigest`): connectorBindingDigest covers only policy, UID, generation, and grant sequence; the grant sequence separates consents to the same Connection and matches the digest the ACP broker records, so audit can tell which consent authorized a call.
- **Only connection-mode tools run in the controller** (`api.loadConnectorBackedTool`): loadConnectorBackedTool returns a Tool only when it sits behind a connection-mode OutboundAccessPolicy; every other Tool runs in the worker Pod.
- **Enabled tools are re-derived server-side** (`api.connectorToolEnabledForTask`): connectorToolEnabledForTask re-derives the Task's enabled tools including the readOnly rule so a worker cannot reach a tool the controller hid.
- **Controller enforces connector approvals** (`api.InternalHandlers.enforceConnectorToolApproval`): The worker's approval gate is advisory once compromised, so enforceConnectorToolApproval rechecks the approval policy frozen into the Job and the Task's approval history: a write-class tool the frozen policy does not cover is refused, and a covered tool executes only with an approved approval binding this tool and exact arguments. The approval is claimed atomically in the Task event stream before any provider request, and connectorApprovalClaim keys include the decision sequence and prior pre-request releases so one approval authorizes exactly one execution.
- **Claim releases are counted per decision** (`api.connectorApprovalClaim`): connectorApprovalClaim.decisionSeq names the human decision a claim executes and releases are counted per decision, so a late release from an older decision can never reopen a newer, already executed one.
- **Approvals bind tool configuration and Connection** (`api.InternalHandlers.enforceConnectorToolApproval`): An approval binds the tool's execution configuration (URL, method, headers, schema) and the Connection frozen for its policy, as digested by ConnectorTargetSpecDigest; the live Tool and the Job's binding must still match, or a retargeted Tool or re-linked account could ride an old approval to a different write.
- **Effect reservation precedes claims** (`api.InternalHandlers.enforceConnectorToolApproval`): The effect record is reserved before the claim is recorded so every claim has a record stating whether its call started; a claim with no record is never assumed unstarted and stays refused.
- **Spent claims reconcile from the effect ledger** (`api.InternalHandlers.reconcileSpentConnectorClaim`): reconcileSpentConnectorClaim interprets an existing claim from the ledger so a controller stopping between claim and call never strands the approval: a Succeeded record for this call replays its result, a Pending record fenced to Failed or a Failed record means nothing reached the provider and the claim is handed back, no record means the claim cannot be shown unstarted and stays refused, an InFlight record with an expired lease settles OutcomeUnknown, and Failed, OutcomeUnknown, or a live InFlight lease is reported as such.
- **Failing a Pending record fences the original call** (`api.InternalHandlers.reconcileSpentConnectorClaim`): For a reserved-and-claimed record that never started, moving it to Failed is the fence: it succeeds only while nothing started, and afterwards the original request's transition to InFlight fails, so it cannot reach the provider once the claim is handed back.
- **Reclaim CAS is pinned to observed state** (`api.InternalHandlers.reconcileSpentConnectorClaim`): The Pending-to-Failed transition is a compare-and-swap pinned to the observed Pending state and version; if a request moved it to InFlight meanwhile, the CAS fails and the claim is reported as still executing.
- **Expired in-flight effects record OutcomeUnknown first** (`api.InternalHandlers.reconcileSpentConnectorClaim`): When the controller that made a call is gone and the provider may have applied it, reconcileSpentConnectorClaim durably records OutcomeUnknown before reporting the approval spent; until then the worker is told to retry.
- **Tool policy is frozen in the Job** (`api.frozenJobPolicy`): frozenJobPolicy is read from the worker environment the Job builder froze at dispatch; because the Job spec is immutable, neither a Tool changing class nor a Task or Agent edited afterwards can widen it.
- **Job Connection bindings are authoritative** (`api.frozenJobPolicy`): The Job's frozen Connection bindings are authoritative and Task status must equal them, or a status rewritten after dispatch could redirect a connector call.
- **Bindings without a grant sequence are refused** (`api.InternalHandlers.ExecuteConnectorTool`): ExecuteConnectorTool refuses a frozen Connection binding that carries no grant sequence, because every linked Connection has one and such a binding cannot have come from the controller's dispatch freeze.
- **Workers cannot forge harness call records** (`api.InternalHandlers.SubmitExecutionEvent`): SubmitExecutionEvent treats the harness identity as controller-owned: workers may submit only their own call records, which are bound to the authenticated Task UID.
- **Usage reports are attributed to the verified Task** (`api.InternalHandlers.SubmitExecutionEvent`): SubmitExecutionEvent attaches usage attribution only for the authenticated Task UID verified earlier, so a worker cannot charge usage to another Task.
- **Chat label attributes events only to an existing chat Session** (`api.executionEventSessionName`): A chat-created Task has no sessionRef, so executionEventSessionName attributes its execution events to the Session named by its orka.ai/chat-session label so the chat timeline is not empty. The label counts only when the store confirms an existing chat Session; without a store, a sessionRef is taken as given but a chat label attributes nothing.

Test helpers pass fiber.TestConfig{Timeout: 30 * time.Second, FailOnTimeout: true} so they measure handler behavior, not scheduler latency.
- **Gateway message body limit covers fully escaped JSON only** (`api.maxGatewayMessageRequestBytes`): maxGatewayMessageRequestBytes allows the content and request identity to be fully JSON-escaped (6 bytes per byte) plus 1 KiB of framing, but not unbounded whitespace or unknown fields. The decoded content is still separately capped at 16 KiB.
- **Gateway capability failure is identified by error identity** (`api.errGatewayInterimDeliveryUnsupported`): The transaction helper preserves the exact *fiber.Error value errGatewayInterimDeliveryUnsupported, and its identity rather than arbitrary error text carries the controller-owned capability failure code. Do not replace it with a freshly constructed error or match on message text.
- **Gateway message submission accepts only the exact native Task Job Pod** (`api.InternalHandlers.SubmitGatewayMessage`): SubmitGatewayMessage (POST /internal/v1/tasks/:namespace/:taskName/gateway-messages) may be called only by the exact active native Task Job's Pod. Runtime and broker callers must use capability-bound authorization; never add a ServiceAccount exception to this endpoint.
- **Map gateway domain errors inside the transaction** (`api.gatewayMessageTransactionError`): submitGatewayMessage converts domain errors through gatewayMessageTransactionError inside the transaction callback because the transaction helper masks unknown failures as generic errors. Mapping after the helper returns would lose the domain error.
- **Gateway message budget read never reserves quota** (`api.InternalHandlers.GetGatewayMessageBudget`): GetGatewayMessageBudget applies the same native caller and writer revocation gates as gateway message POST, but reads only a snapshot and never reserves quota.
- **Gateway reply origin is authenticated independently of message admission** (`api.InternalHandlers.GetGatewayReplyOrigin`): GetGatewayReplyOrigin authenticates the durable origin independently of the mutable message admission gates. Like gateway message POST, it requires the exact native Pod and Job and rechecks revocation and durable state under the authorized writer.
- **Gateway message errors expose only status and stable code** (`api.sendGatewayMessageError`): sendGatewayMessageError never returns authorization, library, or store diagnostics, message content, routing, or provider metadata. The HTTP status and a stable code are enough for worker decisions.
- **Register cleanup fence before injecting revocation** (`api gateway message revocation test`): The gateway message revocation test registers the Task's cleanup fence with WithAuthorizedTaskDataAccess first, so the injected revocation happens only during admission authorization, after the worker has been authenticated.
- **No Kubernetes reads inside the store writer** (`api.InternalHandlers.submitGatewayMessage`): Gateway message admission must finish its Kubernetes reads before entering the store writer. The revocation test performs a real RevokeTaskJob write from inside a Kubernetes Get, which would deadlock if a Kubernetes read ran inside the writer.
- **Cross-task coordination requires the Task provenance webhook** (`api.InternalHandlersConfig.TaskProvenanceProtected`): InternalHandlersConfig.TaskProvenanceProtected permits cross-task coordination on internal worker endpoints only when the Task provenance admission webhook protects coordination ancestry. Without that webhook, ancestry labels could be forged, so coordination stays disabled.
- **Finish the bounded body read before reserving the store writer** (`api.InternalHandlers.SubmitResult`): SubmitResult reads the bounded request body completely before reserving the store writer. A slow upload must not delay Task deletion or keep an earlier authorization alive while the body streams in.
- **Worker workspace status writes target the exact authorized Task version** (`api.InternalHandlers.UpdateExecutionWorkspaceStatus`): UpdateExecutionWorkspaceStatus updates the exact Task resourceVersion it authorized. A concurrent controller change must produce a conflict and repeat authorization before the worker can write.
- **Workers cannot overwrite controller-owned workspace attachment state** (`api.InternalHandlers.UpdateExecutionWorkspaceStatus`): Workers only report provider status through UpdateExecutionWorkspaceStatus. ClassRef, WorkspaceRef, State, AttachedEpoch, and other attachment authority and finalization fields are copied from the previous status because the controller owns them.
- **Message createdAt keeps its RFC 3339 UTC wire format** (`api.InternalHandlers.GetMessages`): GetMessages returns createdAt in the wire format it had when it was a string: RFC 3339 in UTC with the stored fractional seconds. Workers parse this format, so changing the timestamp type must not change its serialization.
- **Internal endpoints fail closed without a verifiable namespace identity** (`api.InternalHandlers internal caller authorization`): Internal worker endpoints are namespace-scoped. A caller without a verifiable namespace identity is refused with 403 and must never pass for arbitrary namespaces.
- **Consuming inbox reads map unknown outcomes to 409 and unavailability to 503** (`api.InternalHandlers.GetMessages`): When a consuming inbox read's ConsumeMessages committed but the storage client could not read the result, GetMessages answers 409 without a retry hint, because a new HTTP request carries a new operation ID and would return the inbox without the consumed batch. When ConsumeMessages never reached the provider, it answers 503 with a retry hint, since nothing was consumed and a new request returns the same batch.
- **Namespace cleanup generation fences worker message routes** (`api.InternalHandlers worker message routes`): Any Task's cleanup advances the namespace's cleanup generation, which fences the worker message routes. A committed operation whose replay finds the fence moved is not reauthorized and rerun.
- **Unreadable replays across cleanup stay unknown** (`api.InternalHandlers.GetMessages`): If a consuming inbox read or send committed, lost its response, and could not be replayed because another Task's cleanup moved the namespace's Task data fence, the route answers 409 without a retry hint. It does not authorize again and repeat the write as a new operation, so no second inbox batch is consumed and a sent message is stored exactly once.
- **Only a consolidation run's own worker may begin or complete it** (`api.InternalHandlers.memoryConsolidationCaller`): memoryConsolidationCaller accepts only the authenticated worker of an active memory consolidation Task. A run reads every user's Sessions, which admission allowed only for the caller that created the Task, so no other identity may begin or complete it. See [ADR 0051](0051-offline-memory-consolidation.md).
- **Consolidation inputs are read once and recorded with the run** (`api.InternalHandlers.BeginMemoryConsolidation`): BeginMemoryConsolidation reads a run's inputs once and records them with the run, so a resumed worker reads the same input and completion is checked against exactly what the model saw. - **Consolidation access runs under the namespace Task data fence** (`api.InternalHandlers.withMemoryConsolidationRun`): withMemoryConsolidationRun authorizes the caller as an active run's worker and performs access under the namespace's Task data fence. A revoked worker can then neither read the run's transcripts nor complete it, even with a request authorized just before the revocation.
- **Re-read consolidation inputs when another run moves the cursor** (`api.memoryConsolidationBeginAttempts`): If another run in the same mode completed while this one read its inputs, it moved the cursor past this window's start and begin fails with ErrPreconditionFailed. BeginMemoryConsolidation then rereads the inputs from the new cursor, up to memoryConsolidationBeginAttempts times.
- **Consolidation completion validates against recorded input and writes proposals atomically** (`api.InternalHandlers.CompleteMemoryConsolidation`): CompleteMemoryConsolidation validates a submission against the input its run recorded and the targets' current generations, then records the report. - **A consolidation result without an operations list is malformed** (`api.InternalHandlers.completeSubmittedMemoryConsolidation`): An absent or null operations list is rejected as a malformed result rather than treated as a run that found nothing, because completing it would move the cursor past Sessions nobody read. A run that found nothing submits an empty list.
- **Completion checks proposals created during the run** (`api.InternalHandlers.completeSubmittedMemoryConsolidation`): At completion, proposals created while the run ran are reloaded so the run does not repeat them. If that reload reached its limit, the report's input is marked truncated, since the proposals left out were not checked.
- **Proposals closed during a run cannot be covered** (`api.InternalHandlers.completeSubmittedMemoryConsolidation`): A proposal the run read may have been applied, rejected, or archived while it ran, and its fact may already be in memory. Completion loads those closed proposals so an operation can no longer cover them.
- **Look up generations of every memory the run read** (`api.InternalHandlers.currentTargetGenerations`): currentTargetGenerations looks up the current generation of every active memory the run read, not only those a submission names. - **Only verified active-Task worker listings count as memory recalls** (`api.InternalHandlers.ListMemories`): Only an agent's recall_memory call counts the memories it returned; prompt memory context and operator listings do not, and a response larger than tools.MemoryRecallResultLimit is not counted because the agent never receives all of it. That check reads Kubernetes, so it runs with the count after the response, on a copy of the caller.

ListMemories clones the namespace and copies the caller before the deferred recall count uses them.

Entries are lower case without a trailing slash and are matched against routeLookupPath output.

Unrouted paths must be classified the same way, or a caller gets a different answer for a spelling the router treats as identical.

- **Telemetry shares the SPA fallback predicate** (`api.spaFallbackEligible`): spaFallbackEligible decides whether a 404 is served as the SPA index page instead of a JSON error, and telemetry middleware calls the same predicate so the recorded status matches what the client receives.

The OpenAI-compatible (/openai/v1) and Anthropic-compatible (/anthropic/v1) APIs format errors in their provider's envelope directly; only their unrouted paths reach customErrorHandler, through compatRouteNotFound. Chat tool results use an internal {success,error,errorType,suggestion} shape inside LLM messages and are not user-facing API errors.

- **Compat API 404s use the provider envelope** (`api.customErrorHandler`): customErrorHandler answers unrouted paths under the compatibility APIs through compatRouteNotFound in that provider's error format, because their callers are provider SDKs that parse only that provider's error envelope.
- **Unsupported compat endpoints name their alternative** (`api.unsupportedCompatRoutes`): unsupportedCompatRoutes lists endpoints of the emulated provider APIs that Orka deliberately does not serve, with the supported route to use instead. Keys are lower case and looked up with a folded path; the explicit message costs a client one log line instead of a confusing parse failure far from the cause.
- **Unsupported compat endpoints answer 501 without retry** (`api.compatRouteNotFound`): compatRouteNotFound answers a known but unimplemented endpoint of an emulated provider API with 501 rather than 404, and sets X-Should-Retry: false so provider SDKs do not retry this permanent failure. compatRouteNotFound sets X-Should-Retry: false on its 501 answer so provider SDKs do not retry a permanently unsupported endpoint.
- **Transcript display text never alters stored tool arguments** (`api.sessionTranscriptMessage`): sessionTranscriptMessage adds display text to tool calls in the public transcript projection without changing the stored arguments, because browsers round large JSON numbers before rendering and continuation must reload exactly the arguments the provider sent.
- **Hashed assets are cached immutably for a year** (`api.staticAssetCacheControl`): staticAssetCacheControl marks files under /assets as public, max-age one year, immutable, because Vite content-hashes every file there so a URL never changes meaning.
- **The SPA index is always revalidated** (`api.spaIndexCacheControl`): spaIndexCacheControl is no-cache because index.html names the current hashed assets; a cached index would keep a browser requesting chunks of an old build.
- **CSP hashes are computed from the built index.html** (`api.inlineScriptPattern`): inlineScriptPattern extracts inline script elements from the built index.html to hash them for the CSP; this works because Vite copies index.html's inline scripts into the build verbatim.
- **Dashboard CSP allows inline scripts only by hash** (`api.spaContentSecurityPolicy`): spaContentSecurityPolicy builds the dashboard document policy with a sha256 hash source for each inline script in the served index.html, so script-src never needs 'unsafe-inline'. External module scripts are covered by 'self' and get no hash.
- **CSP script hashes use LF-normalized text** (`api.spaContentSecurityPolicy`): spaContentSecurityPolicy normalizes CRLF and CR to LF before hashing inline script text, because browsers hash the script after the HTML parser normalizes line endings; hashing raw bytes would block the script.
- **Dashboard state is shared by error handler and telemetry** (`api.dashboardStateKey`): dashboardStateKey marks in Fiber app state that the app serves the embedded dashboard. customErrorHandler and the telemetry middleware both read it through dashboardServed so the status a client receives for an unrouted path and the recorded status always agree.
- **Connector consent has a landing page without the dashboard** (`api.Server.setupStaticFiles`): Server.setupStaticFiles serves the embedded SPA only when the dashboard is enabled. Without it, connector OAuth consent still redirects to connectorSettingsPath, so that path gets a plain completion page when connectors are enabled.
- **Compression is scoped to static routes** (`api.Server.setupStaticFiles`): Server.setupStaticFiles attaches compression middleware only to the static asset, favicon, and SPA routes; API responses, event streams, and the compatibility endpoints never pass through it.
- **Every dashboard route is registered explicitly** (`api.Server.setupStaticFiles`): Server.setupStaticFiles registers index.html for every top-level route under ui/src/routes so each gets the compressed page; unknown paths still reach the error handler's uncompressed SPA fallback. TestStaticFiles_EveryUIRouteIsRegistered derives the routes from ui/src/routes to keep the list complete.
- **Completion page never echoes unvalidated query values into commands** (`api.Handlers.ConnectorCompletionPage`): Anyone can send a person a connector completion URL, so Handlers.ConnectorCompletionPage only puts a query value into the command it tells the person to run when the value is a valid Kubernetes name or a known reason code; anything else is dropped.
- **API tests use the storage client, not the raw store** (`api.testStorageClient`): testStorageClient wraps an in-process SQLite store in storageclient.Client as production does, because Orka's side of the store protocols, such as fenced task data access and memory proposal application, lives in the client; its writes carry the controller epoch the dataset holds.
- **Unknown storage outcomes are never advertised as retryable** (`api.temporaryStorageHTTPError`): temporaryStorageHTTPError answers only known uncommitted storage refusals with a retryable 503; store.ErrOutcomeUnknown becomes a 409 without a retry hint. An HTTP retry does not preserve the storage operation ID, so repeating an uncertain write could lose or duplicate consumed messages or assigned UUIDs.
- **Memory routes map temporary storage refusals first** (`api.memoryStoreError`): memoryStoreError maps a temporary storage refusal to 503 before checking any other storage error, so a not-yet-open storage fence is reported as retryable rather than as a wrapped not-found or conflict.
- **Substrate MCP proxy response bound exceeds the tool result limit** (`api.substrateMCPProxyMaxResponseBytes`): substrateMCPProxyMaxResponseBytes is 16 MiB so one streamed actor response fits the 10 MiB tool result limit plus SSE framing.
- **Substrate MCP proxy write timeout exceeds the upstream timeout** (`api.substrateMCPProxyWriteTimeout`): substrateMCPProxyWriteTimeout bounds writing one proxied response because the upstream timeout cannot interrupt a write blocked by a caller that stopped reading. It is substrateMCPProxyMaxTimeout plus one second so it never cuts short a response the Actor may still send.
- **Substrate MCP proxy request reads are time bounded** (`api.substrateMCPProxyRequestReadTimeout`): substrateMCPProxyRequestReadTimeout bounds reading one proxied request, body included, to 30s so a stalled upload costs only its own connection.
- **Substrate MCP proxy uses the manager's router identity** (`api.SubstrateMCPProxyConfig`): SubstrateMCPProxyConfig's Router uses the manager's pod-certificate identity, the only client on the Substrate router's SPIFFE allowlist, so the API proxy is the sole path to MCP actors. A nil Router leaves the proxy unavailable with 503.
- **Substrate MCP proxy forwards an allowlist of headers** (`api.substrateMCPProxyRequestHeaders`): substrateMCPProxyRequestHeaders is the only set of caller headers forwarded to an actor; Authorization, cookies, the caller's own Txn-Token used for Orka API authentication, and every other header are dropped.
- **Substrate MCP proxy relies on route SAR for Kubernetes identities** (`api.Handlers.ProxySubstrateMCPTool`): Handlers.ProxySubstrateMCPTool trusts the route policy's SubjectAccessReview, which already required `get tools/<name>` in the resolved namespace, for Kubernetes identities; transaction-token callers are checked by the handler itself.
- **Substrate MCP proxy requires enforced transaction-token authorization** (`api.Handlers.ProxySubstrateMCPTool`): Handlers.ProxySubstrateMCPTool rejects transaction-token callers with 403 unless context-token authorization is enforcing, because transaction tokens carry their own scopes and audit-only or disabled authorization would let any valid token invoke an actor.
- **Substrate MCP proxy verifies the caller's Tool snapshot** (`api.Handlers.ProxySubstrateMCPTool`): The caller validated credential authority and approvals against its own Tool snapshot, so Handlers.ProxySubstrateMCPTool refuses, before resolving credentials or contacting an Actor, unless SubstrateMCPToolBindingMatches confirms the snapshot is this exact Tool UID, generation, and Actor.
- **Substrate MCP proxy forwards only the checked message** (`api.Handlers.ProxySubstrateMCPTool`): Authorization named one Tool, so Handlers.ProxySubstrateMCPTool forwards only the message substrateMCPProxyRequestBody checked and rebuilt, never the caller's original bytes.
- **Substrate MCP upstream context is detached from the handler** (`api.Handlers.ProxySubstrateMCPTool`): fasthttp streams the response body after the handler returns, so Handlers.ProxySubstrateMCPTool bounds the upstream request with its own timeout from context.Background and carries over only the trace span context, so the Actor call joins the caller's trace without inheriting handler cancellation.
- **Substrate MCP proxy redacts injected values from responses** (`api.Handlers.ProxySubstrateMCPTool`): Handlers.ProxySubstrateMCPTool redacts every credential and token value it injected into the Actor request from the streamed response, because the caller never held those values and cannot redact them itself.
- **Substrate MCP proxy route matching follows Fiber** (`api.isSubstrateMCPProxyRoute`): isSubstrateMCPProxyRoute matches POST and DELETE /api/v1/tools/:name/mcp on the original path, case-insensitively and ignoring a trailing slash, exactly as Fiber routes it, so every routed spelling gets the proxy's request limits and write timeout.
- **Substrate MCP proxy waits for current-generation Actor** (`workerexecutor.SubstrateMCPToolReadyForCurrentGeneration`): Tool status names the previous Actor until the controller reconciles a spec change, so the proxy answers 503 unless SubstrateMCPToolReadyForCurrentGeneration holds and never pairs the current credential with the previous Actor.
- **Substrate MCP callers need authority over every invocation credential** (`api.Handlers.substrateMCPProxyCredential`): Handlers.substrateMCPProxyCredential checks the caller may use every credential the Tool's invocation uses, including egress credentials the Substrate gateway injects that the proxy never reads, before resolving the auth Secret. Kubernetes identities need `get secrets/<name>`; transaction tokens need the credential-read scope and a matching secret constraint.
- **Substrate MCP proxy admits only the handshake and the named tools/call** (`api.substrateMCPProxyRequestBody`): A Tool stands for the single callable with its name, but its Actor's MCP server may expose others, so substrateMCPProxyRequestBody admits only the session handshake and a tools/call for that name and rejects batches, other methods, and client responses. It forwards a message rebuilt from the checked members so a duplicate or differently cased member the Actor's parser might prefer never reaches it.
- **Injected secrets are redacted longest first** (`api.substrateMCPProxyInjectedSecrets`): substrateMCPProxyInjectedSecrets orders injected values longest first so a value that contains another is replaced whole rather than leaving the remainder of the longer secret visible.
- **Secret matching memoizes failed backslash positions** (`api.substrateMCPProxyMatcher`): substrateMCPProxyMatcher records positions where both readings of a backslash failed so a run of backslashes is explored at most once per position, keeping matching bounded instead of exponential.
- **Redaction matches JSON-escaped secret spellings** (`api.matchSubstrateMCPProxySecret`): matchSubstrateMCPProxySecret matches a secret byte for byte or with any character written as a JSON string escape, including a backslash read either as an escape start or literally, because a JSON serializer may choose escapes freely and the caller decodes them back to the secret.
- **Redaction holds back only possible secret prefixes** (`api.redactSubstrateMCPProxy`): redactSubstrateMCPProxy stops before a tail only when matching shows it may still become a secret once more data arrives, rather than holding back a fixed length, so a complete SSE event is never delayed. When a longer secret may still complete it does not settle for a shorter match.
- **Substrate MCP proxy fails oversized responses** (`api.substrateMCPProxyStream`): substrateMCPProxyStream fails a response that exceeds substrateMCPProxyMaxResponseBytes rather than silently truncating a JSON-RPC message, replaces injected values even when one spans two reads, and releases the upstream request when fasthttp closes the stream.
- **A response at the bound completes only on clean EOF** (`api.substrateMCPProxyStream`): When a response reaches the size bound, substrateMCPProxyStream probes one more byte and treats it as complete only on a clean end of the upstream body; a failed read is reported to the caller rather than passed off as the end.

- **Cancel requests can pin the confirmed Task UID** (`api.cancelRequest.UID`): cancelRequest.UID, when set, is the Task the caller confirmed; a Task recreated under the same name since then is refused with 409 rather than cancelled.
- **A Task gone during cancel is distinct from a refusal** (`api.errCancelTaskGone`): errCancelTaskGone is the 404 for a Task deleted or replaced while it was being cancelled. A Session cancel may skip that Task, but it must not skip an authorization refusal answered as 404, so the two errors stay distinct values.
- **Gateway Sessions answer 404 on the general cancel route** (`api.Handlers.CancelSession`): Handlers.CancelSession answers a gateway-owned Session as not found, before any conflict check or Task is touched, because gateway Sessions are outside the general Session API.

- **Session cancel reauthorizes after stopping the turn** (`api.Handlers.CancelSession`): The stopped chat turn may have created a Task after the first list, so Handlers.CancelSession lists and authorizes every Task again before cancelling any.
- **Session cancel pins the chat incarnation** (`api.Handlers.chatSessionEpoch`): Handlers.chatSessionEpoch returns the chat Session's incarnation, which tells its Tasks apart from an earlier chat under the same name. A cancel that cannot read it stops rather than risk cancelling the earlier chat's Tasks; stores without creation times pin no incarnation and keep name-only matching.
- **Session Tasks are authorized all-or-nothing** (`api.Handlers.authorizedSessionTasks`): Handlers.authorizedSessionTasks authorizes every cancellable Task of the Session, including per-Task credential checks, before the caller cancels any, so a denial leaves none of them cancelled.
- **Cross-namespace chat Tasks need tasks update in their namespace** (`api.Handlers.authorizedSessionTasks`): The Session cancel route authorizes only the Session's namespace, so Handlers.authorizedSessionTasks checks the Task update permission in each Task's own namespace for chat Tasks created elsewhere.
- **Session Task candidates are listed uncached** (`api.Handlers.sessionTaskCandidates`): Handlers.sessionTaskCandidates lists Tasks through the uncached API reader because the cache can miss a Task a just-stopped chat request created. For a chat Session it also lists other namespaces, which only happens when the API may act outside the Session's namespace.
- **Task-to-Session membership rules** (`api.taskInSession`): taskInSession ties a Task to a Session through spec.sessionRef, which names a Session in the Task's own namespace, or, for a chat Session, through the chat labels. A chat-created Task may carry both, naming its continuity Session in spec.sessionRef, and a chat Task without the chat namespace label belongs to a chat in its own namespace.
- **Chat Tasks pinned to another incarnation are excluded** (`api.taskInSession`): taskInSession excludes a chat Task whose chat-session epoch label names a different incarnation of the chat, one deleted and recreated under the same name, because it is not this Session's turn.
- **Confirmed UID is compared only after authorization** (`api.Handlers.recordTaskCancellation`): Task cancellation compares the confirmed UID only after the caller is authorized to act on the Task, so a refused caller gets the same answer for a right or wrong UID and learns nothing about the Task's identity.

Live Task and Session authorization is repeated for each search and each cleanup retry.

## Consequences

- These decisions are still in force. A change that breaks one must supersede that
  entry in a new ADR.
- Entries were recovered from comments in bulk, and a few original comments were stale or
  overstated. If an entry disagrees with the code, treat that as a bug in the entry: confirm the
  intended behavior, then fix the code or supersede the entry in a new ADR.
- Symbols get renamed. When an entry's symbol no longer exists, search for the behavior it
  describes.
- Entries recovered from test comments record why a test is shaped the way it is, so the test
  stays honest. A later ADR may supersede them once the tests explain themselves.
