Architecture

Orka is one controller that turns Task resources into work. Container and native AI Tasks run as per-Task Kubernetes Jobs. Coding-agent Tasks run as private sessions in controller-owned RuntimePools. Everything an agent produces flows back through the controller, which keeps a durable record and, for code changes, hands the work to a separate publisher.

If you are new to Orka, read What is Orka? first. For the source tree and storage internals, see Controller internals.

Overview​

Select the diagram to view it at full size.

Requests arrive from the REST API, the CLI, the dashboard, chat, the OpenAI- and Anthropic-compatible endpoints, gateways, and GitHub webhooks. The controller authenticates them, creates or updates Tasks, and dispatches each Task to where it runs:

Task typeRuns inReaches models through
containerA per-Task Job from the general worker or your image—
aiA per-Task Job running Orka's AI workerThe Agent's Provider and its API key Secret
agentA private RuntimeSession inside a RuntimePool PodThe authenticated provider proxy and your model gateway

Coding-agent runtimes and the Workspace/Publisher use separate network and credential identities. A runtime Pod can reach only the provider proxy and its prompt-scoped tool broker; it has no Git credentials and no route to your source control. The Publisher has the Git credentials it needs for one operation at a time, and no access to models or tools. Security explains the boundaries.

Components​

Controller​

The controller runs as a single-replica Deployment. It contains:

  • API server. The REST API, chat, the OpenAI- and Anthropic-compatible endpoints, the gateway ingress, signed GitHub webhooks, internal worker APIs, and, when enabled, the web dashboard.
  • Task reconciler and priority queue. Routes container and AI Tasks to worker Jobs, in priority order (0–1000), and coding-agent Tasks to the ACP dispatcher.
  • ACP dispatcher and RuntimePool controller. Reserve pool capacity, run fenced prompt attempts, validate workspace changes, and manage digest-pinned, scale-to-zero runtime Deployments. Agent runtimes covers them in depth.
  • Brokers. The credential and artifact brokers give the Publisher short-lived access for one operation. The prompt MCP broker rechecks every tool call a coding agent makes.
  • Workflow reconcilers. Drive repository monitors, security scans, and gateways, each with durable run history.
  • Stores. Sessions, results, artifacts, plans, memory, scans, monitors, gateway ledgers, and usage live in an embedded SQLite database on a persistent volume. Control decisions for coding agents live in Kubernetes resources instead; see Where state lives.

Task lifecycle​

There are two lifecycles, and they are not the same thing.

The first is the Task phase — what kubectl get task prints, and what the UI shows. Every Task has one, whatever its type:

Native and container Tasks without an execution workspace can complete directly from Running to Succeeded or Failed. Finalizing is used when execution-workspace authority still needs revocation.

The second is the attempt state — the fine-grained record of one agent run. Native ai and container Tasks do not have one; they use the worker Job lifecycle instead. Built-in type: agent Tasks record every step in a PromptAttempt:

Two details the diagram compresses:

  • Every state before Accepted can also jump straight to Failed or Cancelled. The arrows are left out so the happy path stays readable.
  • SubmittedUnknown means Orka sent the prompt and never learned whether the runtime got it. It can only become OutcomeUnknown — never Succeeded and never a retry. Orka would rather leave you with an honest "I don't know" than run your prompt twice.

The selected RuntimePool scales from Stopped through Starting to Serving/Accepting. The dispatcher creates or reuses a private RuntimeSession, starts one non-reconnectable prompt stream, renews its lease, and records bounded events. A prompt that may have been accepted is never automatically replayed.

After prompt settlement, the RuntimeSession enters validation. Read Tasks succeed only after the final tree matches the verified baseline. Write Tasks with changes proceed through clean-room preparation, exact-ref publication, independent verification, optional PR reconciliation, and finalization. The controller settles the Kubernetes control records and SQLite transcript/outbox payloads before projecting terminal Task status.

The top-level Task phase, status.execution, and status.delivery are safe compatibility/read-model projections. The authoritative ACP transitions live in PromptAttempt, RuntimeSessionControl, BranchClaim, Publication, ExternalEffect, RuntimePool.status, and the associated coordination Leases.

How the features fit together​

  • Delegation. A coordinator Agent creates child Tasks with delegate_task and collects them with wait_for_tasks. The controller enforces the allowed Agents, depth, and concurrency, and records progress in the parent's status.childTasks. In autonomous mode, the controller reruns the coordinator in a loop, carrying a saved plan between iterations. See Multi-agent coordination and Autonomous tasks.
  • Sessions. Tasks that share a Session run one at a time and see the earlier conversation. Sessions store user and assistant messages only, so a conversation can move between native AI and coding-agent Tasks. A coding agent's session is rebuilt from that canonical transcript and the verified workspace when its Pod is replaced.
  • Tools. Native AI Tasks get built-in tools and custom Tools. Coding agents use their CLI's tools, plus Orka tools through the per-session broker.
  • Memory. AI workers load a bounded set of reviewed, namespace-scoped memories into the system prompt. Agents can only propose new memories; a person reviews and applies them. See Memory.
  • Repository automation. Repository monitors and security scans run their work as ordinary Tasks and keep runs, findings, reviews, and audit events in SQLite. Status on the resource summarizes them; the API and dashboard show the detail.
  • Gateways. An out-of-tree adapter normalizes each external conversation into an orka.gateway.v1 event. A GatewayBinding maps it to one Agent, and unknown or ambiguous identity fails closed. A durable inbox and outbox decouple acknowledgement from execution, deduplicate events, serialize each Session, and deliver replies with stable idempotency IDs. See Gateways and the Gateway API.

Where state lives​

Orka needs no external database. It keeps two kinds of state:

  • Kubernetes resources and Leases are the authority for coding-agent control decisions: which controller is in charge, attempt state, Session ownership, branch claims, publications, and external effects. Updates use resourceVersion compare-and-swap, so a stale writer cannot win.
  • SQLite on the controller's volume holds payloads and records: results, artifacts (up to 10 MB each), sessions and transcripts, plans, memory, scan and monitor history, gateway inbox and outbox, and usage. It is written behind the Kubernetes fences and never acts as a second authority.

Back up both together, with the snapshot encryption key. See Upgrading.
